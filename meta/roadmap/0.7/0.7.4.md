# 0.7.4 — Functions, entry blocks, parameter slots, the `Result<T>` return

**Cycle 0.7 — IR emission core.**

## Goal

`src/backend/ir/ir_func.npk` — the scaffolding every function body hangs from: the
`define` line, the `entry:` block, parameter slots, the locals table, and the
`pass`/`fail` lowering that makes the implicit `Result<T>` wrap explicit.

## The seed's shapes, quoted — and proven to assemble

Every shape mirrors a named seed function: `fn_sig` (bare for `main`/`failsafe`,
`Result<T>` otherwise), the alloca-and-store prologue, `emit_return` and
`emit_return_err`. The test pins each one **byte for byte against the whole emitted
function**, not a substring — and every pinned shape was fed through `llc` to prove
it is IR and not merely self-consistent text.

Two invariants worth naming:

- **The error field of a successful Result is written, never left `undef`.** A
  Result whose error slot is undef is one whose `.is_error` answers differently on
  different runs — a slot that means two things, decided by the optimiser.
- **A failed Result carries a zeroed value slot**, so a caller that unwraps without
  checking reads an empty value rather than whatever the stack held.

## One deliberate departure: locals are a scope stack, not a flat map

The seed keeps `self.locals` as a dict keyed by name, so an inner block's `int32:x`
**overwrites** the outer binding and stays bound after the block ends. The language
permits shadowing (`resolve.npk`: *"an inner one may shadow an outer"*) — so that is
an accepted program the seed lowers **wrongly**. It gets away with it because it
compiles exactly one program, the compiler, which never leans on the pattern. The
real emitter compiles whatever the frontend accepts.

So: bindings append, lookup walks **backward** (innermost shadow wins), and leaving
a block truncates to a mark — the outer binding reappears because it was never
gone. The test's central case: bind `x`, mark, shadow `x` at a different type, see
the inner slot; release, see the outer slot again.

Worse than a rung that lowers wrongly is inheriting a reference's defect on purpose.

## `%tN`, and why the letter is load-bearing

0.7.1's writer numbered temps `%0`, `%1`, … That is the one naming scheme LLVM
attaches semantics to: **bare numeric names are the implicit counter**, required to
be defined in exactly ascending order with no gaps. A temp handed out and not
written — or written after a branch reordered things — would not be sloppy IR but IR
`llc` rejects. Fixed to `%t0` before anything was built on it; parameters arrive as
`%aN`, a disjoint prefix, because two schemes numbering into one space is how a name
comes to mean two things.

## Rung propagation without codes

`fnem_begin`/`fnem_param` return the `LlType` of what they lowered; `LL_RUNG` and
`LL_BROKEN` propagate to the caller and **nothing is emitted** — a signature with a
hole in it is not a signature minus a hole. The rung diagnostic itself lives with
the driver (0.7.7): a module with no codes of its own cannot misreport one, and
`check_codes_centralised` holds that line.

`ll_wrap_result` was exported from `ir_types.npk` on the way: the wrap is usually
implicit — a function *declares* `T` (D-069) — so the emitter mostly holds a `T`
with no interned `Result<T>` beside it. One body serving both spellings keeps "what
does a Result look like" a single place.

## Done when

- Every emitted shape byte-matches its pinned form, and the pinned forms assemble.
- Parameter slots are real bindings; shadowing resolves innermost and un-resolves
  on block exit.
- Counters reset per function — two functions in one writer equal the two emitted
  separately, concatenated.
- A type no rung lowers propagates and the function is not emitted.
