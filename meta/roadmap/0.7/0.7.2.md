# 0.7.2 — Types to LLVM types, agreeing with the seed exactly

**Cycle 0.7 — IR emission core.**

## Goal

`src/backend/ir/ir_types.npk` — a Nitpick type, as LLVM type text, giving the same
answer `bootstrap/generator/ntypes.py` gives.

## Why "exactly" is the whole subcycle

The seed builds stage 1 and stage 1 builds stage 2, so **the two compilers' IR meets
at every runtime symbol and every aggregate that crosses between them**. `llc`
rejects a caller whose struct disagrees with the callee's by one field — the
runtime's own header records that mismatch being caught the first time — and a
disagreement about a *size* does not even get that far: it corrupts memory quietly.

The 0.7 plan said this: `tests/frontend/type_layout.npk` has diffed the two
authorities' **sizes** since 0.4.8, and *"nothing yet compares the LLVM type text the
two emitters produce. 0.7.2 owns that."*

## The instrument

Two halves, because the two authorities live in two languages.

**`tests/backend/ir_types.npk`** declares each shape twice — once in Nitpick, where
`#size_of` is lowered by the seed to `getelementptr T, ptr null, i32 1` and answered
by LLVM, and once inside the source string the checker is handed. Then it asserts
`type_size(…) == #size_of<T>()`, and pins the lowered **text** on the same line:

```nitpick
if (!(raw ll_is(@c, i64t, "i64")))   { exit 43i32; }   // ll: int64
```

**`check_ll_types_agree`** in the harness reads that one line, takes the marker and
the string literal off it, and asks the seed's `ntypes.llvm()` the same question.
Both halves on one line is deliberate: *a marker on the line above could stop
describing the assertion beneath it and nothing would say so.* The check also fails
when a table entry has no line pinning it — an entry nothing compares is an entry
that stopped being a check.

## What it found, on its first run

Both defects are of the kind that does not fail. Both were unreachable from the
tests that existed.

### `Result<T>` was missing its padding — on both sides

The rule was `size(T) + 4`, with the alignment bumped to at least four. LLVM lays
`{T, i32}` out with padding **before** the error field when `T` is not a multiple of
four, and **after** it when `T` is wider than four:

| | was | LLVM |
|---|---|---|
| `Result<int64>` | 12 | **16** |
| `Result<int8>` | 5 | **8** |
| `Result<string>` | 28 | **32** |
| `Result<Pair>` | 12 | 12 ✓ |

The last row is why nothing caught it: `Pair` is `{i32,i32}`, needs no padding, and
is the case 0.4.8 happened to assert.

This was **already observable**, not merely latent. 0.6.4 folds `#size_of` in the
compiler, so `#size_of<Result<int64>>` answered 12 under `check.npk` and 16 under
the seed — two compilers, two numbers, today.

### An enum had no layout at all

`ensure_layout` had arms for struct, array, `Optional` and `Result`, and **none for
`TY_ENUM`**. Both places that intern an enum pass size 0 and alignment 1, and nothing
ever fixed them up. So every enum in every program was zero bytes — and the half that
matters is that **a struct containing one was laid out as though the field were not
there**, moving every later field:

```nitpick
struct:HasEnum = { Flat:f; int64:x; };   // was 8 bytes; LLVM lays it out as 16
```

This is the same defect 0.4.8 found for structs ("every struct in every program was
size zero"), in the one kind that pass did not cover. Nothing caught it because
nothing asked: the checker compares types and almost never needs a size, and no
`#size_of` in the compiler names an enum.

## The fix is one arithmetic, not four corrected formulas

A struct, a `Result<T>`, an `Optional<T>` and a range are the same question — fields
in order, each moved up to its own alignment, the total rounded up to the widest —
and each answered it with a formula of its own. **Four formulas is four chances to
disagree about padding**, which is the argument `struct_field` already makes for
walking and laying out in a single pass.

So `types.npk` now holds `Lay` with `lay_start` / `lay_field` / `lay_end`, and
`align_up` moved there to join it — beside the interning that computes a `Result<T>`'s
total at the moment it is constructed, because *a module they cannot import is a
module whose rule they end up restating*.

`lay_field` **returns the offset it landed at**, which is what lets `struct_field`'s
offset walk and `struct_layout`'s size walk be one walk instead of two that have to
agree.

The empty-struct rule stays at the call site rather than moving into the
accumulator: `Result<NIL>` is `{i32}` and genuinely four, so an accumulator that
refused to return zero would have no way to say so.

## Three states, not two

`ll_type` returns a state, a text and a rung, because **whether a type lowers and
what it lowers to are two questions** and `NIL` already lowers to `void` — a real
answer that reads like an absence.

| | means |
|---|---|
| `LL_OK` | it lowers; `text` is the answer |
| `LL_RUNG` | valid Nitpick that no rung lowers yet; `rung` names the cycle |
| `LL_BROKEN` | not a type the emitter can be asked about at all |

The third is not fussiness. `TY_INVALID` means resolution already failed and said so;
`TY_COMPTIME` is a **value** standing in a type-argument window and was never a type.
Reporting either as "enabled by cycle 1.0" would be a sentence that is not true,
offered to somebody trying to fix their program.

An unclassified kind **fails closed** — `LL_BROKEN`, never a plausible guess. The
plan's own rule: *a rung that lowers something wrongly is worse than a rung that
refuses it.*

## Two rung assignments this subcycle had to make

- **A function value** (`TY_FUNC`, `TY_FUNC_VARIADIC`). Closures are gone (D-018) and
  a function pointer is an ordinary value with a `FuncType` spelling (D-087), so it
  will lower to `ptr` like every other pointer once a rung can *call* through one. No
  rung table named it; 0.7.2 assigns it to **0.9**, with the rest of full type
  lowering, rather than leaving a type whose refusal has no cycle.
- **`fd`, `pid`, `tid`, `uid`, `gid`** lower to `i32` (D-042) rather than refusing.
  The seed has no answer for them at all — they are neither in `INT_TYPES` nor in
  `OUT_OF_SUBSET_TYPES` — so there is no disagreement to have, and `types.npk`
  already states the lowering.

## A tagged enum is `{i32, i64}` because that is what the seed emits

`TYPE_REFERENCE` §9.3 shows the general form — a tag, explicit padding, and a payload
sized to the widest variant. **Computing that now would be worse than not.** The seed
emits `{i32, i64}` uniformly for every tagged enum, so an enum whose only payload is
an `int32` would be eight bytes in the compiler's table and sixteen in the IR the
seed produced for it. The uniform word is the rung's shape; §9.3's is cycle 0.9's,
and `tests/backend/ir_types.npk` is what will force the two to change together.

## Also

`check_codes_tested` swept `src/frontend/**`. It sweeps `src/**` now — a backend code
would have been invisible to it on the day it was written, which is the day it needs
to be visible. No code lives under `src/backend/` yet, so the change is a no-op that
cannot be forgotten later.

## Done when

- Every shape's text agrees with `ntypes.llvm()`, checked by the harness.
- Every shape's size agrees with `#size_of`, checked by the test.
- Removing either fix makes the test fail (verified: exit 26 and exit 23).
