# 0.2.8 — The type grammar's unreachable corners

**Cycle 0.2 — AST and parser.**

## Why this exists

0.2.2 built the type parser against `AST_REFERENCE.md` §4 and 0.2.4 checked the
document's node tables against the generated kinds. Four things came out of that
comparison, and they share a trait worth naming: **none of them fails. Each one
silently produces a different program than the source says.** A parser that
rejects something is a parser you argue with. A parser that accepts something and
means something else is a parser you trust and should not.

Two of §4's eight nodes are **unreachable** — nothing in the parser can ever
build them — one node named by the grammar has no spelling anywhere, and the
array-size path builds a node whose contents are wrong.

## Work

### 1. `ArrayType.size` parses an expression, not one token

This is the one to fix first, because it is the one that miscompiles today.
`p_suffixes` carries a note from 0.2.2 saying size expressions arrive with 0.2.3.
0.2.3 came and went; the note stayed and so did the code:

```
Token:n = relay p_advance(p);
ExprId:se = relay ast_add_expr(p.ast, ExprKind.ExprIntLiteral, n.span,
                               0i32, 0i32, 0i32, n.payload);
```

It consumes exactly one token and calls it an integer literal **whatever it
was**. For `int32[COUNT]:a` the token is an identifier, and an identifier's
payload is its **intern index** — so the array's size becomes whichever slot
`COUNT` happens to occupy in the intern table. Not an error. Not a wrong-looking
AST. An array of a plausible-looking size that has nothing to do with the source.
And `int32[N + 1]` stops after `N` and reports a missing `]`.

§4 says `size: Expr?`. It should call `p_parse_expr`.

**This raises a structural question that must be settled, not worked around.**
`parse_expr.npk` already `use`s `parse_type.npk` — casts need types — so having
the type parser call the expression parser makes the two modules **mutually
importing**. The seed's harness breaks import cycles by post-order visit and
would not notice. `MODULE_REFERENCE.md` says nothing about cycles at all.

Decide it here rather than in 0.3, because 0.3 would find it already done one
way: either mutual `use` is legal in Nitpick and the module loader is built to
resolve it, or it is not and these two modules need a shared lower layer. The
recommendation is that **a cycle among modules is legal** — `use` names a
namespace and imports no initialisation order, so there is nothing to sequence,
and forbidding it forces artificial file splits whose only purpose is to satisfy
the rule. Record the outcome as a decision either way.

### 2. `FuncType` gets a spelling

§4 declares `FuncType { params, return_type }`. **No document gives its syntax.**
`FULL_specs.txt` line 10562 is the whole of it —

```ebnf
FuncType   ::= "func"
```

— followed by a note deferring to a chapter that does not cover it. So a
function-pointer-typed variable cannot be declared, while §3.6 says function
pointers *are* ordinary values ("closures are removed (D-018); function pointers
are ordinary values referenced by `IdentifierExpr`"). Values with no type.

The prototype spells it `(int32)(int32, int32)` — return type in parens, then
parameters in parens. **Proposed instead: `func int32(int32, int32)`.** The
reasons, in the order they matter:

- It reads exactly like the declaration it is the type of. `func:add = int32(int32:a, int32:b)` declares it; `func int32(int32, int32):op` names its
  type. The same three parts in the same order, which is the blueprint rule that
  a construct does not change shape by context.
- It matches `FuncType ::= "func"` as the grammar already has it, so the one line
  of specification that does exist stays true.
- `(int32)(int32, int32)` announces nothing. Parens already group expressions,
  hold call arguments, and wrap `move(…)`; giving them a fourth job means the
  reader works out which one from what follows. `func` says what it is in the
  first token.

Needs a `DECISIONS.md` entry, `LEXICAL_REFERENCE.md`'s grammar, and
`AST_REFERENCE.md` §4's note column.

### 3. `cstring` becomes a builtin type keyword

§4 declares `CStringType`, and `TYPE_REFERENCE.md` §3.2.1 shows
`cstring:cs = "Hello";`. But `LEXICAL_REFERENCE.md`'s `BuiltinType` production
does not list `cstring`, so it lexes as a plain identifier and
`p_parse_type` builds a `NamedType` named "cstring" instead. The node is
unreachable, and a user type called `cstring` would silently shadow the builtin.

Add it to the production, regenerate, and give the type parser its case. D-049 is
the decision it belongs to.

### 4. `any` gets a node, or loses its keyword

`any` **is** in `BuiltinType` and does lex as a keyword, but §4 has no `AnyType`,
so it also becomes a `NamedType`. The mismatch runs the other way from `cstring`:
the token exists and the node does not.

`FULL_specs.txt` §2.7.2 defines it as Nitpick's `void*` — "an untyped pointer to
raw memory (e.g. `wild any->`)". That is a real thing the language needs and the
FFI boundary depends on, so the fix is the node, not the removal. Confirm against
`POINTER_REFERENCE.md` before adding it: if `any` is only ever legal under a
pointer, the checker should say so, and §4 should record it.

## Watch for

**Every one of these is a spec repair before it is a parser change.** The
document is the authority (`nitpick-docs`), `AST_REFERENCE.md` is the working
copy, and the kind tables are generated from it. Editing the parser first would
leave the generator producing a table that disagrees with the code — the exact
failure that put a `MemberAccessExpr` where an identifier belonged.

## Done when

- `int32[COUNT]`, `int32[N + 1]` and `int32[]` all parse, and the fixed-array
  size is the expression that was written.
- The mutual-import question is settled and recorded as a decision.
- All eight of §4's nodes are reachable from source text, with a test each.
- `AnyType` is decided: a node, with the pointer rule stated.
- No node kind exists that the parser cannot build, and no type spelling exists
  that the parser cannot read. The two lists match, and a test asserts it.
