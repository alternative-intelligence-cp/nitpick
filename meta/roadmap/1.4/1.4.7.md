# 1.4.7 — Adoption (D-209) — PLANNED (execution-grade)

> `src/` adopts what D-209 ratified — generics for the duplicated
> collections, `dyn Writer` diagnostics, judicious form upgrades — under
> the new builder. THE STANDING RULE: each step is its own commit with
> the full harness (fixpoint included) between it and the next; smallest
> first; never two idiom migrations in one commit. Decided OUT (not
> deferral): mass `&{ }` re-spell, async in the pipeline, macros in
> `src/`.

## The steps, smallest first

1. **`dyn Writer` diagnostics (D-075's design, deferred since 0.0)**:
   the diagnostic renderers take `dyn Writer` receivers (the prelude
   trait) instead of direct fd writes through lib/nio; the drivers
   construct `std_err()`'s writer once. `check_one_renderer` keeps
   holding (one renderer, now trait-shaped). This is the smallest
   adoption and the one `npkg test`'s capture-and-compare expects.
2. **The generic collections**: the hand-monomorphized table/list
   families in `src/` (the `TokenList`-shape copies — enumerate them
   first: rg for the repeated grow/at/push pattern; the 1.0-era note
   named "the concrete collections become replaceable") collapse into
   the prelude's generic containers or a small `src/` generic module.
   One FAMILY per commit. Expect the drop/move machinery to be
   exercised hard — that is the point (the strongest pre-verification
   generics workout).
3. **Form upgrades where they pay** (file-by-file, mechanical, each
   file's change reviewed against the fixpoint): hand-rolled index
   loops → `for`/`till` where the loop is a plain iteration;
   match-shaped unwraps → `?.`/`?|` where the shape IS the operator.
   No wholesale rewriting — a form changes only where the current
   spelling is longer AND less clear.

## Watch for

- **A stale-snapshot refusal means the step used a feature the snapshot
  builder lacks** — the D-205 rule; refresh the snapshot at the PREVIOUS
  step's commit if a genuinely new feature is needed (unlikely: 1.0–1.3
  features are all in the 1.4.6 snapshot).
- The suspend walk, escape analysis, and drop flags all see new shapes
  through generics in the compiler's own source — instrument failures
  here are FINDS, the adoption doing its job as the biggest test
  program.
- SUBSET_1 §4's final state (the builder rule with adoption done) gets
  its closing edit at the last step.

## Acceptance

Full harness green per step; the fixpoint re-closed and DECLARED at the
final step's commit (the D-202 criterion cited); the snapshot refreshed
at the subcycle's close.

# Execution record — step 1 attempted, REVERTED, and what it found

## `dyn Writer` works; `async main` on a real driver does not (yet)

The erasure itself is sound and was validated by probe BEFORE the compiler was
touched — which mattered, because the plan's phrasing ("the drivers construct
`std_err()`'s writer once") does not survive contact:

- **`dyn Writer` passes BY VALUE, never through a pointer.** A trait method's
  receiver is `Self->`, so the erased call takes the sink's address itself
  (1.1.12d); `dyn Writer->:w` fails method lookup outright. `dyn_stream.npk`
  is the canonical shape and it passes by value.
- A `dyn` is move-only, so a by-value sink cannot be reused across calls. That
  is fine here and only here: `main`'s three report sites are MUTUALLY
  EXCLUSIVE early exits, each already building its own stderr writer.
- **Async reaches exactly to the reporting boundary.** Every `Writer` operation
  is async by D-075 (required by D-071), so `report` and `main` become
  coroutines and nothing else does. `front_run` and the whole front half stay
  synchronous. This does NOT make D-209's decided-out "pipeline async" happen.

With that, the compiler built and REPORTED CORRECTLY — `borrows.npk` printed
all ten diagnostics through the erased sink and exited 1. Then it segfaulted on
every SUCCESSFUL compile, after writing complete, well-formed output.

## The defect: `wild_release_all()` unmaps the frame an `async main` is running on

Bisected by gdb, not by reasoning (two of my guesses were wrong first):

- the fault is `movl $0x0,(%rcx)` inside `npk.resume.main.main`, storing the
  exit code into the frame's result slot (offset 0x10 — slot 3);
- `%rcx` points INSIDE the frame, and `info proc mappings` shows the page is
  no longer mapped;
- `src/main.npk` calls `wild_release_all()` immediately before `exit 0i32` —
  twice (the `-o` path and the stdout path), and `resolve_check.npk` once.

**`exit` in an `async main` is not process exit.** `emit_exit` lowers it as
the ordinary return seam (`ir_stmt.npk`, the comment says so): store the code
into the frame's result slot, run the exit defers, `ret i8 0` from the resume.
The SHIM then reads the slot, `npk_dalloc`s the frame, and returns the code;
`npk_exit` runs after that, with the frame already freed. That is precisely
why every `async main` in the suite that exits 0 — `windup_drop.npk`,
`shared_arena_spawn.npk`, `variadic.npk`, all six driver programs — passes
D-151's leak check: **the frame is gone before the check runs.** The
accounting was never inconsistent; the question in the first draft of this
record was mine, and the answer is that `exit` means two different things.

`npk_wild_release_all` unmaps **the whole heap, both regimes** — its own
comment states the contract: *"after it, only exit; anything still pointing
into the heap points at unmapped pages."* In a sync `main`, `exit` IS an
immediate `call void @npk_exit`, so "only exit" holds. In an `async main`,
`exit` must still write to the frame and return through the shim — and the
frame is in the heap that was just unmapped.

**So the fix recorded in the first draft of this note — allocate the root
frame from the managed pool — fixes nothing**, because the release frees both
regimes. Recorded here because it is the plausible-looking wrong answer.

**Latent, not introduced.** It needs an `async main` that calls
`wild_release_all()`, and no such program existed: the async tests do not call
it, and the drivers that do were synchronous until this step.

## Why the drivers call it at all

It is a **leak amnesty**. `src/` allocates wild arena-style and frees almost
nothing individually, so a driver wipes the heap to make D-151's `exit 0`
check see zero. `nio_end`'s comment records the same effect from the other
side: a leaked writer buffer was invisible "for as long as tests called
`wild_release_all()` before exiting, and reported by D-151's exit check the
moment they stopped." Removing the call is therefore not free — it exposes
every deliberate leak in the compiler at once.

## The decision this needs (the user's, not the executor's)

The question is a language one: **what does `exit` mean inside an async
body?** Today it means one thing in a sync `main` and another in an async one,
which is the blueprint philosophy's own failure mode — and this segfault is
what that costs. Three shapes, none of them improvised into the tree:

- **A — the root frame moves off the releasable heap.** The shim allocates it
  from a dedicated mapping `wild_release_all` does not touch, and frees it the
  same way. Smallest change, preserves both existing contracts, and "after it,
  only exit" becomes true again for async main. Does not address the
  two-meanings problem.
- **B — `exit` means process exit everywhere.** The async lowering dallocs the
  frame and calls `npk_exit` directly instead of returning through the shim.
  One meaning for one spelling, which is the philosophy's answer; it makes the
  shim's return path dead for `main` and needs care that the exit defers still
  run first.
- **C — refuse `wild_release_all()` in an async body**, spanned, D-215's
  shape. Honest about the incompatibility, but leaves an async driver with no
  amnesty, so it blocks this adoption behind making `src/` actually free what
  it allocates — a large piece of work, and one worth wanting for its own sake.

My reading: **B is the philosophy's answer and A is the safe small one**, and
they are not exclusive — B subsumes A. C is the right long-run destination for
`src/`'s own hygiene regardless of which lands here. But `exit`'s meaning is
language design, so it is the user's call.

**Step 1 is reverted** so the tree stands at the green, pushed 1.4.6 state. The
probe (`dyn Writer` over `std_err()`, many lines through one erased sink)
compiles and runs, so the adoption is a small edit away once this is settled.
Steps 2 and 3 do not depend on it.

# Step 2 — the generic collections: the enumeration, and the first family

## What is actually there (measured, not estimated)

The plan said "rg for the repeated grow/at/push pattern". Brace-matched over
every `func:` in `src/`, counting bodies that both `ralloc` and double:

**44 hand-rolled doubling sites over 89 growable arrays.**

- **26 single-array growers** — one `ralloc`, one `=>!`, one capacity store.
  A generic replaces each outright: `strtab_add`, `fnem_defer_add`,
  `fnem_new_seg`, `drop_fn_sym`, `ast_grow_{decls,ids,pats,scratch,types,
  verifies}`, `sink_grow`, `exprtypes_mark_{crossing,owning_decl}`,
  `intern_grow`, `sitetable_add`, `graph_grow`, `rootlist_grow`,
  `srcmgr_grow`, `symtab_{grow_scopes,grow_syms,set_home}`, `tokenlist_grow`,
  `bound_grow`, `impl_grow`, `fninst_grow`, `inst_grow`.
- **18 parallel-array growers** — 63 arrays between them, `fnem_pick_push`
  alone growing eight in lockstep. These are STRUCT-OF-ARRAYS tables, not
  arrays of structs, and the plan's phrasing ("collapse into generic
  containers") reads as though they were the same thing. They are not: the
  collapse for these is N separate `List<T>` fields, which PRESERVES the SoA
  layout rather than changing it. Nothing about the representation moves.

**The reason to do it is not tidiness.** Every one of those 89 arrays carries
its own `=>!` reinterpretation of `ralloc`'s bytes back to the element type,
and 1.4.2 found FIVE latent unchecked pointer reinterpretations in exactly
this shape — invisible for as long as the callee had no type to check them
against. Ninety hand-written casts are ninety chances to write one wrong; one
generic is one cast, checked once, at every instantiation.

## The design, proven by probe before `src/` was touched

`src/frontend/list.npk` — `List<T>` with `list_init`, `list_reserve`,
`list_push`. Four choices, each with the measurement behind it:

- **`wild`, unchanged.** Every family replaced was already wild; the compiler
  allocates arena-style and frees almost nothing. Making the storage managed
  would change when the compiler's own tables die — a different decision from
  this one, and one that collides with the `wild_release_all()` question step
  1 is blocked on.
- **`int64` count and capacity, uniformly.** The families disagreed —
  `TokenList` and `Sink` counted in `int64`, the other eight in `int32`. One
  collection answering "how many" two ways is what the blueprint philosophy
  exists to prevent, and `int64` is also the safe side: under D-210 a doubling
  that overflows TRAPS, and at 64 bits it cannot reach the trap.
- **Storage only — no generic `list_at`.** For an owning `T`, returning `T`
  is a copy, and copies of owning values are refused (TYPE-046). Reading an
  element stays the family's business: `RootList` hands back a deep view,
  others read a scalar through `l.items[i]`, and one generic accessor could
  serve only one of those.

- **`list_reserve` takes a COUNT, and doubles in a loop.** The first draft
  reserved room for one element, which is what all 26 single-array growers
  spell — and reading `Sink` before writing the second family showed why that
  is wrong: it appends BYTES IN BULK, by however many the write is. A
  one-element reserve would have been correct for exactly the families that
  never exercised it and would have silently under-allocated for the rest, and
  a single doubling does not hold a bulk append of ten thousand into a
  capacity-8 list either. `list_push` is now the special case
  (`list_reserve(l, 1i64)`), which is the right way round.

`move T:v` on the push was the one thing worth measuring rather than assuming,
because it has to serve both an owning and a non-owning instantiation. A probe
(`List<int32>` and `List<Owning>` in one program, pushed past a grow)
type-checks and RUNS — exit 42 — so the parameter is consuming where that
matters and indifferent where it does not.

## Family 1 of 12: `RootList`

Chosen first because it is the only family whose accessors never leave its
file: tree-wide, `rootlist_count` and `rootlist_at` are called only inside
`resolve_path.npk`, so the `int32` → `int64` count change has exactly one
consumer loop. `rootlist_init` and `rootlist_add` keep their signatures and
their 28 external call sites are untouched.

What went: the struct's three fields become one `List<Root>`, and
`rootlist_grow` is deleted entirely. What stayed: where a root's `/src` is
appended, and the deep-viewed copy `rootlist_at` returns — the parts that were
ever this file's own.

## The remaining families, in the order they should land

Smallest external surface first, one commit and one full harness each:

`Sink` · `StrTable` · `SiteTable` · `InternTable` · `SourceManager` ·
`ModuleGraph` · `BoundTable` · `ImplTable` · `InstanceTable` · `FnInstTable` ·
`TokenList`, then the parallel-array tables (`TypeTable`'s five, `FnEmitter`'s
seven, `Suspend`'s two, `Ast`'s two, `irw_site`, `vtmap_add`, `reach_add_decl`,
`resolve_decl`, `foldenv_set`, `tt_unit_put`) — those last are mechanical once
the single-array ones have shaken the generic out.


## Why these were hand-written, which turns out to matter

`source.npk` states it, right above `SourceManager`:

> hand-written — the cost SUBSET_1 accepted deliberately, to keep
> monomorphization out of the least-audited artifact in the chain.

**That constraint expired at 1.4.6.** The Python seed is retired (D-203,
D-205); `src/` is built by the committed snapshot, which is npkc itself and
monomorphizes like any other build. The 89 hand-written arrays were never an
oversight and never duplication anybody failed to notice — they were the price
of keeping generics out of the seed, paid deliberately, and D-209 scheduled
this adoption for after the switch precisely because the switch is what stops
the bill. Each family's stale explanation comes out as it converts; a comment
defending a constraint that no longer exists is the next stale document.

## Family 2 of 12: `Sink`

The bulk-append family, and the one that had already shaped the API. Two
things worth carrying forward:

**`Sink` never carried a `=>!` of its own** — its elements were already the
allocator's `int8`, so `out.buf = ralloc(out.buf, n)` needed no cast. It is
the only one of the twelve where the win is uniformity rather than a removed
reinterpretation. Worth knowing before the remaining ten, where the cast is
the point.

**`sink_view` is new, and is the better shape regardless of the generic.**
`irw_text` assembled its mid-function text by reaching into `.buf`/`.len` at
five sites — the IR writer knowing how a sink stores bytes. It now asks for a
view (`string_from_bytes`, D-186's explicit view primitive: a cap-0 string
owning nothing, so the sink keeps its buffer). Five layout dependencies gone,
and the next family that changes a representation will not find them.

### Two process finds, neither of which cost anything this time

- **A frontend-only `quickcheck` went green while the backend was broken.**
  `tools/check.npk` does not include `src/backend/`, so the five `.buf` reads
  in `ir_writer.npk` type-checked as absent. The summary of 1.4.6 records the
  same lesson in a different shape ("the honest claim is: the frontend
  compiles"). For any change to a type that BOTH halves use, the cheap
  verification is `quickemit` on one program, not `quickcheck`.
- **A completeness sweep was truncated by `head`.** The grep that concluded
  "nothing outside `diagnostics.npk` touches Sink's fields" was piped through
  `head -20`, and the `.buf` uses sat below the cut. A sweep whose answer is
  "none" must not be truncated — count it, or read all of it.

### And one measurement that was worth taking

Checking `tools/check.npk` takes **72 seconds**, which is just over
`quickcheck.py`'s 60-second per-file cap, so it reports a timeout that reads
like a hang. It is not one, and it is not new: a worktree built at the
previous commit answers in 1m12.259s against 1m12.097s after the conversion —
the same number. The generic costs nothing measurable. The tool's cap is the
thing that is slightly wrong, and it is the largest entry file in the tree
that trips it.


## Families 3 and 4, and the rule that came out of them

`StrTable` (family 3) has one subtlety: the name it hands back IS the index the
string lands at, so the index is read BEFORE the push — `list_push` advances
the count, and reading it after would name every constant one past itself.
Checked in emitted IR before the harness: `@.str.0` through `@.str.105`,
contiguous from zero.

`SiteTable` (family 4) is where the working rule finally got stated.

### The completeness check for a representation change is the COMPILER, not grep

It has now cost a miss twice and been caught free twice:

- **family 2**: the sweep for "who touches `Sink`'s fields" was piped through
  `head -20`, and the five `ir_writer.npk` sites sat below the cut;
- **family 4**: the sweep for `sitetable|SiteTable` found seven references and
  missed both real ones, because the consumer reads `x.sites.count` — through
  the FIELD name, which never mentions the type at all.

Grep cannot see the second class even when it is not truncated. The procedure
that works is: apply, build, and let `NITPICK-TYPE-019` enumerate every site
with spans in one pass. The only requirement is that the build covers BOTH
halves of the tree — `quickemit` (npkc), never `quickcheck` (frontend only).

Two habits now carry it, and both have already paid:

- **Rehearse a scripted conversion against the live tree before applying it.**
  Family 6's dry run listed three functions (`srcmgr_find`, `srcmgr_path`,
  `srcmgr_text`) that the replacement block did not cover, before anything had
  been written to disk.
- **End the script with a leftover assertion**, not a hopeful grep beforehand.
  Family 7's refuses to apply itself if any `g.mods`/`g.count`/`g.cap` survives
  anywhere in the file. A conversion that can detect its own incompleteness is
  worth more than a sweep that has to be remembered.


## Families 5 and 6: the guarded narrow, and what a new error costs

`InternTable` (family 5) is the first family where `int64` uniformity has a
real price. An intern id is `int32` BY AST DESIGN — every node stores a name as
one — so the list's `int64` count must narrow to produce an id. That narrowing
is GUARDED, never `=>!`: a silent truncation would alias two different names to
one id, which is the single failure this table exists to make impossible.
Before the conversion the `int32` counter got that property for free, because
under D-210 its increment TRAPPED; `intern_id` is what keeps it once the count
is wide. It raises the `BoundsId` the module already declares, so the set of
errors reaching `failsafe` does not change and no `failsafe` grows an arm.

`SourceManager` (family 6) is the one that does need a new error. A file id is
what a `Span` carries in every AST node, so the same guarded narrow applies,
and `BoundsOffset` (a byte offset inside one file) is the wrong invariant to
borrow. Reusing the builtin `IntOverflow` would have dodged the cost and was
rejected: D-179's whole point is that a module's defects carry its own
unforgeable identity, and borrowing a builtin erases it. So `source.BoundsIndex`
is declared, and **38 `failsafe` picks grew an arm** — the predicted, accepted
cost of a new failure mode, and REACH-002 refusing to compile until each one
acknowledged it.

### Grep missed a third class

Two of the 38 spell the arm UNQUALIFIED — `(BoundsOffset)`, not
`(source.BoundsOffset)` — because they import the module directly and the name
is in scope. The sweep that found 36 sites found neither. That is the third
distinct way a text search has been wrong about the same question in this step
(truncated output, field-name access, and now the qualified/unqualified
spelling), against zero times the compiler has been.

### And one finding that is the design working

`ir_types.npk` carried a bare `(BoundsIndex)` arm that named
`types.BoundsIndex` unambiguously — until `source.BoundsIndex` existed, at
which point the unqualified name re-pointed and `types.BoundsIndex` was
suddenly uncovered. **REACH-002 caught it**, refusing the file until the arm
was named again. That is the exhaustiveness rule earning its keep: adding an
error to one module cannot silently cost another module's coverage, because
the check is over what can REACH `failsafe`, not over what the text used to
say. Both arms are qualified now, which is the right spelling regardless.


## Family 7: `ModuleGraph`, and the fourth thing grep cannot see

26 sites, the largest single-array family. Its loop counters STAY `int32` on
purpose: every one is a module index, not a size — an index is `int32` by the
same design that forces the guarded narrow — so the comparison widens
(`(i => int64) < g.v.count`) rather than the counter narrowing. `=>` is the
lossless direction and needs no acknowledgement. Its guard reuses the
`BoundsIndex` the module already declares, so nothing grew a `failsafe` arm.

The find: a **struct literal**. `graph_init` built a `ModuleGraph{ … mods: …,
count: …, cap: … }` by hand, which sits inside no `g.` expression, so neither
the rewrite's scope nor the leftover assertion could see it. `TYPE-026` named
it on the first build. The converter asserts on that class now.

### The tally, because it is the same conclusion four times

Text search has been wrong about "who touches this representation" in four
structurally different ways in this step alone:

| what grep missed | how it was caught |
|---|---|
| output truncated by `head -20` (family 2) | the build, one commit later |
| access through the FIELD name, never the type (family 4) | `TYPE-019` |
| the UNQUALIFIED error spelling (family 6) | `REACH-002` |
| a struct LITERAL (family 7) | `TYPE-026` |

The compiler has been wrong zero times. None of the four reached a harness run,
and the two habits that caught them cost almost nothing: rehearse the script
against the live tree before applying it, and make the script refuse to write
when it can detect its own incompleteness. Both belong in whatever the next
mass migration reads before it starts.


## Families 9-12, and the two classes parallelism surfaced

Running two harnesses at once — the main tree on family 9, a worktree on
9+10 — is what exposed these, because both failed IDENTICALLY in fifteen
seconds. That is worth stating: the first concurrent run produced no flake and
no divergence, just the same real defect twice, which is the evidence that the
scheme is sound.

**Class 5: a field read from ANOTHER FILE.** `impl_scope_of` in
`emit_program.npk` takes `ImplTable->:t` and reads `t.count`; the converter was
single-file, and so was its leftover assertion, so both passed while the tree
did not build. The converter now SCANS `src/`, `tools/` and `tests/` for every
file mentioning the struct and rewrites each — self-discovering rather than
waiting to be told by a compiler error, which would find only whichever file
breaks the build first.

**Class 6: the binding is a LOCAL, not a parameter.** `note_family_instance` in
`ir_expr.npk` writes `wild ImplTable->:t = x.fe.ctx.impls;` inside its body, so
a test that reads the SIGNATURE cannot see it. The binding test now reads the
whole block. It stays a test for THIS struct bound to THIS name, which is what
keeps `ImplTable` and `BoundTable` — same file, both `t` — from contaminating
each other.

That is six structurally different ways to miss a site, five of them found by
the compiler and one by an assertion. The score is unchanged: text search 0,
compiler 6.

### And one process slip worth recording rather than hiding

Family 10 failed for a reason that was not subtle at all: I passed
`count_fns=()` when `inst_count` returns `int32`, so the accessor kept handing
back an `int64`. The parameter was simply wrong. It cost fifteen seconds
because the harness fails fast on a build error — but the reason I did not
catch it earlier is that I skipped `quickemit` on family 9 while setting the
parallel scheme up, which is the one cheap check that stands between an applied
conversion and a harness run. The discipline is: apply, `quickemit`, THEN the
harness. Setting up a faster loop is not a reason to drop the fast check.

# STOP-THE-LINE: a use-after-free in the compiler, exposed by family 10

**Step 2 is paused at family 10 of 12.** Families 1-9 are committed and green.
Family 10 (`InstanceTable`) is NOT committed, because landing it would land a
latent memory-safety defect's trigger without landing its fix.

## What is measured, and what each measurement rules out

| build | result |
|---|---|
| family 9 alone (`ImplTable`) | FULL HARNESS GREEN, fixpoint byte-identical |
| family 10 alone (`InstanceTable`) | self-compiles cleanly, 15,291,741 bytes |
| families 9 + 10 together | `npkc` TRAPS compiling itself, exit 3, empty stderr |
| families 9 + 10, `@npk_quarantine = 1` | **self-compiles cleanly** |

The trap, from `gdb -ex "break npk_trap" -ex bt`:

```
npk_trap <- npk_heap_bad <- npk_small_check <- npk_ralloc
         <- list_reserve<Instance> <- list_push<Instance>
         <- types.inst_record <- resolve_type.resolve_aggregate
         <- ... <- escape.can_connect
```

**The quarantine result is the diagnosis.** Quarantine poisons a freed block
and never returns it to the bitmap, so a stale pointer still passes
`npk_small_check`'s watermark. The failure disappearing under it means the
pointer is to a block that was FREED AND REUSED — a use-after-free — not
garbage and not an uninitialised table.

Ruled out by measurement, not by argument:

- **Not a bad conversion.** The converted `inst_record` is a faithful
  translation of the original; both are in the record above.
- **Not mis-monomorphisation.** Every `list_{init,reserve,push}` instantiation
  is distinct in the IR, and each one's size computation uses its own element
  type (`getelementptr %"npk.types.Instance"` vs
  `%"npk.type_trait.ImplEntry"`). Checked in the trapping build.
- **Not a dangling resolver.** `tr` and `f` are both live in the same frame at
  the `escape_init` call, `TypeResolver.instances` is a POINTER field, and
  nothing copies `Front` by value — `$$m f` is a mutable borrow.
- **Not `ralloc` mis-dispatch.** It routes on the EXISTING pointer through
  `npk_lg_find`, not on the requested size.

## Why this is pre-existing rather than caused

The hazard shape is identical before and after the conversion — a table is
`{ptr, count, cap}` either way, `list_init` starts at the same capacity of 16,
and the doubling is the same, so growth timing is unchanged. What the
conversion changed is LAYOUT: each converted table went from 16 bytes
(`{ptr, i32, i32}`) to 24 (`{ptr, i64, i64}`), which changes allocation sizes
and therefore which block gets reused when. **A symptom that moves when
unrelated things change size** is the ROADMAP's own cycle-0.6 lesson, quoted in
the handoff, and it is what this is.

Families 1-9 are green, but that is not evidence the defect is absent from
them — only that their layouts do not happen to trigger it. The defect is in
the tree NOW.

## What is owed

1. **Find the stale copy.** The reproduction is exact and cheap (about five
   minutes to build, two to run), and quarantine gives a working/failing pair
   to diff against. The remaining question is which `List` value is copied and
   then used after the original grows — `ralloc` frees the old block on
   growth, so any second copy of a grown list is stale from that moment.
2. **`escape.npk:605` indexes `holds` UNGUARDED.** `pass (x.holds[sy.origin
   => int64]);` — its two siblings at 144 and 179 both test
   `>= x.holds_count` first. `sy.origin` is a symbol's origin, which is not
   bounded by the statement count the array is sized to. This is an
   out-of-bounds READ, so it is not the corruption above, but it is a real
   defect found on the way and it is in D-223's neighbourhood.
3. Only after 1 is fixed: families 10, 11, 12 and the ten parallel-array
   families.

## What the parallel scheme contributed

The pair that found this was the first concurrent run — main tree on family 9,
worktree on 9+10. Both failed identically in fifteen seconds on the first
attempt (a real defect, no flake, no divergence), and the second attempt
separated a green family 9 from a trapping 9+10 in one wall-clock window
instead of two. The scheme is sound and it earned its keep immediately; the
deadline-flakiness risk it was being watched for did not appear.
