   match-shaped unwraps → `?.`/`?|` where the shape IS the operator.
   No wholesale rewriting — a form changes only where the current
   spelling is longer AND less clear.

# Execution record — step 1 attempted, REVERTED, and what it found

## `dyn Writer` works; `async main` on a real driver does not (yet)

The erasure itself is sound and was validated by probe BEFORE the compiler was
touched — which mattered, because the plan's phrasing ("the drivers construct
`std_err()`'s writer once") does not survive contact:

- **`dyn Writer` passes BY VALUE, never through a pointer.** A trait method's
  receiver is `Self->`, so the erased call takes the sink's address itself
  (1.1.12d); `dyn Writer->:w` fails method lookup outright. `dyn_stream.npk`
  is the canonical shape and it passes by value.
- A `dyn` is move-only, so a by-value sink cannot be reused across calls. That
  is fine here and only here: `main`'s three report sites are MUTUALLY
  EXCLUSIVE early exits, each already building its own stderr writer.
- **Async reaches exactly to the reporting boundary.** Every `Writer` operation
  is async by D-075 (required by D-071), so `report` and `main` become
  coroutines and nothing else does. `front_run` and the whole front half stay
  synchronous. This does NOT make D-209's decided-out "pipeline async" happen.

With that, the compiler built and REPORTED CORRECTLY — `borrows.npk` printed
all ten diagnostics through the erased sink and exited 1. Then it segfaulted on
every SUCCESSFUL compile, after writing complete, well-formed output.

## The defect: `wild_release_all()` unmaps the frame an `async main` is running on

Bisected by gdb, not by reasoning (two of my guesses were wrong first):

- the fault is `movl $0x0,(%rcx)` inside `npk.resume.main.main`, storing the
  exit code into the frame's result slot (offset 0x10 — slot 3);
- `%rcx` points INSIDE the frame, and `info proc mappings` shows the page is
  no longer mapped;
- `src/main.npk` calls `wild_release_all()` immediately before `exit 0i32` —
  twice (the `-o` path and the stdout path), and `resolve_check.npk` once.

**`exit` in an `async main` is not process exit.** `emit_exit` lowers it as
the ordinary return seam (`ir_stmt.npk`, the comment says so): store the code
into the frame's result slot, run the exit defers, `ret i8 0` from the resume.
The SHIM then reads the slot, `npk_dalloc`s the frame, and returns the code;
`npk_exit` runs after that, with the frame already freed. That is precisely
why every `async main` in the suite that exits 0 — `windup_drop.npk`,
`shared_arena_spawn.npk`, `variadic.npk`, all six driver programs — passes
D-151's leak check: **the frame is gone before the check runs.** The
accounting was never inconsistent; the question in the first draft of this
record was mine, and the answer is that `exit` means two different things.

`npk_wild_release_all` unmaps **the whole heap, both regimes** — its own
comment states the contract: *"after it, only exit; anything still pointing
into the heap points at unmapped pages."* In a sync `main`, `exit` IS an
immediate `call void @npk_exit`, so "only exit" holds. In an `async main`,
`exit` must still write to the frame and return through the shim — and the
frame is in the heap that was just unmapped.

**So the fix recorded in the first draft of this note — allocate the root
frame from the managed pool — fixes nothing**, because the release frees both
regimes. Recorded here because it is the plausible-looking wrong answer.

**Latent, not introduced.** It needs an `async main` that calls
`wild_release_all()`, and no such program existed: the async tests do not call
it, and the drivers that do were synchronous until this step.

## Why the drivers call it at all

It is a **leak amnesty**. `src/` allocates wild arena-style and frees almost
nothing individually, so a driver wipes the heap to make D-151's `exit 0`
check see zero. `nio_end`'s comment records the same effect from the other
side: a leaked writer buffer was invisible "for as long as tests called
`wild_release_all()` before exiting, and reported by D-151's exit check the
moment they stopped." Removing the call is therefore not free — it exposes
every deliberate leak in the compiler at once.

## The decision this needs (the user's, not the executor's)

The question is a language one: **what does `exit` mean inside an async
body?** Today it means one thing in a sync `main` and another in an async one,
which is the blueprint philosophy's own failure mode — and this segfault is
what that costs. Three shapes, none of them improvised into the tree:

- **A — the root frame moves off the releasable heap.** The shim allocates it
  from a dedicated mapping `wild_release_all` does not touch, and frees it the
  same way. Smallest change, preserves both existing contracts, and "after it,
  only exit" becomes true again for async main. Does not address the
  two-meanings problem.
- **B — `exit` means process exit everywhere.** The async lowering dallocs the
  frame and calls `npk_exit` directly instead of returning through the shim.
  One meaning for one spelling, which is the philosophy's answer; it makes the
  shim's return path dead for `main` and needs care that the exit defers still
  run first.
- **C — refuse `wild_release_all()` in an async body**, spanned, D-215's
  shape. Honest about the incompatibility, but leaves an async driver with no
  amnesty, so it blocks this adoption behind making `src/` actually free what
  it allocates — a large piece of work, and one worth wanting for its own sake.

My reading: **B is the philosophy's answer and A is the safe small one**, and
they are not exclusive — B subsumes A. C is the right long-run destination for
`src/`'s own hygiene regardless of which lands here. But `exit`'s meaning is
language design, so it is the user's call.

**Step 1 is reverted** so the tree stands at the green, pushed 1.4.6 state. The
probe (`dyn Writer` over `std_err()`, many lines through one erased sink)
compiles and runs, so the adoption is a small edit away once this is settled.
Steps 2 and 3 do not depend on it.

## SETTLED: the user chose B — `exit` is process exit everywhere (D-224)

Decided 2026-08-30. `exit`'s source-level rule is untouched: it stays legal
only in `main` and `failsafe` (D-013), the program still has exactly two exit
paths, and `failsafe`'s code is still positive. What changes is the LOWERING,
which is where the second meaning had grown.

The investigation that turned the decision into an implementation found one
sub-question the three options had not named. The root task's frame is
allocated by `@npk_alloc`, and that is the WILD-TRACKED entry
(`npk_alloc_impl(n, 1)`; `@npk_alloc_managed` is the untracked one). So the
frame counts toward D-151's `<wild-live>` set, and every `async main` in the
suite that exits 0 passes the leak check only because the SHIM frees the frame
before `npk_exit` runs. Under B the shim's exit path never runs, so a tracked
frame would trap −4105 on a successful exit — B alone would have traded a
segfault for a leak trap.

It cannot be fixed by freeing the frame at the `exit` either: `wild_release_all()`
may legally precede `exit`, and `npk_dalloc` after that release touches unmapped
pages — the original defect, moved one instruction. So the root frame becomes
`@npk_alloc_managed`, which is right on its own terms: it is runtime scaffolding
the shim allocates and the program never sees, the same class as argv and string
bodies, and it was in the program's leak accounting by accident rather than by
design. The ordinary return path still frees it.

**Landed:** `emit_exit` (`ir_stmt.npk`) takes an async arm — exit defers, then
`call void @npk_exit(i32 <code>)` and `unreachable`, the shape `emit_trap` has
used since 0.10.1 — with the sync arm's plain `ret` unchanged, since `_start`
already calls `@npk_exit` on it with nothing in between
(`runtime/npkrt.ll:143`). `fnem_emit_main_shim` (`ir_func.npk`) allocates the
root frame managed.

**Regressed by** `tests/backend/programs/async_exit_release.npk`: an async
`main` that allocates wild, suspends, releases the heap and exits 0. It has to
exit 0 specifically — D-151's leak check runs on no other code, which is the
1.4.4 lesson about a test reporting success as 42 measuring nothing.

# Step 2 — the generic collections: the enumeration, and the first family

## What is actually there (measured, not estimated)

The plan said "rg for the repeated grow/at/push pattern". Brace-matched over
every `func:` in `src/`, counting bodies that both `ralloc` and double:

**44 hand-rolled doubling sites over 89 growable arrays.**

- **26 single-array growers** — one `ralloc`, one `=>!`, one capacity store.
  A generic replaces each outright: `strtab_add`, `fnem_defer_add`,
  `fnem_new_seg`, `drop_fn_sym`, `ast_grow_{decls,ids,pats,scratch,types,
  verifies}`, `sink_grow`, `exprtypes_mark_{crossing,owning_decl}`,
  `intern_grow`, `sitetable_add`, `graph_grow`, `rootlist_grow`,
  `srcmgr_grow`, `symtab_{grow_scopes,grow_syms,set_home}`, `tokenlist_grow`,
  `bound_grow`, `impl_grow`, `fninst_grow`, `inst_grow`.
- **18 parallel-array growers** — 63 arrays between them, `fnem_pick_push`
  alone growing eight in lockstep. These are STRUCT-OF-ARRAYS tables, not
  arrays of structs, and the plan's phrasing ("collapse into generic
  containers") reads as though they were the same thing. They are not: the
  collapse for these is N separate `List<T>` fields, which PRESERVES the SoA
  layout rather than changing it. Nothing about the representation moves.

**The reason to do it is not tidiness.** Every one of those 89 arrays carries
its own `=>!` reinterpretation of `ralloc`'s bytes back to the element type,
and 1.4.2 found FIVE latent unchecked pointer reinterpretations in exactly
this shape — invisible for as long as the callee had no type to check them
against. Ninety hand-written casts are ninety chances to write one wrong; one
generic is one cast, checked once, at every instantiation.

## The design, proven by probe before `src/` was touched

`src/frontend/list.npk` — `List<T>` with `list_init`, `list_reserve`,
`list_push`. Four choices, each with the measurement behind it:

- **`wild`, unchanged.** Every family replaced was already wild; the compiler
  allocates arena-style and frees almost nothing. Making the storage managed
  would change when the compiler's own tables die — a different decision from
  this one, and one that collides with the `wild_release_all()` question step
  1 is blocked on.
- **`int64` count and capacity, uniformly.** The families disagreed —
  `TokenList` and `Sink` counted in `int64`, the other eight in `int32`. One
  collection answering "how many" two ways is what the blueprint philosophy
  exists to prevent, and `int64` is also the safe side: under D-210 a doubling
  that overflows TRAPS, and at 64 bits it cannot reach the trap.
- **Storage only — no generic `list_at`.** For an owning `T`, returning `T`
  is a copy, and copies of owning values are refused (TYPE-046). Reading an
  element stays the family's business: `RootList` hands back a deep view,
  others read a scalar through `l.items[i]`, and one generic accessor could
  serve only one of those.

- **`list_reserve` takes a COUNT, and doubles in a loop.** The first draft
  reserved room for one element, which is what all 26 single-array growers
  spell — and reading `Sink` before writing the second family showed why that
  is wrong: it appends BYTES IN BULK, by however many the write is. A
  one-element reserve would have been correct for exactly the families that
  never exercised it and would have silently under-allocated for the rest, and
  a single doubling does not hold a bulk append of ten thousand into a
  capacity-8 list either. `list_push` is now the special case
  (`list_reserve(l, 1i64)`), which is the right way round.

`move T:v` on the push was the one thing worth measuring rather than assuming,
because it has to serve both an owning and a non-owning instantiation. A probe
(`List<int32>` and `List<Owning>` in one program, pushed past a grow)
type-checks and RUNS — exit 42 — so the parameter is consuming where that
matters and indifferent where it does not.

## Family 1 of 12: `RootList`

Chosen first because it is the only family whose accessors never leave its
file: tree-wide, `rootlist_count` and `rootlist_at` are called only inside
`resolve_path.npk`, so the `int32` → `int64` count change has exactly one
consumer loop. `rootlist_init` and `rootlist_add` keep their signatures and
their 28 external call sites are untouched.

What went: the struct's three fields become one `List<Root>`, and
`rootlist_grow` is deleted entirely. What stayed: where a root's `/src` is
appended, and the deep-viewed copy `rootlist_at` returns — the parts that were
ever this file's own.

## The remaining families, in the order they should land

Smallest external surface first, one commit and one full harness each:

`Sink` · `StrTable` · `SiteTable` · `InternTable` · `SourceManager` ·
`ModuleGraph` · `BoundTable` · `ImplTable` · `InstanceTable` · `FnInstTable` ·
`TokenList`, then the parallel-array tables (`TypeTable`'s five, `FnEmitter`'s
seven, `Suspend`'s two, `Ast`'s two, `irw_site`, `vtmap_add`, `reach_add_decl`,
`resolve_decl`, `foldenv_set`, `tt_unit_put`) — those last are mechanical once
the single-array ones have shaken the generic out.


## Why these were hand-written, which turns out to matter

`source.npk` states it, right above `SourceManager`:

> hand-written — the cost SUBSET_1 accepted deliberately, to keep
> monomorphization out of the least-audited artifact in the chain.

**That constraint expired at 1.4.6.** The Python seed is retired (D-203,
D-205); `src/` is built by the committed snapshot, which is npkc itself and
monomorphizes like any other build. The 89 hand-written arrays were never an
oversight and never duplication anybody failed to notice — they were the price
of keeping generics out of the seed, paid deliberately, and D-209 scheduled
this adoption for after the switch precisely because the switch is what stops
the bill. Each family's stale explanation comes out as it converts; a comment
defending a constraint that no longer exists is the next stale document.

## Family 2 of 12: `Sink`

The bulk-append family, and the one that had already shaped the API. Two
things worth carrying forward:

**`Sink` never carried a `=>!` of its own** — its elements were already the
allocator's `int8`, so `out.buf = ralloc(out.buf, n)` needed no cast. It is
the only one of the twelve where the win is uniformity rather than a removed
reinterpretation. Worth knowing before the remaining ten, where the cast is
the point.

**`sink_view` is new, and is the better shape regardless of the generic.**
`irw_text` assembled its mid-function text by reaching into `.buf`/`.len` at
five sites — the IR writer knowing how a sink stores bytes. It now asks for a
view (`string_from_bytes`, D-186's explicit view primitive: a cap-0 string
owning nothing, so the sink keeps its buffer). Five layout dependencies gone,
and the next family that changes a representation will not find them.

### Two process finds, neither of which cost anything this time

- **A frontend-only `quickcheck` went green while the backend was broken.**
  `tools/check.npk` does not include `src/backend/`, so the five `.buf` reads
  in `ir_writer.npk` type-checked as absent. The summary of 1.4.6 records the
  same lesson in a different shape ("the honest claim is: the frontend
  compiles"). For any change to a type that BOTH halves use, the cheap
  verification is `quickemit` on one program, not `quickcheck`.
- **A completeness sweep was truncated by `head`.** The grep that concluded
  "nothing outside `diagnostics.npk` touches Sink's fields" was piped through
  `head -20`, and the `.buf` uses sat below the cut. A sweep whose answer is
  "none" must not be truncated — count it, or read all of it.

### And one measurement that was worth taking

Checking `tools/check.npk` takes **72 seconds**, which is just over
`quickcheck.py`'s 60-second per-file cap, so it reports a timeout that reads
like a hang. It is not one, and it is not new: a worktree built at the
previous commit answers in 1m12.259s against 1m12.097s after the conversion —
the same number. The generic costs nothing measurable. The tool's cap is the
thing that is slightly wrong, and it is the largest entry file in the tree
that trips it.


## Families 3 and 4, and the rule that came out of them

`StrTable` (family 3) has one subtlety: the name it hands back IS the index the
string lands at, so the index is read BEFORE the push — `list_push` advances
the count, and reading it after would name every constant one past itself.
Checked in emitted IR before the harness: `@.str.0` through `@.str.105`,
contiguous from zero.

`SiteTable` (family 4) is where the working rule finally got stated.

### The completeness check for a representation change is the COMPILER, not grep

It has now cost a miss twice and been caught free twice:

- **family 2**: the sweep for "who touches `Sink`'s fields" was piped through
  `head -20`, and the five `ir_writer.npk` sites sat below the cut;
- **family 4**: the sweep for `sitetable|SiteTable` found seven references and
  missed both real ones, because the consumer reads `x.sites.count` — through
  the FIELD name, which never mentions the type at all.

Grep cannot see the second class even when it is not truncated. The procedure
that works is: apply, build, and let `NITPICK-TYPE-019` enumerate every site
with spans in one pass. The only requirement is that the build covers BOTH
halves of the tree — `quickemit` (npkc), never `quickcheck` (frontend only).

Two habits now carry it, and both have already paid:

- **Rehearse a scripted conversion against the live tree before applying it.**
  Family 6's dry run listed three functions (`srcmgr_find`, `srcmgr_path`,
  `srcmgr_text`) that the replacement block did not cover, before anything had
  been written to disk.
- **End the script with a leftover assertion**, not a hopeful grep beforehand.
  Family 7's refuses to apply itself if any `g.mods`/`g.count`/`g.cap` survives
  anywhere in the file. A conversion that can detect its own incompleteness is
  worth more than a sweep that has to be remembered.


## Families 5 and 6: the guarded narrow, and what a new error costs

`InternTable` (family 5) is the first family where `int64` uniformity has a
real price. An intern id is `int32` BY AST DESIGN — every node stores a name as
one — so the list's `int64` count must narrow to produce an id. That narrowing
is GUARDED, never `=>!`: a silent truncation would alias two different names to
one id, which is the single failure this table exists to make impossible.
Before the conversion the `int32` counter got that property for free, because
under D-210 its increment TRAPPED; `intern_id` is what keeps it once the count
is wide. It raises the `BoundsId` the module already declares, so the set of
errors reaching `failsafe` does not change and no `failsafe` grows an arm.

`SourceManager` (family 6) is the one that does need a new error. A file id is
what a `Span` carries in every AST node, so the same guarded narrow applies,
and `BoundsOffset` (a byte offset inside one file) is the wrong invariant to
borrow. Reusing the builtin `IntOverflow` would have dodged the cost and was
rejected: D-179's whole point is that a module's defects carry its own
unforgeable identity, and borrowing a builtin erases it. So `source.BoundsIndex`
is declared, and **38 `failsafe` picks grew an arm** — the predicted, accepted
cost of a new failure mode, and REACH-002 refusing to compile until each one
acknowledged it.

### Grep missed a third class

Two of the 38 spell the arm UNQUALIFIED — `(BoundsOffset)`, not
`(source.BoundsOffset)` — because they import the module directly and the name
is in scope. The sweep that found 36 sites found neither. That is the third
distinct way a text search has been wrong about the same question in this step
(truncated output, field-name access, and now the qualified/unqualified
spelling), against zero times the compiler has been.

### And one finding that is the design working

`ir_types.npk` carried a bare `(BoundsIndex)` arm that named
`types.BoundsIndex` unambiguously — until `source.BoundsIndex` existed, at
which point the unqualified name re-pointed and `types.BoundsIndex` was
suddenly uncovered. **REACH-002 caught it**, refusing the file until the arm
was named again. That is the exhaustiveness rule earning its keep: adding an
error to one module cannot silently cost another module's coverage, because
the check is over what can REACH `failsafe`, not over what the text used to
say. Both arms are qualified now, which is the right spelling regardless.


## Family 7: `ModuleGraph`, and the fourth thing grep cannot see

26 sites, the largest single-array family. Its loop counters STAY `int32` on
purpose: every one is a module index, not a size — an index is `int32` by the
same design that forces the guarded narrow — so the comparison widens
(`(i => int64) < g.v.count`) rather than the counter narrowing. `=>` is the
lossless direction and needs no acknowledgement. Its guard reuses the
`BoundsIndex` the module already declares, so nothing grew a `failsafe` arm.

The find: a **struct literal**. `graph_init` built a `ModuleGraph{ … mods: …,
count: …, cap: … }` by hand, which sits inside no `g.` expression, so neither
the rewrite's scope nor the leftover assertion could see it. `TYPE-026` named
it on the first build. The converter asserts on that class now.

### The tally, because it is the same conclusion four times

Text search has been wrong about "who touches this representation" in four
structurally different ways in this step alone:

| what grep missed | how it was caught |
|---|---|
| output truncated by `head -20` (family 2) | the build, one commit later |
| access through the FIELD name, never the type (family 4) | `TYPE-019` |
| the UNQUALIFIED error spelling (family 6) | `REACH-002` |
| a struct LITERAL (family 7) | `TYPE-026` |

The compiler has been wrong zero times. None of the four reached a harness run,
and the two habits that caught them cost almost nothing: rehearse the script
against the live tree before applying it, and make the script refuse to write
when it can detect its own incompleteness. Both belong in whatever the next
mass migration reads before it starts.


## Families 9-12, and the two classes parallelism surfaced

Running two harnesses at once — the main tree on family 9, a worktree on
9+10 — is what exposed these, because both failed IDENTICALLY in fifteen
seconds. That is worth stating: the first concurrent run produced no flake and
no divergence, just the same real defect twice, which is the evidence that the
scheme is sound.

**Class 5: a field read from ANOTHER FILE.** `impl_scope_of` in
`emit_program.npk` takes `ImplTable->:t` and reads `t.count`; the converter was
single-file, and so was its leftover assertion, so both passed while the tree
did not build. The converter now SCANS `src/`, `tools/` and `tests/` for every
file mentioning the struct and rewrites each — self-discovering rather than
waiting to be told by a compiler error, which would find only whichever file
breaks the build first.

**Class 6: the binding is a LOCAL, not a parameter.** `note_family_instance` in
`ir_expr.npk` writes `wild ImplTable->:t = x.fe.ctx.impls;` inside its body, so
a test that reads the SIGNATURE cannot see it. The binding test now reads the
whole block. It stays a test for THIS struct bound to THIS name, which is what
keeps `ImplTable` and `BoundTable` — same file, both `t` — from contaminating
each other.

That is six structurally different ways to miss a site, five of them found by
the compiler and one by an assertion. The score is unchanged: text search 0,
compiler 6.

### And one process slip worth recording rather than hiding

Family 10 failed for a reason that was not subtle at all: I passed
`count_fns=()` when `inst_count` returns `int32`, so the accessor kept handing
back an `int64`. The parameter was simply wrong. It cost fifteen seconds
because the harness fails fast on a build error — but the reason I did not
catch it earlier is that I skipped `quickemit` on family 9 while setting the
parallel scheme up, which is the one cheap check that stands between an applied
conversion and a harness run. The discipline is: apply, `quickemit`, THEN the
harness. Setting up a faster loop is not a reason to drop the fast check.

# STOP-THE-LINE: a use-after-free in the compiler, exposed by family 10

**Step 2 is paused at family 10 of 12.** Families 1-9 are committed and green.
Family 10 (`InstanceTable`) is NOT committed, because landing it would land a
latent memory-safety defect's trigger without landing its fix.

## What is measured, and what each measurement rules out

| build | result |
|---|---|
| family 9 alone (`ImplTable`) | FULL HARNESS GREEN, fixpoint byte-identical |
| family 10 alone (`InstanceTable`) | self-compiles cleanly, 15,291,741 bytes |
| families 9 + 10 together | `npkc` TRAPS compiling itself, exit 3, empty stderr |
| families 9 + 10, `@npk_quarantine = 1` | **self-compiles cleanly** |

The trap, from `gdb -ex "break npk_trap" -ex bt`:

```
npk_trap <- npk_heap_bad <- npk_small_check <- npk_ralloc
         <- list_reserve<Instance> <- list_push<Instance>
         <- types.inst_record <- resolve_type.resolve_aggregate
         <- ... <- escape.can_connect
```

**The quarantine result is the diagnosis.** Quarantine poisons a freed block
and never returns it to the bitmap, so a stale pointer still passes
`npk_small_check`'s watermark. The failure disappearing under it means the
pointer is to a block that was FREED AND REUSED — a use-after-free — not
garbage and not an uninitialised table.

Ruled out by measurement, not by argument:

- **Not a bad conversion.** The converted `inst_record` is a faithful
  translation of the original; both are in the record above.
- **Not mis-monomorphisation.** Every `list_{init,reserve,push}` instantiation
  is distinct in the IR, and each one's size computation uses its own element
  type (`getelementptr %"npk.types.Instance"` vs
  `%"npk.type_trait.ImplEntry"`). Checked in the trapping build.
- **Not a dangling resolver.** `tr` and `f` are both live in the same frame at
  the `escape_init` call, `TypeResolver.instances` is a POINTER field, and
  nothing copies `Front` by value — `$$m f` is a mutable borrow.
- **Not `ralloc` mis-dispatch.** It routes on the EXISTING pointer through
  `npk_lg_find`, not on the requested size.

## Why this is pre-existing rather than caused

The hazard shape is identical before and after the conversion — a table is
`{ptr, count, cap}` either way, `list_init` starts at the same capacity of 16,
and the doubling is the same, so growth timing is unchanged. What the
conversion changed is LAYOUT: each converted table went from 16 bytes
(`{ptr, i32, i32}`) to 24 (`{ptr, i64, i64}`), which changes allocation sizes
and therefore which block gets reused when. **A symptom that moves when
unrelated things change size** is the ROADMAP's own cycle-0.6 lesson, quoted in
the handoff, and it is what this is.

Families 1-9 are green, but that is not evidence the defect is absent from
them — only that their layouts do not happen to trigger it. The defect is in
the tree NOW.

## What is owed

1. **Find the stale copy.** The reproduction is exact and cheap (about five
   minutes to build, two to run), and quarantine gives a working/failing pair
   to diff against. The remaining question is which `List` value is copied and
   then used after the original grows — `ralloc` frees the old block on
   growth, so any second copy of a grown list is stale from that moment.
2. **`escape.npk:605` indexes `holds` UNGUARDED.** `pass (x.holds[sy.origin
   => int64]);` — its two siblings at 144 and 179 both test
   `>= x.holds_count` first. `sy.origin` is a symbol's origin, which is not
   bounded by the statement count the array is sized to. This is an
   out-of-bounds READ, so it is not the corruption above, but it is a real
   defect found on the way and it is in D-223's neighbourhood.
3. Only after 1 is fixed: families 10, 11, 12 and the ten parallel-array
   families.

## What the parallel scheme contributed

The pair that found this was the first concurrent run — main tree on family 9,
worktree on 9+10. Both failed identically in fifteen seconds on the first

# RESOLVED: not a use-after-free — the trigger patch deletes a guard it does not own

Escalated per `1.4.7-escalation.md`; diagnosed under gdb on the exact
reproduction. The culprit, the invalidation, and the use are all in the PATCH,
not in `main` — and the shape is an out-of-bounds WRITE, not a stale pointer.

## The culprit, red-handed

**Hunk 2 of `1.4.7-family10-trigger.patch` removes `fninst_record`'s grow
guard** — `if (t.count >= t.cap) { drop fninst_grow(t); }`,
`src/frontend/types.npk:1446` — while converting NOTHING else in `FnInstTable`.
The raw push at `types.npk:1453-1454` (`t.items[t.count => int64] = n;
t.count = t.count + 1i32;`) stays, so the seventeenth distinct
generic-function instantiation writes past the 16-slot block and every later

20-byte `Span`), so the block is 16 × 48 = 768 bytes — exactly size class 10 —
and the very first out-of-bounds byte lands on the NEXT slot's 16-byte header

The converter matched the guard pattern for a table bound to `t`;
`fninst_record` and `inst_record` share the file AND the binding name. That is
the **seventh way to miss a site, and the first in the opposite direction: the
converter EDITING a site it does not own.** Family 9's binding-name discipline
(the ImplTable/BoundTable note above) was applied to the rewrite scope but not

# Step 1 LANDED — `dyn Writer` diagnostics, and four things the plan could not know

Full harness green (`ok 60`, 184 programs, selfhost byte-identical, repro
clean). D-224 unblocked it; the rest is what the adoption itself taught.

## What landed

**Five walks became one.** The plan said "the diagnostic renderers take
`dyn Writer` receivers", which reads like a signature change. The actual find is
that there were FIVE copies of the walk — `report` in `src/main.npk`, `report`
in `tools/check.npk`, the inline loop in `resolve_check`, and TWO inline loops
in `parse_check` — over the one formatter `check_one_renderer` pins. They are
now a single `diag_report(dyn Writer:sink, DiagList->, SourceManager->,
Duration)`, with `diag_report_stderr` and `diag_say` as the drivers' spellings.

**All of stderr goes through one sink.** The six driver one-liners ("usage:",
the two "cannot write the output file", "cannot write the IR to stdout",
parse_check's two-part "cannot read: ") moved onto `diag_say`. Leaving half of
stderr on `lib/nio` would have been two mechanisms for one stream. The single
surviving `nio` call is `nio_write_all(nio_stdout_fd(), …)`, which carries the
IR — the PRODUCT, on the byte path D-050 requires.

**Four `main`s are coroutines**, and the record's correction holds: a `dyn`
passes BY VALUE and is move-only, so "the drivers construct `std_err()`'s writer
once" is not available. Every report site is its own early exit and builds its
own sink; the dup it owns closes at that function's exit.

## The four finds

**1. `async` and `never fails` are mutually exclusive (TYPE-037).** A suspended
task can be CANCELLED, and cancellation is an error the contract would deny. The
old `report` was `never fails` because it was synchronous; making it async
removes that contract BY RULE. The consequence is not cosmetic: `drop` is
licensed by a checked `never fails` callee (D-163), so it is no longer available
on this path and the call site spells its acknowledgement `?| NIL`. The
best-effort promise is now per-write rather than signature-level, which is the
more honest claim anyway — "a broken stderr cannot be reported on stderr" is
about each write.

**2. D-205's ordering, got backwards, and it failed LOUDLY.** A feature enters
`src/` only after a snapshot that understands it. D-224 landed, and step 1 then
made `main` async while the builder was still the pre-D-224 snapshot — which
compiled it with the OLD seam and produced an `npkc` that segfaulted on its own
`wild_release_all(); exit 0i32;`. `npkc.ll`'s `@main` carrying
`call ptr @npk_alloc` is what named it. Refreshed at the D-224 commit
(`e0871ab`), fixpoint held byte-identical. Worth recording that the stale
snapshot did NOT yield a subtly wrong compiler — it died on the first
self-compile, and the refresh procedure's own fixpoint step is what stands
between us and the quiet version.

**3. REACH is IMPORT-scoped, and that decided a module split.** Putting the
async functions in `diagnostics.npk` made `DeadlineExceeded` reachable in every
program importing it — TWELVE of the compiler's own unit tests failed
REACH-002, including `tests/backend/ir_expr.npk`, which does not mention the
report path at all. The obvious fix was twelve `(DeadlineExceeded)` arms, with
precedent: family 6's new error grew 38. But those 38 were TRUE. These twelve
would acknowledge a failure mode that cannot occur in those programs, and an
exhaustive `failsafe` earns its keep by being true — spending the rule's
credibility to avoid a module split is a bad trade, most of all with 1.5 ahead,
where every arm is an obligation somebody discharges. So the async surface is
`src/frontend/diag_writer.npk`, imported by the four drivers alone.
`diagnostics.npk` keeps what it always was — the list, the diagnostic, and
`diag_line`, the one FORMATTER. The new file is the one WRITER.

**4. A module may not share a name with a function it declares.** `mod:` must
match the basename, so `diag_report.npk` declaring `func:diag_report` is
`NITPICK-RESOLVE-001` — the module name is taken first. Hence `diag_writer.npk`.
This belongs with CLAUDE.md's reserved-words table: naming a file after its
principal function is a trap, and the error points at the `mod:` line.

## Owed, and NOT closed by this step

- **`diaglist_render(Sink->)` is still a second walk**, used only by
  `tests/frontend/diagnostics.npk`. It cannot fold into `diag_report`, because
  `dyn` coercion MOVES: a capture buffer handed to the erased walk is consumed
  and cannot be read back afterwards. That is exactly what `npkg test`'s
  capture-and-compare needs to do, so a BORROWING Writer (or a capture sink the
  walk does not own) is a real design question this step surfaced and did not
  answer. It is the user's, not the executor's.
- **The driver path does not sort; `diaglist_render` does.** Driver behaviour
  was kept identical rather than changing output ordering under cover of a
  receiver migration. Whether diagnostics should print span-sorted is its own
  decision, with D-204's reproducibility arguing yes.

# Family 12 of 12: `TokenList` — and a guard that is not an append's

The twelve single-array families are converted. The last one is the first where
the converter's MODEL was wrong rather than its scoping, and the pairing assert
is what said so — on its first real outing, in a dry rehearsal, before anything
reached disk:

```
TokenList: 2 guard deletion(s) vs 1 push conversion(s)
```

**`TokenList` has two legitimate guard-and-grow sites.** `tokenlist_push` is
the ordinary append. `tokenlist_split_shr` — the function that splits a lexed
`>>` into two `>` when the parser asks (D-064's context-free-lexer bargain) —
grows and then SHIFTS THE TAIL UP BY ONE to insert, so there is no
`items[count] = v; count = count + 1` for the push rewrite to match. Deleting
that guard would have left the shift writing past the end at `count == cap`:
**the family-10 defect reached from the other side**, and this time the tool
would have been right about the family and wrong about the shape.

The fix is the tool's model, not a bypass. A guard now has exactly two
legitimate dispositions:

- it pairs 1:1 with an append — deleted, and the append becomes `list_push`; or
- the caller NAMES the function in `reserve_fns` and it becomes an explicit
  `drop list_reserve(@l.v, 1i64);`, which is what the guard always meant.

Anything else still trips. Bypassing the assert to get past it was the option
on the table and is the instinct that produces exactly this class of defect.

**The new assert was checked against failure before it was trusted**, because
this project has shipped a dead one (`check_runtime_sigs_agree`'s derived-inner
leg, dead from birth): naming a reserve function that does not exist is refused
(`0 reserve rewrite(s) for 1 named function(s)`), and omitting the real insert
site still trips the pairing assert.

## One thing the tool got wrong that the source absorbed

The widening rewrite emitted `(i => int64)` where `i` is ALREADY `int64` — the
converter assumes an `int32` counter because eight of the twelve families had
one. `TokenList` and `Sink` counted in `int64` from the start, which the step-2
enumeration recorded at the outset. Two no-op casts, removed by hand rather
than by teaching the tool, because `Sink` was family 2 and `TokenList` is the
last of that pair: the case cannot recur in the ten parallel-array families.

# The index rule — D-226 (user-ratified, 2026-08-31)

Six parallel-array families in, the same question had been answered three
different ways: **when a table's count becomes `int64`, what happens to the
`int32` index it hands out?**

- families 5/6 — a guarded narrow behind a NEWLY DECLARED error (correct, and
  family 6's cost was 38 `failsafe` arms);
- family 7 — a guarded narrow reusing an error the module ALREADY declares
  (free);
- `irw_site` — no narrow at all, because the dedup scan's loop counter already
  WAS the index as an `int32` and D-210 makes its `+ 1i32` trap.

Three mechanisms for one question is what the blueprint philosophy exists to
prevent, and `FnEmitter`'s seven — `fnem_pick_push` grows eight arrays in
lockstep — would have invited a fourth. The rule, ratified rather than
improvised:

> **The index type FOLLOWS THE COUNT — `int64` — unless an external contract
> pins `int32`, and then it is a guarded narrow reusing an error the module
> already declares.**

The test is whether the `int32` is a real contract or an artifact of the old
representation. Family 5's intern id is a contract: every AST node stores a
name as an `int32`, and the whole table exists to make two names impossible to
alias, so the narrow must be guarded and must keep its own error identity
(D-179 — borrowing a builtin erases it). `reg_add`'s index in `Suspend` is not
a contract: it is an `int32` because `lcount` was, and it is consumed by three
call sites in the same file. Under the rule that family needs no narrowing at
all.

A NEW error identity stays the last resort, not the default: it is the one
option whose cost lands on every `failsafe` in the tree, and the point of
reusing an already-declared one (family 7) or removing the narrow entirely
(`irw_site`, and now `Suspend`) is that neither spends that.

## Parallel-array family 7/10: `Suspend` — and the first red

and `reg_add` return `int64`, `idx`/`ni` follow, and `sls` changed element type

# The step-2 enumeration was short by four families — and the eighth way to miss a site

Found by re-measuring at the 1.4.7 midpoint handoff rather than by trusting the
count, which is this file's own standing lesson applied to this file.

**The handoff said "REMAINING IN STEP 2: `TypeTable`'s five and `FnEmitter`'s
seven."** That is what the two landing lists contain. It is not what the tree
contains. Four more families still grow by hand:

| family | file | growers | why it has no slot |
|---|---|---|---|
| `SymbolTable` | `symbols.npk` | 3 | named in the grower enumeration, in neither landing list |
| `ExprTypes` | `expr_types.npk` | 2 | same |
| `LlCtx.drop_types` | `ir_types.npk` | 1 | same |
| `MacroTable` | `expand.npk` | 1 | **never counted at all** |

**The first three are a bookkeeping gap.** The enumeration at the head of step
2 lists 26 single-array growers by NAME, and `symtab_{grow_scopes,grow_syms,
set_home}`, `exprtypes_mark_{crossing,owning_decl}` and `drop_fn_sym` are all

list; six were left with nothing to land them. The two lists were never
reconciled against each other, and nothing checks that they are.

**`MacroTable` is the interesting one, and it is the EIGHTH way a site hides
from a search.** The enumeration's method is stated in its own first line:
"brace-matched over every `func:` in `src/`, counting bodies that both `ralloc`
and double". `macrotable_grow` doubles — and does not `ralloc`. It `alloc`s a
fresh block and copies element by element:

```
func:macrotable_grow = NIL(MacroTable->:t) never fails {
    int32:ncap = t.cap * 2i32;
    wild int8->:mem = alloc((ncap => int64) * #size_of<MacroEntry>());
    ...
    while (i < (t.count => int64)) { dst[i] = t.items[i]; i = i + 1i64; }
```

Every previous miss was the search's SCOPE being wrong — truncated output, the
field name, the unqualified spelling, a struct literal, another file, a local
binding, the tool editing what it does not own. This one is the search's
PREDICATE being wrong: `ralloc` was taken as the signature of "a growable
array", and one family spells growth another way. The compiler could not catch
it either, because nothing is broken — it is a family that was never asked to
convert. **The score's shape changes here: the compiler catches an INCOMPLETE
conversion, and caught six. It cannot catch an unstarted one.** Only
re-measuring does, and the measure has to be the property (a capacity that
doubles) rather than one implementation of it.

Two other findings from the same sweep, both real and both landing with their
families:

- **`ExprTypes` narrows an `int64` capacity with a bare `=>!`** —
  `t.ccap = ncap =>! int32`, twice. The doubled value is unchecked on the way
  back down. Under D-210 the `int32` path would have trapped; this one is
  spelled as an accepted loss and is not.
- **`symtab_set_home` is not an append at all.** It is an index-addressed
  sparse map: `while (decl >= t.home_cap)` grow, hand-zero the new tail, then
  write at `decl`. `List<T>` has `list_reserve` (room for N MORE beyond the
  count) and `list_push`, and neither is this shape — the count never moves and
  the index is the caller's. This one needs a decision, not a conversion; it is
  the first family where the generic as designed does not fit.

**Decided by the user (2026-08-31): all four land inside step 2.** The
migration's whole argument is that ninety hand-written `=>!` reinterpretations
are ninety chances to write one wrong, and one generic is one cast checked at
every instantiation. Leaving four families hand-rolled keeps the raw
`items[count] =` push idiom alive in five places instead of one — and the
1.5 obligation this step is supposed to buy ("the push idiom exists ONLY in
`list.npk:81`, one line below its reserve; a whole-tree check can pin it") is
unavailable for as long as any of them survives. It was never a scope
question; it was a counting error.

**Order, smallest external surface first**, which also puts the two shape
questions before the two wide families rather than after them:

`MacroTable` · `LlCtx.drop_types` · `ExprTypes` · `SymbolTable` ·
`TypeTable` · `FnEmitter`

# FOUND while scouting family 5: `tt_grow` never zero-fills two of its four side arrays

Not caused by any conversion — found by reading `TypeTable`'s field inventory
before drafting its conversion, and **latent since 1.2.5**. Recorded here
before its fix so the finding survives independently of the commit that closes
it. Owner: family 5 (`TypeTable`), this subcycle.

`tt_grow` reallocates five blocks and then fills exactly two:

```
wild int8->:hp  = ralloc(t.haspt …);      wild int32->:hw = hp =>! wild int32->;
wild int8->:dp  = ralloc(t.drops …);
wild int8->:hcp = ralloc(t.haschan …);
wild int8->:hbp = ralloc(t.hasborrow …);
wild int32->:dw = dp =>! wild int32->;
// The grown tail must read "not computed" — ralloc copies only the old block.
int32:z = t.cap;
while (z < nc) { hw[z => int64] = 0i32; dw[z => int64] = 0i32; z = z + 1i32; }
```

`haspt` and `drops` get the fill. **`haschan` and `hasborrow` do not.** Past
the first grow — 64 entries, which every real program exceeds — the tail of
those two blocks holds whatever `ralloc` left there, and the readers
(`tt_haschan`, `tt_hasborrow`, types.npk:1527/1528/1592/1593) guard only
`id >= t.count` before returning it. `contains_channel` and `contains_borrow`
then compare it `== 2i32`.

**The history says what happened, exactly.** The fill loop was written at
0.8.1 (`c70ae4e`) and extended once, when `drops` arrived. `haschan` and
`hasborrow` were added together at 1.2.5a+b (`2ce881e`) and the loop was not
extended a second time. One more instance of this project's most-repeated
defect: two components agreeing by convention until one moves.

**Reads before the write are an ANTICIPATED state, not a hypothetical** — that
is what makes this reachable rather than merely ugly. `drops`' own comment
states the convention ("0 = not computed, 1 = owns nothing, 2 = owns something
and must be dropped"), so the design expects a slot to be read before layout
computes it, and encodes that expectation as zero. `tt_intern` bumps `count`
for a new type immediately while layout runs later — or never, for a type
nothing lays out — so the window is ordinary, not exotic. For `haspt` and
`drops` that window reads 0 and every caller handles it. For the other two it
reads garbage.

Both directions are wrong and one is the unsafe one. Garbage that is not 2
answers "holds no channel" / "holds no borrow", which is what D-183's `gives`
rule and D-215's dyn-coercion refusal key on — a false negative there is a
missing refusal. Garbage that happens to be 2 is a spurious refusal instead.
The allocator's 0xAA poisoning makes the first far likelier, which is the
quiet direction.

**Not yet measured: whether a read actually lands in that window today**, for
some id, in some program the suite compiles. The suite is green, so either it
does not, or it does and the garbage has always answered the same as the
correct value would. That distinction is worth one experiment rather than an
argument — fill the tail with `2i32` (the "yes" answer) instead of leaving it,
and see whether anything changes. Recorded as owed to family 5 rather than
answered here.

**The fix falls out of the conversion, and is better than repairing the loop.**
Adding two terms to the fill is the two-line repair and it leaves the same
trap armed for the next side array anybody adds. Making all five arrays Lists
and pushing an explicit "not computed" into the four side lists at the single
`tt_intern` site makes the invariant true BY CONSTRUCTION at every slot, with
no tail to fill and no loop to remember to extend. That is the same structural
improvement family 4's `decl_home` gets, where "0 means no home" stops
depending on `calloc` and becomes an explicit write — and it is the argument
for the migration restated: the hand-written version has one more place to
forget.


## MEASURED: the read does land in the unfilled window — the defect is live

The experiment the section above called owed, run in a worktree at `7db05ff`
while the main tree's harness was busy, so nothing waited on anything.

**Method.** Fill the two unfilled tails with `2i32` — the "yes" answer —
instead of leaving them as `ralloc` left them, change nothing else, build
`npkc`, and compile the compiler with it. If every read of those slots happens
after layout writes them, the poison is overwritten before anyone looks and
nothing moves. If a read lands in the window, the poison is what it sees.

**Result: `npkc src/main.npk` REFUSES, rc=1, in 8 seconds.**

```
NITPICK-TYPE-056 src/frontend/diag_writer.npk:74:5: this type carries a channel
  endpoint, and coercing it to `dyn` erases that (D-215) …
NITPICK-TYPE-056 src/frontend/diag_writer.npk:84:5: …
```

Two refusals, both D-215's dyn-coercion rule, both at the `dyn Writer` sites
step 1 of this subcycle created. `dyn_slots.npk` — a small program — still
passes, which is the size dependence the whole finding is about.

**What that proves, exactly.** `contains_channel` reads `haschan[id]` for those
types at a point where layout has NOT written it: if it had, the poison would
have been replaced by the correct 1 ("holds no channel") and no refusal could
fire. So in the real build those two reads return whatever `ralloc` left in
the grown tail. **The answer the compiler gives today is correct by accident,
not by construction** — the type genuinely holds no channel, and the garbage
happens not to equal 2.

Both directions are now demonstrated rather than argued:

- **Spurious refusal.** Garbage that reads as 2 refuses a legal coercion. That
  is what the poison run IS — the compiler refusing to build itself over two
  sites that are fine. Any change to allocation sizes can produce it for real,
  and it would present as an inexplicable refusal in a file nobody touched.
  This is the family-10 and family-11 pattern a third time: a latent defect
  that a layout change decides to surface.
- **Missing refusal, which is the one that matters.** D-215 exists so a channel
  endpoint cannot hide behind an erasure — the reclaim is owed by the scope
  that created it and `gives` is how a function promises one, and both rules
  read the TYPE. For a type that genuinely does carry an endpoint, whether that
  refusal fires depends on whether layout happened to run before the coercion
  was checked, not on the type. A safety rule whose input is uninitialised
  memory is not enforced; it is sampled.

`hasborrow` produced no refusals in this run. That is not evidence it is
sound — it is evidence that no site in the compiler's own source exercises the
borrow-containment read in the window. The array has the identical defect and
the identical fix.

**Fixed by family 5, structurally rather than by repair.** The two-term repair
to the fill loop makes today's answer correct and leaves the next side array to
be forgotten the same way — which is how `haschan` and `hasborrow` got here,
since the loop WAS extended once, for `drops`, and not a second time. Five
Lists with an explicit "not computed" pushed at the single `tt_intern` site
leaves no tail to fill. The per-array bounds guards go on in the same change:
the five counts are equal by the push discipline, and a guard against each
list's own count turns a half-done discipline into a trap instead of silent
garbage — fail-closed, in the one place this project's ledger says to expect
drift.

**Residual, named so it is not lost:** nothing structurally forces a SIXTH side
array to be pushed at `tt_intern` alongside the other five. The per-array
guards make its absence a trap rather than a silent read, which is the
fail-closed direction, but the belt is a runtime one. A whole-tree check that
`tt_intern` pushes every `List` field of `TypeTable` would make it a build-time
one, and it belongs with 1.5's obligation list beside the "the push idiom
exists only in list.npk" check this migration is buying.


## And a SECOND defect the poison run exposes, which family 5 does NOT fix

Stated separately because conflating them would let the migration look like it
closed something it does not. Family 5 turns defect A into defect B. That is a
strict improvement and it is not a fix.

- **A — the bit may be uninitialised memory.** Nondeterministic, layout-
  dependent, spurious-refusal-capable. Family 5 closes it: five Lists, an
  explicit "not computed" pushed at the one intern site, no tail to fill.
- **B — the bit may be legitimately NOT COMPUTED at the moment it is read, and
  "not computed" is read as "no".** Family 5 makes that read return 0
  deterministically instead of garbage. It does not change what 0 means to the
  caller.

`type_contains_channel` and `type_contains_borrow` both end the same way:

```
// Structs and enums answer from layout's walk, like `tt_drops` — the
// one pass that sees every field's resolved type recorded the bit.
if (k == (raw TY_STRUCT()))   { pass ((raw tt_haschan(t, id)) == 2i32); }
if (k == (raw TY_ENUM()))     { pass ((raw tt_haschan(t, id)) == 2i32); }
```

`tt_haschan` answers 0 for "not computed" and for out of range, and `== 2i32`
turns both into **false — "holds no channel"**. The comment states the
assumption the code depends on: that layout's walk has already run. **The
poison run measured that assumption failing**, in the compiler's own source, at
two sites.

**The type at both sites is `TextWriter<ByteWriter>` — a GENERIC INSTANCE**, and
that is the sharp end of it. A generic instance's type is interned when the
instantiation is first demanded, which is demand-driven and interleaved with
the passes that ask these questions; a plain struct declared in a module is
laid out on a schedule. This is the same shape as OWED item 3 in the handoff —
`check_instantiations` decides at `pipeline.npk:345` while the escape walk can
still record a first-seen instance after it — and the two should be looked at
together rather than separately.

**Why B is the one that matters.** D-215 exists so that a channel endpoint
cannot hide behind an erasure: the reclaim is owed by the scope that created
it, `gives` is how a function promises one to a caller, and both rules read the
TYPE, which is why the refusal sits at the erasure boundary where the concrete
type is still known. If the bit is unread-because-uncomputed, a
channel-carrying generic instance coerced to `dyn` inside that window is not
refused. **The rule is not enforced there; it is sampled.** Today's answer at
these two sites is right because `TextWriter<ByteWriter>` genuinely holds no
channel — not because anything checked.

**Not measured, and I am not going to assert it either way:** whether a
channel-carrying struct or generic instance can actually reach a `dyn`
coercion inside the window in a program someone could write. The window is
proven; the exploit is not. That distinction is the whole difference between
"a rule with a hole" and "a rule that is currently wrong", and it decides how
urgent this is rather than whether it is real.

**This is a USER DECISION, not an executor's**, because every candidate changes
how a safety rule is enforced rather than how a table is stored:

1. **Compute on demand.** When the bit reads 0 at a containment query, run the
   containment walk then rather than answering "no". This is the file's own
   stated architecture applied consistently — types.npk:1290-1303 records
   record-always/decide-later as the no-modes rule — and it makes the query
   total. Cost: a query can now intern and lay out, which is what OWED item 3
   is already unhappy about elsewhere. **My recommendation**, because it makes
   the answer correct by construction rather than by pass ordering, and pass
   ordering is what has failed here twice.
2. **Guarantee the ordering.** Lay out every interned type before any
   containment query can run, and keep it true as instances are recorded.
   Cleanest to state, hardest to keep: it is a whole-pipeline invariant with no
   instrument watching it, and OWED item 3 is the evidence that the analogous
   invariant is already broken elsewhere.
3. **Fail closed — 0 TRAPS at a query site.** Strongest guarantee and the most
   honest about what is known, but it converts every ordering slip into a trap
   in the compiler, so it can only land after 1 or 2 makes those slips
   impossible. Good as a belt on top, not as the mechanism.
4. **Treat 0 as "yes".** Conservative in the safe direction and refuses legal
   programs — including, today, the compiler's own two sites. Rejected.

Recorded rather than acted on. Family 5 lands A's fix because it is unambiguous
and it is the family's own business; B is raised with a recommendation and
waits for the user, per the standing rule that a semantic decision is theirs.


## B is WIDER than the two sites, and the pipeline states the false assumption itself

Measured after the user ratified "compute on demand", because the ratified fix
needed scoping before it could be built. It is not two sites in one file.

**The same poison method, applied to `type_drops`.** Make its struct/enum arm
answer TRUE when the bit reads 0 ("not computed") instead of false — one line,
nothing else changed — build, and compile a small program:

```
tests/backend/programs/dyn_slots.npk: REFUSED
NITPICK-TYPE-046 prelude.npk:803:10: `LineEnding` owns storage that is released
  at scope exit, so it is move-only (D-183) …
```

So `type_drops` is queried for `LineEnding` at the TYPE-046 move-only check
**before layout computes its bit**. The answer today is "owns nothing", which is
right for `LineEnding` — again by accident, again because the type genuinely
owns nothing rather than because anything checked.

**The root cause is in `pipeline.npk`, and its comment is the whole story:**

```
// EVERY TYPE LAID OUT, once the whole program is known. The checker asks for
// very few sizes, so demand-driven layout leaves most of the table at zero —
// fine for checking, and not fine for what Phase B does with these types. A
// wrong size does not fail; it corrupts memory later.
drop finish_layouts(@tr, (raw graph_at(@f.g, 0i32)).scope);
```

`finish_layouts` is at line 494. **Stage 2 — the type checker — is at line
337.** So through the whole of checking, most of the type table has no layout,
which the comment knows and accepts as "fine for checking". It is fine for
SIZES, which is what the sentence is about. It is not fine for the three
memoised bits that ride the same walk and that the checker also asks:

| query | reads | the rule it decides |
|---|---|---|
| `type_drops` | `tt_drops` | **TYPE-046 move-only**, and whether a scope exit drops at all |
| `type_contains_channel` | `tt_haschan` | **D-215**'s dyn refusal, **D-183**'s `gives` |
| `type_contains_borrow` | `tt_hasborrow` | borrow containment |

All three end in `pass ((raw tt_…(t, id)) == 2i32)` for structs and enums, and
all three turn "not computed" into the permissive answer.

**`type_drops` is the one that matters most**, and it is the one with the widest
surface: 38 call sites outside `types.npk`. A false "owns nothing" means the
scope exit emits no drop — a leak — and, worse, that **TYPE-046 does not
refuse a copy of an owning value**. Two owners and one double free is precisely
what that rule exists to prevent, and D-216's own comment at
`type_stmt.npk:155` describes this hazard exactly:

> THE DROP FLAG IS MEMOISED BY THE LAYOUT PASS, and an enum's is 0 until
> something asks for its layout — so the question has to make sure it has been
> computed before reading the answer, or every consuming pick is told its
> selector owns nothing.

**That fix was applied at ONE site.** `ensure_layout` is called from exactly one
place outside `type_layout.npk` — that line. The hazard was correctly diagnosed
at 1.4.3b, fixed where it was found, and never generalised.

**Why the suite is green.** The rules mostly work because something usually asks
for the type's SIZE first — a struct literal, an assignment, a field access —
and that demand-drives the layout that writes the bits. So the safety rule is
enforced because an unrelated query happened to run earlier. That is the
"correct by accident" pattern for the third time in this stretch, and it is the
argument for the ratified fix rather than a reason to relax about it.

**Scope of the ratified fix (candidate 1, compute on demand).** Make the three
queries TOTAL rather than making every caller remember: a query that finds its
bit uncomputed computes it, instead of answering the permissive default. The
obstacle is that all three take `TypeTable->` while `ensure_layout` needs a
`TypeResolver->` — and `etyper_resolver(e)` already builds one cheaply from the
checker env, which is exactly how D-216's single site does it. So the mechanism
exists; what is missing is that it is opt-in.

**This is no longer step 2's business.** It is a change to when a safety rule
may read a memoised fact, it touches the checker/backend boundary, and it wants
its own commit sequence and probably its own decision number — the rule being
something like "a memoised layout fact is never read before it is computed; the
query ensures, the caller does not remember". Raised with the measurement

# D-229 stage 2, part 1: the tree's first foreign-module impl, and what it found

## The question, answered by the code and then by a probe

**May an impl live in a module other than its type's?** Nothing forbids it.
TRAITS_REFERENCE §4.1 and D-171 say nothing about locality; the impl table is
ONE for the whole program, filled from every module before any check runs
(`pipeline.npk`'s own comment: "an impl in one module may implement a trait
declared in another"), `collect_impls` resolves the target in the impl's own
module scope, and `ImplEntry.scope` exists precisely so that impls from
different modules resolve their names correctly. Coherence is program-wide, so
an overlap anywhere is refused at the second impl — the soundness case an
orphan rule exists for is already covered without one.

**But no impl on a struct declared in another file existed anywhere in the
tree.** All 154 impls sit beside their target; every impl of a prelude trait
sits in the prelude or in a single-file test. So the spec's silence had never
been exercised, and per the standing rule the shape was PROBED before `src/`
was touched: a struct in one module, `impl:S:Writer` in a second (the trait's
methods async, receivers `Self->`), a generic borrowing walk called from an
async `main` in a third, the buffer read back after the call.

## What the probe found: the symbol scheme had never been asked which module

`llc` refused the probe's IR — `base element of getelementptr must be sized` —
because the impl's coroutine was DEFINED as
`%"npk.frame.probe_b.Cap:Writer.write"` and the awaited bound call in the
generic walk asked for `%"npk.frame.prelude.Cap:Writer.write"`: the TRAIT's
module. A sync twin (`impl:P:ToString` in a second module, called through a
`<T: ToString>` bound) failed the same way — `@npk.prelude.P:ToString.to_string`
undefined. Not an async defect: a naming one.

D-156's amendment says a method's symbol is `@"npk.<module>.<Target>:<Trait>.<name>"`
and never says WHICH module. Its vtable row says "in the impl's module", and
`emit_impl_block`'s own comment says "THE DEFAULT'S SYMBOL IS THIS IMPL'S, not
the trait's" — but the implementation qualified every symbol by the module of
**whichever declaration's body was being emitted**, on both sides:

| site | qualified by | which is the impl's module only when… |
|---|---|---|
| definition: an impl's OWN method | the member decl (inside the impl) | always |
| definition: an INHERITED default | the trait's method decl | the impl sits beside its trait |
| the vtable's thunk `real` symbol and frame-size tail | the impl decl | always |
| call through a BOUND (sync and awaited) | the trait's method decl | the impl sits beside its trait |
| `Trait.method(recv)` (D-172) | the recorded decl (own or default) | the impl sits beside its trait, for a default |
| a concrete `recv.method()` to an inherited default | the trait's default decl | the impl sits beside its trait |

Three of those disagreed with the definitions the moment an impl moved — and

coincided for the whole life of the scheme. **"A rule believed in force because
a document says so", in its purest form: the document never said it.**

## The rule, made one, on both ends

own method or inherited default, sync body or coroutine frame — and every

# Step 3 — form upgrades: measured first, then two commits

`src/` contained NO `for`, `till` or `loop` statement at all before this step;
every textual hit was a comment or the parser's own code. So the step
introduces the first uses of the counted forms into the compiler's own source,
under the D-205 rule (the snapshot understands them — they date from 0.9.7).

## What a `for` over a range IS, which decides everything

Two facts, both measured by probe before any loop moved:

- **`..` is the INCLUSIVE range and `...` the EXCLUSIVE one** (OP_REFERENCE
  §5, TYPE_REFERENCE's operator table): `for (int64:i in 0i64..5i64)` runs
  SIX times, and `control_flow.npk`'s own comment ("+0+1+2+3" for `0i64..3i64`)
  agrees. `emit_for`'s comment calls the span "half-open"; the exclusive form
  is. An index loop is therefore `for (intN:i in 0iN...bound)`, three dots —
  which reads exactly as `while (i < bound)`.
- **A `for` evaluates its range ONCE, at entry** — `emit_for` extracts `hi`
  and stashes it in a loop slot; a `while (i < x.count)` re-reads `x.count`
  every iteration. For a bound that is a container's live count the two are
  different programs, and this compiler has loops that depend on the
  difference: the instance loop in `emit_program` "re-reads the table, emits
  it after this body" (transitive monomorphization), the escape settle walks,
  every `tt_count`/`inst_count` bound under a body that can intern. A
  conversion by SHAPE alone would have been silently wrong for exactly those,
  and indistinguishable at a glance from the loops it was right for.

The probe (`.internal/probe_step3/range_forms.npk`) covered a local `int64`
and `int32` bound, a call bound, a literal, `break`, a zero-trip range, and a
range loop across suspensions in a coroutine. All pass under `...`.

## The rule the measurement produced (proposed, for ratification)

> **A counter loop becomes `for (intN:i in 0iN...b)` only where `b` cannot
> change under the loop — a literal, or a local the body never assigns. A
> loop bounded by a container's live count (`x.count`, `raw tt_count(t)`)
> STAYS a `while`: that spelling says the bound is re-read, and the reader
> can trust that a `for` in this tree never hides a live bound.**

So the two spellings carry meaning, which is the blueprint argument for
keeping both rather than a style preference for either. It is an engineering
rule about `src/`, D-226's shape, and it is carried in this record and the
handoff rather than in a reference document.

## The measurement, and what converted

600 loops of the shape `while (i < BOUND)` in `src/`. A classifier admitted
one only when ALL of: `intN:i = 0iN;` is the statement immediately before;
the head has no widening cast on `i`; `BOUND` is a literal or a local the body
never assigns; the body assigns `i` exactly once, as its tail `i = i + 1iN;`;
and `i` is not mentioned after the loop inside the function. **268 converted,
in 32 files; 332 stay `while`, by reason:**

| excluded | count | why it is not a plain iteration |
|---|---|---|
| bound is a call | 116 | a live count, by the rule above |
| bound is a field | 59 | a live count, by the rule above |
| declaration not adjacent | 71 | the counter has a life outside the loop |
| increment not the single tail | 19 | a conditional or mid-body advance |
| counter read after the loop | 14 | a search, not an iteration |
| counter reassigned in the body | 1 | a skip |

Each converted loop loses two lines and its hand-written increment — 536
lines net — and its trip count is now stated in the head, which is the form
1.5's loop obligations want to read. Every file's rewrite carried a leftover
assertion (exactly N `while` heads gone, N `for` heads added) and the
classifier re-run over the converted tree admits zero.

**The converter refused twice in rehearsal before it wrote anything, and the
second refusal was its own bug.** The first made the brace scanner literal-
aware — this file's emitter text is full of `{ ptr, i64 }` inside strings — a
correct change that turned out not to be the cause. The second: the new
`for` head already ends in `{` and the rewrite appended the original brace
too, so every converted INNER loop gained a brace and the outer loop's body
ran past its own end. The tail-increment assertion caught it on the first
nested pair. A count that comes out right can still be a wrong edit
(1.4.7's own lesson, a third time), and the assertion is what stood between
this and 268 silently malformed loops.

## The unwrap half: five sites, twenty left alone

25 `is_error` sites in `src/`, each read. Five have a shape that IS an
operator and are shorter and clearer as one:

- `diag_line`'s `<unknown file>` fallback → `srcmgr_path(…) ?| "<unknown file>"`
  (its own comment had been waiting for the seed's retirement to spell it so);
- `x_site`'s `"?"` fallback → `srcmgr_path(…) ?| "?"`;
- the three proven unwraps (`slice_proven`, `srcmgr_path_proven`,
  `srcmgr_text_proven`) → `… ?! ProvenSlice` / `… ?! FileUnknown`, the
  spelling `module_graph.npk` and `locks.npk` already use 42 times.

The other twenty are not operator shapes: the prelude's retry loops branch on
WHICH error; the drivers' early exits print before exiting; four existence
checks feed a `bool` with no fallback value to name; two return-the-fallback
shapes return where `?|` would continue; one is generated stub text. `?.` had
nothing to do — the Optional-shaped unwraps in `src/` already use `??` (17)
and `?.` (12), and no `is_nil` test exists.

Step 3 is COMPLETE under its own criterion. What remains of 1.4.7: OWED-8
(`TYPE-057`) and OWED-1 (the `extern_c_driver` investigation).

# OWED-1 — the `extern_c_driver` red under load was a race in the C FIXTURE, not in the reactor

The one red the parallel scheme ever produced: `extern_c_driver.npk` exit 29
once in 40 runs under -O2 while three harnesses shared the machine. The
handoff's prior was RACE, not tightness, and its method was followed in
order; every step measured what it predicted.

**(a) Name the error.** Exit 29 collapsed every wrong `r4.err` into one
number. An instrumented copy of the test gives each its own exit. **(b) Time
it.** The elapsed time around r4 goes to stderr. **(c) Attribute the side.**
The driver's stderr tail is printed after r4, and the C driver now SAYS why
it exits when `npkdrv_next` returns −1. **(d) Reproduce the one program under
synthetic contention**, never three harnesses.

## What the code said, and what the measurement confirmed

Kernel 1 (`hostile_tail`) sent its completion and THEN stored the hostile
tail. The Bridge validates the tail at the START of a dispatch, so whether the
next dispatch saw the poison depended on whether the driver process was
descheduled between the completion and the store:

- **Widened window** (`usleep(20 ms)` between the two, 5 runs at -O2 and 3 at
  -O0): every run exits 41 — `EDriverFault` — after ~20.3 ms, and the driver's
  tail reads `npkdrv_next returned -1`. The driver dispatched the next request
  against an honest tail, then poisoned the ring, then read its own poison
  (`tail >= head`) and exited 11. The Bridge saw the child die mid-dispatch
  and reported the fault, CORRECTLY. Identical at -O0, so the optimiser is
  exonerated: the original run's "correct at -O0" was the lottery of 40 runs.
- **Natural window under contention** (48 CPU hogs, 120 runs at -O2):
  **11 × exit 41, 109 × 0**, every failure with the same driver confession and
  an elapsed time between 0.26 and 5.2 MILLISECONDS — never near the 5-second
  deadline, so no wait ever ran out and nothing slept through a wake.
- **Idle machine**: 40 × 0. The window is normally too small to hit.
- **Poison stored BEFORE the completion**: 20 × 0 under the widened window,
  and the real suite test 120 × 0 at -O2 under the same 48 hogs. The
  completion's write and the Bridge's read on the control socket order the
  store before the Bridge's next load; this request still completes normally,
  because its own tail check was already behind it.

So: the Bridge and the reactor behaved exactly as specified at every point
(the fault classification, the pidfd wake, the deadline untouched); the test
fixture had a scheduling-dependent order in it; and exit 29 hid which error
had come back. Not a lost wake, not a deadline too tight, not the optimiser.

## What changed

- `tests/backend/fixtures/ref_driver.c`: the poison is stored before the
  completion, with the reasoning at the store; and the driver prints why it
  exits on a wire defect, so a fault attributes to its side.
- `tests/backend/programs/extern_c_driver.npk`: r4's wrong error is NAMED in
  the exit code (41 fault, 42 deadline, 43 driver error, 44 poisoned, 29
  anything else). A wrong `err` is never one number again.
- The instruments (the probe program and the three driver variants) live
  under `.internal/` and are recorded here; they are not suite material.

## What this unblocks

**D-228's parallel-width calibration**, which was sequenced behind this
investigation because a flake and a real concurrency defect could not be told
apart. They can now: the one red had a cause, the cause was outside the
compiler and the runtime, and it is fixed at its source. The width stays at 2
until the calibration ORCHESTRATION §4 asks for is actually run — that run is
the orchestrator's, and this record is what it starts from.

**Measured, before the harness.** 175 of the 176 backend programs emit
BYTE-IDENTICAL IR, with the same rc and stderr, under the old compiler (built
from the pre-change `src/` by the committed builder) and the new one; the
176th, `diag_capture.npk`, imports `intern.npk` directly and differs by
exactly `fnv1a_step`'s new body and the three-site shift it makes in the line
table. No hash value moved. `extern_c_driver.npk` is the standing known-answer
test of that — its C driver computes the same hash in plain wrapping
arithmetic, and a moved hash refuses at the handshake. The compiler's own
emission differs where it must and nowhere else: `fnv1a_step`'s body (four
per-line overflow-trap sites become one checked 128-bit multiply and a

shorter with every later site id shifted by three, and two generated
drop/vacant bodies carrying new type ids -- the table interns four fewer
entries with the three functions gone. Stage2 == stage3 at 15,450,688 bytes.
