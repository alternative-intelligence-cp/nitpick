# 1.4.3b — The consuming `pick` (D-216) — **COMPLETE**

> `pick (move(v)) { … }`: the selector consumed, ownership transferring
> into the matched arm. Runs AFTER 1.4.3 (the loop-carried move
> analysis) because the moved-from bookkeeping this form writes is the
> machinery 1.4.3 just hardened.

## Semantics (D-216's record, operationalized)

- `move(v)` as the pick selector: legal exactly when `v`'s type owns
  (type_drops true) — on a non-owning selector, `move` here refuses as
  it does anywhere the move is meaningless (match the existing
  move-of-non-owner diagnostic).
- After the pick, `v` is MOVED-FROM on every path (the D-208 analysis
  records it at the pick, not per arm).
- The matched arm's BOUND payloads become owned locals: they drop at
  the arm's scope exit like any owner; binding an owning payload in a
  consuming pick is what TYPE-046 exists to permit here — the copy
  refusal keys off the pick's consuming-ness.
- UNBOUND owning payloads of the matched variant drop AT THE MATCH
  (emitted in the arm's prologue before user code): the value was taken
  apart; nothing may leak.
- The enum's own drop does NOT run for `v` (its drop flag clears at the
  pick — the emitter's existing move-clearing machinery, applied to the
  selector).
- A NON-consuming pick over an owning enum is unchanged: legal while no
  arm binds an owning payload (lending reads), TYPE-046 at any arm that
  does — the message gains a pointer: "…or consume the value:
  `pick (move(v))`".

   consuming selector shape (`ExprMoveExpr` operand); thread a

   emitted); the move analysis records the selector's move (reuse the

# Execution record

**Full harness green**: 60 suites, 179 real-backend programs, fixpoint
byte-identical.

## The premise was wrong, and the gap was a use-after-free

D-216 says TYPE-046 "correctly refuses a `pick` arm binding an owning payload".
It did not. The move-only rule fires on reading an owning PLACE in a value
position; a pattern binding is not one. Measured before implementing anything:
the lending bind compiled, and an executed probe returned the binding out of its
function and read **0xAA — the allocator's free poison** — through it.

The emitted IR said why: the arm's binding is a bitwise copy of the whole
`{ptr, len, cap}`, cap included, so it is a **second owner** aliasing the enum's
body. It was never dropped, which is the only reason it was not also a double
free — `run_scope_drops`'s header lists pick-arm bindings among "the bindings
that are deliberately unflagged … safe precisely because they never drop." Safe
from a double free, yes; the failure mode that reasoning does not cover is the
one the probe hit.

## Both halves, together

They could not land apart: refusing the bind without the consuming form leaves
correct code no spelling at all.

1. **The refusal** — a non-consuming arm binding an owning payload refuses,
   with the message naming `pick (move(v))`. `_` binds nothing and stays legal,
   as does any arm that binds no payload.
2. **The consuming form** — and it needed less than the plan expected.
   `move(v)` as a selector ALREADY cleared the enum's drop flag through the
   ordinary move path, so the enum's own drop was already suppressed. What was
   missing was the other side: the arm's binding carried no flag, so the
   payload leaked. It carries one now and drops at the arm's exit; an arm that
   binds NOTHING calls the enum's own generated drop body, which is already the
   tag dispatch that frees whatever the live variant carries.

The consuming bit is read off the selector's shape in the emitter rather than
carried from the checker — `move(v)` is in the AST and a recorded bit would be
a second place for one fact to be wrong.

## Found on the way — a variant constructor was a "place"

`Msg.Quit` BUILDS a value, but `expr_is_place` walks to its root, finds the
enum's NAME, sees an identifier and says place — so the move-only rule fired on
a temporary, demanding a `move` of something with no second name to invalidate.
The message's own last clause says a temporary needs nothing.

It hid behind an ORDERING ACCIDENT: the rule only runs when `type_drops` is
true, an enum's drop flag is memoised by the layout pass, and nothing had asked
for an owning enum's layout by the time such a declaration was checked. The
consuming pick asks (it must, to know whether the selector owns anything), and
the misclassification surfaced immediately.

## The consequence worth recording

**An owning payload cannot be read through a lending pick at all.** There is no
accessor for a variant's payload without binding it, so a getter over a borrowed
enum must consume: `enum_payloads.npk`'s `read_text` became `move Msg:m`, and
its caller hands the value over. That is D-183's open — "a getter over a
container of owning values has no correct spelling yet" — reappearing for enums,
and the deep-view accessor family D-183 records is what answers it.

`dyn_slots.npk` needed the same repair for a sharper reason: a `dyn` owns the
heap cell its coercion allocated, so a lending bind was a second owner of that
cell.
