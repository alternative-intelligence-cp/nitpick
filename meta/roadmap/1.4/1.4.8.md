# 1.4.8 — `npkg` (D-206) — PLANNED (execution-grade)

> Scope: `npkg build` and `npkg test`, minimal and real, in full Nitpick
> against the compiler's own modules; the spawn primitive and directory
> listing it needs; the closed-world link; parity proven against the
> Python harness. `update` stubs to a named refusal; `verify` refuses
> naming 1.5. The G-2/G-3/G-4 audit riders (path containment,
> restrictive creation modes, at-style file APIs) land in the same
> subcycle's `lib/nfs.npk`.

## Part A — the floor: `npk_spawn`

1. Generalize `npk_driver_clone_exec`'s proven shape
   (`runtime/npkrt.ll` post-1.4.6): same fork-shape `CLONE_PIDFD`
   clone, same allocation-free child (the copied-futex rule bars ANY
   Nitpick in the child), same PDEATHSIG + NO_NEW_PRIVS, same 16-slot
   registry (trap-route kill + the D-151/D-188 exit discipline extend
   to tool children). The generalization is the BLOCK: caller-directed
   stdio — [0]=path, [1]=argv, [2]=envp, [3..5]=the fds to dup3 onto
   0/1/2 (a pipe write-end for captured stdout, a file, or the
   inherited fd), [6]=optional ctrl fd for slot 3 (absent for tools),
   [7]=parent pid, [8..9]=OUT slot/pidfd. `spawn_driver` becomes a
   caller of the same primitive with its driver block (fd3 present,
   stdout→/dev/null preserved for drivers).
2. BUILTIN_REFERENCE gains the row (marked region, Signature + Fails
   columns per D-201's format); the generator regenerates; the builtin
   is table-typed from birth. Waiting stays `sys(WAITID)` from Nitpick
   (the nbridge pattern — reuse its constants and `fd_above_std`).
3. Runtime-floor test (the hand-IR stage) + a backend program spawning
   `/bin/true`-shaped fixtures... — NO: zero-dependency discipline —
   spawn the HARNESS-BUILT C reference driver? Also no: the clean
   fixture is npkc itself or a tiny compiled-by-npkc program from the
   fixtures dir (`tests/backend/fixtures/` precedent, `// argv:`
   substitution). Capture its stdout through the pipe; assert content.

## Part B — directory listing

`sys(SYS_GETDENTS64)` over an owned buffer; the dirent records parsed in
Nitpick in `lib/nfs.npk` (`dir_list(Path) → Result<...>` — names +
d_type; the iteration API shaped like the library tier's bounds-checked
accessors). No floor addition.

## Part C — `lib/nfs.npk` (with the audit riders)

- `dir_list`, `path_canon` (lexical normalization + the containment
  question answered by OPENING, not by string checks):
- **G-2**: `open_beneath(dirfd, Path, flags)` over
  `sys(SYS_OPENAT2)` with `RESOLVE_BENEATH|RESOLVE_NO_MAGICLINKS` —
  the default opening API for untrusted-influenced paths.
- **G-3**: creation defaults 0600 (files) / 0700 (dirs); widening is an
  explicit argument.
- **G-4**: the at-family (`openat`/`unlinkat`/`renameat2`-shaped
  wrappers) so check-then-use never spans a path re-resolution.

## Part D — `npkg` itself

1. `tools/npkg.npk` (or `src/tools/` per LAYOUT's rules — decide by
   LAYOUT's own text: npkg is a SHIPPED tool, `src/` is "the compiler
   and nothing else" — so a NEW top-level `npkg/` or `tools/`; follow
   LAYOUT's "directories are created when a decision names them" and
   name it in the commit). It `use`s the compiler's frontend modules
   for manifest/source handling (the self-hosting dividend).
2. `npkg build`: read nitpick.toml (+ `[toolchain]` verification —
   1.4.5's check moves in or is mirrored), drive npkc → `.ll`, spawn
   `llc`/`ld.lld` per the manifest's flags, **the closed-world link**:
   only npkc-produced objects + the audited runtime allowlist may
   appear; no relaxing flag exists; the D-011 undefined-symbol scan
   runs as a pipeline step (llvm-readelf spawned, or a minimal ELF
   symbol reader in Nitpick — prefer spawning llvm-readelf now, note
   the in-house reader as post-1.5 hardening).
3. `npkg test`: suite discovery via `dir_list`, the in-file
   expectation grammar (`// expect-exit`, `// expect-error`,
   `// stress:`, `// argv:`), compile-link-run per kind, diagnostics
   captured through `dyn Writer` (1.4.7's adoption) and compared on
   CODES and spans. The §7.1 self-check obligation: an `npkg
   test --selfcheck` running the harness-selfcheck case set (wrong
   expectation must fail, etc.).
4. **Parity**: a harness stage (or a one-shot script kept in
   bootstrap/harness/) runs BOTH runners over the full tree and diffs
   verdicts run-for-run; parity holds for the rest of 1.4 and through
   1.5 (both runners stay; retirement is SWITCH.md's).
5. NOT in scope: `npkg update` (named refusal — nothing to resolve),
   `npkg verify` (refuses naming 1.5), the whole-suite instruments'
   Nitpick ports (they stay Python until the SWITCH; npkg runs suites,
   the harness keeps running suites + instruments — never a gap).
