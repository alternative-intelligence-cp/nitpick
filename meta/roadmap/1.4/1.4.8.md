## Part A — the floor: `npk_spawn`

1. Generalize `npk_driver_clone_exec`'s proven shape
   (`runtime/npkrt.ll` post-1.4.6): same fork-shape `CLONE_PIDFD`
   clone, same allocation-free child (the copied-futex rule bars ANY
   Nitpick in the child), same PDEATHSIG + NO_NEW_PRIVS, same 16-slot
   registry (trap-route kill + the D-151/D-188 exit discipline extend
   to tool children). The generalization is the BLOCK: caller-directed
   stdio — [0]=path, [1]=argv, [2]=envp, [3..5]=the fds to dup3 onto
   0/1/2 (a pipe write-end for captured stdout, a file, or the
   inherited fd), [6]=optional ctrl fd for slot 3 (absent for tools),
   [7]=parent pid, [8..9]=OUT slot/pidfd. `spawn_driver` becomes a
   caller of the same primitive with its driver block (fd3 present,
   stdout→/dev/null preserved for drivers).
2. BUILTIN_REFERENCE gains the row (marked region, Signature + Fails
   columns per D-201's format); the generator regenerates; the builtin
   is table-typed from birth. Waiting stays `sys(WAITID)` from Nitpick
   (the nbridge pattern — reuse its constants and `fd_above_std`).
3. Runtime-floor test (the hand-IR stage) + a backend program spawning
   `/bin/true`-shaped fixtures... — NO: zero-dependency discipline —
   spawn the HARNESS-BUILT C reference driver? Also no: the clean
   fixture is npkc itself or a tiny compiled-by-npkc program from the
   fixtures dir (`tests/backend/fixtures/` precedent, `// argv:`
   substitution). Capture its stdout through the pipe; assert content.

### Decisions taken on contact (implementation-level; recorded so the reasons survive)

- **The primitive is the bare builtin `clone_exec`, floor symbol
  `@npk_clone_exec`.** D-206 wrote `npk_spawn`; `spawn` is the task keyword
  (D-062), so the bare name cannot be `spawn`, and a floor symbol that differs
  from its builtin's name for no reason would be an `ABI:` note carrying
  nothing. The old `driver_clone_exec` already said what the primitive does;
  the generalization drops the tenant from the name. `driver_retire`,
  `npk_driver_kill_all`, `npk_driver_live_count` and `DriverLeak` KEEP their
  names: the registry's original tenant is the driver, a tool child is
  supervised identically, and renaming an error identity costs every
  `failsafe` in the tree an arm for cosmetics.
- **The block is ten words and the descriptor rule is CHECKED in the
  runtime**, not trusted: `[3] [4] [5]` are the child's 0/1/2 sources,
  `[6]` the optional ctrl fd (negative = none), and a source below 4 (or a
  ctrl fd in 0..3) refuses `-EINVAL` before any slot is claimed. "Inherit our
  stdin" is spelled by dup'ing it above the std trio first, the same rule
  for every descriptor — one shape, no per-slot special case in the child.
- **`environ() → cstring[]` is a floor builtin**, measured once at `_start`
  beside `argv` by the one cstring-array builder (`npk_cstr_slice`, which
  now serves both). D-089 keeps `main`'s signature; the environment is the
  same boundary's other half and no syscall can return it, so it is the one
  piece of Part A the floor had to add. `npkg` reads `PATH` from it and
  passes it through to the tools it spawns.
- **The syscall vocabulary the Bridge and the tool runner share moves to
  `lib/nsys.npk`** — the x86_64 numbers, `fd_above_std`, `open_devnull`,
  the CLOEXEC-and-NONBLOCK `capture_pipe` — because REACH is import-scoped:
  `nproc` importing `nbridge` for six constants would make every Bridge
  error "reachable" in every build tool. `nsys` fails with the kernel's own
  errno (`fail r.err`, a dynamic operand REACH does not enumerate); the
  Bridge maps those to `EDriverSpawn` at its sites exactly as it did for its
  own copies.
- **`proc_wait` captures BOTH pipes and bounds every wait.** A child blocked
  on a full stdout while the parent waits on stderr is a deadlock, so the
  drain waits on whichever pipe is open (`io_ready2`), then on the pidfd for
  the exit; a deadline kills via the pidfd, reaps, retires, and fails
  `EProcDeadline`. Nothing in the runner ever blocks unboundedly on a live
  child.

### Part A — LANDED (2026-09-02)

What landed is what the "decisions taken on contact" above describe; the
commit message carries the shape. Two things came up on the way that the plan
did not predict, both caught by an instrument before any test ran:

- **A builtin's return-type text must be one the checker can intern.** The
  generated signature table hands `environ()`'s `cstring[]` to
  `builtin_text_type`, which had `uint8[]` (for `string_bytes`) and no other
  slice — `NITPICK-TYPE-054` refused the first program that called it, by
  name, at the first compile. One arm added; `check_builtin_sig_texts` is what
  keeps the table and the resolver in step, and it would have failed the
  harness had the program not failed first.
- **A file's `mod:` name is a declaration in its own scope, and it shadows an
  imported function of the same name** (`NITPICK-RESOLVE-008`, "the local
  declaration wins"): the test was first written as `proc_spawn.npk`
  importing `proc_spawn`. Renamed to `proc_tool.npk`. Not a defect — the
  rule is the language's — but the shape is easy to write, and the diagnostic
  reads as a warning while the program is refused.

Measured: the forty-run stress of `proc_tool.npk` takes 8 s (three spawns per
run, one of them killed at a 200 ms deadline), and the Bridge's `driver_spawn`
and `driver_dispatch` run clean on the ten-word block before the full harness
did. The user ratified D-230's families and S-8 on 2026-09-02 ("the
recommendations are fine with me"), so step 2 lands the four flag families with
`Fcmd` and `Advice` as prelude enums beside `Whence`, and step 2b makes
`range<T>` spellable.
