## Commit 1 — D-210: plain-integer `+ - *` trap on overflow

1. **The emitter** (`emit_arith_value`, `src/backend/ir/ir_expr.npk`
   ~:1948): for `TY_INT` operands under `OpPlus/OpMinus/OpStar`, lower
   through `llvm.sadd.with.overflow.iN` / `llvm.uadd...` (signedness
   from `type_is_signed`; same for sub/mul), extract the flag, branch
   to the D-142 trap route on overflow. BOTH spellings route through
   `emit_arith_value` since 1.3.3 — compound assignment inherits the
   guard for free (that extraction exists for exactly this reason).
   Declare the intrinsics in the fixed declare block (the `llvm.sqrt`
   precedent, `emit_program.npk`). Wide integers (i128..i4096): the
   with-overflow intrinsics are legal at any width; verify llc 20.1.2
   legalizes i256+ (it legalized the wide arithmetic since 0.9.3 —
   expect yes; if a width breaks at llc, the fallback for THAT width is
   the compare-based guard the tbb machinery already uses).
2. **The trap code**: `INT_OVERFLOW` in the D-141 space (next free
   negative), registered in the codes module and npkrt's trap-name
   table if one exists (check how DIV_BY_ZERO −4097 is named).
3. **REACH**: `IntOverflow` joins the reachable set wherever plain-int
   `+ - *` appears (the DivByZero wiring is the model —
   `analysis/reach.npk`); failsafes across `tests/` gain the arm (the
   sweep: every failsafe pick that REACH now flags — mechanical,
   expect many test files; `(*)` counts for nothing per D-179).
4. **Sweep for deliberate wrap**: audit `src/`/`lib/`/`tests/` for
   sites RELYING on wraparound (expected: none in src/ — hash mixing
   rides tbb/wide; any found site converts to widen-compute-truncate
   per D-210.3 with a comment).
5. **Tests**: executed `overflow_trap.npk` (i32 INT_MAX+1 → failsafe
   arm exit; unsigned wrap case; INT_MIN negation via `0 - x`; a
   compound `+=` case — the 1.3.3 lesson; an i128 case for the wide
   path) and the acceptance side (arithmetic that stays in range runs
   unchanged — existing 172 programs are that suite, but add one
   boundary case: exactly INT_MAX, no trap). The opt-O2 leg re-runs
   everything — the with-overflow intrinsics must survive `opt -O2`
   (they do; they're the canonical form — but the leg PROVES it).
6. Spec touch: TYPE_REFERENCE's integer section states the rule (trap,
   code, the D-210.3 idiom for deliberate modularity); DECISIONS D-210
   already carries it.

# Execution record

## Commit 1 — D-210: plain-integer `+ - *` trap on overflow (LANDED)

**Full harness green**: 60 suites, 178 real-backend programs (each through
`opt -O2`), fixpoint byte-identical.

### What landed

1. **`llvm.{s,u}{add,sub,mul}.with.overflow.iN`** for `TY_INT` `+ - *`, the
   overflow bit branching to the D-142 trap route with a new `IntOverflow`
   (−4110) identity. Signedness picks the family. **llc 20.1.2's legalization
   was verified before the guard was written** — all six families at every width
   `i1` through `i4096`, at `-O0` and `-O2`, with non-constant operands, plus
   `opt -O2` — because "the intrinsics are legal at any width" is a claim, and
   the fallback (a compare-based guard for the offending width) would have been
   a different design.
2. **The declare block grew a loop**: 6 families × 13 widths, unconditional, the
   fixed-constant discipline the block already had for `smul`.
3. **REACH arms `IntOverflow`** for both spellings — the expression form and the
   compound `+=`/`-=`/`*=` — suppressed for every family that saturates instead
   (`tbb`/`tfp`/`dim`/`tern`/`frac`/`complex`), the same reasoning the division
   suppression is written from: arming an identity for an arm nothing can enter
   is worse than not arming it.
4. **133 of 187 failsafes gained the arm** — exactly the programs that do
   plain-int arithmetic, found by running the compiler over each rather than by
   blanket insertion, so no file carries an arm nothing can reach.
5. **Five executed programs, one guard shape each** (signed add, unsigned,
   negation, compound `+=`, i128), on the 1.3.1 `simd_div0`/`divmin`/`oob`
   precedent — a trap is terminal, so one program cannot test two. Each also
   carries the in-range boundary cases that must NOT trap, INT_MAX among them.

### Found — unary `-` was never going through the shared core

D-210.1 says negation rides `0 - x` and so traps on INT_MIN. It did not: the
emitter wrote a bare `sub <ll> 0, x` in `emit_unary`, bypassing
`emit_arith_value` entirely, so the sentence would have been false the day it
was written. Negation is routed through the shared core now — **one overflow
guard in the compiler, not two that can drift**, which is the 1.3.3 lesson
applied to the shape it was originally learned on (compound assignment had
quietly become a second implementation of the operators). A `simd` still falls
through to the bare `sub`: a vector's rule is its element's.

The same commit tightened the arithmetic tail to plain-integer ONLY. An
unrecorded operand type used to fall through to unguarded arithmetic; since
D-201 nothing arithmetic goes untyped, and the guard is total only if the tail
is.

### Found — the sweep's prediction was wrong, and in an interesting way

D-210 expected "few or no deliberate-wrap sites (the prelude's hash mixers ride
`tbb`/wide arithmetic already)". The tree had exactly three, and they were all
the same one: **FNV-1a's multiply**, in the prelude's `fnv_mix`, the resolver's
`err_fnv_step` and the emitter's `pat_err_fnv`. The mixing IS the wraparound —
that is what a hash multiply is for — and the hash mixers rode plain `uint64`,
not `tbb`.

Two consequences:

- **`src/` cannot spell D-210.3's idiom yet.** Widen–compute–truncate needs
  `uint128` and the seed lowers subset 1 until the 1.4.6 switch. The prelude
  (compiled by npkc, not the seed) uses the documented spelling; `src/` assembles
  the product from 32-bit halves with every partial provably inside `uint64`,
  verified equal to the wrapping form over the boundary pairs and 200,000 random
  ones. It becomes the clean spelling at 1.4.7, and the comment says so.
- **Two of the three copies collapsed into one.** D-179 derives every error
  constant's identity through this step, and the resolver (which assigns the
  code) and the emitter (which matches a qualified pattern against one) had a
  copy each, kept in step by a comment asking them not to drift. There is one
  `intern.fnv1a_seed/_step/_bytes` now and the question cannot arise — P-3's
  "one authority" principle, arrived at from a different direction.

### Found — the `nf_twin` check was comparing the fixture's own layout

The twins are one program written twice, differing only in their `never fails`
clauses, and the check byte-compares their IR because D-163 is a checked claim
rather than a codegen hint. D-210 gave them their first STAMPED SITE (the
overflow guard's `chain_reset` carries one), and D-179's site table records the
PATH a stamp was taken at — so `with/` versus `without/` became the entire diff
and the check reported that `never fails` had changed the emission. It had not:
the fixture's directory names had. Both twins are now copied to ONE path and
compiled there in turn, so the comparison is about the clause and nothing else,
with nothing elided from the text.

This is worth keeping in view: the check would have reported the same failure
for any future feature that stamps a site, and the answer would have been the
same each time.

### Two process notes

- **The prelude is DATA.** Editing `src/prelude/prelude.npk` without running
  `gen_tables.py` leaves the compiler carrying the OLD prelude in
  `prelude_source.npk`, and the symptom is a test failing for a reason the source
  says is already fixed. Cost one confused iteration.
- **REACH excludes the prelude by design** (`pipeline.npk`: "a program reaches
  its guard-bearing internals only through machinery the program's OWN text must
  contain"). That reasoning is exact for tbb/index/division and weaker for
  overflow — a program with no arithmetic of its own can reach prelude
  arithmetic through any library call. It holds here because the prelude's one
  deliberately-wrapping site is now non-wrapping by construction, and any
  remaining prelude overflow is a genuine fault. **Recorded as an observation for
  1.5**: the verifier discharging overflow obligations is also the thing that can
  answer "can this prelude path overflow at all".
