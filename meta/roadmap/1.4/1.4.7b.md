## RE-HOMED to 1.4.8's open (implementation only; the decisions stand)

Two implementations were sequenced INTO this batch and are moved to the START
of 1.4.8, each because it depends on a layer 1.4.8 builds — not deferred (the
decisions are recorded and ratified), re-sequenced beside their dependency, the
tool-adoption shape the standing rule permits.

- **D-236 in the compiler.** Rendering paths relative to the manifest root
  needs to LOCATE `nitpick.toml` — a walk up from the main file that needs a
  file-existence probe. The compiler's `src/` deliberately reaches no raw
  syscall: it uses `read_file`/`write_file`/`to_cstring` and nothing lower, and
  manifest discovery plus the filesystem surface are exactly what D-206's
  `npkg` and D-213's `lib/nfs.npk` build at 1.4.8. Landing D-236 there reuses
  that layer instead of forcing a second manifest-prober into the driver. The
  design is settled (D-236): the source manager keeps the RESOLVED path
  internally (import resolution and `srcmgr_path_proven` read it), and
  `srcmgr_path` renders root-relative for the two DISPLAY consumers only —
  `diag_line` and the site table (`irw_site` via `ir_expr`); the render anchor
  is the discovered manifest root, `""`/`"."` for a relative-from-root
  invocation so the current snapshot bytes are preserved exactly. The
  verification is the harness's own absolute-invoked emission becoming
  path-free, which arms D-204's H9 leg. The close's `repro` guard (no absolute
  site path in the committed snapshot) holds the line until then.
- **D-230 — `TY_FLAGS`.** A new type kind whose consumer is 1.4.8's
  `lib/nfs.npk` flag surface (D-213's `open_beneath`/`openat2` riders), and it
  opens a families question that is the user's to answer (below). Landing it as

## Questions this batch raised, for the user (both go to the 1.4.8 session)

- **D-230's seven families are not all bitmasks — WAITING ON THE USER.**
  `whence`, `fcmd` and `advice` are enumerations: exactly one value per call,
  never combined with `|`. The language already spells the first as the prelude
  enum `Whence` (1.1.12b), mapped to the kernel's numbers by a `pick` in the
  seek wrapper. A `whence` flags type would be a second mechanism for one job,
  and `F_GETFL | F_SETFL` would be admitted and meaningless — the error class
  D-044 exists to close. **Recommendation put to the user 2026-09-02:**
  `TY_FLAGS` carries the four true bitmask families (`oflags`, `prot`,
  `mflags`, `fmode`); `whence` stays the enum it is; `fcmd` and `advice` become
  prelude enums of the same shape. D-230 lands at 1.4.8 open with his answer.
- **D-093's `range<T>` spelling is not resolvable** ("there is no type named
  `range`") though the decision says a range is a value of that type — found by
  the D-235 probe that tried to spell one. Raised as **S-8** (OPEN_DECISIONS
  §2e), recommendation in the row; the user's call, before the frontend freeze.
- **Typed flag constants as `fixed` module bindings** need the constant
  evaluator to fold `int32 =>! flags` in an initialiser (TYPE-035 refuses a
  cast today); the alternative is the never-fails-function idiom `src/` uses for
  every constant. Decided with D-230 at 1.4.8.
