# 1.4.4 — D-207 lands: per-scope joins — **COMPLETE**

> `join_head` becomes per-scope, threaded through the 1.2 scope-exit
> machinery that already owns drop flags. Order at every scope exit:
> **join that scope's tasks (relaying the first child error, D-163 rule
> 4) → reclaim that scope's channels → release that scope's shared
> arenas** — joined-before-freed, always.

## The work

1. **The frame layout**: today one `join_head` list per frame. Give each
   SCOPE its own list head (the drop-flag machinery already knows scope
   extents — ride the same structure; a scope's head lives beside its
   drop flags, frame-resident in async bodies exactly as flags are).
   `spawn` links the child onto the CURRENT scope's head, not the
   frame's.
2. **Scope exit emission**: the exit walk (sync and async, plus the
   wind-up unwind and the early exits — `pass`/`fail`/`relay`, the
   D-014 rule that a TRAP runs neither still holds) performs
   join-then-reclaim-then-release for that scope before its drops... —
   careful, the precise order against DROPS: the 1.2 order is
   drops-at-exit; joins must run BEFORE the drops of anything a child
   could still reference (the sanctioned crossings are borrows of the
   sync primitives — which are drop-carrying). Order: joins first, then
   ALL drops (which now include channel reclaim and shared-arena
   release as their kinds' drops). Verify against D-062/D-080's stated
   exit order and write the order into the emitted-IR comment.
3. **Channel reclaim moves from function-exit to scope-exit** (the

   LOOP now works — per-iteration reclaim at the body's exit. Lift the
   C-22 refusal (find it by its row name in the refusal string).
4. **`TY_SHARED_ARENA` leaves the excuse tables**: `type_drops` answers
   true; `emit_one_drop` gains its arm (joined-before-freed is

   `type_drops`/`emit_one_drop` are REMOVED in the same commit (the
   walkers-total instrument will refuse a half-done change — that is it
   working).
5. **The `dyn`-element refusal stays** (permanent by D-207) — no code
   change, but the refusal message may now cite D-207 rather than the

6. **S-4 WAS ratified (D-215)** — implement here: the dyn coercion site
   asks `type_contains_channel(concrete)` and refuses a true answer

- **D-062/D-080 do not state an exit order against drops.** The order that IS
  stated is D-183's, in DECISIONS §"The channel's life": *"The creating
  FUNCTION's exit reclaims its channels — after its defers, drops and child
  joins"*. D-207 reorders that deliberately; the order landing here is
  **joins → defers → drops → that scope's channel reclaims**, per scope,
  innermost first. Joins go in front of the defers as well as the drops

  still reach — one rule ("a scope's exit ends its concurrency before it runs
  any cleanup") rather than two.

### The design, as built

**A scope's segment of the join list is delimited by a MARK, not by a second
list.** The list is already a LIFO stack (`child.sibling = join_head;
join_head = child`), so a scope's children are exactly the ones pushed since
it was entered: save `join_head` at scope entry, and the scope's exit joins
until the head is back at the saved value. That is one pointer per scope
instead of one list head per scope, `emit_spawn` is untouched, and the
function's own scope falls out as the mark that happens to be null.

- The mark is **frame-resident in a coroutine** for the same reason drop
  flags are: a scope can span a suspension, and an alloca dies between
  resumes. It rides the existing crossing machinery as **role 41 on the
  block's statement index**, registered by `scan_crossing` for every block of
  an async function — unconditionally, following the loop-state doctrine that
  framing everything means no detector can drift from the emitter's needs.
- **A scope's join is emitted where a spawn was emitted in that frame**, plus
  always at the function's own scope. The gate is sound: within one entry of
  a frame, execution reaches a point having run only that frame's statements
  textually before it (a loop body IS a deeper frame, and `continue` runs
  that frame's exit before the back edge), so a child on frame f's segment at
  an exit was spawned textually before it. Over-emitting is harmless (head ==
  mark joins nothing); the always-on join at the function's scope is the belt
  that makes a miss impossible rather than merely unlikely.
- **`%npk.join` at `fnem_close` is gone.** It was one block every exit
  branched to, which is what forced the join to run last. The join is now
  emitted inline per scope exit like defers and drops already are.
- **The child-error arbitration is preserved bit for bit** by storing the
  function's result BEFORE the unwind rather than after: every exit now
  builds its aggregate, stores it into the frame's result slot, runs the
  unwind (whose joins read that slot exactly as `%npk.jerr` did), and then
  `ret i8 0`. D-136 is unaffected — the value is still *evaluated* before the
  defers; only the store moved. Without this the join would have to relay
  mid-unwind and `fail E` would start losing to a child's error, which is a
  semantic change D-207 does not ask for.
- **Channel stashes window by scope** the way locals and defers already do:
  `fnem_defer_frame_push` records `chfin_count`, the pop truncates to it, and
  a scope's exit reclaims its own window. Without the truncation a later
  sibling block at the same frame depth would reclaim the earlier one's
  stash.

### Two things measured on the way that changed what got written

**`exit` no longer reclaims channels, and that is the point.** It used to,
by accident of routing: every exit reached `%npk.join` through the return
seam, and the reclaims sat just past it. The reclaim DRAINS a ring's owning
elements and runs their generated drops, which is exactly the walk D-183's
own amendment refuses to put on the `exit` path — "walking the entire live
program state to free it on the way out adds failure modes to exactly the
path that exists to have none". So `exit` now runs its joins and its defers
and nothing else, which is one rule instead of an exception. Nothing leaks
that the kernel does not reclaim: a channel's ring is MANAGED storage
(`npk_alloc_internal`, role 0), so D-151's exit check never counted it, and a
channel refuses `OwnedFd` elements outright, so no descriptor rides one.

**D-151's leak check only runs on `exit 0`.** `npk_exit` skips it whenever the
code is nonzero — a failure exit "is already a report of abnormality and keeps
its code". The first draft of `shared_arena_drop.npk` therefore reported
success as 42 like every other program here and proved nothing: it passed
with the drop disabled. Rewritten to exit 0, it answers 97 (`WildLeak`)
against a build whose `type_drops` still says false, and 0 against this one.
`join_order.npk` was checked the same way — with inner-scope joins gated off
it answers 91, the `?! E9` on a message that had not been sent yet.

### Found on contact: `shared_arena` becoming an owner makes it move-only

`require_move_if_owning` keys on `type_drops`, so item 4 makes
`shared_arena<T>` move-only (TYPE-046) as a mechanical consequence. Nothing
in the tree breaks — `tests/backend/programs/shared_arena.npk` is
single-threaded and uses it as a local — but the only way to hand one to a
worker today is a by-value copy of the pointer, and that now demands
`move(...)`, which transfers rather than shares. `shared_arena<T>->` is not
in D-180's sanctioned spawn crossings and `type_access` does not peel a
pointer for its methods, so after this change the type cannot be shared
across a spawn at all.

**RESOLVED — the user ratified the recommendation: `shared_arena<T>->` is the
fifth sanctioned spawn crossing (D-180 amended).** D-180's criterion is "a
mutation the holder cannot see at a suspension point it did not choose", and a
shared arena has no mutation at all — slots are written once at `alloc` and
immutable after, which is the whole D-154 contract — while this subcycle's
joined-before-freed order is exactly what bounds the borrow. Three lines in
`escape_spawn_args`, plus the emitter's one-level peel for a borrowed receiver
(the checker already peels through `access_base`, so it needed nothing), plus
`shared_arena_spawn.npk`.

### And the find that came out of writing that test: EVERY thread join was sleeping five seconds

`shared_arena_spawn.npk` took 5.002 seconds. So did `mutex_basic.npk`, at
HEAD, so it was not this cycle's doing — but 5.000 seconds is the join
deadline exactly, which is not a number a correct wait lands on.

`npk_thread_join` waited on the CHILD_CLEARTID word with
`FUTEX_WAIT_BITSET | FUTEX_PRIVATE_FLAG`. The kernel clears that word at
thread exit and wakes it from `mm_release` — as a SHARED futex wake, which a
private waiter never receives (glibc's `lll_wait_tid` is non-private for
exactly this reason). So the word was zeroed promptly, the wake went nowhere,
the wait ran to its absolute timeout, and the loop then reloaded the word, saw
zero, and reported success. **Right answer, five seconds late, every time** —
which is why nothing failed and nothing pointed at it, since 1.1.9.

Dropping the private flag is one token. Measured: `mutex_basic` 5.00s → 0.12s,
`thread_spawn_join` 5.00s → 0.12s, `join_order` 5.00s → 0.06s,
`shared_arena_spawn` 5.00s → 0.00s; every exit code unchanged. The programs
that still take seconds are the ones that mean to (`windup_drop` drives a real
wind-up, `sync_prims` waits a real 2s).

It is landed here rather than written down for later because it IS the join's
wait, which is this subcycle's mechanism, and because it is not only speed:
D-062 makes the deadline mandatory so a stuck task is CAUGHT, and a join that
consumes the whole deadline on every success makes "finished" and "stuck"
indistinguishable for its full length. The measurement the deadline exists to
make was being thrown away.
