# 0.0.4 — Test harness

**Cycle 0.0 — Foundations.** Last subcycle; closes the cycle.

## Goal

A runner that executes positive and negative tests and compares diagnostics
exactly, so cycle 0.1 can be written test-first.

## Why it closes the cycle

Everything in 0.0 exists to make this possible: 0.0.0 gave it somewhere to live,
0.0.1 told it what language the tests may be written in, 0.0.2 gave it a build,
0.0.3 gave it something to compare.

It also settles a real open item — `BUILD_REFERENCE.md` §8 lists test-target
declaration and negative-test conventions as unspecified.

## Why negative tests carry the weight here

This session's spec work kept finding that **the error cases are where the real
specification lives.** D-057 recovered macro semantics from 49 regression tests
and their error cases. D-064 was settled by `bug403`, a negative test. D-066 was
settled by `OPAQUE-COPY-001`, another one. The prototype's conventions —
`WILL_FAIL TRUE`, `// Expected: COMPILER ERROR` — are the material to work from.

A harness that only runs positive tests would fail to capture the half of the
language that is defined by refusal.

## Work

**1. Test kinds.**

| Kind | Passes when |
|---|---|
| **positive** | compiles cleanly, no diagnostics |
| **negative** | fails, **and** emits the expected diagnostic codes |
| **diagnostic** | compiles, and emits exactly the expected warnings |

A negative test that fails for the wrong reason is a **failing test**. Asserting
only "it did not compile" is how a test keeps passing after the bug it guarded
has been replaced by a different bug.

**2. Expectation syntax.** In-file, next to the code, so a test and its
expectation cannot drift apart:

```nitpick
// expect-error: NITPICK-019
// expect-error-at: 14:9
```

Assert on **codes and spans, not message text** — messages should be free to
improve without breaking the suite. This is why 0.0.3 made codes stable.

**3. Comparison.** Diagnostics are captured through 0.0.3's sink, sorted, and
compared exactly. Unexpected diagnostics fail the test as surely as missing ones;
a suite that ignores extras stops noticing new problems.

**4. Reporting.** Deterministic ordering, and on failure the full expected and
actual output — the harness is itself debugged through this output.

**5. Declaration.** How the manifest names test targets, resolving
`BUILD_REFERENCE.md` §8's first open item. Fold the answer back into
`BUILD_REFERENCE.md`; do not leave the spec saying "open" once it is decided
(spec drift is the failure mode this whole approach exists to avoid).

## Done when

- All three test kinds run and report.
- A deliberately broken sample fails for the **right** code.
- A sample expecting the wrong code **fails**, proving the harness is not merely
  agreeing with whatever it is given.
- `BUILD_REFERENCE.md` §8's test-declaration item is closed.
