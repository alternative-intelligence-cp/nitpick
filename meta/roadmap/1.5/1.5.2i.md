# 1.5.2i — `string_concat` of two empties allocates nothing (DEF-25) — DONE (2026-09-06; reported, planned and landed the same day; two landings, each a cumulative prefix under a full harness, D-228)

> Scope: **DEF-25**, the library workbench's report of 2026-09-06
> (`nitpick-regex`'s cycle-0.0 audit refused its close on it): the runtime's
> `@npk_string_concat` allocates unconditionally, and a result of length 0
> carries cap 0, so the block it allocated for an empty result is never
> freed. Two steps, two commits, each under a FULL harness on a cumulative
> prefix (D-228). A runtime fix, no language change, nothing pending on the
> user.

## 1. Where you are

`main` is the 1.5.2h close (`c81efa5`). The runtime floor is hand-written
LLVM IR and permanent (D-203); `runtime/npkrt.ll` is assembled beside the
compiler's emission, so a change to it moves `build/npkrt.o` and `build/npkc`
and not `build/npkc.ll`. `@npk_string_concat` (`npkrt.ll`, the `qok` block)
computes `n = al + bl`, calls `npk_alloc_internal(n)`, copies both operands
and returns `{p, n, n}`; `@npk_alloc_impl` substitutes 16 for a zero request
(D-150: `alloc(0)` is a real, unique, freeable block). Cap 0 is the not-mine
bit, so the drop of an empty result frees nothing and the block is
unreachable. `@npk_string_slice` has carried the empty branch since D-186
("an empty slice allocates nothing: len 0 is never dereferenced, and cap 0
gives the drop nothing to free"): the hazard was seen and handled in one
primitive and not its neighbour. No other runtime string primitive
allocates (`string_from_bytes` and `string_equals` do not).

Measured on `c81efa5` (the workbench's shape, reproduced here):
`string_concat("", "")` in a bare loop under `ulimit -v 65536` exits 92
(`HeapOom`) at 8,000,000 calls where `string_concat("", "a")` exits 0; under
`NPK_HEAP_STATS` at 1,000,000 calls the empty case reads
`allocated=16000000 peak_live=16000000 count=1000000` against
`allocated=1000000 peak_live=1 count=1000000` — 16 bytes per empty call,
never freed, linear in the calls. Two consequences the report did not name:
the prelude's `impl:string:Clone` is `string_concat(self, "")`, so `.clone()`
of an empty string leaks the same block, and the compiler's own copy idiom
`string_concat(x, "")` (234 sites in `src/`) leaks on every empty operand —
the compiler has been leaking in its own build since the idiom was adopted.

## 2. What this subcycle builds

**Step 1 (DEF-25).** In `@npk_string_concat`, after `%n = add i64 %al, %bl`,
the slice's branch: `%none = icmp eq i64 %n, 0` → `empty:` returns
`{ {ptr %ap, 0, 0}, 0 }` — the first operand's pointer, as the slice returns
its source's (len 0 is never dereferenced, cap 0 gives the drop nothing);
`copy:` is the block as it stands. Tests: `tests/backend/programs/
empty_concat.npk` (200,000 empty concatenations, each dropped, exit 0) and
`empty_concat_one.npk` (the same with `("", "a")`), and
`tests/cost/empty_concat.toml` (kind `probe`, the empty program against the
one-byte program, `bound = 4`): under the runtime as it stands the empty
program's `peak_live` is 3,200,000 against the other's 1, so the unit fails by
a factor of millions; after the fix both peak at 1 or 0. Full harness on
prefix i1. Expected in the compiler's own cost unit: `allocated` and `count`
fall (the copy idiom's empty operands), `peak_live` stays under the ceiling.

**Step 2.** The docs: BUILTIN_REFERENCE's `string_concat` row says an empty
result allocates nothing (regenerate the tables, `--check`), DEF-25 reads
fixed, the 1.5 README row and ROADMAP's 1.5 row read DONE, CLAUDE.md's status
carries the line; this file's records. Full harness on prefix i1+i2. The
workbench told with the six digests — `build/npkrt.o`'s and `build/npkc`'s
move, `build/npkc.ll`'s does not.

## 3. Decisions taken at planning

- **L-1 — The fix is the runtime's.** The floor is the permanent form
  (D-203), and the primitive beside it already handles the case; a guard in
  the prelude or in every caller would be the same rule in many places.
- **L-2 — The empty result's pointer is the first operand's**, as the slice's
  is its source's: len 0 is never dereferenced, so any pointer serves, and a
  null would be one more shape for a reader of `{ptr, 0, 0}` to reason about.
- **L-3 — The instrument is a cost unit**, the designed one: a leak is a
  number the allocator prints, never a clock or a memory cap.
- **L-4 — The prelude's `Clone` and the compiler's copy idiom are unchanged.**
  Both are correct once the primitive is; respelling 234 sites would be
  work that hides the fix.

## 4. Measurements

The two programs at 200,000 iterations, `NPK_HEAP_STATS`: `empty_concat.npk`
`allocated=3200000 peak_live=3200000 count=200000` on the runtime as it stood
(`c81efa5`), `allocated=0 peak_live=0 count=0` with the branch;
`empty_concat_one.npk` `allocated=200000 peak_live=1 count=200000` on both.
The compiler's own build (`self.toml`, the harness's numbers): `allocated`
383,914,731 → 383,897,467, `count` 7,881,550 → 7,880,471, `peak_live`
115,743,127 → 115,725,863 — 1,079 fewer allocations and 17,264 fewer bytes,
and 1,079 × 16 is 17,264: every byte of the difference was an empty
concatenation the compiler leaked in its own build, 1,079 of them.

## 5. What the executor should know

- `runtime/npkrt.ll` is assembled by `llc` with the pinned flags; a label
  must be unique within the function (`empty:` and `copy:` exist in
  `npk_string_slice`, a different function — fine).
- `tests/cost/*.toml` `probe` units name two programs that are ALSO run as
  ordinary programs; both must exit 0 on their own.
- Stop every background waiter before reporting done.
