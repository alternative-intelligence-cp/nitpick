## 2. What this subcycle builds, in one picture

Two compiler runs, one runner, one committed file:

```
build/npkc <entry> --obligations build/verify/obl -o build/verify/plain.ll
        │   every guard retained; one .smt2 per FUNCTION INSTANCE with obligations
        ▼
npkg verify: z3 <profile from [verify]> -smt2 NNNN.smt2   (one fresh process per file)
        │   N `check-sat` answers per file, nothing else on stdout, or the run FAILS
        ▼
the run's rows  ==  nitpick.obligations (committed, root)   else FAIL (D-040's table)
        │
        ▼
build/npkc <entry> --elide nitpick.obligations --obligations build/verify/obl2 -o build/verify/npkc.v.ll
        │   discharged guards removed, `llvm.assume` stated; obl2's hashes == obl's (a belt)
        ▼
llc / scan / ld.lld → build/verify/npkc ; build/verify/npkc <entry> --elide … → stage2.ll == npkc.v.ll
```

The compiler emits TEXT and spawns nothing (D-067's shape, `src/main.npk`'s
own header: "IT WRITES TEXT — and nothing else"); `npkg` owns every tool
invocation (D-206, BUILD_REFERENCE §7); the harness has a Python twin of the
runner's verify leg and the `parity` stage holds the two to each other
(D-206 §5). The obligation walk runs over the typed AST, per function
instance, BEFORE that instance's body is lowered, and never reads the IR
writer — which is what makes run 1's obligations and run 2's identical by
construction, and the `obl == obl2` comparison the belt over that
construction.

## 3. Decisions taken at planning (each with its reason; ratify or amend before step 2)

Numbered P-1… so the record and the commit messages can cite them. None
changes the language. P-1, P-5, P-9 and P-13 are the ones a reader should
look at first: they are the places this plan reads a ratified text one way
where another reading exists.

- **P-1 — the seeds become `zeroinitializer`, not `poison`.** D-218.10
  admits either ("`poison` (LLVM 20 literal) or zeroinitializer"). Reasons,
  in the priority order: (safety) a field an audit missed reads a DEFINED
  zero instead of poison, whose first branch is undefined behaviour; (D-218.9
  itself) elision was ratified to work "without minting poison" — an emitter
  that mints none anywhere is the simpler invariant to state and to have
  1.6's Alive2 leg check; (simplicity) one spelling for every seed,
  aggregates and the simd splat alike (`insertelement <N x T>
  zeroinitializer …` is valid and folds identically). The harness grep BANS
  `undef` (the ratified rule) and REPORTS the `poison` count in its stage
  line without failing on it — LLVM's own value model uses poison, 1.6 may
  need `freeze`, and a ban stricter than the decision would fight the model
  the evidence tools reason in.
- **P-2 — the ban is total: every `.ll` the tree holds or produces.** Every
  emission (programs, fixtures, tools, stage 1, stage 2), `runtime/npkrt.ll`
  (43 seeds today, swept by hand — the floor is in every artifact and r8's
  lesson does not stop at the emitter), `runtime/tests/*.ll` (zero today),
  and the committed snapshot — which is why step 1 REFRESHES the snapshot
  (16,533 `undef` in it today) as its second commit, on the committed sweep,
  and extends the check to the snapshot in that same second commit.
  Comments (`;` to end of line) are stripped before the word is looked for.
- **P-3 — one walk, two consumers.** The obligation walk (`smt_obligations`)
  runs inside the emitter's per-instance loop, immediately before
  `emit_fn_instance` lowers the body, under the same generic bindings, and
  fills a per-instance site table keyed by `ExprId` (an instance's ids are
  unique; the table is cleared per instance). `--obligations` writes files
  from that table; `--elide` marks table entries discharged from the
  manifest; the division emitter asks the table by `ExprId` — threaded into
  `emit_arith_value` as a parameter, so the compound spellings (`/=`, `%=`,
  routed through it since 1.3.3) are sites exactly like the binary ones. The
  walk reads the AST, the expression types and the instance bindings; it
  never reads `IrWriter`. Reason: the two-run protocol needs identical
  obligations in both runs, and "identical by construction" is the only
  version of that claim a verifier can read.
- **P-4 — the obligation's canonical text is its relevance cone, and the
  solver's query IS the cone.** Start from the goal's free names; add every
  hypothesis (definition, range axiom) that mentions a name in the set,
  closing transitively; stop at the fixpoint. That text — de-attributed (no
  `:named`), span-free — plus the module-qualified symbol plus the kind is
  what SHA-256 hashes (D-218.8). The `.smt2` file asserts the cone INSIDE the
  obligation's `(push) … (pop)` (declarations and the `define-fun`s at the
  base level, where they are harmless), so the answer recorded is the
  answer to the text that was hashed — never to a larger context. Reasons:
  identity stable under unrelated edits in the same function (a statement
  that touches none of the cone's names changes no row — the diffable-run
  goal); no vacuous discharge from a contradictory context elsewhere in the
  function; smaller queries. Dropping hypotheses is sound for the direction
  we use (a cone that is unsat makes the whole context unsat).
- **P-5 — names in the canonical text are source-derived SSA, not
  positional.** A binding's k-th definition in walk order is `<name>.<k>`;
  subexpression results are inline terms, never named; an opaque value (P-8)
  is `<name>.<k>` too, with only its range axiom. Reasons: a rename changes
  the text (honest — the obligation's spelling changed) while an inserted
  unrelated statement does not; and a counterexample reads back to source
  without a side table (`x.2 = 0`).
- **P-6 — one solver file per function instance, one fresh z3 process per
  file** (D-218.3), keyed by the mangled symbol (`@"npk.<module>.<name>"`,
  `@main`, `@npk_failsafe` — D-064's readable, reversible, hash-free names
  are the "module-qualified symbol" D-218.8 asks for). Files are numbered
  `NNNN.smt2` in emission order with `index.txt` (`NNNN<TAB>symbol<TAB>count`)
  beside them; the manifest rows carry the symbol, never the number. A
  function with no obligation has no file.
- **P-7 — the verdict pass asks `(check-sat)` and NOTHING else.** Measured
  (§4): `(get-model)` after `unsat` and `(get-unsat-core)` after `sat` each
  print an `(error …)` line and z3 keeps going, so a file that asked for both
  could only be read by matching error prose — a parser that succeeds by
  recognising an error message. The gate path therefore reads exactly N
  answer lines ∈ {`sat`, `unsat`, `unknown`} for N obligations and FAILS the
  run on any other line. Models (counterexamples), `(:reason-unknown …)` and
  cores come from a second, on-request pass — `npkg verify --explain` — one
  small file per obligation that is not discharged (model or reason) and per
  discharged one (core), never on the harness's gate path. D-218.8's
  reverse-mapping lives there.
- **P-8 — the encoder's rule is fail-closed opacity.** A value the encoder
  cannot express is OPAQUE: declared with its type's range axiom and no
  definition. Never skipped, never guessed. Every hypothesis the encoder does
  assert is a fact on every execution that reaches the site (a definition is
  the language's semantics; a range axiom is the type's; the D-210/D-007
  traps make the continuing path satisfy them) — the soundness claim 1.5.6
  and 1.6 will read.
- **P-9 — the obligation file is `nitpick.obligations`, at the manifest
  root, committed, line-oriented, and written only on purpose.** Beside
  `nitpick.toml` and `nitpick.lock` (the `.lock` precedent: read by every
  build, written by one deliberate command). `npkg verify` NEVER writes it
  implicitly: with no committed file it fails by name and says to run
  `npkg verify --record`; `--record` writes it (a deliberate re-baseline, the
  same act as moving the toolchain pin and regenerating every hash). This
  amends D-040's "no manifest → one is generated" row for the D-219 world
  (elision governed by the manifest, never a flag): a file that governs the
  artifact is written on purpose or not at all — and it keeps the standing
  rule that nothing edits the tree while a harness runs on it (the parity
  stage runs `npkg verify`). D-040 gets a dated annotation.
- **P-10 — the row schema, from birth, every column.**
  ```
  # nitpick.obligations v1
  # z3 4.16.0 sha256 <64 hex>
  # options smt.random_seed=0 sat.random_seed=0 rlimit=20000000
  <hash64> <kind> <tier> <verdict> <elision> <symbol>
  ```
  `kind` from the catalogue table (P-11); `tier` ∈ {`int`, `bv`, `fp`,
  `real`, `-`} (1.5.0 writes `int` and `-`); `verdict` ∈ {`discharged`,
  `open`, `budget`, `unencoded`, `checker`} — `open` is a `sat` answer (a
  counterexample exists under the encoding's hypotheses: not a refutation of
  the program, a guard that stays), `budget` is `unknown` under the rlimit,
  `unencoded` a site the encoder could not express (P-12), `checker`
  reserved for frontend-discharged rows (1.5.1+, none here); `elision` ∈
  {`elided`, `retained`, `none`} (`none` for kinds with no runtime guard —
  none in 1.5.0). Rows sorted by symbol then hash (a total order carrying no
  position); duplicate rows (two sites with one cone) collapse, so the
  cross-check is "every site's hash is in the file", never a count. The
  header's options line must equal the manifest's list word for word or the
  file is refused.
- **P-11 — the kind vocabulary is total from birth, and instrumented.** An
  enum in `smt_obligations.npk` names every catalogue row of D-218.7 now —
  `div-zero`, `div-min`, `overflow`, `bounds`, `cast-range`, `exhaustive`,
  `requires`, `ensures`, `invariant`, `limit`, `limit-subsume`, `terminate`,
  `stack-depth`, `err-exit`, `failsafe-post`, `prove`, `assert-static` —
  with only the first two producing rows here. VERIFICATION_REFERENCE gains a
  marked catalogue table with the same names, and a new harness check
  (`check_obligation_kinds_agree`) diffs the enum against the table: two
  lists that must agree are an instrument (1.4's lesson 8), and the "every
  carried obligation appears or the manifest has holes" sentence becomes a
  check rather than a hope.
- **P-12 — every guard site has a row.** A division the encoder cannot
  express (a simd lane division, a site inside a construct the walk does not
  model) is still a row: verdict `unencoded`, tier `-`, its "canonical text"
  the literal `(unencoded <kind> <ordinal>)` — identified positionally on
  purpose, and visibly not proof-backed. Reason: the manifest is then an
  INVENTORY of guards, and the harness can assert that every `-4097`/`-4098`
  trap site left in an elided emission corresponds to a non-discharged row.
- **P-13 — the wall-clock deadline is a hang net, never a verdict.**
  `proc_wait` bounds every wait (D-206); a z3 process killed at its deadline
  FAILS the verify run by name ("z3 exceeded the wall-clock net on F — not a
  verdict"), it never records `budget`. The net is generous and proportional
  (`120 s + 10 s × obligations in the file`) so it only ever catches a
  wedged solver. D-218.2's law is that a verdict is a function of
  (obligation, solver build, budget); a kill is a function of the machine and
  must not be able to become a row.
- **P-14 — `[verify]` pins the tool AND the profile, and every invocation
  is built from it** (D-204's "pinned AND READ" rule, applied to z3):
  ```toml
  [verify]
  z3         = true
  z3-version = "4.16.0"
  z3-sha256  = "<64 hex of the binary z3 resolves to on PATH>"
  z3-options = ["smt.random_seed=0", "sat.random_seed=0", "rlimit=20000000"]
  ```
  The pin check asks the tool (`z3 -version` must read `Z3 version
  4.16.0`) AND hashes the file it resolved to (`shutil.which` / npkg's
  `which`); a mismatch on either refuses. The options list is passed verbatim
  as `z3 <options…> -smt2 FILE`; the check REFUSES a list containing any
  wall-clock knob (`timeout=`, `-T:`, `-t:`, `solver.timeout=`) or a
  parallelism knob (`sat.threads=` other than 1, `parallel.enable`) — the
  determinism profile's two "disabled" rows enforced as refusals, not
  remembered. z3's own defaults for both are already disabled/1 (§4), so
  passing nothing IS disabling them; the refusal is what keeps it so.
  `timeout` is deliberately not spelled in the list: z3 reads
  `timeout=0` as a knob, not as "off".
- **P-15 — the budget value.** `rlimit=20000000` (r5's example figure)
  opens; step 4 records the `:rlimit-count` of the largest obligation in the
  compiler's own set (`-st`) and the executor raises the figure only if a
  tracer-kind obligation lands `budget` — a budget change is a manifest
  change with a `--record` behind it, never a quiet bump. Per-check-sat, by
  measurement (§4).
- **P-16 — the logic is per file, by content, the most specific standard
  logic the file's terms fit**: `QF_LIA` when every `*` has a literal operand
  and every `div`/`mod` a literal divisor, `QF_NIA` otherwise. Forced, not
  chosen: measured (§4), z3 under `QF_LIA` REFUSES `(* a b)` and `(div a b)`
  with an error line, and accepts `(div a 7)`. The logic line is part of the
  file, not of the canonical text (a cone's identity does not depend on what
  else the function contains).
- **P-17 — signed division is a `define-fun`, and its truncation is
  measured.** SMT-LIB's `div`/`mod` are Euclidean; Nitpick's `/` and `%` on
  plain ints are LLVM's `sdiv`/`srem` (truncate toward zero, remainder takes
  the dividend's sign — `div_ok.npk` pins `(-9)/(-3)` and OP_REFERENCE §1
  says "truncates"). The base-level definitions every file carries:
  ```
  (define-fun npk_sdiv ((a Int) (b Int)) Int
    (ite (>= a 0) (ite (>= b 0) (div a b) (- (div a (- b))))
                  (ite (>= b 0) (- (div (- a) b)) (div (- a) (- b)))))
  (define-fun npk_srem ((a Int) (b Int)) Int (- a (* b (npk_sdiv a b))))
  ```
  Measured (§4): `npk_sdiv(-7, 2) = -3` and `npk_srem(-7, 2) = -1` proven
  (their negations `unsat`). Unsigned `/` `%` are `div`/`mod` directly (on
  non-negative operands the two conventions coincide). `(div a 0)` is a
  total unspecified function in SMT-LIB, which is fine: the `div-zero`
  obligation precedes the quotient's definition in walk order, and the
  definition is never a hypothesis of its own guard.
- **P-18 — the range bounds are exact decimals at every width of the
  ladder.** `intN`/`uintN` for N ∈ {8, 16, 32, 64, 128, 256, 512, 1024,
  2048, 4096} (D-231). `2^N` is rendered by repeated doubling of a decimal
  digit vector (a 1,234-digit literal for 4096), computed once per width and
  cached; pinned by known answers (2^64, 2^128 in full; 2^4096's digit count
  and tail generated by python at plan time — the D-193 vector precedent).
- **P-19 — `llvm.assume` at an elided site, declared in the fixed block.**
  A discharged `div-zero` emits `%nz = icmp ne T %den, 0` then
  `call void @llvm.assume(i1 %nz)` in place of the branch-and-trap; a
  discharged `div-min` emits the negation of its `and` as the assumed bit.
  `declare void @llvm.assume(i1)` joins the fixed declare block
  unconditionally (the `@npk_trap` precedent — a declared-unused intrinsic
  is harmless, and the declare block is a constant). Never `nsw`/`nuw`
  (D-218.9). A build without `--elide` emits byte-identical IR to today's:
  the elision path is reached only through the flag.
- **P-20 — the driver grows its argument table.** `src/main.npk` parses
  `-o` positionally and `--extra-picky=no-wildx` by scan, and its own comment
  says the second flag "becomes the driver's argument table". The third and
  fourth flags are that moment: `-o PATH`, `--extra-picky=no-wildx`,
  `--obligations DIR`, `--elide PATH`, each at most once, order-free, an
  unknown argument exiting 2 with the usage. `--obligations` and `--elide`
  may be given together (run 2 writes `obl2` for the belt).
- **P-21 — SHA-256 lives in `lib/nhash.npk`, one implementation for both
  consumers.** The compiler hashes obligations and `npkg` hashes the z3
  binary; `src/` may import `lib/` (`src/main.npk` imports `../lib/nio.npk`
  — the `absent-fact` stage already copies `lib/` for that reason). FIPS
  180-4 over `uint32` words; the mod-2^32 additions ride `uint64` and narrow
  with `=>!` (D-210.3's widen-compute-truncate, the 1.4.7 FNV precedent);
  rotations are shifts and `|`. Known answers as a real-backend program
  (`tests/backend/programs/sha256_kat.npk`): "", "abc", the 448-bit and
  896-bit FIPS messages, and one million `a`. Plain Nitpick under the
  current snapshot — no new builtin, no floor change, no refresh needed for
  D-205.
- **P-22 — the `verify` test stage and its marker.** A new `[[test]]` stage
  `verify` (`path = "tests/verify"`), both runners, one marker:
  `// expect-obligation: KIND VERDICT N` (or `// expect-obligation: none`).
  Exactness in the D-237 shape, scoped to the TEST'S OWN MODULE: the multiset
  of (kind, verdict) counts over the module's rows must EQUAL the
  expectations (the prelude's rows are compiled into every program and would
  otherwise dominate and churn every expectation; they are still verified and
  still reported in the stage line). A verify test with no
  `expect-obligation` is a failing test (the negative-test precedent). Then
  the program is re-emitted with `--elide` over the run's rows, the elided
  IR is checked (no `-4097`/`-4098` trap site for a discharged row; an
  `llvm.assume` for each), linked, run for `expect-exit`, and run again
  through the opt-O2 leg — the assume path is exactly what the optimiser
  consumes, so the 1.3.8 instrument covers it from the first commit.
- **P-23 — the runner self-checks grow four cases each**, driven through
  their failure paths like the toolchain pin's: `undef-in-emission` (an
  `.ll` holding `insertvalue { i32 } undef` must fail; the same word in a
  comment must pass), `z3-mismatch`/`z3-unpinned`/`z3-restored` (the sha
  moved, the pin absent, the real pin passing), and `wrong-verdict`
  (`expect-obligation: div-zero discharged 1` over an opaque denominator
  must fail) beside `right-verdict`.
- **P-24 — the SMT modules live in `src/backend/smt/`.** They consume the
  typed AST and produce text, as `src/backend/ir/` does, and D-067 names
  "the IR emitter and the SMT-LIB2 emitter" as the two Nitpick-source
  emitters in this repository. Four modules: `smt_writer.npk` (the text
  buffer, s-expression helpers, deterministic naming), `smt_encode.npk`
  (sorts, range axioms, the value encoder, the `define-fun`s, the cone),
  `smt_obligations.npk` (the kind enum, the per-instance walk, the site
  table, file assembly, the index), `smt_manifest.npk` (reading
  `nitpick.obligations` for `--elide`; the row renderer both runners'
  outputs are compared against). LAYOUT.md gains the directory and the two
  files (`nitpick.obligations`, `build/verify/`).
- **P-25 — `npkg verify` is the compiler tree's command today, and says
  so.** `npkg build` needs `bootstrap/seed/stage1.ll` (the ladder), so every
  tree `npkg` can build is this one; the "stage-1/stage-2 comparison for the
  compiler itself" (BUILD_REFERENCE §7) therefore always applies and needs no
  detection. A user-project mode is BUILD_REFERENCE §8's open item, not
  1.5's.
- **P-26 — TCB.md's floor table is generated and checked, never
  hand-maintained.** The classification in §4 (by inline asm, transitive
  reach of the syscall trampoline, atomics) is produced by an instrument
  (`check_tcb_floor_current`, harness) that recomputes it from
  `runtime/npkrt.ll` and FAILS when the table in TCB.md differs — the
  D-204/D-238 rule ("a table nothing reads is the next stale document")
  applied to the one table an auditor will read first. 1.5.6 fills the
  per-row DISPOSITION column by hand; the membership columns stay
  generated.
- **P-27 — the compiler trusts the manifest it is handed; the runner is the
  gate.** `--elide` checks the file's format and options header and reads
  the discharged hashes; it does not spawn z3, hash z3, or compare rows —
  `npkg verify` did all three before run 2 exists, and the harness's stage
  does the same. A hand-edited `nitpick.obligations` fed to `npkc --elide`
  by hand is the same act as hand-editing the IR: outside every gate,
  recorded here so nobody mistakes the compiler's trust for a check.

## 4. Measurements the plan rests on (made 2026-09-03 with the wheel's z3 4.16.0)

The digest's reliability note 2 asked for the profile to be verified against
the pinned z3's own parameter list rather than the reports' citations. Done:

- `z3 -p`: global `rlimit` (default 0 = unbounded) and `timeout` (default
  4294967295 = disabled); module `smt` has `random_seed` (default 0); module
  `sat` has `random_seed` (default 0) and `threads` (default 1). The
  command-line spellings are `smt.random_seed=0 sat.random_seed=0
  rlimit=N`; `-T:`/`-t:` are the wall-clock knobs the profile refuses.
  `(set-option :rlimit N)` and `(set-option :smt.random_seed 0)` are ALSO
  accepted in-file; the plan passes the profile on the command line from
  the manifest so the canonical text carries no profile (P-14).
- **`rlimit` is per `check-sat`, not per process**: with `rlimit=3000` a
  file asking easy / hard / easy / easy answered `sat` / `unknown`
  (`(:reason-unknown "canceled")`) / `sat` / `sat`. An exhausted obligation
  does not starve the next one in the same file (this is what makes P-6's
  per-function file safe).
- **Run-to-run identity**: the same file under the profile twice gave
  byte-identical stdout (`cmp` silent).
- **Output shapes** the parser will read: answers are bare lines `sat` /
  `unsat` / `unknown`; a model is `(` … `(define-fun v1 () Int 0)` … `)`
  across lines with negative numerals as `(- 3)`; an error is
  `(error "line L column C: …")` on STDOUT, after which z3 KEEPS PROCESSING
  and the process exits 1 at the end — so the exit code is a belt and the
  line scan is the check.
- `(get-model)` after `unsat` → `(error "… model is not available")`;
  hence P-7.
- **Logic strictness**: under `(set-logic QF_LIA)` z3 refuses `(* a b)` and
  `(div a b)` (`logic does not support nonlinear arithmetic`) and accepts
  `(div a 7)`; a linear-only problem under `QF_NIA` decides normally (an
  `unsat` in 201 rewrites). Hence P-16.
- **The truncating definitions** (P-17) proven on the solver: the negations
  of `npk_sdiv(-7,2) = -3` and `npk_srem(-7,2) = -1` are `unsat`; a named
  core came back as `(def_v1 ob_divz_1)` — the hypotheses used, exactly the
  reverse-map input D-218.8 describes.
- `-st` reports `:rlimit-count` per run — the calibration number P-15 uses.
- **The floor, classified** (159 `define`s in `runtime/npkrt.ll`, by a
  script the executor turns into P-26's instrument): 3 defines contain
  inline asm (`@npk_sys6`, `@npk_clone_exec`, `@npk_exec`) plus the
  `module asm` block `npk_clone_raw`; 23 use atomics (`atomicrmw`/`cmpxchg`
  or an atomic load/store — the channel, mutex, park, scheduler, sarena,
  driver-registry and step paths); 0 use `volatile`; 116 reach inline asm
  transitively (every syscall goes through `@npk_sys6`); **38 are pure IR**
  (no asm reach, no atomics): the four `__*ti3` and `npk_udivmod128`,
  `fmod`/`fmodf`, `memcpy`/`memset`/`memmove`, the allocator's arithmetic
  helpers (`npk_m_*`, `npk_chtab_find`, `npk_lg_entry/find/remove`,
  `npk_frame_bucket/drain`), `npk_arena_at/free/reset`,
  `npk_string_equals/from_bytes`, `npk_environ`, `npk_frozen_get`,
  `npk_wild_live_count`, `npk_wildx_call`, `npk_zero`. That is TCB.md's
  first table; 1.5.6 writes each row's disposition.
- **The `undef` inventory**: 32 code sites in the emitter (28 in
  `ir_expr.npk`, 3 in `ir_func.npk`, 1 in `emit_program.npk`; the other hits
  are comments), every one an `insertvalue … undef` seed or the simd splat's

- Symbols: `mangled_fn_sym` gives `@"npk.<module>.<name>"` (instantiations

## 6. What the executor should know before starting (gotchas, carried from the handoff and this reading)

- A full harness is ~100 min today and gains the verify legs at step 4
  (~15 min); its stdout is block-buffered — the log is empty until the end;
  progress is `ls /tmp/npk-harness-*`. Invocation that worked:
  `python3 bootstrap/harness/harness.py --verdicts .internal/verdicts_150_N.txt > .internal/harness_150_N.log 2>&1 &`.
- Do NOT edit the tree while a harness runs on it; develop the next step in
  a worktree and bring the diff back (the handoff's paragraph, verbatim in
  practice).
- `python3 bootstrap/harness/quickemit.py --keep npkg/main.npk` builds
  `npkg` (exit 2 = usage = the compile passed; run
  `.internal/quickemit/p_main_npk` from the tree root); `quickcheck.py`
  builds the checker once; both are for iterating, never for concluding.
- **A backend change reaches the tools only through the snapshot** — the
  SMT walk is backend code, but nothing in `tools/` calls it, so no
  mid-cycle refresh is needed for D-205 after step 1's.
- The reserved words that bit 1.4 (`fails`, `end`, `pid`, `fd`, `limit`,
  `any`, `on`, `unit`, `trit`, `nit`, `oflags`/`prot`/`mflags`/`fmode`,
  `error`, `buffer`, `raw`, `move`) — CLAUDE.md's table. New code here
  wants `limit` as a local name constantly; it is the keyword.
- Strings are move-only owners (TYPE-046): build a name per use; consume
  with `move T:p`; the writer's buffer is the one thing that accumulates.
- D-004's conservative rule: a value produced by a call handed `@local`
  cannot be returned or stored; `proc_wait` CONSUMES its `Proc` for that
  reason; the z3 runner takes its arguments BY VALUE like `run_argv` does.
- `check_codes_centralised` scans `src/` and `tools/`: no diagnostic code
  literal outside a `*_codes.npk` — the verify pipeline reports no new
  diagnostic CODE (its refusals are `npkg`'s and the harness's, by name on
  stderr), so nothing new is owed there; if step 3 wants a compiler-side
  refusal (e.g. a bad `--elide` file), it is a driver message at exit 2, not
  a diagnostic.
- `npkg/toml.npk` takes single-line arrays; keep `z3-options` on one line.
- Both self-checks share one case set by NAME and count (`CASE_COUNT`);
  add a case to both or `parity` will say so.
- Every `failsafe` in `npkg` and the tests is exhaustive over what can
  reach it (REACH-002); a new `error:` in `lib/nhash.npk` or the verify
  runner costs arms tree-wide — `nhash` declares none (a hash cannot fail),
  and the verify runner reuses `nproc`/`nfs`/`ETextInt`-class identities
  where it can, declaring new ones only where a new failure genuinely
  exists (record each).

## 7. Interfaces this subcycle freezes for the rest of the cycle

Written down because 1.5.1–1.5.8 build on them and ORCHESTRATION §2 licenses
parallel work only against a frozen, committed interface:

- The site table's shape (`ExprId` → {kind, hash, verdict-bit}) and the
  encoder's opacity contract (P-8) — later kinds ADD rows and hypotheses
  (path conditions, contracts, invariants), they never weaken a hypothesis
  the walk already asserts.
- The canonical-text rules (P-4, P-5): a later subcycle that must change
  them (e.g. the BV crossing) re-baselines `nitpick.obligations` with
  `--record` and says so in its record.
- The row schema (P-10) and the kind vocabulary (P-11): additive only.
- The two-run protocol and the belt (`obl == obl2`).
- `npkg verify`'s options (`--record`, `--explain`) and exit codes (the
  tree's contract: 0 verified, 1 a verdict/manifest failure listed, 2 the
  environment/manifest/pin, 3 a trap).

## 8. What 1.5.0 does NOT do (by decision, each owned elsewhere)

No typing of `Rules`, `limit<R>` names or contract expressions (1.5.1); no
`prove`/`assert_static` (1.5.4); no path conditions (1.5.4 — `divz_after_branch`
pins today's conservative answer so the improvement is visible); no overflow
obligations (1.5.8; the D-210 trap stays at every `+ - *`); no bounds, cast,
