## 2. What this subcycle builds

**Step 1 (D-265 §3).** `ladder_digests(Ctx->)` in `npkg/build.npk`: for each
intermediate the ladder produced, in ladder order, one line
`  sha256      <64 hex>  <bytes> B  <path relative to the root>` (the
`stage_text` shape, label `sha256`), the digest by `sha256_hex` over the
file's bytes, the count the file's length; a file that cannot be read back
is reported by name in the same position rather than skipped, since a
missing line is the silent failure. `main.npk` prints the lines after the
`builder` stage line on EVERY ladder run — `build`, `test` and `verify` alike
— because a report that exists in one mode and not another is the kind of
context-dependence the blueprint philosophy refuses. The harness's `parity`
stage parses the `  sha256 ` lines from `npkg test`'s stdout and compares
each to `hashlib.sha256` over the same file under `build/`, failing by name
on a missing line, an unknown path, or a digest or byte count that differs;
the runner self-check is not extended (the lines are not verdicts). Test:
the cross-check IS the test, and it runs on every full harness.

## 3. Decisions taken at planning

- **L-1 — Every ladder run reports, no flag.** A `--digests` flag would be a
  mode, and the report costs one read and one hash per intermediate (about
  45 MB, well under a second). The same lines in every run also mean the
  parity stage sees them without running the ladder a second time.
- **L-2 — The cross-check lives in the harness's `parity` stage**, which is
  the one place both an `npkg` run's stdout and an independent hash are at
  hand. When the harness retires (`meta/SWITCH.md`), the check moves into
  `npkg`'s own self-check as a comparison against `sha256_kat.npk`'s
  vectors over the same code path; recorded here so the retirement does not
  drop it.
- **L-3 — The unreadable case is a line, not an omission.** The report's
  consumer is a person comparing two machines; a shorter list on one side
  reads as "a different ladder", which is the wrong diagnosis.
- **L-4 — `npkc.opt.ll` rides only when it exists.** `[build] opt-level` is
  0 for the compiler's own build; under 2 the optimised text is a real
  intermediate and is reported in its position (between `npkc.ll` and
  `npkc.o`).
