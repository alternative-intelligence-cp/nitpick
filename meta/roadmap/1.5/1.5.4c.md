## 2. What lands (D-273 §1–§4)

1. **The qualified call is a DIRECT call.** A call whose base names a module —
   an inline module, an alias, a nested path `core.math.f(x)` — calls that
   member with no receiver; the checker records the member as the callee, the
   emitter lowers it as `emit_call` does a direct call, the SMT walk records
   its rows as at any direct call (`requires` `bypass`, `limit-subsume`,
   `uf_value` for a `pure never fails` callee), and a `pure never fails`
   member is admissible in a contract as any named function is.
2. **`use` over a module path.** A `use` whose first segment names a module
   symbol in the importing file's scope binds that module's public names in
   every form the file forms have — `use hidden.*;`, `use hidden.{f, Point};`,
   `use hidden.f;`, `use core.math.*;` — through the SAME `bind_wildcard`/
   `bind_named` the file forms use. This is the only way an inline module's
   TYPES are named from outside (there is no qualified type path, for files
   either). A first segment that names no module symbol in scope and is not
   `std` is `RESOLVE-002` naming the segment (a typo is never silent); `std.…`
   stays the driver's as today; `std` joins D-239's owned names for a module
   declaration or a file (`RESOLVE-001`).
3. **Visibility from either spelling.** A private member reached by a
   qualified path from OUTSIDE its module, or named by a `use` over its
   module, is `RESOLVE-004` ("`f` is private to `m`", the note at the
   declaration) — the resolver's code, imported by the checker for the
   qualified spelling (one mistake, one code; D-240). Inside the module (the
   accessing scope has the module's scope among its ancestors) everything is
   reachable, as §3 says. A `pub mod` is an exported symbol a file's wildcard
   or named import binds WITH its scope, so `helpers.f()` works across files.
4. **One field.** A module symbol's `inner` is the scope its members live in:
   set by collection for an inline module (`symtab_set_inner`), by
   `apply_one_import` for an alias (the source module's `scope`), and copied
   by `bind_or_report` whenever a module symbol is bound into another scope.
   `nested_module_scope` and the new `namespace_path` read it; nothing
   searches for a scope (D-115's rule).

Two readings of D-273 the plan makes executable, recorded for the user to
veto (neither changes a program that compiles today):
**R-1** an unknown first segment refuses (§2 item 2) rather than binding
nothing; **R-2** within a file, namespace and file imports are applied
BEFORE logical ones (two passes in `apply_imports`), so `use lib.*;` works
whether it is written above or below `use "./lib.npk" as lib;` —
MODULE_REFERENCE §2.4: resolution is never order-dependent.

## 3. Steps (D-228: one worktree per step, one full harness per cumulative prefix, landed on `main` by cherry-pick with the record appended here)

### Step 0 — the checker, the emitter and the encoder: the qualified call

- `namespace_path(e, ExprId) -> int32` in `type_members.npk`: an identifier
  whose symbol is `SYM_DECL` over a `DeclModuleDecl` with `inner != 0`, or a
  member access whose operand is a namespace path and whose member (by
  `scope_lookup_local(inner, name)`) is such a symbol — returns the module's
  SYMBOL; anything else 0. The visibility rule of §2 item 3 is asked at every
  hop taken from outside (`scope_is_inside(e.tab, e.scope, inner)`: walk
  `scope_parent`).
- `namespace_member` uses it for its base (nested paths work as values too):
  a member that is a module in VALUE position is TYPE-007 "`m` is a module,
  not a value"; a type name likewise "is a type, not a value" (the identifier
  arm's sentence, reused — no new text); a function → `fn_type`; a global →
  its type. A member the module lacks stays `TYPE_NO_METHOD`'s "module `m` has
  no member `x`".
- `type_method_call`: FIRST `namespace_path(e, receiver)`; nonzero → look the
  method name up in `inner` (visibility, existence as above); it must be a
  `DeclFunctionDecl` (else TYPE-007 "`m.x` is not a function"); then type the
  call through the SAME path a direct call of a known function symbol takes —
  factor `type_call`'s known-function-symbol body into
  `type_direct_call(e, id, n, sym, arg_start, arg_count)` and call it from
  both (a second implementation of the call rule is the 1.3.3 `op=` mistake).
  It records `callee` and `callee_sym` as a direct call does and writes the
  new per-expression slot **`ns_callee`** (`expr_types.npk`: the callee's decl
  index; 0 for every other node). Contract context (`contract_method_refused`)
  and purity (`pure_method_rules`) treat a namespace call as the NAMED call it
  is (admissible when `pure never fails`).
- Every reader of an `ExprMethodCallExpr`'s RECEIVER asks `ns_callee` first
  and skips the receiver when it is set: the executor lists every
  `ExprMethodCallExpr` site in `src/` (`rg -n ExprMethodCallExpr src`) in the
  record, classified — the emitter (`emit_method_call`, ir_expr.npk:8469 →
  the direct path of `emit_call`, 6632, with the node's argument window and
  NO receiver; an awaited `async` member through the same await-site code a
  direct awaited call uses), the SMT encoder's call arms (`smt_encode.npk`:
  the callee's rows and `uf_value`), and the analyses (`bindings`, `escape`,
  `reach`, `suspend`, `locks`, `exhaust`, the purity walk, `macro/`) — each
  either skips the receiver or needs no change, said per site. A namespace
  call that any walker still treats as a value receiver is the defect this
  step exists to not leave.
- Tests: `inline_mod.npk` calls `hidden.fetch(3i32)` and exits 7 (its
  comment rewritten); `tests/backend/programs/mod_qualified.npk` — nested
  `core.math.sq(3i32)`, an alias `lib.f()` over a fixture module, a global
  `hidden.MAX`, an `async` member awaited, a `pure never fails` member in a
  `requires` clause, exit through the sum; `tests/types/rejection/
  mod_not_value.npk` (TYPE-007: `int32:x = hidden;`, `hidden.nosuch(1i32)`
  → TYPE_NO_METHOD, `hidden.MAX(1i32)` → "not a function");
  `tests/modules/rejection/mod_private_qualified.npk` (RESOLVE-004 through
  `hidden.internal()`); `tests/verify/req_qualified.npk` (a `requires` on a
  member called qualified: one `requires` row, `bypass`, discharged; the
  `failsafe-post` rows named). `nitpick.obligations` must not move (no call in
  `src/` is qualified); a moved manifest is red.

### Step 1 — `use` over a module path, the alias's scope, `std`

- `apply_one_import`: a logical path's first segment is looked up
  `scope_lookup_local` in the importing file's scope; a module symbol → walk
  the remaining segments through `inner` (each hop a module symbol, exported
  when reached from outside), then `bind_wildcard`/`bind_named` over the final
  scope with the dotted text as `target` for messages; `std` first → return
  as today; anything else → RESOLVE-002 "cannot find module `x` in this
  scope" (R-1). `apply_imports` runs two passes per file: file/alias forms,
  then logical (R-2).
- `bind_or_report` copies `inner` for a module symbol; the alias arm sets it
  to `src.scope`.
- D-239's `owned_name_error`: `std` for a module declaration and for a file's
  header (a `std.npk` in a program is refused at its header).
- Tests: `mod_qualified.npk` grows `use hidden.*;` (bare `fetch`), `use
  core.math.{sq};`, a struct type imported from an inline module and used in
  `main`, and a cross-file `pub mod` reached as `helpers.f()` after `use
  "./mod_helpers.npk".*;` (a fixture beside it, header `mod:mod_helpers;`);
  `tests/modules/rejection/mod_private_use.npk` (RESOLVE-004 via `use
  hidden.internal;`), `mod_use_unknown.npk` (RESOLVE-002 via `use nosuch.*;`),
  `std_declared.npk` (RESOLVE-001 for `mod:std = { … };`), and an
  order-independence pair in `tests/accept/` (`use lib.*;` above and below its
  alias). `whole_grammar.npk`'s `use std.math.*;` keeps parsing and binding
  nothing.
