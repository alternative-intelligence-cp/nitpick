## 2. What this subcycle builds, in one picture

```
Rules<int32>:r_pos = { $ > 0i32 };                 subject resolved; `$` : int32; clause : bool
Rules<int32>:r_small = { limit<r_pos>, $ < 100i32 }; the refinement RESOLVES to r_pos; subjects equal
func:f = int32(limit<r_pos> int32:n)                the limit resolves; r_pos's subject == int32
    requires n < 50i32                              : bool, evaluable anywhere (V-9)
    ensures result > old(n)                         `result` : int32; `old(n)` : int32, n copyable
{
    limit<r_pos> int32:m = n;                        the limit resolves; subject == int32
    while (m > 0i32) invariant m >= 0i32 { … }      : bool
    prove(m == 0i32);                                : bool
    pass m;
};
func:helper = int32(int32:v) never fails pure { … } what a contract may CALL (V-14, V-15)
```

Every line above is accepted in full silence at the close, and every way of
getting one of them wrong is a NAMED refusal at the stage that owns it:
an unknown or non-`Rules` name at resolve (RESOLVE-002 / RESOLVE-011), a
type disagreement at the checker (TYPE-059), a construct a contract may
not contain (TYPE-060), an effect inside a `pure` body (TYPE-061). The
emitter keeps refusing the whole family by rung until 1.5.2/1.5.3 give
each its lowering.

## 3. Decisions taken at planning (each with its reason; ratify or amend before the step that lands it)

Numbered V-1… so the record and the commit messages can cite them.
V-13, V-16, V-17, V-18 and V-19 read a ratified text one way where another
reading exists or add a spelling; each is one of §9's questions. Everything
else follows from D-220/D-221 and the tree as measured (§4).

- **V-1 — a `limit<name>` resolves through the ordinary scope lookup, and
  a miss is the ordinary miss.** `resolve_limit` runs `scope_lookup` from
  the site's scope (a local's block, a parameter's function scope, a
  `Rules` body's module scope) exactly as `resolve_ident` does for an
  identifier; a name found nowhere reports `NITPICK-RESOLVE-002` with the
  identifier's own sentence ("cannot find `r_pos` in this scope"), and a
  name that resolves to anything but a `DeclRuleDecl` reports the new
  `NITPICK-RESOLVE-011` naming what it is (`decl_kind_article`: "`limit<f>`
  names a function; `limit` takes a `Rules` block"). Reason: one lookup
  rule for every name in the language (blueprint facet 1); a typo in
  `limit<…>` is the same mistake as a typo anywhere and gets the same
  answer. The resolved `Rules` declaration is RECORDED on the
  `VerifyLimitNode`'s slot `a` (the `IdentifierExpr.a` precedent — resolve
  writes the binding once, every later pass reads it), through a new
  accessor `limit_target(v) → DeclId`.
- **V-2 — a `Rules` refinement stores its `VerifyId`, not a bare intern.**
  `p_parse_rules` pushes `l.index` where it pushed `limit_rule(ln)`;
  `rule_refine(ast, d, i)` returns a `VerifyId`; the name is
  `limit_rule(ast_verify(…))` as everywhere else. Reason: the refinement's
  SPAN is what a resolve error points at, and the node the parser already
  built carries it — discarding the node and keeping its name was the one
  place the surface threw information away. The only AST-window change in
  the subcycle; nothing else reads the window.
- **V-3 — a refinement cycle is refused at resolve, under RESOLVE-006's
  rule.** After every module resolves, `check_rule_cycles` walks each
  `Rules` declaration's refinements (fuel-bounded like `check_global_cycles`,
  the D-165 precedent it sits beside) and reports a declaration that
  reaches itself — once, at the declaration that closes the cycle, with a
  message naming the chain. Reason: 1.5.2 discharges a `limit` by expanding
  refinements into a conjunction and subsumption by an implication over
  the same expansion; a cycle would not terminate there, and "refuse the
  shape at the front" is cheaper and clearer than a fuel counter deep in
  the encoder. RESOLVE-006 IS the "a declaration may not depend on itself"
  rule (its message was written for constants; it gains a `Rules` sentence).
- **V-4 — the resolve audit covers limits.** `resolve_audit` counts every
  `VerifyLimitNode` whose slot `a` is 0 alongside its unbound-identifier
  count, and `tests/modules/resolvable.npk` declares a `Rules` and spells
  `limit<…>` at all three sites (a local, a parameter, a refinement).
  Reason: the audit exists because "a construct the walk forgets is
  invisible until 0.4 asks what it means" — the exact history of this
  surface, which the walk forgot for eleven cycles.
- **V-5 — `$` is the innermost enclosing construct's subject: a counted
  loop's counter, or a `Rules` body's subject.** One node
  (`ExprIterationVarExpr`), one meaning — "the value under consideration"
  — typed from `e.rules_subject` when the typer is inside a `Rules` body and
  from the counted-loop rule otherwise. The two constructs cannot nest (a
  `Rules` body holds expressions; a loop is a statement), so no reader has
  to remember which `$` this is. Reason: the grammar already spells the
  subject `$` (VERIFICATION §2, 0.2.5's parser); a second node for the
  same spelling would be two mechanisms for one idea.
- **V-6 — a `Rules` declaration types eagerly.** `check_decl` gains a
  `DeclRuleDecl` arm: the subject type resolves (a broken subject refuses
  even when nothing uses the rule — the D-196 `unit:` precedent), every
  clause is held to `require_bool` under the RULES contract context (V-9),
  and every refinement's subject must EQUAL this rule's by type identity
  — `NITPICK-TYPE-059`, the message showing both subjects. Any subject type
  is admitted: a predicate over a value is well-formed whatever the value
  is, and what the clause may DO is V-9's question, not the subject's.
- **V-7 — a limited binding's declared type equals the rule's subject by
  identity.** At a local (`check_var_decl`) and at a parameter (the
  parameter loop in `check_function`), the declared type must be the
  subject type — no widening, no `fits`, no `Optional` wrap, and no generic
  parameter (a `T:x` cannot carry `limit<r>` for a `Rules<int32>`; the
  template refuses and the author spells the concrete type). TYPE-059.
  Reason: D-220 injects the check at the binding's write points with the
  binding's own value; a rule over another type would need a conversion
  the author did not write, and "which conversion" is exactly the silent
  default the blueprint forbids. A `for` binding cannot carry a `limit`
  (the parser builds a bare `ParamDecl` there) and this plan leaves that
  so: a counted binding already carries its bound.
- **V-8 — every proposition is a `bool`, through `require_bool`.** The
  `requires` and `ensures` conditions, each `invariant` conjunct, each
  `Rules` clause, and the operands of `prove` and `assert_static` — the
  same check and the same sentence every `if` gets. `prove`/`assert_static`
  come off the `stmt_carries_expr` fall-through in `check_stmt` into their
  own arm for exactly this. Reason: "one rule with no exceptions to
  memorize" — a proposition that is not a `bool` is not a proposition.
- **V-9 — the contract context, and what it refuses.** `ExprTyper` gains
  `contract_ctx` ∈ {0, REQUIRES, ENSURES, INVARIANT, RULES, PROVE} (set
  around each contract expression's typing and restored after) and
  `rules_subject` (V-5). Inside a nonzero context `type_of_expr` refuses,
  by node kind and by name under one code `NITPICK-TYPE-060` (the TYPE-054
  convention — one rule, several ways to fail it, the message says which),
  returning the invalid type so no second sentence follows (D-240):
  `await` (a contract does not suspend); `move` (it does not consume);
  `relay`, `?!`, `?|`, `drop`, `is_err` and a BARE may-fail call (a contract
  is a proposition, not an outcome — the one call form is `raw f(…)`, and
  `f` must be `never fails` [this subcycle's step 2] and `pure` [step 4,
  V-14]); a `pick` EXPRESSION (its arms are statement blocks — assignments,
  `give`s — which no expression-level rule can bound); `old` outside
  `ensures`, nested, of `result`, or of a non-copyable value (V-17). Admitted:
  every literal, identifier, `$` (V-5), `result` (V-10), member access,
  indexing, `<-` reads, `@x`/`$$i` borrows as call arguments, the arithmetic
  and comparison operators, `is (c) : a : b`, casts, `comptime(…)`,
  `raw f(…)` under the callee rule, struct/array literals. Reason: D-221's
  purity sentence names the property — "a contract that can fail or
  suspend is a contradiction in terms" — and this is that sentence made
  checkable at the site rather than remembered.
- **V-10 — `result` is the function's SUCCESS type, in `ensures` only —
  and it becomes a keyword with a LEAF node (§9, S-18).** Today `result`
  is "an ordinary identifier here, given meaning by the verifier"
  (parse_decorate.npk:219): the resolver exempts an UNBOUND `result` inside
  `ensures` (`resolve.npk:135`) and nothing types it. Two things are wrong
  with that spelling, and the SMT side raised the second: (1) a parameter
  named `result` BINDS first, so inside its own function's `ensures` the
  word means the parameter, not the return value — one spelling, two
  meanings by what else was declared, the blueprint's first facet broken;
  (2) 1.5.3's encoder would meet an `IdentifierExpr` with no binding and
  treat it as opaque, and re-matching it by name-in-context is the fragile
  path. The prototype RESERVED `result` (RESERVED_WORDS.md, "Borrow &
  Safety": `is requires ensures invariant result`), and D-221 gives the word
  exactly one meaning. So: `result` joins VerificationKeyword, parses to
  `ExprResultValueExpr` — a leaf like `$` (`ExprIterationVarExpr`), shape
  LEAF, no operand — and the checker types it as `e.fn_success` under
  ENSURES and refuses it anywhere else (TYPE-060: "`result` is the return
  value, and only `ensures` has one"). The resolver's exemption and the
  audit's excuse retire; `tests/frontend/resolve.npk`'s "a stray `result`
  is refused at resolve" case moves to the type suite. The token needs a
  name the generator does not derive: `Result` already owns `KwResult`, and
  the title-case derivation would collide — `gen_tables.py` gains an
  explicit-name map (`"result" → "KwResultValue"`), the one keyword whose
  token name is not its spelling. The measured rename cost is in §4 (~110
  identifier sites, all one FIELD name). Step 2 types `ensures` under the
  identifier spelling with a five-line arm (an unbound `result` under
  ENSURES types as `fn_success`) so steps 1–2 wait on nothing; step 3
  replaces that arm with the node's. If S-18 is answered the other way,
  the fallback is the SMT side's second option: the typer records every
  `result` occurrence's `ExprId` per function on `ExprTypes` (a mark, the
  `owning_decl` shape) and the resolver REFUSES a parameter or local named
  `result` in a function that carries an `ensures` — the name wins or is
  reserved; nothing in between.
- **V-11 — a loop's invariants are typed in the loop's arm of
  `check_stmt`**, before the body, under INVARIANT, each conjunct through
  `require_bool` (V-8); a `for`'s binding and a counted loop's `$` are in
  scope there (the resolver already binds them from the inner scope).
- **V-12 — `prove(e)` and `assert_static(e)` are typed as propositions
  under PROVE** — a `bool` operand, the V-9 rules. Whether an
  `assert_static` FOLDS is 1.5.4's (the frontend fold); whether a `prove`
  HOLDS is 1.5.4's obligation. Typing the operand is the surface, and the
  surface is this subcycle's.
- **V-13 — D-163 rule 2's contract row retires (§9, S-14).** The row
  ("`requires` / `ensures` / `limit<Rules>` on the function or its
  parameters — a contract that can be violated at runtime is a failure
  channel. **C-15/C-16 decide which**") delegated the channel to C-15/C-16,
  and D-220/D-221 decided it: the TRAP route, never a `Result`. A
  `never fails` body already admits that channel — `?!`, D-210's overflow
  trap, D-007's division trap — so the row's basis is gone, and keeping it
  would bar contracts from exactly the functions contracts may CALL (V-14:
  `never fails` and `pure`). `TYPE_NEVER_FAILS_CAN_FAIL` keeps its other
  rows (`fail`/`relay`/`return`, `async`, the terminal clause);
  `tests/types/rejection/never_fails.npk` loses `with_requires` and one
  expectation, and `tests/accept/never_fails.npk` gains `never fails
  ensures result >= 0i32`. Lands in step 5 once ratified; steps 1–4 run
  under the row as it stands.
- **V-14 — purity is DECLARED, never inferred (§9, S-15).** `pure` is a
  contract clause in the `never fails` shape: a keyword (VerificationKeyword),
  a marker in the contracts window (`VerifyPure`, `VerifyKind` 7,
  `fn_declares_pure`), checked MODULARLY in the body (V-15, TYPE-061) and
  read by name at direct call sites. Contract expressions (V-9) and `pure`
  bodies admit only NAMED callees — a direct call to a function or a
  method whose declaration is visible; a call through a function value or
  a `dyn` is refused there ("the callee is not known at the site") — so
  purity never rides a function TYPE and D-163 rule 8's identity question
  (interning, mangling, assignability) does not reopen. D-163's
  rejected-alternatives paragraph applies verbatim: inference is implicit
  (a store added deep in a callee silently changes which distant contracts
  are legal, with the error far from the cause), non-modular (a fixpoint
  to verify instead of a walk over kinds), and unreadable at the
  declaration. `pure` and `never fails` are ORTHOGONAL words — a pure
  function may `fail` (a checked division helper refuses a zero divisor);
  a contract needs both, and writes both.
- **V-15 — what a `pure` body may not contain** (the checkable meaning of
  D-221's "no allocation, no I/O, no suspension" plus "no effect its caller
  can observe"), refused under `NITPICK-TYPE-061`, the message naming
  which: (a) a call to a callee not declared `pure`, a call through a
  function value or a `dyn`, or a builtin the `Pure` column marks `effect`
  (V-16); (b) `await`, the spawn form (`drop` of an `async` call),
  `channel()`, any method on a `Mutex`/`RwLock`/`CondVar`/`Barrier`/
  `atomic`/channel endpoint receiver (a lock or an atomic READ is a read of
  shared mutable state — the result would not be a function of the
  arguments), `sys`, and a `wild`/`wildx`-qualified declaration; (c) an
  assignment whose target is not a LOCAL place — a `<-` dereference, or a
  field/index reached through a pointer or borrow (a store the caller can
  see); (d) a `move` parameter (the consumed owner is dropped at exit — a
  deallocation) or a local of an owning type (`type_drops`: its scope-exit
  drop is generated code with effects; a `string` PASSED in is fine — the
  callee does not own it, D-183 §4); (e) `pure` on `async`, `thread`,
  `main` or `failsafe`; (f) an impl method dropping its trait method's
  `pure` (the `TYPE_NEVER_FAILS_IMPL` direction: the implementation may not
  claim less than the trait promised; a `dyn` call reads the trait's word).
  Permitted: reads of everything, `fixed` globals (constants by D-211),
  `comptime`, arithmetic (its traps are Layer 3), `!!!`, `defer` whose body
  obeys the same rules, `pick`. The check is D-163 rule 2's shape — a flag
  on the typer (`fn_pure`) read in the arms that already exist for calls,
  assignment, `await`, declarations — no new walk.
- **V-16 — builtins declare their purity in the one signature table.**
  `BUILTIN_REFERENCE.md`'s marked region gains a fifth column, `Pure`
  (`pure` / `effect`), `gen_tables.py` reads it (the cell count moves from
  six to seven, and a row without the column hard-fails the generator as
  every other malformed row does), `builtins.npk` gains `builtin_pure(name)`
  (the `builtin_never_fails` shape, D-163 rule 9). The classification rule,
  applied to each row's IR body or inline lowering, never its prose: `pure`
  iff it allocates nothing, makes no syscall, stores nothing outside its own
  frame, suspends nothing, and reads no mutable shared state. Expected:
  `#ptr_add`, `#sqrt`, the comparisons and measurements (`string_eq`,
  `string_bytes`-style views, `string_from_bytes`), the numeric helpers →
  `pure`; the allocator family, every string op that builds a new body
  (`string_concat`, `string_slice` — D-186's owned copy — `int_to_string`),
  `buffer_new`, the descriptor and file surface, `environ`, `sys`, the
  suspension primitives, `wildx_*` → `effect`. The executor classifies at
  step 4 and records the table in the record; a disagreement with the IR

- **V-17 — `old(expr)` is a keyword operator with its own node (§9,
  S-16).** `old` joins VerificationKeyword (`KwOld`); the parser's
  keyword-operator group (`move(place)`, `comptime(expr)`, `is_err(x)`)
  gains `old` `(` expr `)` → `ExprOldExpr`, operand in slot `a`, shape ONE

  measured every walker's default). D-096's reasoning is the reason: a
  call that is not a call ("`old` resolves to nothing and the checker
  recognises the name") confuses every reader and every tool, and the
  language already answered that question for `is_err`. Typing (V-9's
  context): legal only under ENSURES; not nested; its operand may not be

## 4. Measurements the plan rests on (made 2026-09-03 on `950bb1d`)

- **What the surface is today, site by site.** `DeclRuleDecl`: parsed
  (`p_parse_rules`: subject `TypeId` in `a`, window `[refines, clauses,
  refined-name INTERNS…, clause ExprIds…]`), collected as a symbol, its
  clauses RESOLVED in the module scope (`resolve.npk:675`), its subject
  never resolved, its clauses never typed (`check_decl` has no arm),
  refinements never resolved (interns, no node). `VerifyLimitNode`: built by

   body like `never fails` and read by name at direct call sites, with the
