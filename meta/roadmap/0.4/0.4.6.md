# 0.4.6 — Traits and impls

**Cycle 0.4 — Type system and checking.**

## Goal

`trait`, `impl`, coherence, object safety, and associated types.

## Work

1. A trait's methods, its supertraits (joined by `&`, D-029), and its `assoc`
   types with their defaults (D-028).
2. `impl:Type` and `impl:Type:Trait` — the type is always slot one (D-031).
3. An impl must supply every method the trait declares without a default, and may
   not add ones it does not.
4. **Coherence: at most one implementation of a trait for a type**
   (`TRAITS_REFERENCE.md` §4.1). Overlapping implementations are an error naming
   both.
5. **Object safety** (§4.2). `dyn Trait` requires: every method takes `self`; no
   method returns `Self`; no method has comptime type parameters. A non-object-safe
   trait used as `dyn` is an error naming **which rule** it broke.
6. `Self` inside a trait or impl body resolves to the implementing type.
7. Blanket impls — `impl:<T: Printable>:Loggable` (D-031).

## Watch for

**Object safety is three separate rules and the diagnostic has to say which.**
"Trait is not object safe" sends the reader to re-derive it; "method `new` takes
no `self`, so `dyn Drawable` cannot dispatch it" does not.

## Done when

- A missing method, an extra method, and an overlapping impl are each refused.
- Each object-safety rule is tested separately and names itself.
- `Self` resolves, and is refused outside a trait or impl.

## Outcome — DONE

`src/frontend/type_trait.npk` — the impl table, coherence, method lookup, impl
completeness, and `dyn` assignment. Object safety lives in `resolve_type.npk`
beside the `dyn` resolution it guards.

**All seven plan items are done.** D-102 covers the impl table, method lookup and
coherence; D-103 covers completeness, `assoc`, `Self`, object safety and `dyn`
assignment; D-105 covers supertraits and blanket impls; D-106 closes the
duplicate-name question D-102 opened by allowing two inherent blocks.

### Two things the plan did not predict

**A method declared in an `impl` could not be called at all** (D-102). `impl`
declares nothing at module scope and `type_method_call` looked names up in the
scope, so UFCS reached only module-level free functions. The 0.4.5 UFCS tests
passed because their fixture declares `magnitude` at module scope — which is the
one form §2.4 does not use.

**`resolve_named` treated every type name as possibly a token kind** (D-104). A
program's 88th distinct identifier, used as a type name, resolved to `int32`
silently. Found because a two-trait `dyn` reported both of its perfectly good
traits as "not a trait": they had been interned late enough to land in the keyword
range. This is D-096's defect at its root — that decision fixed the symptom for
`Result` and left the representation.

`dyn` assignment was also missing outright: §5.2's own example
`dyn Serializable:obj = msg;` had no rule admitting it.

**Supertraits and blanket impls closed by D-105.** Supertraits had parsed since
0.2 and nothing read them; they are enforced now, transitively, with a fuel bound
because a supertrait cycle is something a program can write. The blanket impl form
**did not parse at all** — a D-085 violation, since the frontend takes the whole
grammar from day one — and was absent from `tests/grammar/`, which is why nothing
caught it. Both are fixed; blanket impls are recorded and left for 0.4.7, which
owns bound satisfaction.

### Four of seven items were repairs, not construction

| Found | Had been true since |
|---|---|
| a method in an `impl` could not be called at all | cycle 0.3 |
| supertraits parsed and nothing read them | cycle 0.2 |
| a blanket impl did not parse | cycle 0.2 |
| a type name could resolve to `int32` | cycle 0.4.1 |

**Three of the four survived because the thing meant to catch them did not cover
the case.** The 0.4.5 UFCS tests declared their method at module scope — the one
form §2.4 does not use. `whole_grammar.npk` lacked the blanket impl. And
`tests/grammar/` never resolves anything, so no corpus could have caught the name
collision. Standing lesson for 0.4.7 and 0.4.8: **write each test from the
specification's own example**, and treat a construct missing from
`whole_grammar.npk` as a construct nothing checks.

### Carried to 0.4.7

**Blanket impl semantics** — which types one applies to, and concrete-wins
priority (§2.6). They parse and are recorded; bound satisfaction and
monomorphization are 0.4.7's, and finding them is what the table is for.
