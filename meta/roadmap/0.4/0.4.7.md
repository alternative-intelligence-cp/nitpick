# 0.4.7 — Generics

**Cycle 0.4 — Type system and checking.**

## Goal

A generic body checked **once**, at its definition (D-064).

## The rule, and why it is not a preference

**A generic body is type-checked once**, treating each parameter as an opaque
type satisfying exactly its declared bounds and **nothing else**. Instantiation
checks only that the arguments satisfy the bounds; the body is never re-checked.

The consequence to implement deliberately: **a body may not use any capability
its bounds do not declare. There is no duck typing.**

The reason is not elegance. **Astrée analyses monomorphized output**, so a body
that happens to be correct for the instantiations a program contains may still be
wrong in general — and the single verification run (see
`astree-verification-one-shot-constraint`) is the worst possible place to
discover it. Checking at the definition is what makes the property hold for
instantiations nobody has written yet.

## Work

1. Type parameters with bounds, combined by `&`.
2. **Value parameters** — `<comptime int32:LEVEL>` (D-064). Not a type, and the
   `comptime` marker is what keeps the two readable apart.
3. Definition-time checking: inside the body, `T` satisfies its bounds and nothing
   more. Every use of a capability is checked against the bound list.
4. Instantiation: arguments checked against bounds, at the call and in a type.
5. **Inference** at the call site — `TRAITS_REFERENCE.md` §3.3 says nothing is
   written at the overwhelming majority of them.
6. Monomorphization bookkeeping: **depth-capped at 64, deduplicated, reversibly
   mangled with no hash** (D-064). The cap is what makes expansion terminate.
7. Turbofish is the only expression-position form for explicit arguments; bare
   `f<T>(x)` is two comparisons (D-064, and the parser already agrees).

## Inherited from 0.4.6

**8. Blanket impls** — `impl:<T: Printable>:Loggable` (D-105, §2.6). They **parse
and are recorded** in the impl table; nothing decides which types they apply to.
That is bound satisfaction, which is item 4, so it lands here rather than there.

Two rules come with it, both already written down and neither yet enforced:

- **Concrete impls take priority** over blanket-generated ones (§2.6). D-102 built
  the same precedence for inherent-over-trait method lookup, so this extends an
  existing rule rather than introducing one.
- A blanket impl is deliberately **not** a coherence conflict with a concrete one
  (D-105) — overlapping is the point. Once bound satisfaction exists, *two blanket
  impls whose bounds can be satisfied by one type* becomes a real conflict, and
  that is the coherence question this subcycle actually has to answer.

`Self` inside a blanket impl is the parameter, not a concrete type. D-103's
signature comparison substitutes one level; check that it does the right thing
here before assuming it carries over.

## Watch for

**The test that matters is a body using something its bounds do not declare.** It
must be refused *at the definition*, with no instantiation anywhere in the
program — that is the whole property, and it is invisible to a test that only
instantiates.

**Write each test from the specification's own example.** Four of 0.4.6's seven
items were repairs, and three of those survived because the thing meant to catch
them did not cover the case — a UFCS test declaring its method at module scope,
the one form §2.4 does not use; `whole_grammar.npk` missing the blanket impl
entirely. A construct absent from that corpus is a construct nothing checks the
parser against.

`tests/grammar/` is **parse-only** and resolves nothing, so it cannot catch a
resolution defect at all. D-104 — a type name silently resolving to `int32` — got
past every suite for that reason.

## Done when

- A body using an undeclared capability is refused with no instantiation present.
- An instantiation violating a bound is refused, naming the bound.
- Depth-capped expansion terminates and says so when it hits the cap.
- A blanket impl applies where its bound is satisfied, a concrete impl outranks
  it, and two overlapping blanket impls are refused naming both.

# What happened

### Items 3 and 1 — bounds, and the definition-time check (D-107)

The bound table sits beside the impl table and stores the **transitive closure**
of each parameter's bounds, so `T: Ordered` where `Ordered = Equatable & { … }`
lets a body use `Equatable`'s methods. The closure must not repeat a trait: `T:
Equatable & Ordered` reaches `Equatable` twice, and two copies read as two bounds
declaring one name, so every method of `Equatable` would report as ambiguous on a
correct program.

Three rules the plan did not spell out, all settled in D-107:

- **`find_method` answers a parameter from its bounds, not from the impl table.**
  Asking the impls *would be* duck typing, arrived at by omission.
- **UFCS does not reach a free function through a parameter.** A free function
  taking a `T` is a capability the surrounding module happens to contain, not one
  `T` declares — and reaching it would compile the body and break at an
  instantiation, reported against a caller who supplied a reasonable type.
- **A `comptime` value parameter is not a type**, refused by name where a type
  belongs.

A parameter resolves from the **declaration** rather than from a scope, because it
is not reliably in one: the checker walks a body holding the module scope, and a
struct's parameters are declared into no scope at all. The same structure carries
both halves of D-064 — unbound is the definition, bound is an instantiation.

**One repair.** A method's signature is resolved with `Self` bound to the
receiver. A trait declares its methods in terms of `Self` and nothing else, so a
signature resolved without it reported "`Self` is valid only inside a `trait` or
`impl` body" at a call site inside neither. Reachable since 0.4.6 through an impl
method written with `Self`; the bound path cannot avoid it.

### Items 4 and 6 — instantiation, identity, and the cap

`Container<int32>` and `Container<string>` were **one type**: the arguments had
parsed and been stored since 0.2 and nothing read them, so a field of type `T` had
nothing to substitute and `c.value` answered "there is no type named `T`".

**An instantiation's identity is its interned mangled name.** `tt_intern` compares
every slot and an argument *window* cannot be compared that way — two spellings
commit two windows at two starts — so field equality would make one instantiation
two types, and `type_eq` is an integer compare everywhere else. Keying on the name
is sound because the name is a total function of the declaration and the
arguments. It is also the display name, so every diagnostic says which
instantiation without anything extra, and it is reversible with no hash.

**Bound satisfaction is a pass, not a check at the annotation.** `resolve_type`
runs during collection, when the impl table is still being filled, so "does `Point`
implement `Printable`" would answer `false` for an impl recorded on the next line.
The resolver records every instantiation with the span it was first written at,
and the pass decides afterwards. Arity stays at the annotation, because counting
needs nothing but what was written.

**One repair, in the parser.** `p_looks_like_decl` scanned at most 64 **tokens** to
tell `Container<int32>:c;` from a chain of comparisons, while D-064 caps
instantiation at 64 **levels** — and a level costs three tokens. A declaration
could sit well inside the type system's limit, outrun the scan, and silently
reparse as an expression: D-104's failure one layer up. The budget is now 512,
above the deepest type the checker accepts, so the depth cap is the binding limit
and says so; exhausting even that is now a diagnostic rather than a wrong answer.

### Two gaps this surfaced, both older than this subcycle

Neither is created here and both are now load-bearing, so they are recorded rather
than left to be rediscovered.

**A declaration nothing reaches is never type-resolved.** 0.4.5's own fixture says
so — "a case testing a bad signature has to CALL the function". A bound violation
in an uncalled signature therefore goes unreported. Fixing it means resolving every
declaration's types unconditionally, which double-reports every signature error for
declarations that *are* reached — so it needs `diaglist_push` to deduplicate
identical diagnostics first. **Both belong to 0.4.8**, which owns diagnostics and
the driver; they are one coherent change there and two half-changes here.

**No struct ever gets a layout.** `struct_layout` exists, nothing calls it, and it
could not work if it did: `tt_intern` ignores `size`, so re-interning with a
computed size returns the original zero-sized entry. Every struct is size 0, which
makes `Result<Point>` four bytes instead of sixteen. It needs a `tt_set_layout`
writing in place plus an ordering pass — the ordering is guaranteed acyclic, since
`module_graph.npk` already refuses containment cycles. **0.4.8.**
