# 0.9.3 — Wide integers, the `__divti3` family, and the alignment correction

**Cycle 0.9.** Integers wider than 64 bits — `int128`/`uint128` through
`uint4096` — and the runtime symbols LLVM emits for their division. This subcycle
also resolves a three-way representation contradiction that lands exactly here, and
corrects a memory-corruption-class alignment disagreement.

## Decision resolved here: native `iN`, not LBIM (below 256 bits)

The audit found a three-way contradiction (total_audit Theme D): `TYPE_REFERENCE §4`
says wide integers are LBIM limb-structs "working around LLVM backend bugs"; `§6`
(same document) and **D-011 (settled, with measurements)** say native `iN`; the 0.9
scope line and an `ir_types.npk` comment follow the dead LBIM reading.

**D-011 is authoritative and its measurements are on this toolchain:** `add i128` =
5 instructions no libcall, `add`/`mul i256` inline, and only *division* emits a
libcall (`__divti3` for exactly `i128`, inline for `i256`). So:

- **Lower `int128`/`uint128` and `tbb128`/`tbb256` to native LLVM `i128`/`i256`.**
  Do **not** hand-roll multi-limb add/sub/mul — the intrinsics are correct,
  dependency-free, and better than hand-written sequences (D-011 §1).
- **The `{i64,i64}` / `{i64 x N}` in TYPE_REFERENCE §4/§6 describe storage layout**,
  which native `iN` already matches. Correct §4's "works around LLVM bugs" text and
  the `ir_types.npk:183-185` comment in the same subcycle (they are factually
  contradicted by D-011's own measurements).
- **Above native width** (LLVM caps practical native integers; `uint4096` is beyond
  it), lower to limb arrays with hand-written IR routines — but only there, and only
  the operations that don't lower natively.

## The `__divti3` runtime family (D-011 §2)

`sdiv`/`udiv`/`srem`/`urem` on `i128` emit calls to `__divti3` / `__udivti3` /
`__modti3` / `__umodti3` — libcalls the floor does not provide, and exactly the
zero-dependency violation the 0.8.2 undefined-symbol scan exists to catch. It
**will fail the build by name** the first time this subcycle emits an `i128 sdiv`,
which is the scan working as designed (0.8.2 was scheduled precisely so this could
not ship silently).

Provide the four as **hand-written LLVM IR** in `npkrt.ll` (D-015 discipline),
shift-subtract long division, TCB code under the same verification obligation as the
rest and under the three-way signature diff. Consult the prototype for *algorithm*,
rewrite C-free (D-015 "consult for approach, never copy through"). **Measure `i256`
division** before shipping the inline expansion (D-011 §4: 287 inline instructions
is correct but a purpose-written routine may beat it — do not assume either way).

## The alignment correction (type-sys #5, memory-corruption class)

Three sources disagree on 128/256-bit alignment: `TYPE_REFERENCE §4/§6/§5` say 8,
`src/frontend/types.npk:303-327` computes `bits/8` (→ i128 align 16, i256 32, i4096
512), and LLVM x86-64 says i128 align 16 (capped there). The frontend's struct
layout uses these aligns, so disagreement with the target datalayout **corrupts
memory** (the file's own warning, types.npk:297-302). Publish **one alignment
column per width matching the LLVM x86-64 datalayout** (i128 = 16, capped) in
TYPE_REFERENCE, and make `tt_int`/`tt_tbb`/`tt_float` read it. This is corrected
here rather than in the doc-sync pass because it is load-bearing for layout, not
cosmetic.

## Tests

`tests/backend/programs/wide_int.npk`: `i128` add/mul (native, no libcall — verified
by the undefined-symbol scan staying green after the `__divti3` symbols land),
`i128` division (exercises `__divti3`), `i256` division, and a `uint4096` shift the
crypto path relies on (D-037 wrapping). A struct embedding an `int128` field, read
back, proving the alignment is right (a wrong align reads garbage or faults).

## Done when

Wide integers lower natively below the LLVM cap and via hand-written IR above it;
the four division symbols exist, pass the three-way diff, and clear the
undefined-symbol scan; the alignment column is corrected and `tt_int`/`tt_tbb`/
`tt_float` read it; TYPE_REFERENCE §4 and the `ir_types` comment no longer describe
LBIM as the representation.
