# 0.9.1 — Two instruments, before the bulk lowering

**Cycle 0.9.** The audit that produced this plan was a manual run of the check 0.6
proved most effective: diff the compiler against the thing that describes it. Its
findings should not need finding twice. Two standing checks — in the house style of
`check_kinds_reachable` (0.2), `check_kinds_typed` (0.6.3), and `check_codes_tested`
(0.6.6), each of which found something on its first run — go in **before** 0.9's
large lowering additions, so the diff is watching while they land.

## Instrument 1 — `check_kinds_lowered_or_refused`

### What it diffs

The AST expression/statement kind list against the **backend walk**. Every kind
must resolve to exactly one of: it lowers (the emitter has a real case), or it emits
`NITPICK-RUNG-001` naming a cycle. A kind that does *neither* — that falls through
to a default, a no-op, or a silent drop — is the third outcome D-085 forbids, and
this check names it.

### Why it would have caught this cycle's safety repairs

Every Theme-A hole is a kind in the third outcome: `limit`-carrying declarations
(dropped), integer division (bare emit), int⇄tbb casts (no-op fast path), inline-
`mod` members in `emit_all` (shed). `check_kinds_typed` found eight untyped
expression kinds on its first run in 0.6.3 by exactly this method; there is no
reason the backend should be less instrumented than the type checker. Run it and it
lists today's holes on day one — which is the point of building it before the cycle
that would otherwise add more.

### Shape

A whole-tree harness check (like the existing three), not a test. It walks the kind
enumeration and, for each, confirms the emitter dispatch reaches either a lowering
arm or an `iv_rung` call — the mechanism can be a maintained table (kind → lowered |
rung "N") that the check diffs against the emitter's actual dispatch, refusing on
any kind present in one and not the other. The table is the description; the emitter
is the compiler; the diff is the instrument. First run is expected to fail, listing
the Theme-A holes; 0.9.0 and 0.9.6 clear them, and the check holds the line after.

## Instrument 2 — `check_decisions_current`

### What it diffs

`DECISIONS.md` against its own consistency: a `## D-NNN … SETTLED` heading whose
"blocks X" or "settle before Y" clause names a cycle already in `done/` is stale
(the block was resolved or the deadline passed); a decision heading marked OPEN
whose work is demonstrably landed is stale; a decision superseded by a later
D-number with no in-place marker misleads a targeted reader.

### Why

Theme F of the audit is ~15 such staleness instances, several of which actively
mislead — D-129 still "OPEN, scheduled 0.6.7" though landed; D-114 says "settle
before Phase B" while `OPEN_DECISIONS` silently demoted it, with neither document
annotated; D-030 shows superseded `impl:...:for:` syntax. An implementing agent
trusts the decision log — it is the authority — and a stale entry sends it to build
the dead design. This check makes the doc-sync backlog (OPEN_DECISIONS §6)
**self-reporting**, so it is drained once and does not silently regrow.

### Shape

A lint over `DECISIONS.md` headings and their cross-references: flag any SETTLED
decision whose blocks/settle-by clause cites a `done/` cycle; any OPEN decision
whose code/construct is now implemented (cross-check against the codes modules and
the kind tables); any "superseded by D-NNN" relationship missing an in-place banner.
It cannot judge prose semantics, so it reports *candidates* for a human pass rather
than failing the build — the same posture as a spell-checker, not a type checker.
Its first run drains the Theme-F backlog into a worklist; thereafter it fires when a
new decision supersedes an old one without marking it.

## Scope discipline

Neither instrument is a substitute for the whole-suite harness, and both say so in
their output, the way `--only` and `quickcheck` already do. They are diffs, and a
diff proves the cases nobody thought to write — which is exactly and only what the
manual audit did once by hand.

## Done when

- `check_kinds_lowered_or_refused` runs on every full harness invocation; its first
  run enumerates the Theme-A holes; 0.9.0's repairs move `limit`/contracts/division
  from "third outcome" to "refused"/"lowered", and the remaining two (tbb cast,
  inline-mod) are ticketed to 0.9.5/0.9.6.
- `check_decisions_current` runs on every full invocation; its first run produces
  the Theme-F worklist; the doc-sync pass (0.9.8) drains it.
- Both are documented in `CLAUDE.md`'s instrument list beside the existing five, so
  a future maintainer knows the backend and the decision log are now diffed the way
  the parser and type checker already are.
