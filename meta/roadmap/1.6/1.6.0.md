## 0. What 1.6.0 is, and is not

It is a MEASUREMENT with a decision at the end. It builds three tools at
pinned commits outside the tree, prepares one fixed set of inputs from the
compiler under test, runs every engine over every input under one fixed
option profile per engine, twice, and writes the numbers down; then the user
ratifies the engine the numbers name (S-102, asked when the numbers exist).
It lands documents, decisions and the gate's own scripts under
`meta/roadmap/1.6/tools/` (the `../done/1.5/tools/` precedent: committed,
outside every gate, built into nothing).

It is NOT: a harness stage (1.6.1's), a `nitpick.toml` change (1.6.1's
pinned-tool table), an emitter change (a `target datalayout` line, if the
gate finds an engine needs one, is 1.6.1's — §2.2 (4) says how the gate
measures without it), a floor byte, a `src/` byte, an alarm ledger (1.6.1's),
or a port of either engine. The one thing it may change in an engine is a
one-line demotion of an abort into a warning where the abort stops a
measurement (§2.3 (5)), recorded as a patch whose sha256 is part of the pin,
and only if S-101's rule for patches is ratified.

**NIKOS, probed as it stands** (the Debug build, then a Release build of
v2.4.0 in a worktree — 36 s on 40 cores — for the timings):

- `ikos-pp -opt=basic -entry-points=main` then `ikos-import` accept
  `dyn_slots`'s bitcode (`llvm-as-20`) with the warning "input module has
  no debug information"; `ikos-analyzer -a=boa,dbz,nullity,uva,sio,uio,shc,poa
  -d=interval --entry-points=main --proc=inter` answers in **0.04 s, 18 MB**:
  **1,086 checks ok, 53 warning, 134 unreachable, 0 error**, over 12 of the
  28 functions. Every warning is a pointer with "no points-to information"
  — the result of `@npk_alloc_managed` (an external call: the floor's
  allocator is unknown to it) and the vtable slots read through it — or
  "pointer may be null" on the same. The 134 "unreachable" are checks INSIDE
  analyzed functions (93 in `main`, 16 in a drop body, 8 in `speak`, …) that
  the analysis marked dead — the indirect vtable calls whose pointer had "no
  points-to information" are among them (`check_mem_access(call %…(%d))
  [unreachable]`). Whether an unresolved indirect call is treated as dead
  (a vacuous "ok" for everything past it — an UNSOUND reading if the call
  runs) or as an unknown call is read at step 3 before any NIKOS count is
  trusted (§2.3 (4)); the controls of §2.4 (c) and (g) reach their defects
  through exactly such calls in one variant each.
- **Determinism**: without `--name-values` the check lines name variables by
  ADDRESS (`%0x56deaaf45e40`), different every run; with it, two runs are
  byte-identical (`diff` rc 0). `-j` exists (threads); `-j 1` is pinned.
  The output is an SQLite database (`checks`, `statements`, `functions`,
  `call_contexts`, `memory_locations`, `operands`, `settings`, `times`) —
  `ikos-report` needs the python virtual environment `make install`
  creates; `sqlite3` reads the tables directly (§6). No file, line or
  column exists for any check (all NULL: no debug info), so an alarm's
  identity is (function name, statement, kind).
- **It has NO model of `llvm.*.with.overflow`** — the string appears
  nowhere under `frontend/`, `analyzer/` or `ar/` — and **none of
  `llvm.assume`** (only `__ikos_assume`). An unknown external call is
  havoc: the value after every `+ - *` of ours is top, and D-218.9's
  channel does not reach it. Inline asm: the importer has a branch for
  `llvm::InlineAsm` (function.cpp:1799).
- **Over the compiler's own emission (3,392 functions): the preprocessor
  takes 1.8 s, the analysis 6.2 s and 448 MB — and reaches ONE function.**
  `npkc`'s `main` is an executor-driven coroutine: after the preprocessor,
  its 36 lines call `@npk_exec`, `@npk_rq_push` and `@npk_run_until` and
  nothing else — the body is handed to the floor as a function pointer in
  the run queue and driven by the floor's resume loop (D-177/D-178). With
  the floor absent, nothing past `main` is reachable from `main`; with the
  floor present, reachability depends on the pointer analysis resolving the
  executor's indirect resume call through the queue. `-opt=none` changes
  nothing (8.9 s, 692 MB, the same one function). So the gate defines
  "whole program" precisely (§2.2 (2)) and measures BOTH procedurality
  modes — `--proc=intra` ("every function with a body is analyzed
  separately", USAGE.md) is the honest per-function evidence for an
  emission of this shape, and inter-procedural reach through
  `npk_run_until` is its own row.
- **Whole-program preparation: `llvm-link` is the wrong tool.** Linking
  `dyn_slots` with `runtime/npkrt.ll` drops 25 of the floor's 187 defines —
  `npk_start_main` among them, the floor's IR entry (reached from
  `npk_start` only through the `module asm` stack switch, `npk_switch_stack`,
  as a function-pointer argument) — so the analyzer then reports "could not
  find function 'npk_start_main'". Text concatenation works: strip from the
  program the `declare`s of symbols the floor defines (89 in `dyn_slots`),
  strip from the floor the `declare`s of symbols the program defines
  (`main`; it is `invalid redefinition of function 'main'` otherwise), keep
  ONE `target triple`; the result (215 defines) assembles under LLVM 18 and
  20. The floor's IR roots are the functions whose address is taken by the
  assembly or the kernel: `npk_start_main` (the main thread after the stack
  switch), `npk_thread_entry` (a spawned thread's first IR function), the
  signal handlers installed through `rt_sigaction`, the failsafe path —
  enumerated by the input script from the floor's own text (§2.2 (2)), and
  `main` for the program-only form.

**Clam, probed after a build** (master `e80f9745` of 2026-09-10 against
`llvm-18-dev` 18.1.3 and `clang-18`, with crab `dev` `49773d0a` (2026-09-22),

- **It models what NIKOS does not.** `--crab-lower-with-overflow-intrinsics`
  replaces each `llvm.OP.with.overflow` by the exact OP and defines the
  overflow bit FALSE (`CfgBuilder.cc:3498`) — the trap arm is unreachable in
  the analysis and the value is the mathematical result, which is exactly
  what D-210 makes true on every execution that continues past the guard
  (an overflow traps; a controlled stop is not a runtime error for leg A
  and its proof is leg B's). `llvm.assume` is an assume statement
  (`isAssumeFn`, CfgBuilderUtils.cc:209), so D-218.9's channel reaches it.
  The converse hole: a PLAIN `add`/`sub`/`mul` — the wrapping family `+% -%
  *%` (D-312), `xor`, the shifts — is unbounded-Int arithmetic to Crab's
  default domains, which is the wrong model for a value that wraps at run
  time; Crab has wrapped-integer domains for that, and §2.4's control (f)
  measures it.
- **Its inter-procedural heap analysis ABORTS on our calling convention.**
  With `--crab-inter --crab-track=mem --crab-heap-analysis=cs-sea-dsa` (and
  with `ci-sea-dsa`, and intra with memory, and `--crab-inter` with
  `--crab-track=num`): `CLAM ERROR: caller cell cannot be mapped to callee

  0] not mapped to a caller node` — the callee's `extractvalue` of a pointer
  field from a BY-VALUE aggregate parameter (a `dyn` fat pointer `{ptr,
  ptr}`, a struct payload) is a node the callee/caller simulation mapping
  has no caller cell for. sea-dsa's local builder does model
  `insertvalue`/`extractvalue` (`DsaLocal.cc:1109`, `:1147`); the gap is in
  Clam's mapping of a callee's aggregate-parameter cells at a call. Our
  emission passes aggregates by value everywhere (61,905 `extractvalue` and
  54,759 `insertvalue` in the compiler's), so this is not a corner: it is
  the port item for Clam, sized at the gate (§2.3 (5)).
- With `--crab-heap-analysis=none --crab-track=num` (numbers only, no

- Output: a text summary (`Number of total safe / error / warning checks`)
  and, with `--crab-check-verbose`, one line per check naming the

### 2.2 The inputs — one fixed set, produced by `gate_inputs.py`, digests recorded

1. **The three plain emissions**, exactly as the harness assembles them
   (`-O0`, the compiler under test at the gate's commit): `dyn_slots`,
   `extern_c_driver`, `src/npkc.npk`. For the two programs
   `quickemit.py --keep` writes the `.ll`; for the compiler `npkg build`'s
   `build/npkc.ll` (its sha256 is the ladder's emission row, D-265).
2. **The three whole-program forms**: each plain emission with the floor
   appended BY TEXT — the program's `declare`s of floor-defined symbols
   removed, the floor's `declare`s of program-defined symbols removed, one
   `target triple` kept — and a `roots.txt` beside each naming the entry
   points: the program's `main`, and every floor function whose address is
   taken by the assembly or handed to the kernel (`npk_start_main`,
   `npk_thread_entry`, the signal handlers, the failsafe route), read off
   `runtime/npkrt.ll` by the script (a `ptr @npk_…` operand that is not a
   call's callee), not written by hand. Both assemblers must accept each
   form (a belt in the script).
3. **The verified emission of `src/npkc.npk`** (`npkc --elide
   nitpick.obligations`, the committed manifest): the `llvm.assume` channel
   as leg A will read it. One input, npkc only (the two programs have
   manifests only inside the harness's verify run).
4. **The datalayout twins**: every input of (1)–(3) once more with the
   x86-64 line `opt` writes prepended (`target datalayout = "e-m:e-p270:32:32-p271:32:32-p272:64:64-i64:64-i128:128-f80:128-n8:16:32:64-S128"`).
   An engine whose counts or verdicts differ between an input and its twin
   is measuring the default layout, and 1.6.1 then owes the emitter the
   line (P-5). The plain emission is the artifact; the twin is the probe.
5. **The opt pairs for Alive2**: `dyn_slots` and `extern_c_driver`, pre =
   the plain emission, post = `opt` under `nitpick.toml`'s `opt-flags`
   (`-O2 -S`), the harness's own leg — and, since step 3, each pair's
   NO-INLINING TWIN `<name>.opt.noinline.ll` (the same pipeline under
   `-inline-threshold=-100000000`), which tells an inliner's verdict from an
   inter-procedural one at the smoke: a verdict the twin keeps is not the
   inliner's. The compiler's pair is NOT smoked at
   the gate: 28 functions took 133 s and 4.3 GB, so 3,392 is a day-scale
   run whose cadence is 1.6.2's to measure.
6. **The controls** (§2.4), built the same way.

Every input's sha256 goes into `.internal/gate/inputs.txt` and the record
quotes the list; the inputs are reproducible from the tree, so none is
committed.

### 2.3 The runs and what each measures (the gate's criteria as rows)

`gate_run.py` runs every engine over every input under ONE option profile
per engine and mode, fixed in the script and printed at the head of every
report, twice — from two working directories — and normalises the outputs
(timing lines, temp paths, addresses) before comparing. Per (engine, input,
mode) it records: the ingestion verdict; functions defined / functions
analyzed; checks by kind and status; every alarm's text; wall-clock and
peak RSS (`/usr/bin/time -f "%es %MKB"`); whether the two runs agree byte
for byte. The profiles:

- **NIKOS**: `ikos-pp -opt=basic -entry-points=<roots>` then `ikos-analyzer
  -a=boa,dbz,nullity,uva,sio,uio,shc,poa,uaf,dfa -d=interval
  --entry-points=<roots> -j 1 --name-values --display-checks=no`, once with

  row and six hours of it would not be); the SQLite result read directly. A
  second domain (`dbm`) and `-opt=none` are step 4's readings on one input
  each, not rows of the run.
- **Clam**: `llvm-as-18` on the text, then `clam.py <bc> --crab-dom=zones
  --crab-lower-with-overflow-intrinsics --crab-check-verbose=1
  --crab-print-invariants=false`. `--crab-check` takes ONE property per run —
  `none`, `assert`, `null`, `uaf`, `bounds`, `is-deref` (and two legacy
  spellings) — and Clam has NO division-by-zero check (measured at step 3:
  `invalid choice: 'div-zero'`), so leg A's third named property has no Clam
  row. Ten settings: `bounds`, `null`, `uaf` and `is-deref` under
  `--crab-track=mem --crab-heap-analysis=cs-sea-dsa`, each with and without
  `--crab-inter` (the memory settings, which abort today), and
  `--crab-track=num --crab-heap-analysis=none --crab-check=assert` with and
  without `--crab-inter` (the numeric settings: no `__CRAB_assert` in our IR,
  so 0 checks — they measure that the numeric machinery reads and walks the
  module, and its cost). If D-321's patch rule admits the abort's demotion
  (§2.3 (5)) the memory settings are run under the patch too, and both results
  are recorded.
- **Alive2** (leg C's smoke, §2.6): `alive-tv --smt-rlimit=20000000
  --smt-random-seed=0 <pre> <post>` at the pin (D-321's patch: no wall-clock
  knob), once per pair, twice; determinism is read on the VERDICT PER
  FUNCTION (correct / doesn't verify / the error class), never on the
  counterexample models z3 prints, which are its choice.

The rows, in the order the decision rule reads them (§2.5):

1. **INGESTION (criterion 1).** For each engine and each of the six
   `.ll` inputs: read, or refused — with the construct named. For Clam the
   reading is LLVM 18's: the belt `llvm-dis-18(llvm-as-18(x)) ==
   llvm-dis-20(llvm-as-20(x))` modulo the header lines, run on every input,
   is what makes "18 reads our 20-emitted text as 20 does" a measured
   sentence rather than the survey's guess. An abort inside an analysis
   (Clam's cell mapping) is recorded HERE as "read, analysis aborted at
   <site>", separately from a refusal to read.
2. **SOUNDNESS ON THE CONTROLS (criterion 2, the half that is not
   negotiable).** §2.4's planted defects: found or missed, per engine, per
   mode, per class. A missed planted defect under a check the engine
   claims is an unsound verdict in that class.
3. **REACH.** Functions analyzed over functions defined, per input and
   mode. Inter mode's reach through the executor's queue is its own line
   for the whole-program forms, since it decides what "whole-program
   evidence" can mean for this emission.
4. **ALARM QUALITY (criterion 2, the other half).** Alarms per input per
   check class, each READ and put in one of four causes: the floor-model
   class (an unknown external callee: the allocator, a syscall wrapper —
   1.6.1's model of the enumerated floor, TCB.md's tables, is the remedy),
   the aggregate-by-value class (a pointer inside a by-value aggregate the
   engine loses track of), the overflow-intrinsic class (a value the engine
   dropped at a `with.overflow`), and everything else, which is read one by
   one. All alarms of the two programs are read; the compiler's are
   sampled by class (every alarm of the functions of `src/frontend/lexer.npk`
   and `src/backend/ir/ir_rules.npk` — the lexer for byte indexing and
   arithmetic over a buffer, the rules emitter for pointers and containers
   — plus a random 100 under a fixed seed). An
   `unreachable` count is read for its cause before it counts as anything.
5. **PORT DISTANCE (criterion 1's second half).** For each engine, the
   enumerated changes it needs to score on rows 1–4 for our emission —
   NIKOS: a model of `llvm.*.with.overflow` (the exact op, the bit false —
   Clam's rule, right under D-210), `llvm.assume` as `__ikos_assume`, the
   no-debug pointer typing from uses (its own doc says instructions without
   debug info are already typed "from their uses and operands"), the entry
   through the executor; Clam: the aggregate-parameter cell mapping, the
   wrapped-integer class, the 18-reads-20 belt as a standing check — each
   sized by READING the code (files, functions, lines), none built at the
   gate. The one exception, admitted only under S-101: where an ABORT
   stops a measurement (Clam's `CLAM_ERROR` at the cell mapping), a
   one-line demotion of that abort to a warning that marks the region
   unknown (top) is applied as a recorded patch, because "top" is the sound
   answer and the abort hides every number behind it. The patch's sha256
   joins the pin; the results with and without it are both recorded.
6. **DETERMINISM (criterion 4).** The two runs' normalised outputs byte
   for byte; the option profile has no thread count above one, no seed
   other than a fixed one, no clock. NIKOS's `--name-values` is part of its
   profile because without it the output names variables by address.
7. **COST (criterion 3).** Wall-clock and peak RSS per input and mode,
   from `/usr/bin/time`; the compiler's whole-program form under each
   engine's intra mode is the number 1.6.1's cadence question is sized by.

### 2.4 The negative controls — the instrument must FIND what is planted

Seven programs under `meta/roadmap/1.6/tools/controls/`, each a
`// expect-exit:` program the harness would accept, each with ONE defect
the language's guards make impossible at run time — so the defect is
planted in the EMISSION, by an exact-line substitution of the guard
(`old:`/`new:` pairs over the `.ll`, the explorer's control grammar,
VERIFICATION_REFERENCE §10), and the program is compiled, planted, and
handed to the engines as `<name>.planted.ll` beside `<name>.plain.ll`. A
control that the planted program does not actually exhibit at run time is
blind: each control's `.ll` is also assembled, linked and RUN, N times, and
must answer its planted exit every time — a fault (SIGSEGV/SIGFPE under D-307
answers `MachineFault`, exit 99) for (a)–(f), and for (g) the deterministic
answer the floor's 0xAA free-poisoning gives a read of freed memory (42 where
the plain program answers 5) — before its engine verdicts count.
`gate_controls.py` is the belt; its `controls.txt` is quoted in the record.

| # | class | the program | the plant |
|---|---|---|---|
| a | out-of-bounds read | a fixed `int32[8]` indexed by an argument-derived value | the `bounds` guard's compare-and-branch removed |
| b | out-of-bounds write | the same shape, a store | the same |
| c | null dereference | a `T->` local seeded `null` (D-225's vacant) read through | the `if (p != null)` branch removed |
| c' | null dereference, KNOWN null | the same shape as (c) with the literal address `0i64` — an analyzer can know this pointer is null, where (c)'s comes from an argument and is merely unknown (added at step 3, when (c) showed that NIKOS flags an unknown pointer's dereference the same way guarded or not) | the same |
| d | division by zero | `a / b` with `b` from an argument | the `div-zero` guard removed |
| e | uninitialised read | an `alloca` loaded before any store | the seeding `store zeroinitializer` removed |
| f | wrapped arithmetic decides a branch | `uint8:x = 250u8 +% seed` (seed 9: x is 3 at run time, 259 to unbounded-integer reasoning); `if (x < 8u8)` guards an index a million past a fixed array | the bounds guard INSIDE the branch removed: the branch is entered at run time and the planted program faults; an engine that reasons in mathematical integers finds the branch dead and reports nothing — the class 1.6.0.md §1 named for Crab's default domains, made a soundness control (this row read "a positive control" until step 2 measured the shape: a wrapped value is never mistaken for an in-range one by itself, since the wrap only happens outside the range; it misleads only through a comparison that unbounded reasoning decides the other way) |
| g | use after free | a `wild` block `dalloc`ed then loaded | the load moved after the `dalloc` in the text (the checker refuses it in source) |

Each control's twin with the guard INTACT is run too, and the engine's
answer on the guarded site is recorded as precision (an alarm on a guarded
site is a false alarm of the class in question, not a miss).

### 2.5 The scorecard and the decision rule (S-100)

The record's scorecard has one column per engine and the rows of §2.3.
The rule, proposed for ratification BEFORE the numbers exist (P-2):

1. An engine that REFUSES to read a plain emission (row 1) or MISSES a
   planted defect under a check it claims (row 2) is disqualified in that
   class; disqualified in `bounds`, `null` and `div-zero` — leg A's three
   named properties (the README's "OOB, div-by-zero, null/uninitialized
   reads") — it loses.
2. Among the rest, the engine that gives MORE evidence about our IR wins:
   reach (row 3) times the fraction of its alarms that are real or
   remediable by the floor model alone (row 4) — an alarm whose cause is
   the engine losing a value the IR states (the overflow-intrinsic class,
   the aggregate class) counts against the engine; an alarm the enumerated
   floor model will answer counts against neither.
3. The winner must hold row 6 (determinism); an engine that cannot be
   made deterministic under a fixed profile cannot be a verdict source
   (D-218.2 as D-233 generalises it) and loses regardless of row 2.
4. Row 7 breaks ties. Row 5 never decides: it becomes 1.6.1's step list
   for the winner, and the loser's is kept in the record.
5. The loser is DECIDED OUT (D-233: "one engine wins; the other is decided
   out — fewer mechanisms") with its scorecard kept, and the decision
   names the measurement that decided.

If the numbers disqualify BOTH under rule 1, the gate does not pick: the
record states which classes each fails, the smaller port to a passing
state is estimated by reading, and the user chooses the port (S-102's
other shape). The plan does not assume this outcome and does not exclude
it.

### 2.6 Leg C's smoke (Alive2)

At the pin, linked against the pinned z3 as a static library, over the two
pairs of §2.2 (5): the counts (correct / incorrect / failed-to-prove /
errors), each error's class READ (the "return domain" class of §1 is

No harness or `npkg` stage (1.6.1); no `nitpick.toml` key (1.6.1's

## 5. Decisions taken at planning (each with its reason)

- **P-1 — the candidates are measured AS THEY STAND, on the emission AS IT
  IS.** No emitter change to suit an engine before the gate (a datalayout
  line, debug metadata for NIKOS's importer, a different calling
  convention): the gate's question is which engine reads the artifact, and
  an artifact reshaped for the gate answers a different question. What an
  engine needs from the emission is a row of the scorecard (§2.2 (4),
  §2.3 (5)), and 1.6.1 lands it for the winner if the winner needs it.
- **P-2 — the rule before the numbers** (S-100). The 1.5 cycle's lesson 3:
  a fixture that claims a property is evidence of nothing until something
  decides it; a decision rule written after the data is a claim about the
  data.
- **P-3 — every landing runs under a full harness, docs and tools
  included.** The tree's invariant is that every commit on `main` is
  harness-green (D-228 R3), and a docs-only commit that skipped the run
  would be the first exception; 1.5.8c step 0 (four string functions
  nothing called) and 1.5.8b step 0 (the plan and the decisions) ran it.
  Three hours of wall-clock per landing is not a constraint here.
- **P-4 — an evidence tool's binary is pinned by DIGEST beside its
  commit.** D-265's asymmetry, applied: a toolchain pin is a version
  (`llc`'s bytes are checked by the ladder, not trusted), a solver pin is a
  digest (its output is a committed verdict). An analyzer's alarm and
  Alive2's refinement answer are verdicts, so `pins.txt` records the
  sha256 of every binary and library the gate ran, and 1.6.1's manifest
  table inherits the rule. A different build of the same commit is a
  different pin, re-recorded with its results.
- **P-5 — the datalayout question is measured by twins, not assumed.**
  Both engines read sizes and alignments from the module's layout, our
  emission states none, and `opt` has been supplying one silently on the
  -O2 leg since 1.3.8. If any count moves between an input and its twin,
  the emitter owes the line at 1.6.1 (the artifact should state what its
  analyzers assume); if none moves, the record says so and nothing
  changes.
- **P-6 — no APRON at the gate.** Both engines' native domains (NIKOS:
  interval, congruence, DBM, gauge; Crab: intervals, zones, and its own
  octagons) are enough to measure ingestion, soundness, reach and cause;
  a richer domain moves precision, which is 1.6.1's triage, and APRON's
  build is a fourth pin the gate would then carry for a question it does
  not ask. `REPOS/apron` stays where it is.
- **P-7 — the whole-program form is built by text, with the roots read
  off the floor.** `llvm-link` drops the floor's asm-reached internal
  functions (§1), and a hand-written entry list is the next stale list;
  the script derives the roots from `runtime/npkrt.ll`'s own function-
  pointer operands, and the record lists what it derived.
- **P-8 — an abort in an engine is demoted, never worked around in the
  input.** Where a `CLAM_ERROR` hides every number behind it, the sound
  demotion (the region is top) is a one-line patch on the engine under
  S-101's rule; rewriting our IR so the engine does not hit the abort would
  measure a different artifact (P-1).
- **P-9 — the controls are planted in the EMISSION.** The language's
  guards make the seven defects unreachable in source; the explorer's
  `old:`/`new:` substitution (VERIFICATION_REFERENCE §10) is the house
  mechanism for planting a defect the source cannot express, and each
  planted program is RUN to prove the defect is real before its verdicts
  count — a control whose planted binary answers like its plain twin is blind
  (1.5.7 step 4's lesson).
- **P-10 — the compiler's Alive2 pair is not smoked at the gate.** 133 s
  and 4.3 GB for 28 functions; the cadence question belongs to 1.6.2,
  which owns the ledger that would make the answer mean something.
- **P-11 — the gate's tools are Python and shell, outside the artifact.**
  The zero-dependency rule governs the artifact and its gates
  (D-233's doctrine restated); the gate builds nothing that ships and is
  itself not a gate of the tree. `npkg` grows nothing here; 1.6.1 decides
  what the standing stage is written in, with D-206's runner parity in
  view.
