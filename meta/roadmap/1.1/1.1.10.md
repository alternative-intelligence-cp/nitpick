# 1.1.10 — Channels (D-182, C-9's channel half)

**Cycle 1.1's last build.** Four stages, each harness-gated.

- **A — `atomic<T>`.** The type set (integers ≤64, `bool`, pointer-shaped),
  the five operations with explicit orderings, `Cas<T>` for
  `compare_exchange`, all `never fails`. Needed first: the channel's own
  state rides them, and the executor's park word already wants one.
- **B — the channel type and its handle.** `Channel<T, LEVEL, CAP>` as an
  opaque handle value; `channel()` typed from context; the runtime's channel
  table with generation checking; `send`/`recv`/`close` over a ring.
  **`CAP == 0` moved to stage C** — see below.
- **C — blocking that suspends.** `send`/`recv` park the TASK on the
  channel's wait word under the deadline (D-071/D-176), so a full or empty
  channel never stalls a sibling. Cross-thread wake through the futex the
  park word already uses. **Also owns the rendezvous** (`CAP == 0`), which
  stage B refuses by name — see the stage C plan below.
- **D — `Work`, pools, actors.** The trait, generic `ThreadPool<J, …>` as N
  workers on one channel, and an actor example that is a struct plus a loop
  — proving no new primitive was needed.

## Done when

Two tasks on one executor, and two threads, exchange values through a
channel; a full channel's sender suspends rather than spinning; and the
async-`dyn` refusal has a named rung with a test.

*"A stale endpoint is a caught error" was struck from this list at stage B,
because it cannot be shown here.* The check exists and is right; what makes
it fire is a slot being REUSED, and nothing reuses one until the managed
lowering reclaims a channel at its creating scope's exit. That is **B-6** in
`OPEN_DECISIONS.md` — a whole missing half of the memory model, not a
channel matter — and D-182 now records the interim. A done-when that no test
can honestly satisfy is worse than one that admits what it is waiting on.

## Stage A — `atomic<T>` — DONE

Six operations, **all SeqCst, no ordering argument**. The design study had
proposed explicit orderings and was overruled by D-016 and
CONCURRENCY_REFERENCE §4.3 before anything was built: a misused weak
ordering does not fail loudly or reproducibly, it is intermittent corruption
on another CPU months later that passed every test written for it. Test:
`tests/backend/programs/atomic_ops.npk`; rules refused in
`tests/types/rejection/atomic_rules.npk`.

## Stage B — the channel type and its handle — DONE

`Channel<T, LEVEL, CAP>` with both constants in the type, `channel()`
context-typed, endpoints as `{ index, generation }` handles, and
`send`/`recv`/`close` over the runtime's ring — every blocking form carrying
a mandatory `Duration` deadline, because an untimed wait is an uncontrolled
stop with no failsafe path.

Tests: `channel_basic` (send, close, drain-then-`ChannelClosed`, send-after-
close), `channel_cross` (a producer receiving the endpoint through a spawn,
with a suspending receive on the other side), `channel_deadline` (both
directions bounded, and *timed* — an earlier executor waited on its own next
timer rather than the caller's deadline, so containment silently became
patience), `channel_struct` (a pointer-free struct rides), and the two
refusals `channel_rendezvous` and `channel_owning_elem`.

**Two of the four defects this stage came from instruments, not tests.**
`check_slot_sites_agree` found that `type_channel_method` asks `fits` — which
admits a `T` into a `T?`, a concrete value into a `dyn`, and (new at stage A)
a `T` into an `atomic<T>` — while the emitter stored the argument raw into the
element's slot: the same shape as the bug that once wrote 4 bytes over a
16-byte fat pointer. And the seed's own parser turned out to reject
`Channel<int32, 3i32, 2i64>`, because a generic argument list parsed each
argument as a TYPE; the negative suites run through the seed, so a rung test
could not reach the backend to be refused there. The parser must never
restrict (D-085) — that is the seed disagreeing with stage 1 about the
grammar, and it was one line of the seed away from hiding every value-generic
rung test.

Three things this stage decided, each because it broke first:

- **`close` does not move the generation.** Closing is a state change on a
  live channel, not reclamation of its slot; a consumer must still drain
  what is buffered. Bumping it made every outstanding endpoint stale the
  moment the producer finished — `StaleHandle` reported for an orderly end
  of stream. Written into D-182 along with what the generation *is* for.
- **A channel await's receiver is frame-resident.** An ordinary `await`
  consumes its arguments into the callee's frame before suspending, so those
  uses are genuinely before the suspension point; a channel retry loop
  re-reads its handle on the far side of one. The walk recorded the use on
  the wrong side, the handle rode an alloca, and the second turn of the loop
  read whatever the resume path had left there.
- **An element that owns heap storage is refused by name.** A channel hands
  its element to another task, and D-065 settled that nothing moves by being
  passed — ownership transfers only where `move` is written. A `string`
  element would therefore arrive as a SECOND owner of one body. D-072 writes
  `send(move(v), deadline)` in its own signature, but nothing requires the
  `move`, and requiring it would mean nothing until there is a drop for it to
  suppress — B-6 again, from the other side. Scalars, `Handle<T>`, endpoints,
  pointer-free structs and arrays of those transfer by copying their bytes and
  ride today (`channel_struct`, the spec's own `Sample` example);
  `channel_owning_elem` shows the refusal.
- **`CAP == 0` is refused by name, not monomorphized.** A rendezvous is not
  a one-slot buffer: its sender waits for a RECEIVER, and the hand-off is
  the synchronisation being asked for. The buffered path would give a send
  that returns the moment it deposits — the same source, quietly not
  synchronising. It needs stage C's waiter registration, so it refuses with
  `NITPICK-RUNG-001` naming stage C until then.

## Stage C — the plan

**What stage B leaves in place.** A blocked `send`/`recv` re-polls: the retry
loop calls `npk_park_until(mono_now() + 1ms)` and tries again, bounded by the
caller's deadline. It is correct and it is bounded — no sibling stalls, no
thread blocks, the deadline is honoured — and it is a poll. Two costs, and
the second is the one that matters:

1. Up to a millisecond of latency on every hand-off, and a wakeup per
   millisecond per blocked task whether or not anything happened.
2. **It cannot express a rendezvous.** A rendezvous sender waits for a
   RECEIVER, and a poll loop has no way to ask whether one is there — which
   is why `CAP == 0` refuses at stage B rather than lowering onto the
   buffered path and quietly not synchronising.

**The mechanism.** A channel grows a waiter list; `%npk.chan` has the room
and `%npk.exec` already carries the park word the join uses. A task that
cannot proceed registers `(executor, task)` on the channel — on the receive
side for an empty channel, on the send side for a full one — and parks with
no timer of its own beyond the caller's deadline. A `send` that deposits pops
a receive-waiter, and a `recv` that frees a slot pops a send-waiter.

**Waking is two different problems and must be built as two.** Same-thread,
the waker owns the target's executor and can put the task straight back on
the ready queue. Cross-thread it owns nothing: the push has to be an atomic
MPSC hand-off onto the target executor's queue, and the target thread may be
asleep in `futex`, so the push is followed by a wake on that executor's park
word. Missing the wake is a lost wakeup — the task sleeps to its deadline and
reports `DeadlineExceeded` for a value that arrived — so the ordering is
register-then-recheck: register, re-test the condition, and only then park,
because the state can change between the two.

**The rendezvous falls out of it.** With a receive-waiter list, `CAP == 0`
means a send deposits only when a receiver is registered, and otherwise
waits; the hand-off is then the synchronisation the type was asked for. Strike
the stage B refusal, and `tests/rejection/channel_rendezvous.npk` becomes a
program test.

### C1 — the channel lock — DONE

**Found by asking whether the thing D-182 built channels FOR actually worked.**
Two threads and one channel compiled and ran, and every channel operation read,
compared and wrote `count`, `head` and `tail` with plain loads and stores.
Two senders both saw room, both wrote the same slot, and the receiver waited
out its deadline for values that had been overwritten: **21 of 40 runs lost
messages.** The other 19 passed. That ratio is the whole lesson — a data race
is not a test that fails, it is a test that stops failing when you look at it,
and this one was reachable from ordinary source with no `wild`, no `raw`, and
no unsafe spelling anywhere in it.

Three things landed together, because the first two are the same bug at two
scales:

- **A futex mutex per channel**, three-state so the uncontended path stays
  syscall-free in both directions, taken by every operation.
- **The table stopped moving channels.** It held the structs inline and grew
  by copying them to new addresses — fine with one thread, a use-after-free
  with two, since a reader mid-operation holds the old address. Each channel
  is now allocated on its own and never moves; only an array of POINTERS
  grows, the old array is never freed, and a reader that loaded the previous
  one still resolves every index below the count it observed. So no reader
  needs the open lock: the count is released after the pointer is stored and
  acquired before it is used.
- `tests/backend/programs/channel_threads` — 100 messages, 50 from each of two
  threads, one value each, so the sum IS the count and a lost message cannot
  be cancelled out by a duplicated one.

**This does not violate D-071's "suspend the task, never the thread".** What
that rule is about is waiting for a PEER OPERATION — an unbounded wait, which
is exactly what C2's waiter lists keep off the thread. A mutex around a memcpy
of one element is a bounded critical section, and no task ever holds it across
a suspension.

### C2 — waiter lists, and the end of the poll — DONE

**A blocked task is on two lists at once, and that is the design.** Its own
executor's sleepers hold it against the caller's deadline, through `qnext`;
the channel's waiter list holds it against a peer operation, through a new
`chan_next`. Whichever comes first wins, neither knows about the other, and in
both cases the task re-runs the same call and re-tests the same condition.

The frame header grew two slots: `chan_next`, and `owner` — the executor the
task is pinned to (D-032). A waker has to reach it, and nothing else answered:
`thread_tls` is set only on a thread's ROOT task, so it is a different
question wearing a similar shape. `owner` is stamped where the frame is born,
the one moment the creating thread is certainly the owning thread.

**The whole protocol is one runtime call.** `npk_ch_{send,recv}_wait` locks
the channel, unlinks the frame from the list it may still be on, re-tests, and
then completes, errors, or registers and parks. The emitted loop is a call, a
branch, and a resume point, with no timing decision in it. The unconditional
unlink is what makes the call idempotent across all three ways a task arrives
at it — first try, woken by a peer, woken by its own deadline — and without it
a task that timed out would stay listed, and the next peer would make a task
due that had stopped waiting, writing over a `wake_at` that may by then mean
"finished" (−1).

**The wake ordering is the part that had to be got right.** The waker makes
the task due, THEN sets the owner's park word, THEN futex-wakes. The executor
clears its park word, re-checks its sleepers, and only then waits. So a waker
arriving before the sleep is caught by the re-check, and one arriving after
finds a non-zero park word that makes the `FUTEX_WAIT` return immediately.
Either half reversed is a lost wakeup: a task that sleeps to its deadline and
reports `DeadlineExceeded` for a value that already arrived. `wake_at` is read
and written from two threads and is atomic on both sides.

`channel_pingpong` is the test that can tell the two implementations apart:
500 round trips through two capacity-1 channels, every one of them a real
park-and-wake on both sides. Polling could not finish it in under about half a
second whatever the machine; woken by its peer it takes **4 ms**. The
assertion is 250ms — far under what a poll can do, far over what an event
needs.

### C3 — the rendezvous — DONE

With a receiver list there is something to ask, so `CAP == 0` means what it
says: a send deposits only when a receiver is REGISTERED and therefore certain
to take it. Stage B's refusal is struck and
`tests/rejection/channel_rendezvous` became
`tests/backend/programs/channel_rendezvous`.

One asymmetry had to be added for it. Registering as a receiver is ITSELF the
event a rendezvous sender waits for — on a CAP 0 channel a value never arrives
first — so a receiver that parks wakes a waiting sender. Without that, both
sides park and neither is the other's wake: a deadlock that resolves only when
the deadlines run out. The test exercises both arrival orders and times the
sender-first case, because "the sender waited" is the property, and a
capacity-1 buffer would pass every functional assertion without it.

### D1 — a generic async callee, and the ordering bug it uncovered — DONE

**Stage D could not start without this.** D-182's pool is `ThreadPool<J, …>` —
N worker TASKS generic in the job type — so every one of its spawns is an
`await` or a spawn of a generic callee, and all three sites refused outright.
The fix is small once seen: a coroutine's frame type and resume symbol are
derived from its NAME, and a generic one's name is the instantiation's
(`twice<int32>`, the spelling the definition is already emitted under), not
the template's. `fninst_for_call` — the same lookup an ordinary generic call
uses — supplies it. What still refuses is a generic callee with no recorded
instantiation, which is the honest case: the specialization would not exist to
call. `tests/rejection/thread_spawn` was the refusal's test and became
`tests/backend/programs/async_generic`.

**And then the first program that used it found a bug nothing had caught.**
`async func:main` awaiting a helper declared BELOW it did not compile — not
with a diagnostic, with `base element of getelementptr must be sized` out of
llc. A call site asks for the callee frame's SIZE, and LLVM will not size a
named type it has not seen yet. A coroutine's frame shape is not known until
its body has been scanned for locals that cross a suspension, so the type is
written where it is discovered, in the middle of the module, while the sites
that need it may be anywhere.

Every async test written before this one happened to declare its callees
first. **The bug was in the shape of the test files, not in the feature under
test** — which is the kind of hole a test suite cannot find by growing, only
by someone writing a program in the ordinary order and having it fail. The
writer now keeps frame types in their own sink and splices them in ahead of
the first function; `tests/backend/programs/async_decl_order` is the case.

### D2–D5 — DONE

- **D2 — `await` of a METHOD call.** The checker already resolves which method
  a call reaches; the await site reads that answer rather than repeating the
  lookup, and the receiver becomes parameter 0 of the child frame. Two things
  had to be got right and neither announced itself. The checker asked "is this
  callee async?" BEFORE the call underneath had been typed, so the table said
  0 and an `async` method was reported as not async — the same ordering the
  channel-await acceptance needs, for the same reason. And a method call's
  argument window is not a call's: the slot `expr_generic_count` reads means
  something else on that node, and read blind it swallowed the whole argument
  list, so `await a.run(2i32)` reached `run` with its parameter unwritten and
  returned 40 instead of 42.
- **D3 — the `Work` trait and a pool**, in `tests/backend/programs/thread_pool`.
  Three holes in the generic machinery came out of writing it, all of the same
  shape — a type kind added at 1.1.10 that an existing walker had never been
  taught:
  - `type_subst` covered pointer, slice, array, optional, result, instances and
    `dyn`, but not `arena<T>`, `Handle<T>`, `atomic<T>` or
    `Channel<T, LEVEL, CAP>`. So `worker<J>(Channel<J, …>)` met
    `Channel<Sum, …>` and reported a mismatch **against its own parameter**: a
    generic function taking any of those four could not be instantiated at all.
  - `type_mentions_param` was missing `atomic` and `channel`, so
    `subst_emitted_type` answered "nothing to substitute" for `Channel<J, …>`.
    The channel was then opened with `J`'s size — and an unsubstituted
    parameter measures **zero** — so the ring copied nothing and every job
    arrived blank. Nothing failed anywhere; the values were simply zero.
  - Layout's `field_holds_ptr` reached its conservative default for `Handle<T>`
    and channel endpoints, calling every struct that holds one
    "pointer-bearing". Both are indices rather than addresses, which is the
    entire reason they exist in those shapes.

  Two language constraints shaped the pool and are worth recording, because
  both are consequences of decisions rather than accidents. Its operations are
  **free generic functions**: D-161's segment rule reads `impl:<J>:ThreadPool<J>`
  as a blanket impl of a trait, so an inherent impl over a FAMILY cannot be
  spelled — the same constraint `generic_list` works within. And the **workers
  are spawned by the owning scope**, not inside a `create`, because D-062 joins
  a function's spawned tasks at that function's exits: a pool whose workers
  were spawned in its constructor would join them before returning, blocking
  until workers it had given no work had finished. "A pool is N worker tasks
  receiving from one channel" is not a slogan; it is what the lifetime rule
  leaves you with.
- **D4 — an actor** (`tests/backend/programs/actor`): a struct and a loop, with
  the reply endpoint riding INSIDE the message. That is the thing D-182
  changed — endpoints were specified as borrows, and a borrow cannot cross a
  spawn, which is why the prototype needed `set_reply_channel`/`reply` and why
  all of them were stubs. Its state is an ordinary local touched by exactly one
  task, so the property actors exist for falls out of the scoping rather than
  out of a rule anybody enforces.
- **D5 — async is not object-safe**, as a fourth object-safety rule rather
  than a new mechanism. An `async` method is a coroutine: a frame whose SIZE
  belongs to the concrete callee, which `dyn` erases, and a vtable slot is one
  address with nowhere to put it — rule 2's problem in a different place.
  Caught by emitting one: a trait with an `async` method got a vtable thunk
  like any other, and the thunk called a synchronous symbol that does not
  exist for a coroutine, so llc reported `use of undefined value` — the
  compiler discovering at link time what the type system should have said at
  the declaration.

### The pattern in stage D's defects

Five of the seven were **a type kind added in this cycle meeting a walker
written before it**: `type_subst`, `type_mentions_param`, `field_holds_ptr`,
the escape analysis's pointer question, and the vtable emitter. None was found
by a test of the feature that broke — they were found by writing an ordinary
program that used two features together. The obligation a new type kind places
on every existing walker is real and is not currently checked by anything; that
is worth an instrument, and it is the natural companion to
`check_kinds_lowered_or_refused`, which asks the same question about
expressions.

### The original D2–D5 plan

- **D2 — `await` of a METHOD call.** Still refused
  (`an await of a method, indirect or builtin call`), and `Work` needs it:
  a worker does `await job.run()` on a generic `J: Work`. D-182 settled that
  async trait methods work through generics.
- **D3 — the `Work` trait and `ThreadPool<J, LEVEL, CAP>`**, as library code
  in `lib/`, not a primitive. Note the constraint that shapes it: workers
  cannot be spawned inside `create`, because D-062 joins a function's spawned
  tasks at ITS exits, so a pool whose workers were spawned in `create` would
  join them before returning. The owning scope spawns them — which is what
  "a pool is N worker tasks receiving from one channel" actually means when
  the lifetime rule is taken seriously.
- **D4 — an actor**: a struct and a loop, proving no new primitive was needed.
- **D5 — the async-`dyn` refusal**, with a named rung and a test. D-182
  settled async trait methods as generics-yes, `dyn`-no; the refusal has to
  exist and be shown refusing.
