# 1.1.10 — Channels (D-182, C-9's channel half)

**Cycle 1.1's last build.** Four stages, each harness-gated.

- **A — `atomic<T>`.** The type set (integers ≤64, `bool`, pointer-shaped),
  the five operations with explicit orderings, `Cas<T>` for
  `compare_exchange`, all `never fails`. Needed first: the channel's own
  state rides them, and the executor's park word already wants one.
- **B — the channel type and its handle.** `Channel<T, LEVEL, CAP>` as an
  opaque handle value; `channel()` typed from context; the runtime's channel
  table with generation checking; `send`/`recv`/`close` over a ring.
  **`CAP == 0` moved to stage C** — see below.
- **C — blocking that suspends.** `send`/`recv` park the TASK on the
  channel's wait word under the deadline (D-071/D-176), so a full or empty
  channel never stalls a sibling. Cross-thread wake through the futex the
  park word already uses. **Also owns the rendezvous** (`CAP == 0`), which
  stage B refuses by name — see the stage C plan below.
- **D — `Work`, pools, actors.** The trait, generic `ThreadPool<J, …>` as N
  workers on one channel, and an actor example that is a struct plus a loop
  — proving no new primitive was needed.

## Done when

Two tasks on one executor, and two threads, exchange values through a
channel; a full channel's sender suspends rather than spinning; and the
async-`dyn` refusal has a named rung with a test.

*"A stale endpoint is a caught error" was struck from this list at stage B,
because it cannot be shown here.* The check exists and is right; what makes
it fire is a slot being REUSED, and nothing reuses one until the managed
lowering reclaims a channel at its creating scope's exit. That is **B-6** in
`OPEN_DECISIONS.md` — a whole missing half of the memory model, not a
channel matter — and D-182 now records the interim. A done-when that no test
can honestly satisfy is worse than one that admits what it is waiting on.

## Stage A — `atomic<T>` — DONE

Six operations, **all SeqCst, no ordering argument**. The design study had
proposed explicit orderings and was overruled by D-016 and
CONCURRENCY_REFERENCE §4.3 before anything was built: a misused weak
ordering does not fail loudly or reproducibly, it is intermittent corruption
on another CPU months later that passed every test written for it. Test:
`tests/backend/programs/atomic_ops.npk`; rules refused in
`tests/types/rejection/atomic_rules.npk`.

## Stage B — the channel type and its handle — DONE

`Channel<T, LEVEL, CAP>` with both constants in the type, `channel()`
context-typed, endpoints as `{ index, generation }` handles, and
`send`/`recv`/`close` over the runtime's ring — every blocking form carrying
a mandatory `Duration` deadline, because an untimed wait is an uncontrolled
stop with no failsafe path.

Tests: `channel_basic` (send, close, drain-then-`ChannelClosed`, send-after-
close), `channel_cross` (a producer receiving the endpoint through a spawn,
with a suspending receive on the other side), `channel_deadline` (both
directions bounded, and *timed* — an earlier executor waited on its own next
timer rather than the caller's deadline, so containment silently became
patience), `channel_struct` (a pointer-free struct rides), and the two
refusals `channel_rendezvous` and `channel_owning_elem`.

**Two of the four defects this stage came from instruments, not tests.**
`check_slot_sites_agree` found that `type_channel_method` asks `fits` — which
admits a `T` into a `T?`, a concrete value into a `dyn`, and (new at stage A)
a `T` into an `atomic<T>` — while the emitter stored the argument raw into the
element's slot: the same shape as the bug that once wrote 4 bytes over a
16-byte fat pointer. And the seed's own parser turned out to reject
`Channel<int32, 3i32, 2i64>`, because a generic argument list parsed each
argument as a TYPE; the negative suites run through the seed, so a rung test
could not reach the backend to be refused there. The parser must never
restrict (D-085) — that is the seed disagreeing with stage 1 about the
grammar, and it was one line of the seed away from hiding every value-generic
rung test.

Three things this stage decided, each because it broke first:

- **`close` does not move the generation.** Closing is a state change on a
  live channel, not reclamation of its slot; a consumer must still drain
  what is buffered. Bumping it made every outstanding endpoint stale the
  moment the producer finished — `StaleHandle` reported for an orderly end
  of stream. Written into D-182 along with what the generation *is* for.
- **A channel await's receiver is frame-resident.** An ordinary `await`
  consumes its arguments into the callee's frame before suspending, so those
  uses are genuinely before the suspension point; a channel retry loop
  re-reads its handle on the far side of one. The walk recorded the use on
  the wrong side, the handle rode an alloca, and the second turn of the loop
  read whatever the resume path had left there.
- **An element that owns heap storage is refused by name.** A channel hands
  its element to another task, and D-065 settled that nothing moves by being
  passed — ownership transfers only where `move` is written. A `string`
  element would therefore arrive as a SECOND owner of one body. D-072 writes
  `send(move(v), deadline)` in its own signature, but nothing requires the
  `move`, and requiring it would mean nothing until there is a drop for it to
  suppress — B-6 again, from the other side. Scalars, `Handle<T>`, endpoints,
  pointer-free structs and arrays of those transfer by copying their bytes and
  ride today (`channel_struct`, the spec's own `Sample` example);
  `channel_owning_elem` shows the refusal.
- **`CAP == 0` is refused by name, not monomorphized.** A rendezvous is not
  a one-slot buffer: its sender waits for a RECEIVER, and the hand-off is
  the synchronisation being asked for. The buffered path would give a send
  that returns the moment it deposits — the same source, quietly not
  synchronising. It needs stage C's waiter registration, so it refuses with
  `NITPICK-RUNG-001` naming stage C until then.

## Stage C — the plan

**What stage B leaves in place.** A blocked `send`/`recv` re-polls: the retry
loop calls `npk_park_until(mono_now() + 1ms)` and tries again, bounded by the
caller's deadline. It is correct and it is bounded — no sibling stalls, no
thread blocks, the deadline is honoured — and it is a poll. Two costs, and
the second is the one that matters:

1. Up to a millisecond of latency on every hand-off, and a wakeup per
   millisecond per blocked task whether or not anything happened.
2. **It cannot express a rendezvous.** A rendezvous sender waits for a
   RECEIVER, and a poll loop has no way to ask whether one is there — which
   is why `CAP == 0` refuses at stage B rather than lowering onto the
   buffered path and quietly not synchronising.

**The mechanism.** A channel grows a waiter list; `%npk.chan` has the room
and `%npk.exec` already carries the park word the join uses. A task that
cannot proceed registers `(executor, task)` on the channel — on the receive
side for an empty channel, on the send side for a full one — and parks with
no timer of its own beyond the caller's deadline. A `send` that deposits pops
a receive-waiter, and a `recv` that frees a slot pops a send-waiter.

**Waking is two different problems and must be built as two.** Same-thread,
the waker owns the target's executor and can put the task straight back on
the ready queue. Cross-thread it owns nothing: the push has to be an atomic
MPSC hand-off onto the target executor's queue, and the target thread may be
asleep in `futex`, so the push is followed by a wake on that executor's park
word. Missing the wake is a lost wakeup — the task sleeps to its deadline and
reports `DeadlineExceeded` for a value that arrived — so the ordering is
register-then-recheck: register, re-test the condition, and only then park,
because the state can change between the two.

**The rendezvous falls out of it.** With a receive-waiter list, `CAP == 0`
means a send deposits only when a receiver is registered, and otherwise
waits; the hand-off is then the synchronisation the type was asked for. Strike
the stage B refusal, and `tests/rejection/channel_rendezvous.npk` becomes a
program test.

### C1 — the channel lock — DONE

**Found by asking whether the thing D-182 built channels FOR actually worked.**
Two threads and one channel compiled and ran, and every channel operation read,
compared and wrote `count`, `head` and `tail` with plain loads and stores.
Two senders both saw room, both wrote the same slot, and the receiver waited
out its deadline for values that had been overwritten: **21 of 40 runs lost
messages.** The other 19 passed. That ratio is the whole lesson — a data race
is not a test that fails, it is a test that stops failing when you look at it,
and this one was reachable from ordinary source with no `wild`, no `raw`, and
no unsafe spelling anywhere in it.

Three things landed together, because the first two are the same bug at two
scales:

- **A futex mutex per channel**, three-state so the uncontended path stays
  syscall-free in both directions, taken by every operation.
- **The table stopped moving channels.** It held the structs inline and grew
  by copying them to new addresses — fine with one thread, a use-after-free
  with two, since a reader mid-operation holds the old address. Each channel
  is now allocated on its own and never moves; only an array of POINTERS
  grows, the old array is never freed, and a reader that loaded the previous
  one still resolves every index below the count it observed. So no reader
  needs the open lock: the count is released after the pointer is stored and
  acquired before it is used.
- `tests/backend/programs/channel_threads` — 100 messages, 50 from each of two
  threads, one value each, so the sum IS the count and a lost message cannot
  be cancelled out by a duplicated one.

**This does not violate D-071's "suspend the task, never the thread".** What
that rule is about is waiting for a PEER OPERATION — an unbounded wait, which
is exactly what C2's waiter lists keep off the thread. A mutex around a memcpy
of one element is a bounded critical section, and no task ever holds it across
a suspension.

**Done when** the 1 ms poll is gone from the retry loop, a rendezvous runs,
a cross-thread send wakes a sleeping consumer, and a test asserts the wake is
prompt rather than poll-shaped — with the lost-wakeup ordering exercised, not
assumed.
