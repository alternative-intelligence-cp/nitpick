# 0.8.4 — The string floor the compiler actually calls

## The question

BUILTIN_REFERENCE.md §2 listed ~50 string names as builtins. A builtin is a
name the *compiler* must know; every one is surface the verifier must trust
without reading Nitpick source. So: which of them does the compiler — the one
real program — actually call?

## The measurement

**Fifteen.** The audit swept every call in `src/**` and `tools/*` against the
builtin list: `alloc calloc dalloc exit int_to_string path_exists ralloc
read_file read_stdin string_concat string_from_bytes string_slice to_cstring
write_file write_raw`. (An earlier reading claimed `sys` ×2 — both were string
literals inside `builtins.npk` itself, the list describing, not calling.)

Everything else on the list — 35 names: pad/trim/split/join, case mapping,
parse/format, char classification — is *library* material: expressible as
ordinary Nitpick over the floor, no compiler knowledge required.

## The decision (recorded in BUILTIN_REFERENCE.md §2)

- **The floor stays builtin**: the 15, plus `mcpy`/`mmov`/`memset` (§1, lowered
  to `@memcpy`/`@memmove`/`@memset` — defined in npkrt.ll, so the zero-dep scan
  stays closed), plus `sys` (rung 0.9), plus a comptime-foldable trio
  `string_equals`/`string_byte_length`/`string_is_empty` (the two length forms
  lower INLINE — an extractvalue is not a call).
- **The 35 are demoted** to nlibc-tier documentation: same doc, outside the
  `<!-- builtins:begin/end -->` markers the generator now scans. The generated
  builtin table shrank to 21 names; scavenged prose (`write(2)`, `close(2)`)
  can no longer fake an entry.

## The library tier exists now

`lib/nstr.npk` is the first module of it: eq/starts/ends/index_of/contains/
substring, ordinary Nitpick over the floor, imported by a program test and run
through npkc (`tests/backend/programs/string_lib.npk`, which also holds
`nstr_eq` and the floor's `string_equals` to each other, and exercises the §1
trio at runtime). `lib/` is swept by the real parser like `src/`; the layout
note marks it as the in-tree beginning of `nlibc`.

## The instrument learned the true rule

`check_runtime_sigs_agree` demanded set-equality between npkc's floor and the
seed's. The floors may legitimately differ now: the seed compiles only compiler
sources (the shared 15), npkc serves whole programs (all 21). The rule as of
this subcycle: a compiler-only entry is fine **iff npkrt.ll defines its
symbol** — a floor entry pointing at nothing is still refused.
