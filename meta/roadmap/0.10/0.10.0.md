# 0.10.0 — The heap

**Cycle 0.10.** Replace the bump-never-free floor with a real allocator for
programs that run and keep running: size-classed small allocations, a large-block
path, and a real `dalloc` that actually frees — with a header that detects the
corruption and double-free the compile-time analysis cannot reach.

## What it provides

The four native allocator builtins (`alloc`, `calloc`, `ralloc`, `dalloc`) keep
their signatures and gain real behavior:

- **Small allocations** via size-classed slabs (the prototype's `slab_alloc` design,
  rewritten C-free per D-015 — consult for the class layout and the free-list
  structure, never copy through). Allocation is a free-list pop; free is a push.
- **Large allocations** via direct `mmap`, tracked so `dalloc` can `munmap` them.
- **`ralloc`** preserves the 0.7.3 lesson: the copy is bounded by the *old* block's
  recorded size, never the new size (the SIGBUS that taught the floor to carry a size
  header). With a real allocator this becomes grow-in-place where the class allows,
  else allocate-copy-free.

## The header, stated correctly (fixes total_audit C-1)

The spec's "hidden 8-byte CRC32 header" is wrong three ways. Build and document the
real shape instead: a per-block header carrying **the block's size** (already the
floor's discipline, load-bearing for `ralloc`) and **a canary/magic word** —
following the prototype's proven scheme, an atomic magic Xed against a per-pool
secret and the block address, so a use-after-free that writes the freelist is caught
on the next pop (`slab_alloc.cpp`'s `pool_secret` pattern), plus a footer magic for
overrun detection (`wild_alloc.cpp`). **Not a CRC** — a CRC over payload on every
op is an O(size) cost nobody signed up for, and it is not what any allocator in the
project's history uses.

Double-free and header corruption route to `failsafe` (0.10.1 wires the OOM/trap
path). Note this is **defense in depth**: double-free of a tracked binding is
*already* a compile-time error (D-119, the move analysis) — the runtime check covers
what static analysis cannot follow (a `wild` pointer laundered through `extern`, an
`any->` fabricated from an integer). Correct MEMORY_REFERENCE §111 and
BUILTIN_REFERENCE §28 to say exactly this.

## Small correctness items the audit flagged (allocator dive §5)

- **`calloc` overflow:** compute `count * size` with an overflow check (a plain
  `mul i64` silently wraps into an undersized allocation). Harmless in the compiler
  (known-small sizes) but the real `calloc` must check it; state it in the spec.
- **`ralloc(p, 0)`:** C's is implementation-defined and a footgun. Nail it down —
  proposed: `ralloc(p, 0)` frees `p` and returns a non-dereferenceable non-NULL, or
  is simply refused. Decide here.
- **Alignment:** the floor fixes 16. `#[align(N)]` exists in the type system, so the
  real allocator needs an aligned path (over-allocate and round, or a class per
  alignment). Provide it.

## Tests

`tests/backend/programs/heap.npk`: allocate/free/reallocate cycles that reuse freed
blocks (proving `dalloc` frees); a double-free of an `extern`-laundered pointer
trapping with the double-free failsafe code; a `calloc` whose `count*size` would
overflow being refused/trapped rather than under-allocating; an aligned allocation
whose returned pointer meets the requested alignment. The undefined-symbol scan
stays green (any `mmap`/`munmap` go through `sys`, not a libc symbol).

## Done when

The four builtins have real behavior; freed memory is reused; the header canary
detects double-free/corruption and routes to `failsafe`; `calloc` overflow,
`ralloc(p,0)`, and alignment are decided and tested; the three spec passages are
corrected to describe the real header, not a CRC that does not exist.
