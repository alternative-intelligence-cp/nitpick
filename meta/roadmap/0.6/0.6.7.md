# 0.6.7 — The expressions nothing typed

**Cycle 0.6 — Macros and comptime.** Inserted during 0.6.3 (D-129).

## Goal

Every expression kind is typed, and the allow-list that admits the exceptions is
empty.

## The rule, and why it was not being kept

`type_of_expr_inner` reaches every kind by name and falls through to type `0` — the
**invalid** type. That encoding exists so one bad annotation produces one diagnostic
rather than a cascade (0.4.0), so it is **silent by design**. A kind with no case is
therefore not a crash and not a diagnostic: it is a construct the checker accepts
without looking at it.

Eight of the forty-seven are in that state, and two were found by accident while
doing something else:

```nitpick
int32:v = #totally_not_a_macro_or_builtin(3i32);   // 0.6.2 — compiled clean
P:p = P{ x: 1i32, zzz: 3i32 };                     // 0.6.3 — field does not exist
P:q = P{ x: 1i32 };                                // 0.6.3 — `y` never gets a value
```

## Work

1. **`ExprStructLiteralExpr`** — every named field exists on the type, every value
   checks against that field's type, **every field is named**, and no field is named
   twice. The completeness half is a safety property, not an ergonomic one: there is
   no field-default syntax, so an omitted field has no value, and an unassigned
   binding is what D-010 refuses everywhere else.
2. **`ExprArrayLiteralExpr`** — one element type, and the count against the declared
   length for a `T[N]`.
3. **`ExprVectorCtorExpr`** — the same, for vectors.
4. **`ExprPipeExpr`** — the left side is what the right side takes.
5. **`ExprDynCastExpr`** — the target trait is implemented by the source type, and
   is object-safe (0.4.6 already has both questions answered).
6. **`ExprPickExpr`** — the arms share a type, which is the expression-`pick` half of
   D-059 that the statement form already checks.
7. **Empty `UNTYPED_EXPR_KINDS`** in the harness, minus the two 0.6.4 owns.

## Watch for

**The invalid type is what hid all of this, and it is still the right encoding.**
The fix is never "make the fall-through report" — a kind reached with no rule is a
compiler defect, and `type_of_expr_inner` returning `0` for it is how a *program*
error stays one diagnostic. The instrument is the diff, not a runtime check.

**Two of these have a `known`/`which` split waiting to be got wrong.** A struct
literal's field lookup already returns `FieldInfo`, which answers "was there a
field" separately from "what type"; the array and vector cases have the same shape
and the same temptation to merge them.

**Struct literal completeness will break existing tests**, and that is the point:
anything in the suites that omits a field has been relying on a hole. Each one is
read before it is edited.

## Done when

- Every expression kind is named by the type checker.
- `UNTYPED_EXPR_KINDS` holds only what 0.6.4 owns, and then nothing.
- A struct literal naming an absent field, omitting a field, repeating a field, or
  giving one the wrong type is refused, each with its own case.
