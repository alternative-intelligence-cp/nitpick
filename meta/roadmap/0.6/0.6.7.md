# 0.6.7 — The expressions nothing typed

**Cycle 0.6 — Macros and comptime.** Inserted during 0.6.3 (D-129).

## Goal

Every expression kind is typed, and the allow-list that admits the exceptions is
empty.

## The rule, and why it was not being kept

`type_of_expr_inner` reaches every kind by name and falls through to type `0` — the
**invalid** type. That encoding exists so one bad annotation produces one diagnostic
rather than a cascade (0.4.0), so it is **silent by design**. A kind with no case is
therefore not a crash and not a diagnostic: it is a construct the checker accepts
without looking at it.

Eight of the forty-seven are in that state, and two were found by accident while
doing something else:

```nitpick
int32:v = #totally_not_a_macro_or_builtin(3i32);   // 0.6.2 — compiled clean
P:p = P{ x: 1i32, zzz: 3i32 };                     // 0.6.3 — field does not exist
P:q = P{ x: 1i32 };                                // 0.6.3 — `y` never gets a value
```

## Work

1. **`ExprStructLiteralExpr`** — every named field exists on the type, every value
   checks against that field's type, **every field is named**, and no field is named
   twice. The completeness half is a safety property, not an ergonomic one: there is
   no field-default syntax, so an omitted field has no value, and an unassigned
   binding is what D-010 refuses everywhere else.
2. **`ExprArrayLiteralExpr`** — one element type, and the count against the declared
   length for a `T[N]`.
3. **`ExprVectorCtorExpr`** — the same, for vectors.
4. **`ExprPipeExpr`** — the left side is what the right side takes.
5. **`ExprDynCastExpr`** — the target trait is implemented by the source type, and
   is object-safe (0.4.6 already has both questions answered).
6. **`ExprPickExpr`** — the arms share a type, which is the expression-`pick` half of
   D-059 that the statement form already checks.
7. **Empty `UNTYPED_EXPR_KINDS`** in the harness, minus the two 0.6.4 owns.

## Watch for

**The invalid type is what hid all of this, and it is still the right encoding.**
The fix is never "make the fall-through report" — a kind reached with no rule is a
compiler defect, and `type_of_expr_inner` returning `0` for it is how a *program*
error stays one diagnostic. The instrument is the diff, not a runtime check.

**Two of these have a `known`/`which` split waiting to be got wrong.** A struct
literal's field lookup already returns `FieldInfo`, which answers "was there a
field" separately from "what type"; the array and vector cases have the same shape
and the same temptation to merge them.

**Struct literal completeness will break existing tests**, and that is the point:
anything in the suites that omits a field has been relying on a hole. Each one is
read before it is edited.

## Done when

- Every expression kind is named by the type checker.
- `UNTYPED_EXPR_KINDS` holds only what 0.6.4 owns, and then nothing.
- A struct literal naming an absent field, omitting a field, repeating a field, or
  giving one the wrong type is refused, each with its own case.

---

## Done, and what each of the six turned out to need

`UNTYPED_EXPR_KINDS` is **empty**. All forty-seven expression kinds are typed.

| kind | what it now checks |
|---|---|
| `ExprStructLiteralExpr` | the field exists, the value fits it, **every field is named**, none twice |
| `ExprArrayLiteralExpr` | one element type, and the count against the annotation |
| `ExprPipeExpr` | the right side is a one-parameter function the left fits |
| `ExprDynCastExpr` | the trait is implemented, and object-safe |
| `ExprPickExpr` | the arms give the same type |
| `ExprVectorCtorExpr` | **refused, naming the tier** |

### The struct literal is the one that was a safety hole

Three of its four rules got their own code, on D-120's argument: a field that does
not exist is fixed by changing the name or the struct, a mismatched value by
changing the value, and a missing field by adding one.

**Completeness is the half that is a safety property.** There is no field-default
syntax, so an omitted field holds nothing — and an unassigned binding is exactly
what D-010's definite assignment refuses everywhere else. A struct literal was the
one place in the language a value could come into existence without anybody
choosing it.

The plan predicted this would break existing tests and that anything relying on it
"has been relying on a hole". **Nothing broke** — no test in the tree omitted a
field. Worth recording: the prediction was reasonable and the answer was better than
expected.

### Two design points that were not obvious

**The expected type wins when it names the same declaration.** A struct literal
stores a NAME and nothing else, so `Container<int32>{ … }` has no way to say which
`Container` it is except through the context that asked for it. A generic struct
with no context is refused rather than resolved to the bare declaration — which is
precisely what made `Container<int32>` and `Container<string>` one type before
0.4.5.

**A vector constructor is refused rather than typed**, and that is D-085's rule one
layer up. `TYPE_REFERENCE` §15 put vectors in Tier 1 and nothing implements it, so
typing it as INVALID would accept it silently and inventing a type would make the
program mean something the language had not decided. Refusing with the tier named
takes the kind off the list honestly: it is not accepted unchecked.

## What the vector question turned into

Measuring `ExprVectorCtorExpr` found that **two sections of one document described
the same idea twice**: §14's `simd<T, N>` lowering to an LLVM vector, and §15's
`vec2` backed by a struct. **D-135** settles it — `simd<T, N>` is the mechanism,
`vec2`/`vec3`/`vec4`/`matrix`/`tensor` are library types built on it, and seven
keywords were removed because **a library cannot declare a type whose name is a
keyword**.

That also resolved an inconsistency by deletion: `vec4` was in `TYPE_REFERENCE` and
absent from `LEXICAL_REFERENCE`, so it was a type the two specs disagreed about and
the lexer had never heard of.

**And it uncovered a latent parser defect.** The vector-constructor path fired for
*any* builtin type keyword followed by `(` — right while `vec2` and `vec3` were
keywords, wrong for the rest: `int32(5i32)` read as a vector constructor, when a
cast is `x => int32` and what that should read as is a parse error. Narrowed to
`simd`.

**The ternary family stays primitive, and for a stronger reason than the one first
given.** "No hardware implements balanced ternary" is an argument that expires the
day some does. The real one is that ternary hardware is a direction this project
has, so the abstraction must exist for a backend to target — and
`TYPE_REFERENCE` §7 now separates **what a `trit` is** (three states) from **how the
binary rung lowers it** (`i8`), because a compiler that treats those as the same
thing has baked the emulation into the type.

## The fourth layering problem, and why this one was declared rather than moved

Three earlier ones this cycle — `ensure_layout`, `stmt_carries_expr`,
`te_assign_mismatch` — were each a function in the wrong module, found because a
smaller compile group did not contain the module it had been leaning on. Each was
moved to the layer whose question it answers.

**This one is not that.** `type_pick_expr` needs `check_stmt`, and `type_stmt.npk`
already uses `type_expr.npk`. Neither direction is wrong: a statement contains
expressions, and an expression contains statements, because an expression-`pick`'s
arms **are** statement bodies (D-059). The language nests the two inside each other,
so the checker does too — and the cycle is declared rather than worked around,
because the alternative is a duplicated statement walk.

The distinguishing question, worth keeping: **is either direction wrong?** If one
is, move the function. If neither is, say so.
