# 0.6.4 — `comptime`, and the debts it pays

**Cycle 0.6 — Macros and comptime.**

## Goal

A constant expression is folded, and the five places that have been refusing
anything but an integer literal stop having to.

## The rule

**Expansion precedes evaluation.** `comptime(double_it!(3))` expands the macro
first and then evaluates the result, and it nests —
`comptime(add_one!(double_it!(10)))` (`COMPTIME-006/007`). One rule, and it is the
same one 0.6.1 implements: expansion runs to a fixed point before anything reads
the AST.

## The five debts

Each of these refuses a non-literal today and says so **by name**, pointing here.
Each was written that way deliberately rather than silently taking a wrong value —
0.2.8 found that exact path reading an intern-table slot as an array length.

| Site | Refuses | Code |
|---|---|---|
| `resolve_type.npk:667` | an array size `int32[N]` | `TYPE-004` |
| `resolve_type.npk:471` | a `comptime` generic argument `Mutex<Config, 2>` | `TYPE-004` |
| `analysis/locks.npk:176` | an `acquires N` level | `LOCK-003` |
| `analysis/bindings.npk:414` | a `const` global's initialiser | `TYPE-004` |
| `parse_decl.npk:917` | *(the macro body's shape, fixed at parse)* | — |

## And one tripwire, armed in 0.5.0

`tests/frontend/expr_types.npk` asserts that **exactly one** expression in its
program is unrecorded by the checker — the `int32[4]` size, which
`resolve_fixed_array` reads directly and nothing types.

**When array sizes start being folded, that count goes to zero and the assertion
fails.** It was written for this moment, and the note in it says so. The failure is
the tripwire working; confirming the change was intended is the work.

## Work

1. The evaluator: integer arithmetic, comparison, the operators a constant
   expression can contain.
2. `--comptime-budget <N>` — the existing precedent D-057 names for bounding
   expansion, and the bound on evaluation itself.
3. Pay each of the five debts, and **delete the "only an integer literal is
   constant-folded at this rung" sentence from each** rather than leaving it to
   drift into a lie.
4. Re-arm or retire the 0.5.0 tripwire, deliberately, with a note saying which.

## Watch for

**Folding is where a compiler runs the program it is compiling.** Everything the
evaluator can do is something the compiler does at build time, so an unbounded loop
in a `comptime` expression hangs the build — the same failure D-057 bounds
expansion for, arriving through the other door.

**The five sites do not all want the same answer.** An array size must be a
non-negative count; an `acquires` level is a rank; a `const` initialiser may be any
literal including a string. Folding produces a value, and each site still owes its
own check on what it got — the debt being paid is "must be a literal", not "must be
valid".

**Type, not just value.** `Mutex<Config, 2>` needs `2` to be an `int32` because the
parameter says so (D-092: no implicit widening). A folded value carries a type and
the site checks it, exactly as `resolve_value_arg` does today for a literal.

## Done when

- A constant expression folds wherever a literal is accepted today.
- Each of the five sites accepts a folded constant and still refuses a non-constant.
- Evaluation is bounded, and exceeding the bound is an ordinary compile error.
- The 0.5.0 tripwire has been dealt with on purpose.

## What it took, measured

**Four code debts, not five.** The fifth row was the macro body's shape, fixed at
parse — and 0.6.2 settled it a different way (D-125: a body is a declaration body if
it *contains* a declaration, decided by a token scan). Nothing was owed here.

**The evaluator lives in `resolve_type.npk`, and that is forced rather than
chosen.** Folding needs to resolve types (`#size_of<T>`) and resolving types needs
to fold (`int32[N]`). Mutually recursive, so one module — split in two, each would
have to `use` the other and the frontend has no forward declaration.

The layering below is one-way and had to stay that way: a first attempt called
`ensure_layout` from the folder, which is in `type_layout.npk`, which uses this
module. It built under `quickcheck` — where `check.npk` pulls both in — and failed
in `tests/frontend/resolve_types.npk`, which compiles a smaller group. **A cycle
that only shows up in the smallest group that contains one half of it.**

## Two bounds, and the second was found by segfault

The fuel bounds total work. It does not bound recursion depth:

```nitpick
comptime func:forever = int32(int32:n) { pass (raw forever(n)); };
```

Each level spends about three units of a 4096-unit budget and costs several native
frames, so **the compiler's own stack went first** — the checker segfaulted. That is
the same shape D-057 gives for expansion needing two bounds: a deeply nested single
evaluation and one that does not terminate are different mistakes.

`FOLD_DEPTH` is 64, the number `GENERIC_DEPTH` already uses.

The budget also gets its own code — `NITPICK-TYPE-025` — because "this is not a
constant expression" and "it is, and it never ends" send the reader to opposite
places. And the site that asked for the fold does not add its own sentence on top:
one failure, one diagnostic, the rule D-126 already established.

## The whole of section 8, not a subset of it

`MACRO_REFERENCE.md` §8 recovered the evaluator's capabilities from
`COMPTIME-001…013`, and the first pass implemented the easy half — literals,
arithmetic, `while`, calls. Three of §8's rows were missing, and two of them were
holes rather than smaller versions of the feature:

- **The counted `loop(lo, hi, step)` and `$`.** `while` is the easier shape and was
  written first, but `loop` is what `COMPTIME-001` actually uses. `$` needs a field
  on the resolver rather than a slot in the frame, because it is not a name — it has
  a node kind of its own precisely because nobody declared it.
- **Strings** (`COMPTIME-005`) — `string_concat`, `string_equals`,
  `string_byte_length`, `string_is_empty`. A bare-name builtin resolves to **no
  symbol** (AST_REFERENCE 3.3), so these are answered before the declaration lookup
  rather than after it fails. Those four have compile-time answers; every other
  builtin allocates, opens a file, or talks to the kernel, and none of those is a
  thing the compiler does on the program's behalf while compiling it.
- **`assert_static comptime(…)`, short-circuiting to the verifier.** Not built, and
  it has a real home rather than a park: `--verify` (D-068) and the obligation
  machinery do not exist, and an assertion that discharges to a verifier there isn't
  is not a smaller feature — it is a different one.

**A zero-step loop gets its own sentence**, not the budget's. "This did not finish"
is true of it, and so is something narrower the compiler can see at a glance — the
same argument D-120 makes for exhaustiveness having three codes rather than one.

Every specific failure the evaluator can report — the budget, the depth bound, a
division by zero, a step of zero — goes through one place that reports **once**, and
the site that asked for the fold then stays quiet. Printing "this is not a constant
expression" after "this divides by zero" sends the reader nowhere.

## The two type kinds 0.6.4 owed

`#size_of<T>` → `int64`, `#wild_ptr<T>(addr)` → `T->`, `#wild_slice<T>(p, n)` →
`T[]`, and `comptime(...)` types as what it folded to, taking the context type when
the value carries none (D-092, exactly as an unsuffixed literal does).

**Both came off `UNTYPED_EXPR_KINDS`**, which is the allow-list D-129 shipped in
0.6.3 — it shrinks and never grows, and this is the first time it shrank.

The generic argument names what the thing is *of* in both pointer forms:
`#wild_ptr<int8>(a)` is an `int8->` and `#wild_slice<int8>(p, n)` is an `int8[]`.
That is the reading that makes the two consistent rather than one naming the pointee
and the other the pointer.

## The tripwire, re-armed on purpose

`tests/frontend/expr_types.npk` expected its unrecorded count to reach zero here.
**It did not move, and that is right: folding is not typing** (D-131). `fold_const`
computes a value and the type it carries, but never goes through `type_of_expr` and
records nothing in `ExprTypes` — whose readers are the 0.5 analyses, which walk
bodies and never enter a type node.

The assertion still says something true. The note now says why, which is the part
that changed.

## What the acceptance suite is for here

**The value is observed through the TYPE, and it has to be.** A checker does not run
the program, so `if (x != 55i32) { exit 2i32; }` proves nothing. An array's length
*is* part of its type, so `int32[comptime(sum_to(10i32))]` passed where an
`int32[55]->` is expected is an assertion the checker enforces — and any other
number stops the file compiling. Six lengths are pinned that way.

## Three existing tests asserted the debt, and each was read before it was edited

- `tests/frontend/type_generic.npk` — `Lock<Point, (COUNT)>` was refused; it folds
  now. Replaced with a **local**, which is what is still refused, keeping the same
  code so the rule still reads as one rule.
- `tests/analysis/rejection/definite_assignment.npk` — `const COMPUTED = MAX;` folds;
  a `const` initialised from a **`fixed`** global does not, because `fixed` is
  assigned once at RUN time.
- `tests/analysis/rejection/lock_levels.npk` — `acquires (1i32 + 1i32)` folds; the
  same `fixed` substitution keeps the case.

Each replacement moves the test from "the rung cannot fold this" to "this is not a
constant", which is the distinction the debt existed to blur and no longer does.

## Done, and what is checked by what

- `tests/accept/folding.npk` — the four debts, six pinned lengths, an `acquires`
  ordering that still passes, and the two newly-typed kinds. Named `folding` and not
  `comptime` because **`comptime` is a keyword**, and a module named after one
  reports `NITPICK-RESOLVE-005` at the `mod:` line, which reads as a missing file.
- `tests/types/rejection/comptime_bounds.npk` — recursion, the depth bound.
- `tests/types/rejection/comptime_loop.npk` — a loop, the fuel bound.
- `tests/types/rejection/not_constant.npk` — a local, a `fixed` global, and a
  `comptime` over a non-constant.
