# 0.6.3 — Splicing

**Cycle 0.6 — Macros and comptime.**

## Goal

A macro emits declarations, struct fields and `impl` methods — the things nothing
else in the language can do.

## Why `macro:` survives at all

D-057 kept it on exactly this ground:

> Splicing fields into a struct and methods into an `impl`, and emitting
> mutually-referencing declarations, are things generics, `comptime`, and
> `#[derive]` cannot do. Months of regression tests exist because the feature is
> load-bearing, not vestigial.

So this subcycle is the justification for the whole cycle. Everything else a macro
does, something else in the language does better.

## Work

1. **Multiple declarations from one invocation**, including ones that reference
   each other (`bug591`, `bug592`).
2. **Struct field splicing** (`bug595`, `bug597`, `bug598`).
3. **`impl` method splicing** (`bug596`, `bug599`).
4. The refusals: a splice whose result does not fit where it landed — fields into
   something that is not a struct, methods into something that is not an `impl`.

## Watch for

**Every downstream pass assumes a declaration was written by a person.** A spliced
field participates in layout (0.4), a spliced method in coherence and object
safety (0.4.6), a spliced declaration in the module graph (0.3). None of those
passes has ever seen a declaration that arrived after parsing, and each has
invariants worth re-reading before assuming they hold — `collect_impls` in
particular walks a module's members once, and 0.5.1 already found it silently
skipping a nesting level it had not been told about.

**Cross-referencing declarations mean order is not enough.** `bug591`/`bug592`
emit declarations that name each other, so they cannot be resolved as they are
emitted. That is the same constraint cycle 0.3 solved with three passes — collect
every declaration, bind imports to a fixed point, then resolve bodies — and the
expansion output has to be complete before any of them runs.

**A spliced name can collide.** Two invocations of the same macro in one module
emit the same declaration names, and the hygiene rule (0.6.2) is about *reading*
names rather than *emitting* them. Whether emitted names are hygienic is a question
the corpus may or may not answer, and 0.6.0 is where that gets recorded.

## Done when

- One invocation emits several declarations, and they may name each other.
- Fields splice into a struct, and methods into an `impl`.
- A splice into the wrong kind of thing is refused, naming both.
