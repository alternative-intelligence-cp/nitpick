# 0.8.2 — The undefined-symbol build check, and the D-011 symbol set

**Cycle 0.8.**

## The check

D-011 item 3, verbatim: *"After codegen, scan every object for undefined external
symbols and fail the build on anything outside an explicit allowlist of
self-provided runtime symbols."* Implemented as `check_zero_dependency`, run on
**every object the harness produces** — every seed-compiled test, every
npkc-compiled program, `stage1.o`, and `npkrt.o` itself:

- A program object's undefined set must be ⊆ the symbols `npkrt.ll` **defines** —
  the allowlist is parsed out of the runtime's own `define` lines, never a config
  file, so a symbol is allowed exactly when the project provides it.
- **`npkrt.o` may need exactly one symbol: `main`.** Anything else would mean the
  floor is standing on something.

Negative-controlled with the canonical case: an `sdiv i128` object is refused
with *"needs symbol(s) the project does not provide: `__divti3`"* — the exact
libcall D-011 measured LLVM emitting behind the program's back.

## What the first scan proved

Today's objects are **already clean**: `stage1.o` needs exactly the runtime
floor's `npk_*` set and nothing else, and `npkrt.o` needs only `main`. The second
fact settles a real hazard quietly: `npkrt`'s `memcpy`/`memset`/`memmove` are
defined *in terms of* `llvm.memcpy`-family intrinsics, and if `llc` ever lowered
one of those as a **libcall**, the runtime's own `memcpy` would call itself. The
scan shows the intrinsics lower inline today — and will name the symbol on the
day any toolchain change makes that stop being true.

## Why `__divti3` and family land with 0.9, guarded from today

D-011 item 2 asks for Nitpick-native `__divti3`, `__udivti3`, `__modti3`,
`__umodti3`. Nothing in the language can *reach* them yet — the wide integer
types are rung-refused until 0.9, so hand-writing 128-bit shift-subtract division
now would be TCB code with zero callers and zero tests, which
`check_codes_tested`'s whole philosophy says is a rule nobody has watched work.
They land in 0.9 **with** the types whose conformance tests can exercise them —
and this subcycle's check is what makes that scheduling safe rather than
forgetful: the day 0.9 first emits `sdiv i128`, the build fails **by name** until
the routines exist. The gap cannot ship silently; that is what "enforce it
mechanically" was for.

`memcpy`/`memset` — the other half of the D-011 minimum — already exist in
`npkrt.ll` as hand-written IR and are now under the scan.

## Done when

- Every object the harness produces is scanned on every full run.
- `npkrt.o`'s undefined set is `{main}`, checked as its own line.
- The `__divti3` control is refused by name.
