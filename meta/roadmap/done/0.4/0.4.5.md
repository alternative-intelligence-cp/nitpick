# 0.4.5 — Member access, calls, and UFCS

**Cycle 0.4 — Type system and checking.**

## Goal

Everything 0.3.5 deliberately left alone.

## Work

1. `p.x` — a struct field, **auto-dereferencing** through pointers (D-006). `.`
   is the only member operator; `->` is type-position only.
2. `p?.x` — the same, short-circuiting on absence.
3. `Net.Disconnect` — an enum variant. Identical in the AST to `math.sqrt`, and
   told apart **here**, by what the base resolved to in 0.3.5.
4. `math.sqrt` — through a module alias.
5. Calls: arity, argument types, and the variadic `..*T[]` (D-070).
6. **UFCS** — `p.magnitude()` resolves to `Point_magnitude(p)` (D-006). The
   receiver is already apart from the callee in the AST (0.2.8), which is what
   makes this a lookup rather than a rewrite.
7. Index: bounds-checked, on arrays, slices and pointers.

## Watch for

**Auto-dereference must not hide a level.** `pp.x` where `pp` is `Point->->` is
either an error or two dereferences, and whichever it is has to be the same
everywhere. Decide it once, here, and write it down.

## Done when

- A field, an enum variant and a module member all resolve, and each says
  something useful when it does not exist.
- UFCS resolves, and a method that does not exist names the type it was sought on.
- Calling with the wrong arity names both counts.

---

## Outcome

`src/frontend/type_layout.npk` — struct layout, field lookup, enum variants.
`src/frontend/type_access.npk` — member access, indexing, calls, UFCS.

**D-098** answers the question the plan flagged: **auto-dereference is one level
only.** `pp.x` on a `Point->->` is an error naming `<-`, and the same rule
applies to UFCS, because a method call that peeled differently from a field
access would make `.` mean two things one character apart.

### Struct layout was a placeholder

0.4.1 interned a named type from its declaration and left the size at zero —
"computed once every field's type is known". Field types become known here, and
the debt was worth tracking: a `Result<Point>` built from a zero-sized `Point` is
four bytes where it should be twelve, and nothing downstream would have said so.
The layout walk and the field lookup are **the same walk**, because splitting
them would mean two traversals that have to agree about padding.

### An enum variant and a module member are the same node

Told apart by what the base resolved to, exactly as 0.3.5 deferred. Two things
this needed:

- **The namespace question has to be asked before the base is typed as a value.**
  `Net` is an enum name, and typing it as an expression reports "`Net` is a type,
  not a value" — right in general, wrong where a type name is exactly what belongs.
- **A `Scope` records its parent, not its owner**, so a module's members were
  unreachable from its name. `Symbol.inner` now carries the scope a namespace
  name opens; walking the tree for a child scope would have found every sibling
  block too.

### Three defects, one shape between them

**`namespace_member` returned a type id and used zero for "not a namespace".** So
a variant that did not exist reported its own error, returned zero, fell through
to the value path, and reported a second, misleading one. Split into `handled`
and `type_id` — the same *whether* versus *which* fix as `expr_shape` and
`num_width_kind`, now the fourth time.

**`expr_generic_count` reads the payload, and a method call's payload is the
method NAME.** Asking a `MethodCallExpr` for a generic count returns an intern
index and slices the argument window by it. The accessor is only meaningful on
`CallExpr` and `BuiltinExpr`; that is now written where it is defined.

**The test built its values with `NULL`.** `NULL` is valid only where a pointer
is expected, so a `NULL`-initialised slice is an error in its own right and every
case built on one was measuring that instead of what it meant to. The values come
in as parameters now.

### `Optional` construction — closed by D-099, after a wrong answer

The item raised here was real: nothing built an `Optional`, so `??` and the `?.`
positive case had no value to test against. The first answer was wrong and is
worth recording, because it is the failure D-097 exists to prevent, repeated.

Reasoning from symmetry with `Result{…}`, an `Optional{…}` literal was drafted —
node kind, shared parser, typing rule, passing tests. **Nothing was missing.** The
prototype has two test files named for the question (`test_nil_optional.npk`,
`test_nil_vs_null.npk`) in which an `Optional` is emptied by writing `NIL` and
filled by writing the value, with no constructor anywhere. `NULL` is no pointer;
`NIL` is no value. That is the user's original design, stated as a pair.

D-097's countermeasure — *find the production, the table, or the prototype test
that fixes its shape* — was applied to `Some` and then not to its replacement.
**Striking one invention is not the same as checking whether the thing it replaced
needed inventing.**

What the withdrawn draft did leave behind is independently right and is kept: the
`Result{…}` parser matched the two names it knew and let anything else fall
through untouched, so `Result{value: v, is_error: true}` parsed clean and silently
dropped a field — and the test asserted **zero errors** for it. Unknown names,
repeated fields and non-identifier field names are now all refused under
`NITPICK-PARSE-008`.

Three defects surfaced on the way, each a rule that was written at one spelling
and not the other:

- **Only `NIL` was not reading its context.** `NULL` had been contextual since
  0.4.2, so `int32?:a = NIL;` reported a mismatch against the type it constructs.
- **The context-taking node list held only unsuffixed integers**, so `NIL == opt`
  and `NULL == p` failed while `opt == NIL` and `p == NULL` worked — the same
  question, refused in one direction.
- **`?.` would have manufactured `Optional<Optional<T>>`** behind the back of the
  rule that refuses the annotation. It flattens.

### Variadics — closed by D-100

Plan item 5, and it was worse than "not done": `fn_type` built a plain `TY_FUNC`
from the fixed parameters and dropped the variadic spec, so every variadic call
was checked against a function with one fewer parameter than it has. The
zero-extra-arguments case passed by accident and every other one was refused for
the wrong reason.

`TY_FUNC_VARIADIC` is a distinct kind rather than `TY_FUNC` plus a flag, for the
reason `AST_REFERENCE.md` already gives about `FailsOn`/`NeverFails` — *an
encoding that can be misread by ignoring a field* is a description of the bug
being fixed, not a hypothetical. The window's last entry is the variadic
parameter typed as its slice, so the element is `type_elem` of it and nothing
extra is stored.

`..^` position checking came with it, which 0.4.2 had explicitly left here: it
must expand into a tail that exists, must not fill a fixed parameter, and nothing
may follow it. Its type is the collector rather than the element, which is what
makes D-026's "`..*` and `..^` are inverses" an enforced claim.

One accessor was named for the wrong thing: `variadic_elem` returned the **slice**,
so a caller trusting the name would have checked every trailing argument against
`int64[]` instead of `int64` — accepting slices and refusing values, the defect
inverted. Renamed `variadic_type`.

Both new rules were verified by making them fail: disabling the variadic kind
check, and checking the tail against the slice instead of its element, each break
the suite at the case that names them.

### The statement walk — closed by D-101, and it was bigger than it looked

Assignment was the reported symptom. The finding was that `check_stmt` answered
**nine of twenty-five** statement kinds and returned quietly for the rest —
including every kind that contains statements. An `if` had its condition checked
and its body ignored; nothing inside any block, loop, `pick` arm or `defer` was
type-checked at all.

**The suite reported the hole as a convention.** `type_stmt.npk` unrolled a
function body's top level under a comment saying nested blocks were not descended
into — true of the checker, not of the helper. A test that works around a hole in
the thing it tests turns a defect into a house style, and this one hid sixteen
unvisited kinds for two subcycles.

Third instance of this failure in three passes, so it gets the answer the other
two got: every kind reached explicitly, an out-loud "nothing to check" for the
label-only kinds, `NITPICK-TYPE-011` where the walk used to return quietly, and a
total `stmt_is_classified` the suite walks `1..STMT_KIND_MAX` against. Both were
verified by making them fail.

Two defects fell out. `check_cond` was being called on a `till`, whose slot `a` is
its **body** — a `StmtId` read as an `ExprId`, the third slot-means-two-things bug
here. And `resolve_stmt`'s trailing catch-all absorbs any kind added later and
reads slot `a` as an expression regardless; the checker uses a named list instead.

Assignment itself: target must be storage, value must `fit` (the same predicate
every other slot uses), and `op=` answers to its operator's own rule by calling
it — `type_arithmetic` and `type_bitwise` now take a `Span` rather than an
`ExprNode`, which is all they ever read.
