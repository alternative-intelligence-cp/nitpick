# 0.4.3 — Casts

**Cycle 0.4 — Type system and checking.**

## Goal

`=>` converts only when nothing can be lost. `=>!` is the sole opt-out (D-021).

## The rule

**`=>` is a compile error if loss is possible** — not if loss *occurs*, if it is
*possible*. `int64 => int32` is refused whatever the value happens to be, because
the check is on types and the value is not known.

`=>!` is the unchecked form and the **only** way to say "I know". It is
deliberately ugly and greppable: an audit for lossy conversions is a search for
one token.

There is no third spelling. `cast<T>`, `#cast<T>` and `@cast<T>` do not exist
(D-021) — one operation, one syntax.

## Work

1. The widening lattice: which integer conversions are lossless in every case.
2. Signedness: `int32 => uint32` loses the negatives and is refused.
3. `bool` and `char8` cast explicitly and never implicitly, in either direction.
4. **`tbb` casts have a width problem** (D-008 §6) — the ERR sentinel is the most
   negative value, so a narrowing cast maps a valid number onto ERR. Read that
   section before writing this.
5. `=>!` accepts what `=>` refuses and is recorded so a later audit can find it.
6. A cast to a `dyn` type is a `DynCastExpr`, not this (0.2.8), and builds a fat
   pointer.

## Watch for

**`=>` between two types of the same width is not automatically lossless.**
`int32 => uint32` and `uint32 => int32` are both refused, and `int32 => tbb32` is
refused for a different reason again.

## Done when

- Every widening pair is accepted and every narrowing pair refused.
- The `tbb` width rule from D-008 §6 is implemented and tested.
- `=>!` accepts exactly what `=>` refuses.

## Carried in from 0.4.2

With implicit widening removed (D-092, corrected), **the cast is the only way to
combine operands of different widths**, which makes this subcycle the one that
restores expressiveness rather than merely adding a feature.

`tests/frontend/type_expr.npk` deliberately does not assert
`(1i32 => int64) + 2i64`: an untyped cast yields the INVALID type, which
suppresses the mismatch the case exists to demonstrate is gone. It belongs here,
where a cast has a type, and it should be the first thing this subcycle asserts.

---

## Outcome

`src/frontend/type_cast.npk` — the lossless set, the three-way answer, and the
`tbb` rules from D-008 §6. `src/frontend/type_names.npk` — `type_display`, lifted
out so cast checking and expression typing can both reach it without depending on
each other. **48 tests pass.**

**D-095** records what `=>` accepts. The rule that mattered most: losslessness is
computed from **value ranges**, not from signedness families. `uint8 => int16` is
lossless and is accepted, where the prototype's rule refuses it — and the reason
to care is that **`=>!` is an audit tool**, so a provably-safe conversion forced
into it is a false positive in the one search that finds the dangerous ones.

Three answers, not two: checked-legal, unchecked-only, and **not a conversion at
all**. `intN => bool` is the third — not a conversion that loses information but
one with no definition, and `=>!` opts out of a check rather than of a meaning.

Integer-to-float goes by **significand width**, so `int32 => flt64` is accepted
and `int64 => flt64` is refused. The significands for `flt256` and `flt512` were
never specified anywhere and now follow IEEE 754-2008 §3.6 rather than a guess —
a guess would not have been visible as one.

### Two defects, both silent

**The seed picked a function by accident.** `type_cast.npk` defined `type_range`
while `type_expr.npk` already had one, and the seed's `self.p.funcs[name] = item`
let the last definition win. It failed in `llc` only because the two signatures
differed; had they matched, the compiler would have been built calling the wrong
function, correctly, forever. The seed now refuses a name claimed twice, and
`_claim` explains why the real resolver reports it as an ambiguous glob import.
Verified by making it fire.

**The width table classified 26 of 45 suffixes.** `num_width_is_integer` and
`num_width_is_float` between them covered integers and floats, and every checker
treated the rest as *no suffix at all* — so `1tbb8` reported "this literal has no
width suffix" while carrying one, and `1.5tfp256` typed as a `flt256` because the
float predicate had swept `tfp` in with the floats. A literal silently becoming a
different type is the worst version of this. `num_width_kind` now emits a `TY_*`
for every suffix, and the two literal-typing functions collapsed into one.

### The transferable part

Both defects are the same shape as 0.4.2's: **a predicate that answers a question
narrower than the one being asked.** `is_integer` answers "is it one of these
twenty-six", and callers read it as "does it have a suffix". `slot a` answered
"what is stored here", and callers read it as "is there a child". In both cases
the honest fix was to return **which one** rather than **whether**, so a case
nobody classified is visibly unclassified instead of silently defaulting.

Three functions now follow that shape: `expr_shape`, `num_width_kind`,
`cast_class`. Each has a value meaning *nobody has said*, and each of those is
either a test failure or a diagnostic — never a default.
