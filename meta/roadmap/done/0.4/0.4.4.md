# 0.4.4 — `Result<T>`

**Cycle 0.4 — Type system and checking.**

## Goal

Every function returns `Result<T>`, and the unary family is the only way through
it.

## The rule (D-013)

**Every function returns `Result<T>` except `main` and `failsafe`.** The AST holds
the declared **success** type; the wrapping is added here.

This is the blueprint philosophy's first facet in its purest form: **a caller
never has to ask whether this particular function needs error handling.** One
rule, no exceptions to remember, and that is worth more than the keystrokes it
costs.

## Decision — is `Result<T>` spellable as a return type?

`func:f = Result<int32>()` — redundant, or a nesting nobody wants?

**Proposed: writing it is an error that says so.** Both readings are worse than
refusing the spelling, and refusing it keeps one way to write a signature.

`Result<T>` stays writable in a **variable** declaration, where it is the ordinary
way to hold a call's outcome before unwrapping — `Result<string>:r = read_file(p);`
is exactly how the compiler's own sources are written.

## Work

1. Wrap declared return types; `main` and `failsafe` excepted.
2. `pass e` requires `e` to be the success type; `fail c` requires a `tbb32`.
3. The unary family, each with its own typing (D-081 gave them a precedence level;
   this gives them meanings):
   - `raw` / `_!` — yields `T`, unchecked
   - `drop` / `_?` — yields nothing, discards
   - `relay` / `_^` — yields `T`, propagates the error, **illegal in `main` and
     `failsafe`** because there is no `Result` to relay into
   - `?` — `T`, with a default
   - `?!` — `T`, trapping with exactly one `tbb32` argument (D-009)
   - `await` — `T`, legal only in `async` (`NITPICK-040`)
4. `.value`, `.error`, and `.is_error` — the last **derived**, never stored
   (D-069).
5. `ok(x)` clears the taint explicitly; `is_err(x)` never traps.

## Watch for

**`relay` runs `defer` and `?!` does not** (D-014, amended). That is a lowering
property, but the typing has to keep them distinct nodes so 0.7 can honour it.

## Done when

- A function's declared type is its success type, and its actual type is wrapped.
- `relay` in `main` is refused, naming why.
- `.is_error` is derived and there is no stored field to disagree with it.

## Outcome

`src/frontend/type_decl.npk` — function signatures, where `Result<T>` is added.
The unary family, the three members, `ok` and `is_err` in `type_expr.npk`.
`Result<T>` and `Optional<T>` resolve as types. **49 tests pass.**

All three done-when criteria hold: the declared type is the success type and the
actual type is wrapped, `relay` in `main` is refused naming why, and `.is_error`
is derived with no stored field to disagree with it.

### `ok(x)` and `is_err(x)` could not be written

**D-096.** Three documents require them — a taint "must be cleared via
`ok(val)`", `is_err` is how a program "tests without trapping", and both are in
`LEXICAL_REFERENCE`'s keyword grammar — and **neither had an AST node.** Being
keywords they never lexed as identifiers either, so `ok(1i32)` was *"expected an
expression"*. The language's only non-trapping failure test was unwritable.

They are now `OkExpr` and `IsErrExpr`, the `move(place)` shape. `is_err` gets a
node rather than being a recognised call name because it **carries a guarantee**:
0.5 and 0.7 have to see which construct is the safe test, and recovering that
from a callee's name is a string comparison standing in for a language rule.

A comment in `resolve.npk` had asserted both were bare-name builtins that
"resolve to nothing and that is correct". One mechanical cross-check — the 36
bare-name builtins against the keyword list — showed the overlap is **zero**.

### `Result<T>` did not resolve

`Result` is a builtin name taking generic arguments, matched nothing in the
scalar table, and fell through to the user-name lookup where a **token kind was
read as an intern index**. D-091 requires the spelling to work outside a return
position, and it is how the compiler's own sources hold an outcome.

### Two smaller things

`ok` was the only way to build a `Result` value, so until it existed the tests
had no way to make one — the first draft cast `1i32 => Result<int32>`, which
D-095 rightly refuses. **Nothing constructs an `Optional` yet**, so `??`'s
positive case is owed to 0.4.5, where an `Optional<int32>:o` declaration gives
one a type. It is noted in the test rather than written vacuously.

The real parser rejected `DeclNode:dn` in the new test: **`an`, `bn`, `cn` and
`dn` are balanced-nonary literals**, not identifiers. The rule that every test
file must parse with the real parser caught it.

### The transferable part

Same as the last two subcycles, third instance: **a comment asserting a
relationship that nothing checked.** "Slot `a` is an operand on every node that
has one" (0.4.2). "`is_integer` means it has a suffix" (0.4.3). "`ok` and
`is_err` are bare-name builtins" (here). Each was true or plausible when written,
none was ever verified, and each failed silently.

The cheap countermeasure keeps working: **when a comment quantifies over a list,
cross the two lists mechanically.** It took one command here and settled the
question outright.

## Correction pass (D-097)

The first pass got three things wrong, all the same mistake: **giving semantics
to a construct from a passing mention, without establishing its shape.**

**`ok` is not a `Result` constructor.** The prototype settles it —
`tests/special/test_unknown_ok.npk` shows `ok(x)` asking whether an ordinary
value is `unknown`. And D-007 had already removed user-writable `unknown`, so it
was an operator whose subject no longer existed, offering a second route to what
`.is_error` does. **Removed from the language.**

**`is_err` takes a `tbb`, not a `Result`.** `OP_REFERENCE` §5 says why: branching
on an ERR value traps, so a program needs one test that is safe on every value.
The half-sentence I read was preceded by the one that fixes the operand.

**`Result{value: v, error: e}` is the constructor, and it did not parse.**
`TYPE_REFERENCE` §11 has carried the full `pass`/`fail` desugar table all along,
and `ReturnStmt` is restricted to this form. The struct-literal path is gated on
`TokenKind.Ident` and `Result` is `KwResult`, so the real parser answered
`NITPICK-PARSE-002` for the form every function ultimately returns. I never
looked for it, then wrote in these notes that nothing constructs a `Result`.

`is_error` stays derived — confirmed, not changed. The prototype stores it as an
`i8` third field; D-069 departed deliberately, and the literal has two fields.

Also corrected: the desugar table wrote `error: 0i32` while the struct definition
two lines above said `tbb32:error`, and with no implicit conversion between them
(D-092, corrected) the table was contradicting itself. Now `0tbb32`.

### Statement checking (plan item 2), and identifier typing under it

`src/frontend/type_stmt.npk` closes plan item 2, and it needed a foundation
neither 0.4.2 nor 0.4.3 had: **an identifier's type**. Resolution had already
stored the symbol index in slot `a` (0.3.5), so this is a lookup rather than a
second search — a local reads its `VarDeclStmt`'s annotation, a parameter its
`ParamDecl`'s, a function name gets a `func Result<T>(P…)`.

Nothing is inferred anywhere. Every binding states its type, which is what makes
`int8:n = 10;` work and makes it the *only* reason it works: the annotation is
the context the unsuffixed literal reads (D-092). Reading a parameter declared
`Type:_~name` is now an error naming the `_~` (D-089).

`pass v` is checked against the **success** type and `fail c` against `tbb32`,
because that is what they desugar to. `fail` in `main`/`failsafe` is refused for
the reason `relay` is. `return` takes a `Result{…}` literal and nothing else.
Every condition is a strict `bool`, and `exit` is legal only in the two terminal
functions.

### Two silent slot bugs, both found by one wrong count

**A declaration's window starts with a four-slot header.** Walking it raw read
those counts as node indices, so the test's own module walk visited the function
twice and every diagnostic appeared twice. `item_member` is the accessor that
knows about the header.

**`stmt_value` reads slot `b`, and `pass`/`fail`/`return`/`exit` keep their
operand in slot `a`.** `stmt_value` is the *assignment* accessor — its name reads
like "the value this statement carries", which is exactly the wrong thing on a
`pass`. It typed whatever node index sat in slot `b`. Split into
`stmt_assigned` (slot `b`, assignment) and `stmt_operand` (slot `a`, the
value-statements), with the near-miss written down at the definition.

Both are the accessor-layer version of D-094's rule: the layer exists so call
sites never touch slots, and it only works if each name means exactly one slot.
