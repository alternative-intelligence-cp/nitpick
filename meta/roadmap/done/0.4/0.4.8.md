# 0.4.8 — Diagnostics, suites, and closing

**Cycle 0.4 — Type system and checking.**

## Goal

Every type error has a code, a span, and a test. The checker is complete.

## Work

1. Codes centralised, as in 0.1.6, 0.2.1 and 0.3.6.
2. `tools/check.npk` — the full frontend: load, resolve, type-check, report.
   `resolve_check` becomes its earlier half.
3. A type-rejection suite, sited like `tests/modules/rejection/` and for the same
   reason: a type error is refused at a **different stage** from a rung error, and
   collapsing the two makes "correctly refused" mean less.
4. Close the cycle — `done/0.4/`, ROADMAP, push.

## The check worth building here, and why it is different

0.2 and 0.3 each got a mechanical completeness check — every node kind
constructible, every identifier bound. **Type checking does not have one of that
shape**, because the failure mode is different: a walk that forgets a case is
silent, but a *rule* that is subtly wrong produces a program that compiles and
misbehaves. No structural diff finds that.

What substitutes for it is **negative coverage**: the specification of a type
system is what it *refuses*. So the measure here is that every rule stated in
`TYPE_REFERENCE.md` and `TRAITS_REFERENCE.md` has a test that shows it being
enforced — and the honest version of that is a checklist in this file, worked
through, not a script that reports a number.

## Done when

- Every code has a test.
- Every rule in the two references has a test that shows it refusing something.
- `tools/check.npk` validates a whole program and emits nothing.
- The cycle is archived and pushed.

# The negative-coverage checklist

**The specification of a type system is what it refuses**, so this is the measure,
and it is a checklist worked through rather than a script reporting a number. A
script could only count codes; whether each *rule* is enforced is a question about
meaning, and the only honest way to answer it is to write the program the rule
forbids and watch it be refused.

Every row is a file in `tests/types/rejection/`, run through `tools/check.npk` —
the real frontend, over a whole program.

**Three codes are tested elsewhere on purpose, and the reason is the same in each
case: the rejection suite runs whole programs, and these three are not about a
program.**

- **`TYPE_INTERNAL`** is a defect in the *checker*, not in any source — a statement
  kind the walk has no entry for. There is no program that provokes it, which is
  the point; `type_stmt.npk` walks `1..STMT_KIND_MAX` against the classification
  table instead, so the next statement kind cannot arrive unvisited.
- **`TYPE_GENERIC_DEPTH`** needs a type nested 65 deep. `type_generic.npk` builds
  the source with a loop, because sixty-five levels typed by hand is a
  transcription error waiting to happen and the *number* is the whole test.
- **`TYPE_UNKNOWN`** and **`TYPE_NOT_A_TYPE`** fire on names, and a program whose
  names do not resolve is refused by `resolve_check` before it reaches a type
  checker at all — which is what `tests/modules/rejection/` is for. They are
  reachable here only through a builtin constructor no rung supplies yet, which is
  a rung statement rather than a type rule.

**What this checklist is not.** It does not prove the rules are *right* — only that
each is enforced. 0.2 and 0.3 each got a mechanical completeness check because
their failure mode was a walk forgetting a case; type checking's failure mode is a
rule that is subtly wrong, which produces a program that compiles and misbehaves,
and no structural diff finds that. Negative coverage is the closest honest
substitute, and its value is exactly proportional to how faithfully each case is
written from the specification's own example.
