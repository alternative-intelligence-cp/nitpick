# 0.6.6 — Diagnostics, the suites, and closing Phase A

**Cycle 0.6 — Macros and comptime.**

## Goal

Every rule has a code, a span and a test — and **Phase A is over**.

## Work

1. Codes centralised, as in 0.1.6, 0.2.1, 0.3.6, 0.4.8 and 0.5.7.
2. `tests/expansion/` — the suite shape this cycle needs and the others did not.
   See below.
3. The negative-coverage checklist against D-057's rules, worked the way 0.5.7's
   was.
4. Close the cycle, and close Phase A: `done/0.6/`, ROADMAP, push.

## The suite shape this cycle needs

Every earlier cycle could assert on **diagnostics** — a code and a span, or
silence. That is enough when a pass reads the AST and reports.

**Expansion rewrites it**, and a rewrite that is wrong in a way that still
type-checks produces no diagnostic at all. The program compiles and means something
other than what was written, which is the failure mode the whole cycle README
opens with.

So this cycle needs tests that assert on **what the expansion produced**, not only
on what the checker said about it. The cheapest honest form is a program whose
expanded body is *observable* — it computes a value that only the correct expansion
produces, and `tests/conformance/` already asserts exit codes. A macro that expands
wrongly but plausibly then fails on the answer rather than on a diagnostic.

**That is a real gap in the harness and it is worth naming here** rather than
discovering at the end: nothing in the current harness compares ASTs, and building
an AST-comparison rig is a larger thing than this subcycle should absorb. Exit-code
observation covers the cases that matter and costs nothing new.

## The negative-coverage checklist

Every rule in D-057, against the case that shows it refusing:

- expansion exceeding its **depth** bound
- expansion exceeding its **iteration** bound, the `m!()` calls `m!()` case
- a macro body naming something absent from its **defining scope**
- `#caller(NAME)` naming something absent from the **call site**
- a splice into the wrong kind of declaration
- a `comptime` expression that cannot be folded
- `comptime` evaluation exceeding its budget
- a `derive` of an underivable trait
- a `derive` beside a hand-written impl of the same trait

## Watch for

**Spans are the thing this cycle most easily gets wrong.** A diagnostic about
expanded code points into a macro body the reader did not write, at a call site
that does not obviously relate. Whether a span carries both origins is 0.6.1's
decision; **this is where it gets tested**, because a span rule that is only
described is a span rule nothing checks.

**Phase A ends here, so the closing note is bigger than a cycle's.** What the
artifact is, what it refuses, what the six cycles cost and what they taught —
`ROADMAP.md` carries a per-cycle retrospective and Phase A deserves one of its own.

## Done when

- Every code in the cycle has a test.
- Every rule in D-057 has a case showing it refuse something.
- At least one test asserts on **expansion output** rather than on a diagnostic.
- Cycle 0.6 is archived, Phase A is closed in `ROADMAP.md`, and both are pushed.

## What it took, measured

### Three checks, because six cycles said the same thing and nothing enforced it

**Codes centralised** has been the closing note of 0.1.6, 0.2.1, 0.3.6, 0.4.8 and
0.5.7, always for the same reason: *a mistyped literal at a call site silently
invents a new code, and the test asserting the old one then fails for a reason
unrelated to the bug it guards.* Six cycles said it; nothing checked it.
`check_codes_centralised` does now, and the tree was already clean — which is the
answer you want from a check like this and not a reason to have skipped it.

**Every code has a test** — `check_codes_tested`. 89 codes, 77 had cases. The
twelve split three ways, and the third category is the one worth having:

| category | count | what it means |
|---|---|---|
| internal | 5 | a defect in this compiler. No source triggers one, and a test asserting it would be asserting the compiler is broken. |
| **ahead of the language** | 3 | the rule is **written, correct, and unreachable** because the construct it governs does not exist yet. |
| open | 1 | the C variadic tail, a question rather than an omission. |
| fillable | 3 | filled here. |

The three **ahead of the language** are `BORROW_SPAWNED`, `BORROW_SUSPENDED` and
`BORROW_CAPTURED` — there is no spawn, no reachable `await` and no closure in the
language yet. They were written early on purpose, and `escape.npk` says why: *a rule
added AFTER the analysis is verified is a re-verification, and this project gets one
Astrée run.* Cycle 1.1 makes them testable.

The three filled: the macro **depth** bound, a `Result{…}` **wrapper field**, and an
**untracked borrow** (`for` over a borrow, `pick` on one).

### A bound that was declared and not enforced

`EXPAND_DEPTH` was 32 and nothing read it; `CLONE_FUEL` at 512 did the work. So the
compiler carried a constant naming a bound it did not enforce, and enforced one
whose name did not say what it was. **A number nothing reads is worse than no
number** — it reads as a decision somebody made. One depth bound now, named for
what it does, and 512 rather than 32 because it counts *nodes*.

## The suite shape: the plan's proposal cannot work

The plan suggested `tests/conformance/`, which compiles and RUNS through the seed.
**The seed has no macro support at all** — not in its parser, its checker or its
emitter — so a conformance test containing one does not build.

`tests/frontend/expansion_output.npk` asserts in-process instead, which is better
anyway: it links the real expander, runs it to a fixed point, and then **walks the
resulting AST**. Not the general comparison rig the plan rightly says is too large;
targeted assertions about member counts and names, which is what the failure mode
needs — a rewrite that is wrong in a way that still type-checks produces no
diagnostic at all.

Writing it produced its own lesson: **a file's own `mod:` line is a member**, so
every count includes it. The first version counted without it and one of four cases
passed anyway, on a number that was right for the wrong reason.

## Spans: the rule is checked now rather than described

`MACRO_REFERENCE.md` §10 left this open after 0.6.1. A node in an expanded body was
**written** in the macro and **instantiated** at the call site, and its span carries
only the first — so "cannot find `only_local` in the scope this macro was written
in" reported the body's line, about a declaration the reader may not have written,
while the line that made it wrong appeared nowhere.

**The finding keeps the body's location and a note carries the invocation.** Three
choices inside that:

- **A span range, not a mark on every node.** A diagnostic is a source location, not
  a node handle, so mapping one back to its expansion is done in source terms. A
  macro body occupies a contiguous run of lines.
- **One entry per instantiation, not per macro.** A body expanded twice has two
  invocation sites and only one may be at fault.
- **Attached just before reporting.** A diagnostic about expanded code can come from
  the resolver, the type checker or any analysis, none of which know about macros.
  Teaching each would be five places to forget it.

Two smaller decisions followed. `check` prints `note CODE line:col`, because
otherwise every expansion-related rejection test would have to assert a code about a
**location** among its errors. And the harness gained `expect-note:` /
`expect-note-at:`, so the note is asserted **with its location** — the location is
the content of the note, and *a span rule that is only described is a span rule
nothing checks.*

## And one dependency that was never declared

`stmt_carries_expr` lived in `type_stmt.npk`. It is a question about a statement
**kind** — about the grammar — and nothing about it needs a type, but living in the
type checker made every module that asked it depend on the type checker. The
expander does ask, and `expansion_output.npk` compiles a group with the expander and
without the checker: it did not build. **A dependency that only holds because some
other group happens to pull both in is not one anybody declared.**

## Why Phase A does not close here

Two things are scheduled before it, and both were found *after* this subcycle was
planned:

- **0.6.7** — six expression kinds are never typed (D-129), struct literals among
  them. A checker that accepts `Point{ zzz: 1i32 }` does not "validate completely",
  which is the whole of what Phase A's artifact claims to be.
- **D-127** — which was recorded as "something writes past the end of its own
  allocation" and is **not that**. It is a call passing nine arguments to a
  ten-parameter function, which the seed never checked. Settled in 0.6.7; the entry
  keeps the wrong theory on the record because what it cost is the useful part.

Closing before either would be closing on a claim that is not true yet. The close
itself — `done/0.6/`, the ROADMAP retrospective, Phase A's own — is the last thing
this cycle does, after both.
