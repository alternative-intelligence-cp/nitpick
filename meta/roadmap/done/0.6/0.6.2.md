# 0.6.2 — Hygiene

**Cycle 0.6 — Macros and comptime.**

## Goal

An identifier in a macro body means what it meant where the macro was **written**,
and `#caller(NAME)` is the only way to mean anything else.

## The rule, and why it is a flip

The prototype resolves a macro-body identifier in the defining scope, notices when
the call site disagrees, emits `NITPICK-061 MACRO_HYGIENE_VIOLATION` — and **keeps
the caller's binding anyway.** `bug603` states the intent outright: "the macro
doesn't use `#caller()`, so the back-compat path keeps the caller-scope binding
while NITPICK-061 surfaces the hazard."

D-057 calls that what it is:

> A back-compat path, not a design. And it is precisely the failure the blueprint
> philosophy exists to prevent: **the macro means something different depending on
> where it is invoked**, with a warning as the only guard. A warning is not a
> mechanism; it is a request that someone be paying attention.

Flipped, in four parts:

1. An identifier in a macro body resolves in the **defining scope**. Always.
2. If it does not resolve there, that is a **compile error** — never a silent
   fallback to the caller's scope.
3. **`#caller(NAME)`** is the sole way to reach the call site.
4. **`NITPICK-061` disappears as a warning**, because the hazard is structurally
   absent rather than detected.

## Work

1. Resolve macro bodies in their defining scope, which means the expansion pass
   has to carry that scope with each body it instantiates.
2. Refuse an unresolved identifier, naming the defining scope it was looked for in.
3. **`#caller(NAME)`** — and note that `caller` is **not currently a builtin**:
   `builtins.npk` does not list it, so a program writing `#caller(x)` today gets
   "unknown name" from the resolver. The sigil is right (D-020, D-046); the entry
   is missing.
4. Delete `NITPICK-061` rather than leaving it unreachable. A warning whose hazard
   cannot arise is a code a reader will eventually try to trigger.

## Watch for

**This is the one subcycle where the prototype is not the oracle.** Everywhere
else in this project the prototype's behaviour is what to check against; here it
is explicitly what to replace, and its 49 tests encode the old rule. A test
recovered from the corpus that asserts the caller's binding wins is asserting the
thing D-057 removed.

**`#caller` is an escape hatch, so it must be greppable and it must be checked.**
Naming something through it that does not exist at the call site is the same error
as failing to resolve in the defining scope, and it needs its own diagnostic —
otherwise the opt-out is the one path with no rule.

## Done when

- A macro body naming something from its defining scope resolves there, even where
  the call site has a different binding of that name.
- A macro body naming something absent from its defining scope is refused.
- `#caller(NAME)` reaches the call site, and is refused when the name is not there.
- `NITPICK-061` no longer exists.

## What was actually there, measured

The plan assumed hygiene was the work. Two things had to be built first, and
neither was optional.

### Three of the four invocation positions did not expand at all

0.6.1 made all four **parse**. Only the declaration-position one **expanded** —
`expand_module` scanned a module's members for `DeclMacroSplice` and never entered
a body. So:

```nitpick
int32:a = #doubled(3i32);                          // never expanded
int32:b = #totally_not_a_macro_or_builtin(3i32);   // compiled CLEAN
```

Both reached the end of the frontend as `ExprBuiltinExpr`. `type_of_expr_inner`
has no case for that kind, so it fell through to type `0` — the **invalid** type,
which exists to suppress cascades and is therefore silent. **Verified: exit 0, no
diagnostics.**

Hygiene cannot be built on that, because every hygiene test in the corpus —
`bug600` through `bug605`, all six — is an **expression-position** invocation.

And it is why 0.6.1's own acceptance case passed without proving anything.
`#doubled(3i32) + #doubled(10i32)` was written to show that two instantiations are
two subtrees; it showed that an unexpanded builtin types as invalid.

### The parse could not tell a splice from an expression

`#name(...)` is spelled the same in all four positions (D-046), and 0.6.1 made `#`
count as a declaration start so that `macro:outer = () { #inner(); func:f3 = …; };`
would parse. That made **every body beginning with `#` a declaration body**:

```nitpick
macro:opt   = () { #caller(x) + 1i32; };   // refused: "not a single expression"
macro:twice = () { #setup(); #setup(); };  // a statement macro cannot call one
```

D-125 settles it: **a body is a declaration body if it contains a declaration**,
decided by a token scan from `{` to its match before the first item is parsed.
That is what §1 of the reference already said.

## What hygiene cost, once D-124 was decided

**A macro is invocable only in the module that declares it.** With that, the
defining scope and the landing scope are the same scope, and hygiene collapses:

- declaration position — nothing at all; the expansion landed where it was written
- statement position — the expansion becomes a **block** whose parent is the module
  scope, which also keeps the body's locals from colliding with the caller's
- expression position — one flag on the substituted node, one switch in
  `resolve_expr`
- type names — nothing; no type is declared inside a function, so every type name
  already resolves at module scope or above

Without it, all six scope-threading walks (`resolve`, `resolve_type`, and the four
`type_*`) would have to carry a second scope, each with a call site that can be
forgotten — and forgetting binds a name to the wrong thing in silence.

## Five defects found, none of them about hygiene

**The expression body's window holds a `StmtId`.** An expression body is one
expression *statement* — that is how the parser recognises the shape — so the
expression is a step further in. Reading the window entry as an `ExprId` cloned
whichever expression happened to sit at that index. Silent in the usual way: the
wrong node is a real node, so the clone succeeded and the program meant something
nobody wrote. **The sixth instance of a slot read as the wrong thing.**

**The clone dropped numeric literal widths.** `ast_add_expr` does not take a width
and sets `WNone`, which is the encoding for "written without a suffix" — so a
cloned `3i32` came out as a cloned `3`. Declaration position hid it completely,
because a `pass` takes its type from the return type; it surfaced the moment an
expansion stood somewhere with no context type.

**`module_scope` did not follow nesting.** `resolve_module` set it and the nested
module case never updated it. Nothing read the field, which is why the omission was
invisible — and hygiene is the first thing to read it.

**An `impl` is not an item, and the clone read it as one.** Shipped in 0.6.1:
`clone_decl` sent `DeclImplDecl` to `clone_item`, and the two headers are different
sizes in a different order —

| slot | item (`ITEM_HDR` = 4) | impl (`IMPL_HDR` = 5) |
|---|---|---|
| 0 | generic count | target type |
| 1 | **member count** | **trait type** |
| 2 | attribute count | member count |
| 3 | extra count | attribute count |
| 4 | — | generic count |

— so `item_member_count` on an `impl` returns **the trait's type id**, and the walk
then reads that many slots of whatever follows. It never fired in 0.6.1 because
reaching it takes a macro body containing an `impl` and no test had one. The
expansion walk reaches every `impl` in the program, so it fired at once: **a
segmentation fault in files with no macro in them at all**, and one that moved
around when unrelated declarations were added, because the count read was a type
index that could be anything.

AND THE ASYMMETRY IS FINDABLE: `struct`, `enum`, `trait` and `mod` are all built by
`p_finish_item`, and `impl` is the one built by hand — five pushes of its own at
`parse_decl.npk:964`. Anything that treats "the item kinds" as a set should be
checked against that list, because `impl` is in the set by resemblance and not by
construction.

That is the **seventh** slot read as the wrong thing, and the second in two days.
The fix is the one the file already prescribes above `ITEM_HDR`: named accessors,
never a raw slot — `clone_impl` uses `impl_member`, and `impl_attr` was added
because the tail had no accessor at all.

**`ralloc` copies the NEW size out of the OLD block** — and the fix for it found
something worse. Recorded as D-127 and **not fixed here**, because it cannot be
fixed until the second half is understood.

Found while hunting the segfault above; it was not its cause. It is a genuine
out-of-bounds read that has been in the seed runtime since it was written:

```llvm
define ptr @npk_ralloc(ptr %old, i64 %n) {
  %p = call ptr @npk_alloc(i64 %n)
  call void @llvm.memcpy.p0.p0.i64(ptr %p, ptr %old, i64 %n, i1 false)
```

Every growth reads past the end of the block being grown — harmless while a bump
allocator has something mapped after it, a fault the first time it does not.

The obvious fix is a size header, so `ralloc` copies the smaller of the two. **It
breaks the seed**, and the bisect is exact:

| variant | result |
|---|---|
| every allocation padded by 16 bytes, pointer unchanged | **passes** |
| pointer moved 16 bytes forward, nothing written | **passes** |
| header written on the `grow` path only | **passes** |
| header written on the `bump` path — 8 bytes at the block's start | **segfaults** |

Shifting every address is harmless; *writing* into the gap is not. So **something
writes past the end of its own allocation, and the allocator's rounding to 16 bytes
has been absorbing it.** The three tests it kills are `type_cast`, `type_expr` and
`type_result`, and the visible symptom is an `ExprTypes` whose `items` pointer reads
back as null.

**The conclusion drawn here was wrong, and 0.6.7 found out why.** There is no
out-of-bounds write. `etyper_init` was called with nine arguments where it takes
ten, so a parameter read an unwritten register — and *what junk sits in an unwritten
register depends on the binary's layout*, which is why every size change moved the
symptom and why the allocator looked guilty. The seed did not check call arity;
D-127 carries the full account, including what the wrong theory cost.

What survives from this subcycle is the `ralloc` over-read itself, which is real and
still unfixed: `npk_ralloc` copies the NEW size out of the OLD block. It never
faulted, and with the arity defect gone the header experiment can be redone cleanly
whenever the seed's runtime is next touched.

## Done, and what it is checked by

- `tests/accept/hygiene.npk` — all four parts, on a program that must be accepted.
  **Which binding won is observable through the TYPE**: the two `shared`s have
  different types and the macro does arithmetic only one of them permits, so if
  hygiene picked the other the file stops compiling. A checker does not run the
  program, so this is the only way to assert it.
- `tests/expansion/rejection/` — a name only at the call site, `#caller` absent,
  `#caller` outside a body, an unknown `#name`, a wrong-shaped body, and a
  cross-module invocation.
- `NITPICK-061` was never introduced, which is the whole of item 4.
- The two bound tests had to be **rewritten to still recurse**. Under D-125 a body
  of nothing but `#self_recursive();` is an expression body, so a module-level
  splice refuses it for shape before the loop it was written for is ever entered —
  the tests passed for a reason unrelated to the property they name. Each body now
  emits a declaration alongside the invocation, and `bounds_expr.npk` drives the
  same loop from expression position, which could not be reached at all until this
  subcycle.
