# 0.6.3 — Splicing

**Cycle 0.6 — Macros and comptime.**

## Goal

A macro emits declarations, struct fields and `impl` methods — the things nothing
else in the language can do.

## Why `macro:` survives at all

D-057 kept it on exactly this ground:

> Splicing fields into a struct and methods into an `impl`, and emitting
> mutually-referencing declarations, are things generics, `comptime`, and
> `#[derive]` cannot do. Months of regression tests exist because the feature is
> load-bearing, not vestigial.

So this subcycle is the justification for the whole cycle. Everything else a macro
does, something else in the language does better.

## Work

1. **Multiple declarations from one invocation**, including ones that reference
   each other (`bug591`, `bug592`).
2. **Struct field splicing** (`bug595`, `bug597`, `bug598`).
3. **`impl` method splicing** (`bug596`, `bug599`).
4. The refusals: a splice whose result does not fit where it landed — fields into
   something that is not a struct, methods into something that is not an `impl`.

## Watch for

**Every downstream pass assumes a declaration was written by a person.** A spliced
field participates in layout (0.4), a spliced method in coherence and object
safety (0.4.6), a spliced declaration in the module graph (0.3). None of those
passes has ever seen a declaration that arrived after parsing, and each has
invariants worth re-reading before assuming they hold — `collect_impls` in
particular walks a module's members once, and 0.5.1 already found it silently
skipping a nesting level it had not been told about.

**Cross-referencing declarations mean order is not enough.** `bug591`/`bug592`
emit declarations that name each other, so they cannot be resolved as they are
emitted. That is the same constraint cycle 0.3 solved with three passes — collect
every declaration, bind imports to a fixed point, then resolve bodies — and the
expansion output has to be complete before any of them runs.

**A spliced name can collide.** Two invocations of the same macro in one module
emit the same declaration names, and the hygiene rule (0.6.2) is about *reading*
names rather than *emitting* them. Whether emitted names are hygienic is a question
the corpus may or may not answer, and 0.6.0 is where that gets recorded.

## Done when

- One invocation emits several declarations, and they may name each other.
- Fields splice into a struct, and methods into an `impl`.
- A splice into the wrong kind of thing is refused, naming both.

---

## What it took, measured

The three sites needed one mechanism and one conversion.

**Two of them are a copy; the struct is not.** `int32:x;` parses as a STATEMENT
inside a macro body and as a FIELD inside a struct, because those are different
grammars reading the same text — so splicing a statements body into a struct is a
**conversion**, which is exactly what `MACRO_REFERENCE.md` §1's table already said
("variable declarations → a `struct` body → fields"). An impl or trait body takes
declarations as written.

The site is passed IN rather than worked out from the body, because the body is the
same in every case and only the surrounding declaration knows what it can hold:

| site | body | how |
|---|---|---|
| module | declarations | cloned |
| struct | variable declarations | **converted to fields** |
| impl / trait | declarations | cloned |
| enum | — | refused |

**An enum body is refused, and that is the absence of a spelling rather than a
restriction.** A variant is a name with an optional payload and no macro body can
contain one, so mapping some other body shape onto variants would be inventing a
rule.

**A field carrying an initialiser or a qualifier is refused rather than stripped.**
`fixed int32:a = 5i32;` spliced as a field would silently lose both, and losing a
safety qualifier quietly is worse than not accepting the program.

**`bug598` works because a nested invocation converts to a splice.** An `ExprStmt`
holding an invocation becomes a `DeclMacroSplice` among the fields, and the next
round expands it — the fixed point at struct level, for the same reason as at
module level.

## What the acceptance suite is for here

**The strong case is the TRAIT impl.** `check_impls_complete` asks whether every
required method is supplied, so an `impl:Box:Pair` whose methods arrive by splice
can only pass if the spliced members were in the list by the time it looked. A
splice that emitted nothing reports a missing method rather than passing quietly —
which is the property a rejection suite cannot check, and the same argument
0.6.1's acceptance suite was written on.

## Two defects, and one of them is not about macros at all

**A duplicate field was accepted, and the second was unreachable** (D-128). Field
lookup returns the first match and gets no say in which was meant, while layout
gives both storage — so the struct was the size of two fields with one of them
permanently unwritable, and nothing said so.

Found through splicing, because `struct:P = { #one_x(); #one_x(); };` produces the
collision by accident. But `struct:P = { int32:x; int32:x; };` was accepted just
the same, so **the rule is about structs and enums** and the check went there. A
check that fired only on spliced members would make a construct mean something
different depending on where it came from.

It also settles §10's open question: **a macro never renames what it emits.**
Renaming makes the feature useless in every position — a renamed field cannot be
named by the caller, a renamed method cannot satisfy the trait it implements — so a
collision is an error like any other name declared twice.

**Eight expression kinds are never typed** (D-129), found while checking that a
spliced field participates in layout. It does; what does not happen is any checking
of the literal that names it:

```nitpick
P:p = P{ x: 1i32, zzz: 3i32 };   // `zzz` is not a field of P
P:q = P{ x: 1i32 };              // `y` never gets a value
P:r = P{ x: 1i32, y: true };     // y is an int32
```

All three compile clean, and so does the same code with no macro anywhere near it.
`ExprStructLiteralExpr` has no case in the type checker, so it falls through to the
INVALID type — the encoding that exists to suppress cascades and is therefore
silent. Seven other kinds are in the same state.

**The instrument shipped here; the rules are 0.6.7.** `check_kinds_typed` diffs the
kind list against the checker the way `check_kinds_reachable` has diffed it against
the parser since cycle 0.2, and `UNTYPED_EXPR_KINDS` names where each hole is
scheduled. Two accidental discoveries in consecutive subcycles is what turned this
from a cleanup into a cycle-level item.

## Done, and what it is checked by

- `tests/accept/splicing.npk` — fields, mixed order, nesting, methods on a trait
  impl, a parameter into a spliced method, and a trait body.
- `tests/expansion/rejection/` — each site refusing the wrong body, an enum splice,
  and a field with an initialiser.
- `tests/types/rejection/duplicate_members.npk` — the hand-written collision, in
  the suite the rule belongs to.
