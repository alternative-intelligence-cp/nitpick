# 0.6.5 — `#[derive]`

**Cycle 0.6 — Macros and comptime.**

## Goal

`#[derive(…)]` generates the implementations it names, and refuses the ones the
type cannot support.

## What exists today

`#[derive(Copy, Clone)]` **parses**, as an ordinary `DeclAttribute` with the name
`derive` and its arguments in a window. Nothing reads it. That is the same
"parses and means nothing" shape cycle 0.5 spent eight subcycles clearing out, and
it is the last one in the frontend.

**SETTLED as D-123 in 0.6.0**, which is what this subcycle implements. Seven, not
the nine `TRAITS_REFERENCE.md` listed: `PartialOrd`, `ToString`, `Eq`, `Hash`,
`Clone`, `Debug`, `Ord`.

`Default` and `Display` were removed. `Default` would have the compiler choose
values that carry meaning — `fd` zero is stdin, `tbb32` zero claims "no error" —
reintroducing through an explicit door what D-010 removed. `Display` was a second
name for `ToString`'s job.

## This subcycle is now mechanical, because 0.6.0 settled the shape

D-123 fixes what each derive generates:

| Derive | Generates |
|---|---|
| `Eq` | field-wise equality |
| `Ord`, `PartialOrd` | lexicographic comparison in **declaration order** |
| `Clone` | field-wise clone |
| `Hash` | field-wise combination, **FNV-1a** |
| `ToString` | a function returning `string`, built with `&{ }` |
| `Debug` | the same, in a diagnostic form naming the type and its fields |

`Ord`'s declaration order makes reordering a struct's fields a semantic change,
which is the stated cost. `Hash`'s combiner is specified rather than left open,
because a derived hash varying between builds is not something a verified compiler
can have.

## Work

1. Read the attribute, resolve the trait names, and refuse ones that are not
   derivable — naming which.
2. Generate an `impl` per derived trait, through the same splicing 0.6.3 built.
3. Refuse a derive the type cannot satisfy — a `Hash` on a struct containing
   something unhashable, an `Ord` on one containing something unordered — naming
   the field that blocks it rather than the type.
4. Check coherence: a derived `impl` and a hand-written one for the same trait are
   two impls of one trait, which `check_coherence` (0.4.6) already refuses. It
   should keep refusing, and the message should say one of them was derived.

## Watch for

**Derive is a macro that does not look like one.** It emits declarations, so it
runs in the same phase and inherits the same constraints — including that its
output must be complete before resolution begins.

**A derived implementation is written by the compiler and read by a person.** Its
diagnostics point at generated code, which is the span problem 0.6.1 raises,
arriving in the place a user is most likely to meet it: they wrote `#[derive(Ord)]`
and the error is inside something they never saw.

## Done when

- Each of the seven derives generates its implementation, or is refused as
  underivable with the reason. *(Written as "eight" — a stale count from before
  D-123 removed `Default` and `Display` from the nine. There are seven.)*
- A derive the type cannot satisfy names the field that blocks it.
- A derived impl beside a hand-written one is refused as a coherence violation,
  saying which was derived.

---

## What was actually there, measured

The plan called this "mechanical, because 0.6.0 settled the shape". It was not.
**D-123 named the seven and said what each generates; it did not say what any of
them IS.** `#[derive(Eq)]` generates `impl:Point:Eq`, which needs a trait `Eq` to
exist, and nothing declared one — not this compiler, not a library, and neither
`TRAITS_REFERENCE.md` §2.5 nor D-123 gave a method name or a signature.

**The prototype answers it** (`expandDeriveAttributes`), and is followed where it
speaks — `eq`, `clone`, `hash`, `to_string`, `debug` are its names. Two are
corrected rather than copied, and D-132 gives the arguments: its `Ord` returns
`less_than`, which makes `Ord` weaker than `PartialOrd`; and its `partial_cmp`
returns an `int32` meaning less, equal or greater by sign, which is three meanings
in one number — the shape D-036 rejects for `bool` and `char`.

It also registers the traits as **empty** declarations. Copying that would undercut
0.4.6: `check_impls_complete` would have nothing to check and a `<T: Hash>` bound
would promise no methods.

## The prelude, and two wrong turns getting there

**A multi-line string constant compiles through the seed and is rejected by the
compiler the seed builds.** The real lexer refuses a newline inside a plain string
literal; the block form `"""` is the other way round — the real lexer has it, the
seed does not. So the prelude is readable Nitpick at `src/prelude/prelude.npk` and
the generator emits it escaped onto one line, which is the one spelling both accept.

**The root scope is not above module scopes.** Collecting the prelude into scope 0
looked right — every module's scope has 0 as its parent — and does nothing, because
`scope_lookup` **stops at the first module scope**. A module is a closed namespace
reachable only through `use`, and that is the whole of what a module means here.

The prelude is bound the way `use "prelude.npk".*` would bind it, into every module
scope including nested ones. That is the honest model rather than a workaround: the
prelude is an import nobody has to write.

## Generation is source, and it caught itself

Building `DeclImplDecl` and `DeclFunctionDecl` by hand would be several hundred
lines of slot-filling, and **every slot is a chance to write a member count into the
field a trait id lives in** — 0.6.3's `impl`-read-as-an-item segfaulted files with
no macros in them. Generated text goes through the same parser as everything else.

It failed once, immediately: `pick self { … }` written from memory, where the real
syntax is `pick (self) { (pattern) { … }, … }`. A hand-built tree would have been
malformed instead of unparseable.

## The defect this uncovered, which is not about derive

**`Self` IN RETURN POSITION WAS UNMATCHABLE** (D-134), found by the prelude's
`Clone` — the first trait method in this compiler's history to return `Self`.

`check_impls_complete` substitutes `Self` one level deep, deliberately. But **every
function returns `Result<T>`**, so `func:clone = Self(Self:self);` has the type
`Result<Self>` and the impl's has `Result<Point>` — putting `Self` a level below
where the substitution could see it. Every trait method returning `Self` was
reported as not having the signature its trait declares, about two signatures that
were identical.

The general shape: **a rule about what the author wrote has to account for what the
language adds.** `Result` is invisible in the source and present in every type.

## What is refused rather than guessed at

- **`Ord`/`PartialOrd` on an enum** — ordering a variant means comparing its tag,
  and `<` on an enum is refused by the type checker. Measured, not assumed.
- **`Hash`, on anything** — FNV-1a folds bytes, and nothing in `builtins.npk`
  exposes a `string`'s bytes. A derived hash that skipped string fields would vary
  with data it ignored. One primitive unblocks it.

Both refuse at the `#[derive]` rather than generating code that fails to type-check.

## What is still owed, with its home

D-123's "a refusal names the field that blocks it" **cannot be answered where derive
runs**: generation is in the expansion phase, before types exist. It is the same
mechanism 0.6.6 builds — a diagnostic about generated code that has to be told where
the reader's code is — and it lands there. A derived impl carries `DECL_DERIVED`
already, which is what lets the coherence message say one of the two was generated.

## Done, and what is checked by what

- `tests/accept/deriving.npk` — **every derived method is called**, because a derive
  that generated an empty impl passes every rejection test there is. Named
  `deriving` because **`derive` is a keyword**, the same trap `comptime` sprang in
  0.6.4.
- `tests/derive/rejection/` — the two removed names with their reasons, an unknown
  name and a non-name, a duplicate in one list and across two attributes, the wrong
  target, the two that are not generated, a redeclared prelude name, and a derived
  impl beside a hand-written one.
