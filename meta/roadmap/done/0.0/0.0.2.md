# 0.0.2 — Seed: lexer and parser

**Cycle 0.0 — Foundations.** First of three subcycles building the seed.

---

## Correction to the plan as originally written

The earlier version of this subcycle said the generator *"emits a subset-1 → LLVM
IR compiler as `.ll` text"*, and that `llc` would turn that into a binary which
then compiles the conformance suite. **That is the wrong architecture**, and it
would have cost enormously.

It requires writing a subset-1 compiler **as IR-emitting code** — a compiler
expressed as a program that prints LLVM IR — or else writing the subset-1
compiler twice, once in the generator's language and once in Nitpick. D-085
warned against exactly that duplication for the parser, and the warning applies
here.

**What is actually correct:**

| | |
|---|---|
| **The seed** | a program that reads subset-1 `.npk` and writes `.ll`. It is the generator. There is no separate "seed binary" and none is needed. |
| **The committed IR** | `bootstrap/seed/stage1.ll` — the IR of **the real compiler**, produced by running the seed over `src/` once `src/` can compile subset 1. |

Rebuilding from nothing is then `llc bootstrap/seed/stage1.ll` → a working
compiler → compile `src/` → stage 2. **No generator needed to build**, which is
the property that matters: a machine with only the LLVM toolchain can build the
compiler.

The generator is needed only to *regenerate* the seed, and there is no
duplication anywhere — the only subset-1 compiler written in Nitpick is the real
one.

**So `bootstrap/seed/` stays empty until roughly cycle 0.7**, when there is a
compiler worth freezing. Until then the seed compiles our sources directly. That
window is development-only and costs nothing.

---

## Scope: why this is three subcycles, not one

A subset-1 compiler is a lexer, a parser, a checker, an emitter, and a runtime
floor. That is not one workable chunk, and a subcycle that cannot be finished is
not a plan. Split:

| | |
|---|---|
| **0.0.2** | lexer and parser — **this file** |
| **0.0.3** | checker and IR emitter |
| **0.0.4** | runtime floor and linking |

## Goal

A lexer and parser for subset 1 that produce an AST, validated by parsing every
file in `tests/conformance/`.

## Scope discipline

The seed is the one place where "just enough" is correct engineering, and the
temptation to over-build it should be resisted actively:

- **Subset 1 and nothing else.** Every construct past `meta/SUBSET_1.md` is work
  on something that gets deleted.
- **Diagnostics may be crude.** The seed compiles exactly one program in its life
  — our compiler, which is under our control. Good diagnostics are the real
  compiler's job.
- **No error recovery.** First error, report, stop.

If the seed starts looking like a compiler worth keeping, subset 1 is too big and
0.0.1 needs revisiting.

## Work

**1. Lexer.** `LEXICAL_REFERENCE.md`, restricted to subset 1. The pieces that are
easy to get wrong and are specified precisely:

- **integer literals require a suffix** — `42i32`, not `42`
- **`>>` splitting** does not arise: subset 1 has no generics, so there is no
  type-argument context. Emit `>>` as one token.
- **`!` is positional** (D-046) — leading is negation, trailing/repeated is
  unchecked. Subset 1 uses `!` and `!=` only.
- **`_^`, `_!`, `_?`** resolve **before** identifiers that begin with an
  underscore.
- float literals are **lexed and stored as text**, never evaluated.

**2. AST.** Mirror `AST_REFERENCE.md`'s node set, restricted to subset 1. The
seed's AST is throwaway and need not use the index-based representation the real
compiler will — ordinary object references are fine here.

**3. Parser.** Recursive descent. The precedence table from `OP_REFERENCE.md` §0,
including **level 2**, the `Result` unary operators — `raw`, `drop`, `relay` —
which bind looser than postfix and tighter than cast (D-081).

**4. Parse the conformance suite.** All 11 files, to an AST, with no errors.

## Done when

- Every file in `tests/conformance/` parses.
- Every file in `tests/rejection/` **also parses** — they are valid Nitpick and
  must reach the backend to be rejected there. A parse error on any of them is a
  failure of this subcycle, not of the file.

That second criterion is the one that matters. It is the first executable proof
of D-085's rule:

> **The parser never restricts. The backend does.**

## Not in this subcycle

No checking, no IR, no runtime. Parsing only.
