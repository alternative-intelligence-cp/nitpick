# 0.7.3 — The compiler parses itself

**Cycle 0.7 — IR emission core.** Inserted after 0.7.2 measured around its own
subject and found this.

## What was true before it

**The compiler could not read its own source.** Fed through `tools/parse_check.npk`
— the real parser, the one stage 1 is — **22 of the 62 files under `src/` and
`tools/` were rejected, and five crashed it.**

Nothing said so, because the harness's real-parser sweep covered `tests/**` and
`src/prelude/` and had never covered the compiler itself. Every test in the tree was
put to the real parser; the thing the parser is part of never was.

This is not cosmetic. **Stage 1 is built by the seed and must then parse these exact
files to build stage 2.** A source the real parser cannot read is a source that never
self-hosts, and the seed accepting it is not evidence of anything — the seed is
throwaway and deliberately laxer.

## Three causes, and the first one is a memory-safety defect

### `ralloc` read off the end of its old block, and the read left the mapping

The bump allocator had no size header, so `npk_ralloc(old, n)` copied **`n` bytes —
the NEW size — out of a block that was only the old size long.**

```llvm
%p = call ptr @npk_alloc(i64 %n)
call void @llvm.memcpy.p0.p0.i64(ptr %p, ptr %old, i64 %n, i1 false)   ; <-- n, not old
```

Every growing array over-read by exactly the amount it grew. When the old block sat
near the end of an mmap'd chunk, that read left the mapping and took the process
down with **SIGBUS** — in the least-audited artifact in the chain.

**It was not latent.** About 511 declarations in one file is enough to reach such a
growth; five of the compiler's own sources exceed it.

**The fix is a sixteen-byte header in front of every block**, and a copy bounded by
`min(old, n)`. Sixteen and not eight because the header has to keep the returned
pointer 16-aligned, which every caller's struct array depends on.

The alternative — pass the old size in at every call site, which every caller does
know — was rejected: it moves a memory-safety obligation onto twenty call sites, and
the one that forgets is silent corruption rather than a compile error. Sixteen bytes
per allocation in a process that runs once and exits is not a cost worth that.

### A memory qualifier was read in two positions out of five

`wild`, `stack`, `wildx`, `const`, `fixed`, `nodrop` were read on a local
(`parse_stmt.npk`) and on a return type (`parse_decl.npk`) and nowhere else — while
`parse_type.npk`'s own header had said since 0.4 that *"`wild int8->:buf` is a
declaration qualified `wild`"*. So a **struct field**, a **parameter** and a **cast
target** could not carry one, and sixteen of the compiler's files begin a struct or
a signature that way.

The cast is the interesting one. `p => wild int8->` is **load-bearing, not
decoration**: to LLVM a `wild` pointer and a managed one are the same word, and the
distinction is enforced entirely by the type checker (D-038) — so the cast target is
where a program *says* the result is unmanaged. Dropping the qualifier to make the
parser happy would have been changing the language to suit a gap in it.

Two decisions fell out:

- **The bits and the loop moved down to `parser.npk`.** They lived beside the
  statement parser that first needed them, and `parse_expr.npk` cannot import
  `parse_stmt.npk` — which imports *it*. The shared rule has to sit below both. The
  loop had been written out twice and would have been written out three more times.
- **The qualifier goes in the payload on all three cast kinds**, not in a spare slot
  on two of them. `DynCastExpr` has used `b` and `c` for its trait window since 0.4,
  so a qualifier put in `c` would be recorded for `=>` and silently dropped for
  `=> dyn A` — and `wild dyn A` would be a thing nothing could refuse, because
  nothing would know it had been written.

Slot `c` is the flags slot on a field, on a parameter and on a global, so one shape
reads all three.

### Four identifiers were numeric literals

`LEXICAL_REFERENCE` §6.2 gives the base by **suffix**:

```
TernaryLiteral ::= [01Tt] ([01Tt_]* [01Tt])? ("t" | "ter" | "tri")
NonaryLiteral  ::= [0-4a-dA-D] ([0-4a-dA-D_]* [0-4a-dA-D])? ("non" | "n")
```

So `dn` is −4, `bn` is −2, `cn` is −3, and **`tt` is −1**. The compiler used all four
as variable names, at 131 sites across 13 files. `CLAUDE.md` lists exactly this trap
and `tests/frontend/type_layout.npk` carries a comment about avoiding it — the seed's
lexer accepts them and the real one does not, and nothing was asking the real one.

They were found by **generating the check from the grammar** rather than by grepping
for the ones already seen: a scanner built directly from those two productions found
`tt`, which four rounds of fixing the others had not.

## The instrument, which is the actual deliverable

The harness now sweeps **`src/**` and `tools/*`** through the real parser on every
full run, alongside the tests. That is what would have caught all three, and it is
the fourth whole-tree check in this project to find something on its first run —
this one more than the other three combined.

`tests/conformance/14_alloc_growth.npk` is the allocator's own regression test: a
growable array doubled past a megabyte, its contents checked after every growth, then
shrunk. **The assertions are about contents and the loop is about size**, and the
split is deliberate — the over-read does not corrupt what it copies, so no single
comparison can see it. What sees it is crossing a chunk boundary. Verified: against
the old runtime the test exits −7.

## Done when

- Every file under `src/` and `tools/` parses with the real parser, and the harness
  checks it on every run.
- A growable array survives repeated growth, and the test fails against the old
  allocator.
