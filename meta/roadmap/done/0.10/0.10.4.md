# 0.10.4 — `shared_arena<T>`

**Cycle 0.10.** The multi-threaded arena — a distinct type with a deliberately
smaller contract than `arena<T>`, whose smaller contract is exactly what makes
concurrency safe without epochs, hazard pointers, or reference counting (D-017).

## The contract, and why it is smaller

`arena<T>` is single-threaded because **growth moves memory**: a pointer from `get()`
dangles if another thread's `alloc()` reallocates the slab, and no amount of atomic
generation-counting fixes a pointer whose target moved (D-017's decisive hazard).
`shared_arena<T>` removes that hazard by construction (D-017):

| | `arena<T>` | `shared_arena<T>` |
|---|---|---|
| Operations | `alloc`, `get`, `free`, `reset`, `destroy` | **`alloc`, `get`, `destroy` only** |
| Per-slot `free` | yes | **no** |
| Storage | may reallocate on growth | **chunked, never moves** |
| Cost | zero | one atomic bump per allocation |

Dropping per-slot `free` is the whole trick: slots are never reused while the arena
is live, so generation counters never increment during concurrent access (race 1
gone), there is no freelist to contend on (race 2 gone), and chunked storage means
growth allocates a **new chunk** rather than moving existing ones (race 3 gone).
Allocation reduces to a single atomic `fetch_add` into non-moving storage.

## What it provides

- **Chunked, non-moving storage** — a list of fixed chunks; a full chunk triggers a
  new chunk, never a move. This is where the atomic-bump allocation offset lives —
  an `atomic<int64>`, and **this subcycle lowers it**, minimally: the type plus
  load/store/`fetch_add` at the SeqCst ordering D-016 mandates. (No earlier cycle
  owns atomics; the general `atomic<T>` surface — the permitted-`T` set, the full
  method set, `compare_exchange`'s return shape — is C-9, settled at 1.1. What
  lands here is exactly what the bump needs, no more.)
- **`alloc` / `get` / `destroy`**, no `free`, no `reset`.
- **`destroy` requires no thread still holds handles** — ownership, not
  synchronization: the owner destroys it after joining (D-017). This composes with
  the lexical thread/task lifetime 1.1 will build (D-062/D-083), so the "after
  joining" is structural rather than a runtime check.

## Decisions D-017 left open (settle here)

- **Chunk-size policy** — fixed or geometric growth. Proposed: geometric, capped,
  matching the heap's large-block threshold so a big shared arena does not fragment
  into thousands of small chunks.
- **`get()`'s borrow status** — D-017 says "likely yes, composes well." Decide yes,
  matching 0.10.2's `arena<T>` decision, so both arena types hand out non-escaping
  borrows uniformly.

## Tests

A runtime harness (no surface concurrency until 1.1, so drive the type directly, or
gate the executed test on 1.1): allocate from two threads concurrently, confirming
no torn slots and that a `get` pointer stays valid across another thread's `alloc`
(the non-moving guarantee — the property that fails for `arena<T>`); `destroy` after
join. Until 1.1 provides threads, a single-threaded correctness test plus a review
against the atomic-ordering obligation.

## Done when

`shared_arena<T>` lowers with chunked non-moving storage and atomic-bump allocation;
the no-`free`/no-`reset` contract is enforced (calling `free` on one is a compile
error); the chunk-policy and borrow decisions are recorded; its keyword refusal is
replaced by lowering, completing the arena family so 1.1 has both single- and
multi-threaded arenas available.

## Outcome (recorded at close)

Landed as D-154. Both open items decided — chunk policy geometric-capped
(each chunk carries current capacity in slots, cap 65536), and `get`'s
borrow status NO, because the plan's "matching 0.10.2" pointed at a
decision that had gone the other way: D-152's BORROW-001 argument is
type-independent, so both arenas copy. The deeper call the plan did not
anticipate: with no `put`, **`alloc` must carry the value** — and that IS
the concurrency design: write-once-before-publication makes every slot
immutable under concurrent readers, no per-slot machinery, the handle
transfer being the synchronizing edge (SeqCst channels, D-016, stated as
1.1's obligation).

Growth is reservation-then-publish: `fetch_add` on capacity hands racing
installers disjoint ranges, CAS publishes the chunk; storage never moves.
The "lowers atomic<int64>" line dissolved on inspection — the atomics are
runtime-internal IR instructions, no surface type needed; `atomic<T>`
stays wholly 1.1's. One real find: virgin `arena<T>` slots issued
generation ZERO, colliding with shared handles' constant zero — caught by
the cross-arena test, fixed by promoting virgin arena generations to 2,
which makes the wandering-handle refusal real rather than claimed.

`shared.ll` (runtime stage) proves the non-moving property with a raw
pointer across 10000 allocations; `shared_arena.npk` proves the surface;
the rejection files lock no-free and use-after-destroy for the shared
type too.
