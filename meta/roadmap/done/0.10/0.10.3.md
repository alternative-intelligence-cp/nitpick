# 0.10.3 — The executor frame allocator

**Cycle 0.10.** The allocator D-034 actually needs — distinct from the surface
`arena<T>` of 0.10.2. This is the subcycle that exists because the concurrency audit
caught a conflation that would otherwise have blocked 1.1 mid-cycle.

## The distinction, and why it is load-bearing

D-034 says "each thread's executor owns an `arena<T>` from which it allocates task
frames, released on task completion." Read literally that points at 0.10.2's
`arena<T>` — but **the surface `arena<T>` cannot allocate coroutine frames** (the
concurrency audit's sharpest finding, total_audit B-1):

- `arena<T>` is a **fixed-slot** allocator of `T`-sized cells returning
  generation-checked `Handle<T>` **indices**.
- Coroutine frames are **per-function, variably sized**, and `@llvm.coro.begin` needs
  a **raw pointer**, not a handle indirection.

So D-034's "arena" is really a distinct allocator that *shares the arena philosophy*
(batch lifetime, drop-cheap) but has its own contract. Building it here — named,
separate — is how 1.1 avoids discovering at its own mid-point that the type it was
told to use does not fit.

## What it provides

- **A bump-per-task frame allocator, one per executor.** Because tasks are pinned
  (D-032), the executor's frame allocator is **single-threaded** — a plain bump into
  a growable chunk list, zero atomic cost (the D-034 rationale: pinning is what lets
  frames use a zero-cost allocator instead of `shared_arena`'s atomic bump).
- **Free at task completion**, a well-defined point (D-034) — no reachability
  question, no generation counter. A completed task's frame is returned to the
  executor's free list or its chunk is reset when the executor drains.
- **Raw-pointer handout** sized to the frame `@llvm.coro` computes, with the
  alignment coroutine frames require.

This is runtime-internal — it is **not** a surface type, has no keyword, and is
reached only by the coroutine lowering (1.1). It is built here because it is a heap
concern and this is the heap cycle; it is *consumed* in 1.1.

## Relationship to 1.1

1.1's C-7 (coroutine lowering) depends on this allocator's interface being fixed:
the frame-alloc/frame-free calls the coro lowering emits, and the executor's
ownership of the chunk list. Fixing the interface here (even though the coro lowering
that calls it is 1.1) means 1.1 builds against a stable, tested allocator rather than
designing one under the pressure of also designing the state machine.

## Tests

Since there is no surface syntax, test via a runtime harness that drives the
allocator directly (as the runtime-floor routines are tested): allocate frames of
several sizes, complete them out of order, confirm reuse and that a drained executor
resets its chunks; confirm single-threaded correctness (no atomics on the path).
A stress case allocating more frames than one chunk holds, proving chunk growth.

## Done when

The frame allocator exists with a fixed interface (frame-alloc, frame-free,
executor-owned chunk list); it is single-threaded and zero-atomic; it is documented
as distinct from `arena<T>` in MEMORY_REFERENCE (a note preventing the exact
conflation the audit found); 1.1's coroutine-lowering plan (C-7) cites it as its
frame source.

---

## Outcome (recorded at close)

Landed as D-153. The interface is fixed at five calls (new / alloc(size,
align) / free / drain / destroy), runtime-internal with no surface — and
1.1's map already cites it (row 1.1.1 builds `@llvm.coro` machines over
this allocator). Exact-size free-list bucketing was chosen over first-fit
because the coroutine workload IS exact-size recurrence: one frame size
per async function. Zero atomics on every path; chunks kept across
`drain` so the steady state allocates from memory it already owns;
oversize frames ride dedicated heap blocks; headers carry secret-keyed
state magics so double-free traps -4102 deterministically. Executor and
chunks are wild-role: the D-151 exit check counts an un-destroyed
executor.

Testing needed a new instrument, since nothing can reach the family from
Nitpick source until 1.1: the harness's `runtime` stage runs hand-written
`.ll` drivers from `bootstrap/runtime/tests/` — `frames.ll` passed first
run, covering LIFO reuse, out-of-order frees, bucket separation, drain,
oversize, growth, and a clean destroy proven by wild_live_count and the
exit-time check both.
