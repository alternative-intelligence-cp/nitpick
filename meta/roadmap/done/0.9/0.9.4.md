# 0.9.4 — Floats, the float runtime symbols, and two decisions

**Cycle 0.9.** IEEE floating point — `flt32`/`flt64`/`flt128` — with the libcall
replacements their arithmetic needs, and two small decisions the audit found
unmade.

## What lowers

- **`flt32`/`flt64`** to LLVM `float`/`double`: `fadd`/`fsub`/`fmul`/`fdiv`/`frem`,
  `fcmp`, and the `sitofp`/`fptosi`/`fpext`/`fptrunc` conversions (checked `=>` vs
  unchecked `=>!` per the data-loss rule — float→int is always lossy, so `=>!` only).
- **`flt128`** to `fp128` — but its arithmetic (`__addtf3`, `__multf3`, …) and `%`
  on floats (`fmod`) lower to **compiler-rt / libm libcalls** the floor does not
  provide (type-sys #7, the same D-011 class as `__divti3`). Provide them as
  hand-written IR or explicitly defer `flt128` arithmetic to a named later subcycle
  — but do not let the undefined-symbol scan fail without a plan, and do not emit an
  unprovided `fmod` silently.

## Decision 1 — float divide-by-zero (type-sys #8)

D-007's table puts `flt64` in the **trap** row; `OP_REFERENCE` says floats give
inf/nan with **no trap**, crediting D-037 — but D-037 covers only float *overflow*,
and its div-by-zero section is int/uint only. **Proposed resolution: IEEE, no
trap** (float division by zero yields ±inf/nan per IEEE 754, which is defined
behavior, unlike integer division) — and correct D-007's float row to say so, with
a one-line decision cited. This is the natural reading (floats have inf/nan
precisely so division is total) and it means `fdiv` needs no guard branch, unlike
`sdiv`.

## Decision 2 — `flt256` / `flt512` (type-sys #7)

`OP_REFERENCE` names `flt32…flt512`, D-095 defines their significands, and the
resolver marks them `known` with lexer suffixes — but `TYPE_REFERENCE §1.4` defines
only up to `flt128` and **LLVM has no `fp256`/`fp512` type**. Decide one:
- **descope** `flt256`/`flt512` (rung-refuse them naming a later cycle or "not
  planned"), which matches "the compiler needs no floats" and avoids inventing a
  soft-float representation nobody has asked for; **or**
- commit to a soft-float limb representation with hand-written IR, which is
  substantial TCB work for a type with no current consumer.

**Proposed: descope** — give `TYPE_REFERENCE §1.4` the honest float set
(`flt32/64/128`), rung-refuse the wider two, and remove the stale `known:true` /
suffix entries so the resolver does not accept a type nothing can lower.

## Float literal suffix (type-sys #19, fold into this subcycle)

`TYPE_REFERENCE:113` says `3.14flt32`; the lexer and impl use `f32`/`f64`. Correct
the doc to the implemented spelling (`f32`/`f64`/`f128`) — a one-line fix landing
where floats are the subject anyway.

## Tests

`tests/backend/programs/float.npk`: `flt64` arithmetic and comparison; a division
by zero yielding inf (asserting no trap, the decision above); a `flt32`↔`flt64`
conversion; a `flt64 => int64` refused at compile time and `=>! int64` accepted
(the data-loss rule). If `flt128` arithmetic lands, an `__addtf3` exercise that
keeps the undefined-symbol scan green.

## Done when

`flt32`/`flt64` lower and run with correct IEEE semantics; the div-by-zero and
`flt256+` decisions are recorded and the docs corrected; `flt128` arithmetic either
works with provided symbols or is cleanly deferred with the scan still green; the
literal suffix doc matches the lexer.
