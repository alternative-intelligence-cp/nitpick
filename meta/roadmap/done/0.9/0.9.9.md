# 0.9.9 — The leading-digit rule (D-147)

**Added mid-cycle at the user's request** — not in the merged plan. The trigger
was empirical: four separate edit-build-fail cycles in 0.7–0.9 were caused by a
variable name (`cn`, `bn`, `an`, `tt`) turning out to be a balanced-base numeric
literal, each reported as a parse failure lines away from the mistake. The
grammar made whole English words literals: any word over `a`–`d` ending in `n`
(`ban`, `can`, `dan`) was a nonary literal, and hex's letter digits did the same
to words ending in `hex` (`chex`). The user proposed a universal `value<T>`
annotation; review found `<` ambiguous in expression position (`5<u8>` vs the
comparison `5 < u8` — the same ambiguity that forced the turbofish), and the
minimal rule below was chosen instead.

## The rule

> **Every numeric literal begins with a decimal digit (`0`–`9`). Identifiers
> never do.** A literal whose leading significant digit is a letter (balanced
> bases, hex) takes a value-neutral leading zero: `0an`, `0Tt`, `0FFhex`.

One rule, no context, and it was already true of every base except the
letter-digit ones — this closes a hole in an existing rule rather than adding a
prefix system. The lexer's identifier/literal split becomes a first-character
test instead of scan-the-run-and-decide-from-the-right.

In the same decision, the **legacy C-style prefixes** (`0x`, `0b`, `0o`, `0n`)
are **removed**, not just discouraged. They were retained "for C FFI
compatibility", but Nitpick never parses C headers, and two spellings for one
literal is the exact thing the blueprint philosophy refuses. `0xFF` now dies as
LEX-002 (`x` is not a decimal digit) rather than parsing.

## Work

1. `src/frontend/numeric.npk` — entry guard (first char not `0`–`9` → the run
   is an identifier); delete the legacy-prefix block; the bad-digit branch's
   letter-leading fallback becomes unreachable and goes; header comment
   rewritten (its "FFhex cannot be a variable name" lament is repealed).
2. `bootstrap/generator/lex.py` — delete the `0x`/`0X`/`0b`/`0B` branches (the
   seed's numeric path already fires only on a leading digit — it implemented
   this rule from day one); `check.py`'s rung message drops "and the 0x/0b".
3. `src/frontend/macro/derive.npk` — PRIME_TEXT/BASIS_TEXT migrate from `0x…`
   to suffix form (`100000001B3hexu64`, `0CBF29CE484222325hexu64`).
4. Tests — `tests/frontend/lexer_numeric.npk` asserts the new split (`0FFhex`
   literal / `FFhex` identifier / `0xFF` error / `0an` −1 / `dn` identifier);
   `tests/backend/programs/nonary_literals.npk` becomes the freed-names
   demonstration (`int32:dn = 0dni32;`).
5. Specs — LEXICAL_REFERENCE §6.2 grammar (`Hex ::= [0-9]…`, `Ternary ::=
   [01]…`, `Nonary ::= [0-4]…`), the legacy blockquote replaced by the rule;
   TYPE_REFERENCE's two `0xFF…` suffix examples; DECISIONS.md D-147; CLAUDE.md
   trap table (the literal rows mostly EMPTY — the point of the change).

## Added in flight — D-148, the value must fit

Probing the FNV-constant migration surfaced two holes that predate this
cycle: NOTHING checked a literal's value against its type (`int8:a = 300i8;`
reached the backend and emitted `i8 300`), and the lexer's overflow guard
was decimal-tuned, so the FNV basis `0xcbf29ce484222325` slipped under it
and WRAPPED silently while `uint64`'s real maximum was refused. Fixed in the
same subcycle (no-deferring): exact per-radix overflow detection in
`num_scan`; the signed-64 literal envelope with extremes CONSTRUCTED, not
spelled; `lit_ranged` in the checker (`NITPICK-TYPE-031`) for int/tbb/char,
suffixed and contextual, with char32 scalar validity; the missing `char`
rows in `num_width_bits` (numeric char literals had been typing as ZERO-BIT
chars). `derive.npk`'s basis is now `(0u64 - 3750763034362895579u64)`.

## Done when

The full harness is green, `FFhex`/`an`/`dn`/`tt` lex as identifiers with the
old spellings' values reachable via the leading zero, `0xFF` is a lex error,
and no document still calls the prefixes "retained".

---

## Outcome (recorded at close)

Landed as planned, plus the in-flight D-148. Full harness green — 63 tests,
`types` suite 19 → 20 (`literal_range.npk`), selfhost fixpoint byte-identical
under the new rules, which is the proof the compiler's own sources contain no
literal the new checks refuse.

- **D-147 in both lexers.** The real one gained the first-character guard and
  lost the legacy-prefix block and the bad-digit identifier rescue (now
  unreachable); the seed's numeric path had gated on `isdigit()` from day one,
  so it only lost its `0x`/`0b` branches. `FFhex`, `an`, `dn`, `tt`, `ban`
  lex as identifiers — `lexer_numeric.npk` holds tokens named `dn` and `tt`
  as its own demonstration — and `0xFF` dies as LEX-003 at the `x`.
- **D-148 exact and ranged.** The FNV-basis hex constant that silently
  wrapped under the decimal-tuned guard is now LEX-004 (locked in
  `lexer_numeric.npk`); `300i8`, `999u8`, contextual `int8:c = 300`,
  `128i8`, `128tbb8`, `0anu8`, and the char32 surrogate all refuse as
  TYPE-031 at the literal's own span (`literal_range.npk`); the boundary
  values 127i8 / 255u8 / i64-max / 127tbb8 / U+10FFFF all still accept, and
  int8's most negative value is spellable as `0b4bni8`.
- **Two latent defects found by the new checks**: `num_width_bits` had no
  `char` rows, so every numeric char-suffixed literal had typed as a
  ZERO-BIT char since the suffixes landed (also the likely mechanism behind
  0.9.5's "`4000000000000tbb64` hit TYPE-007" note — that literal accepts
  cleanly now); and `derive.npk`'s FNV constants turn out to be dead code
  until Hash derive lands with string bytes, so their migration is
  provably safe and the arithmetic is documented at the definition for its
  first live use.
- The CLAUDE.md reserved-word trap table shrank by its worst rows, which was
  the point of the request.
