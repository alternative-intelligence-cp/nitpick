# 0.9.0 — The safety repair

**Cycle 0.9.** Before any new lowering, close the two places where a construct
parses and then compiles to unsafe nothing. Both are confirmed against the live
compiler; both violate the language's own safety doctrine in shipped behavior; both
are cheap. This subcycle comes first because a feature that is merely missing can
wait, and a silent miscompile cannot.

## Why this is first, and not a footnote

D-085's contract is the spine of the whole bootstrap: **the parser accepts every
construct, and the backend either lowers it or refuses it with
`NITPICK-RUNG-001`.** There is no sanctioned third outcome. The audit found four
constructs in the third outcome (total_audit Theme A); two are safety and are
repaired here, two are correctness and are repaired in 0.9.1/0.9.6. The two here
were confirmed by compiling through npkc and reading the emitted IR
(`../audit-0.8-close/probes/limit_drop.npk`, reproducible with `../audit-0.8-close/probes/npkc_build_and_run.py`).

## Part 1 — `limit` / `requires` / `ensures` / `invariant` are dropped (LIVE-1)

### The defect

`prove` and `assert_static` refuse correctly (`src/backend/ir/ir_stmt.npk:182-187`,
`iv_rung("prove","1.3")`). The other four verification carriers are read by nobody
in the backend:

- `emit_vardecl` never reads `stmt_decl_limit` — a `limit<r_pos> int32:x = e;`
  lowers to a bare `alloca`+`store`, the rule absent from the IR.
- `emit_while` never reads the invariant node.
- No `src/backend/` code reads function contracts at all — a `requires b != 0i32`
  function lowers as if the clause were absent (**observed:** its body was a bare
  `sdiv i32` — which is also LIVE-2).
- The only consumers of `stmt_decl_limit`/`param_limit` in the tree are the parser
  and the macro cloner.

This is precisely what D-068 forbids ("a safety property must not depend on a
compiler flag") and what the rung discipline exists to make impossible.

### The fix

Add `NITPICK-RUNG-001` refusals naming cycle **1.3**, the same shape `prove` has,
at the four sites the backend reaches them:

1. **A declaration or parameter carrying `limit<R>`** — in `emit_vardecl` (and the
   parameter path), before emitting the `alloca`, check for a non-empty limit node
   and `pass (raw iv_rung("a `limit<Rules>` constraint", "1.3", span))`.
2. **A function carrying `requires` / `ensures`** — in the function-emission entry
   (`ir_func.npk`), before emitting the body, check the contract list and refuse
   with `iv_rung("a `requires`/`ensures` contract", "1.3", span)`.
3. **A `while`/`when`/counted loop carrying `invariant`** — in `emit_while` (and the
   counted-loop path), refuse with `iv_rung("a loop `invariant`", "1.3", span)`.

The message must name the construct and the rung, per the rung-diagnostic rule
(SUBSET_1 §3): *"…not supported at this backend rung; the verification checks arrive
in cycle 1.3."*

### Why refuse rather than "just ignore until 1.3"

Ignoring is the current behavior and it is the bug. A program that writes
`limit<r_positive> int32:x = read_sensor()` and compiles clean has been told its
constraint holds when nothing checks it — the worst failure for this project's users
(total_audit LIVE-1). Refusing says the truth: *this guarantee is not available at
this rung yet.* When 1.3 lands the real check, the refusal is replaced by
enforcement, and the migration is exactly the one `tests/rejection/` → conformance
that every rung has done.

### Tests

`tests/rejection/verification.npk` (new — the slice has none, itself a gap the audit
noted): one case each for `limit` on a declaration, `limit` on a parameter,
`requires`, `ensures`, and a loop `invariant`, each asserting `NITPICK-RUNG-001` and
the *absence* of an earlier parse/type error (D-085's dual assertion — the construct
must parse and be refused by emission, not fail sooner). Register the code in
`check_codes_tested` so it cannot regress to untested.

## Part 2 — integer division is unguarded (LIVE-2)

### The defect

`TYPE_REFERENCE.md:56` mandates that integer `/` and `%` still trap to `failsafe`
on a zero divisor (D-007), and **§71-76 prints the exact guard IR the backend is
supposed to emit** — `%is_zero = icmp eq i32 %b, 0 ; br i1 %is_zero, label
%failsafe_trap, label %do_div`. `src/backend/ir/ir_expr.npk:455-456` maps
`/`→`sdiv`/`udiv` and `%`→`srem`/`urem`, and the emission (≈521-528) writes a bare
`<ins> <ty> <lhs>, <rhs>` with **none** of that guard. The static spot-check found
**no `icmp`-zero, no `failsafe_trap`, and no `is_zero` anywhere in
`src/backend/`** — there is no guard-emitting code path at all, not merely a
skipped branch. **Observed** in the LIVE-1 run: `checked`'s body was
`%t4 = sdiv i32 %t2, %t3` with nothing in front of it. At runtime `int32 / 0` is a hardware fault (SIGFPE) — an uncontrolled
crash, the event Layer 3 exists to convert into a controlled `failsafe`. Separately,
`INT32_MIN / -1` is also LLVM UB and has no specified result for plain integers
(D-008 §2 fixes it only for `tbb`).

### The fix (choose per the div-hardening schedule)

Two defensible placements; **pick one and state it in this subcycle** so it is not
ambiguous:

- **Preferred — emit the guard now.** Before each `sdiv`/`udiv`/`srem`/`urem`, emit
  the `TYPE_REFERENCE §1.2` pattern: `%z = icmp eq iN %divisor, 0 ; br i1 %z,
  label %failsafe_trap, label %do_div`. The trap block calls `@npk_failsafe` with a
  reserved divide-by-zero code and exits (the same shape `emit_trap` already emits,
  `ir_stmt.npk:386`). Add the `INT_MIN/-1` guard alongside (a second `icmp`/`and`),
  and **decide its result**: trap (proposed — it has no defined value for a plain
  int, and inventing one is what D-008 refused) rather than wrap.
- **Alternative — rung-refuse `/` and `%` on integers until a later 0.9 subcycle
  hardens arithmetic.** Only acceptable if the schedule genuinely defers arithmetic
  hardening; the guard is small enough that deferring it buys little, so the
  preferred path is to emit it now.

Under no option does `/` continue to emit a bare `sdiv` with no guard and no
refusal. That is the one outcome this subcycle exists to end.

### Reserved code

Pin a `DIV_BY_ZERO` failsafe code (and an `INT_MIN_OVERFLOW` code if trapping) in
the D-141 error-code space, so the trap is identifiable and the test can assert on
it — the same discipline that pinned `E_EOF = -4096`. Record it beside the other
reserved codes.

### Tests

`tests/backend/programs/div_guard.npk`: a program that divides by a
runtime-computed zero and asserts the process exits with the div-by-zero failsafe
code (executed-exit-code test, the 0.7.7 instrument). A second case for
`INT_MIN / -1`. A control case (`10 / 2`) that returns `5` normally, so the guard is
shown not to fire on good input.

## Done when

- `limit`, `requires`, `ensures`, and loop `invariant` each produce
  `NITPICK-RUNG-001` naming 1.3, with a rejection case each and the code registered
  in `check_codes_tested`.
- Integer `/` and `%` either emit the div-by-zero (and `INT_MIN/-1`) guard with an
  executed-exit-code test, or are rung-refused — decided and recorded here, not
  left ambiguous.
- The `../audit-0.8-close/probes/limit_drop.npk` program no longer compiles to unguarded IR: it
  either refuses (limit/contract path) or traps at runtime (division path).
- A one-line note lands in `total_audit.md`'s LIVE section marking both closed, so
  the audit record stays honest.
