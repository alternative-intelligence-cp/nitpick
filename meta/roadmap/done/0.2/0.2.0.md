# 0.2.0 — AST representation

**Cycle 0.2 — AST and parser.**

## Goal

Storage for every AST node: typed handles, growable per-category arrays, and the
node struct itself.

## Design

**Four categories, four arrays** — expressions, statements, declarations, types.
Each node is `{ kind, span, … }` with a tag: a tagged enum over a struct, which
is what `CLAUDE.md` means by "tagged enums over composable structs" and what
Nitpick has instead of base/derived nodes.

**Handles are distinct types**, not bare `int32`. An `ExprId` must not be passable
where a `StmtId` is wanted -- that is a semantic type, exactly as `fd` is not an
`int32` (D-042). Costs nothing at runtime and removes an entire class of mixup
from a data structure built almost entirely of indices.

**No pointers in the AST.** Indices survive array growth, are easier to verify
than a pointer graph, and keep an enum payload inside one machine word
(`SUBSET_1.md` §1.2).

**Slot meanings are per-kind, and call sites never touch slots.** A node carries
a small fixed set of index slots; every kind gets named constructor and accessor
functions. Without generics, one array per node shape would be thirty
hand-written containers; the accessor layer restores the readability at zero
runtime cost, and it is the only place a slot is interpreted.

## Done when

- Nodes of every category can be created, stored, and read back by handle.
- Growth past initial capacity preserves every node.
- An out-of-range handle is an error, never a sentinel.

## Not in this subcycle

No parsing. This is the shape the parser will fill.
