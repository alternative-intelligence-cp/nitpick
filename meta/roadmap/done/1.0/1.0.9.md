## The disposition of every "1.0" string

Three outcomes exist, and every row below has exactly one: **lower** it;
**convert** it to `LL_BROKEN`/`EMIT_INTERNAL` because the frontend already
refuses the program and the emitter can never be asked (the `ir_types.npk`
header's own rule: reporting an unreachable shape as "enabled by cycle 1.0" is
a sentence that is not true); or **re-point** it at a cycle that genuinely
owns it, by name, never as "next".

## The defects that are not rung strings (found at 1.0.7's opening)

- **`==` on a non-scalar emits `icmp` on an aggregate.** `struct:P` compared
  with `==` passes the checker (`type_comparison` unifies and checks ordering
  only) and `llc` refuses the IR: "icmp requires integer operands". 1.0.7 makes
  it a named refusal; this subcycle decides what it means — **T-5**.
- **A `for` binding's type is never compared with the element type.**
  `for (int8:i in 300i64..302i64)` passes the checker and `llc` refuses the IR
  ("defined with type i64 but expected i8"). And **a struct is accepted as an
  iterable** — `for (int32:v in p)` with `p` a struct reaches the backend and is
  refused as a rung, which calls it valid Nitpick. Both are checker fixes with a
  named code each, landing with T-2.
- **`check_kinds_lowered_or_refused` counts a refusal as coverage**, which is
  correct for its question and is why none of the above was a finding: a kind
  that refuses by name IS covered. The gap this subcycle closes is the
  refusal's TRUTH, which is the instrument below.

## The decisions — SETTLED at 1.0.9's opening as D-165–D-172

The user accepted every recommendation below (T-1…T-5 explicitly; T-6…T-8
under the standing instruction to take the recommended approach on trait,
generic and `dyn` questions, judged by the priority order and the language's
own style). T-3 was decided by measuring the prototype, as it said it must:
`?|` turned out to be a second spelling of `?` and is struck (D-167). Each is
raised here with the recommendation it was settled on. **`T-n` are the stable handles** (the tail's),
in the roadmap's convention: a decision takes its `D-` number when it is
settled, and `OPEN_DECISIONS.md` already proposes numbers from D-165 for the
G-rows, so naming these by number here would collide.

- **T-1 — module-level bindings.** The parser and checker accept them
  (`type_stmt.npk`: "a global's annotation and its initialiser"); the backend
  refuses at the declaration. **Recommend:** a module-level binding requires a
  CONSTANT initialiser — a literal, a sentinel, or a `comptime(…)` — and lowers
  to an LLVM `global` with that constant. No module initialiser runs before
  `main`: an initialiser that calls a function is order-dependent across
  modules, which is a value appearing in an order nobody chose (D-010's
  objection), and it is the one thing a verifier cannot see from the
  declaration. `fixed`/`const` rules apply as they do to locals.
- **T-2 — what `for` iterates.** D-023 says "a range or collection"; the
  backend lowers ranges, slices and arrays; TRAITS_REFERENCE §2 shows an
  `Iterator` trait whose `next` returns a bare `Item` with no way to stop.
  **Recommend:** `for` iterates a range, a slice, an array, or a value whose
  type implements the prelude trait `Iterator` — `assoc:Item;
  func:next = Item?(Self->:self);` — where `NIL` ends the loop. `Item?` is
  expressible only now (1.0.7), which is why this was not decidable earlier.
  The binding's type must equal the element type (no wrap, no widening). The
  spec example is corrected to the `Item?` signature.
- **T-3 — the defaults operator.** `expr ?| fallback` is "a scoped fallback
  for an entire expression chain" (OP_REFERENCE §0), typed today as "both
  sides one type" with nothing that says WHEN the fallback is taken. Under
  D-013 a chain containing a `Result` does not typecheck without `raw`/`relay`,
  so the prototype's reading (any error in the chain yields the fallback) has
  no chain to apply to. **Check the prototype's tests for the construct before
  deciding** (its lexer and parser are the authority on what was meant), then
  either define the trigger precisely or strike the operator with the reason
  recorded, per D-097's countermeasure.
- **T-4 — how an interpolated value becomes text.** `&{x}` in a template
  (D-053 moved all formatting here). **Recommend:** a `string` is itself; every
  other type goes through the prelude trait `ToString` (`func:to_string =
  string(Self:self)`), with the prelude supplying impls for the builtin scalar
  types over runtime conversions, and a type with no impl refused at the
  CHECKER by name. The template lowers to a `string_concat` chain. No format
  specifiers — a width or a radix is a `to_string` variant someone writes.
- **T-5 — equality on non-scalar types.** **Recommend:** `==`/`!=` on a
  struct, array, `Result`, `Optional` (both sides non-`NIL`), `string` or `dyn`
  is refused at the checker with a named code, and a type that wants equality
  implements `Eq` and is compared with `a.eq(b)` — which `#[derive(Eq)]`
  already writes fieldwise. A silent fieldwise `==` would make `Eq` a second
  spelling of it (the D-123 objection to `Display`), and a `dyn` comparing by
  pointer would be a third meaning. `string` equality is `string_eq`, as
  `src/` already spells it everywhere.

- **T-6 — grouping a type: an array, pointer or `Optional` OF a `dyn`.**
  Found at 1.0.6e: the `dyn` production parses each operand with the full type
  grammar and takes no suffix of its own, so `dyn Speaks[2]` can only mean
  `dyn (Speaks[2])` — refused, since an array is not a trait — and **no
  spelling exists** for `[dyn Speaks; 2]`, a pointer to a `dyn`, or a `dyn?`.
  The only reachable form today is by substitution (`Pair<dyn Speaks>` with a
  `T[2]` field). **A grammar change, so the user's call.** Two candidate
  shapes: (a) suffixes after a `dyn` set apply to the WHOLE set
  (`dyn A & B[2]` is an array of `dyn A & B`) — one fewer token, but it is a
  precedence rule a reader must know, and it reads two ways; (b) a
  parenthesised type, `(dyn A & B)[2]` — explicit grouping, no rule to
  remember, and the expression grammar's own answer to the same question.
  **Recommend (b)**: one production in `p_parse_type` (`(` type `)` then
  suffixes), no new node kind, nothing else in the tree changes. Until it is
  settled the checker refuses the unspellable shape by name rather than with
  "every operand of `dyn` must be a trait", which describes the parse rather
  than the mistake.

- **T-7 — an inherent impl over a generic family.** Found at 1.0.7:
  `impl:<T>:List<T> = { … }` is refused as "not a trait", because D-161's
  amended segment rule reads one segment after a generics window as a blanket
  impl's trait. So a generic struct cannot have inherent methods; they must go
  through a trait, which is a distinction no concrete struct has to make
  (`impl:Holder = { … }` is fine) — the kind of context-dependent rule the
  blueprint philosophy forbids. **A spelling, so the user's call.**
  **Recommend:** the blanket form takes an explicit target — `impl:<T: P>:T:Loggable`,
  "for `T`, implement `Loggable`" — after which every impl reads by ONE rule,
  `impl:<generics>:Target(:Trait)?`, the inherent family is the trait-less
  case of it, and no segment counting or shape test decides anything. The
  cost is rewriting the blanket impls in `tests/` to the explicit form (none
  exist in `src/`, which the seed builds). The alternative — a distinct
  keyword for the blanket form — adds a token to say what the target already
  says.

## Owed by the 1.0.8 message audit

The audit read all 218 construction sites; it fixed the messages and the
small code defects under them, and left these, each too large or too
decision-shaped for a message subcycle:

- **A qualified call spelling for an ambiguous method — T-8.** D-102 promised
  "the free-function form, which UFCS guarantees is available" and none
  exists: an impl's method declares nothing at module scope, and
  `Trait.method(p)` resolves `Trait` as a type. The `TYPE_AMBIGUOUS_METHOD`
  message now says so; the decision needs a form (or an amendment of D-102
  that withdraws the promise). The same ambiguity on two BOUNDS of a generic
  parameter has no form either.
- **`#unreachable()` (D-061)** — the builtin the `(!)` refusal names does not
  exist; provide it (traps through D-142's route), and restore that message's
  advice.
- **The two derives not generated (D-123):** `Hash` (FNV-1a over every field,
  strings through `s.ptr[i]`) and `Ord` on an enum (the tag through
  `=>! int32`). Both refuse under `DERIVE_NOT_GENERATED` with the true reason;
  the generators are the work.
- **Unary minus on a `tbb`** is refused by the checker while D-008 §2 makes
  negation total on it — decide which is right and align the other.
- **`#wild_ptr`'s argument form:** D-019's examples write
  `#wild_ptr<int8->>(addr)` (the pointer) and the implementation, its message
  and `tests/grammar/whole_grammar.npk` use the pointee form — a spec/code
  disagreement to settle by decision, not by edit.
- **`LEVEL:x` is reported at the parameter's declaration**, not at the misuse
  (`value_param_in_type_position` has only the declaration's span).
- **`T-> => any->` erasure** is `=>!`-only today; whether erasing is a checked
  conversion is a `cast_class` question D-095 does not answer.
- **The bare-trait rung (`TY_TRAIT` in `ll_type`)** renders "the type `Shape`
  … enabled by cycle 1.0" for something the comment says is never a value
  type — the conversion row above covers it.

## The instrument: `check_rung_names_open_cycle`

A whole-tree check in the existing mould: every `iv_rung`/`ll_rung` string in
`src/backend` names a cycle, and that cycle's folder is **not** in
`meta/roadmap/done/`. The day 1.0's folder moves, any surviving "1.0" string
fails the harness. The two row-citing forms ("1.1 (G-3)", "a later cycle
(G-2)") are parsed for their leading cycle or their row, and a row must exist
in `OPEN_DECISIONS.md`. This is the check 0.9.7 did by hand and this subcycle
does by hand for the last time.

## Tests

One executed program per lowered row (multi-payload variants, struct
destructuring, a call through a function-valued field, the `dyn` cast, a `dyn`
over a family instance, a `comptime` value at run time, a pipe, a template with
three interpolated types, a `for` over an `Iterator`, a module-level constant);
one rejection case per checker refusal introduced (non-scalar `==`, a `for`
binding that does not match, a non-iterable, a turbofish on a function value, a
global with a non-constant initialiser, an interpolated type with no
`ToString`); the converted rows each get a probe in `tests/grammar/` showing the
frontend refuses the shape first.

## Done when

`rg '"1\.0"' src/backend` returns nothing; every row above has its outcome
recorded against it; T-1…T-7 are settled in `DECISIONS.md` (numbered there) with the specs
updated in the same change; `check_rung_names_open_cycle` runs on every harness
invocation; the fixpoint holds; **cycle 1.0 closes** — generics, traits, `dyn`
and `Optional` all lower, no refusal names the cycle, and the concrete
collections are ready to retire when 1.2 switches the builder.

## Outcome — part one

**The eight decisions are settled and recorded (D-165–D-172), three earlier
decisions amended (D-008 negation admitted, D-019's `#wild_ptr` example
corrected to the pointee form its sibling uses, D-095 extended: retyping a
pointer is `=>!` in both directions), and the tail is four subcycles with a
plan each.** The user took every recommendation; T-3 was decided by measuring
the prototype, whose changelog defines `?|` as the same node as `?`.

**The instrument found a stale rung on its first run.** `check_rung_names_open_cycle`
reads every `iv_rung`/`ll_rung`/`pv_rung` string in `src/backend` and fails
the harness when the cycle it names is in `done/` (or the row it cites is not
in OPEN_DECISIONS); the day `1.0/` moves, twenty strings fail unless the tail

real on `"0.8"`: `addr_of`'s "assignment to a name that is not a local" is a
`pv_rung`, and 0.9.7's sweep grepped `iv_rung`. Re-pointed at 1.0 (D-165,

**Conversions, each with the frontend refusal measured first:** bare `any`
(`TYPE-003`), `Self` outside a body (`TYPE-005`), a template parameter outside
