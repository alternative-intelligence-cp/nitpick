# 1.0.9a — Allocas are hoisted to the entry block

**Cycle 1.0, the tail, inserted.** Found the moment part one's added code made
the seed-built `npkc` **segfault compiling `src/`** — a latent codegen bug the
larger source finally tripped, and a hard blocker on self-hosting, so it lands
before the rest of the tail can run its self-check.

## What was measured

`npkc src/main.npk` crashed in `expand_audit`, with the stack pointer ~8 MB
below its top — a stack overflow, confirmed by its succeeding under
`ulimit -s 262144`. The cause is **`alloca` inside a loop body**: the seed
(and the real backend) emitted every local's `alloca` where the local was
declared, so a `while` that declares an `ExprId` and an `ExprNode` each
iteration allocated fresh stack on every one and reclaimed none until the
function returned. `expand_audit` walks `ast_expr_count` expressions — ~100k
for `src/` compiled as one program — and 100k × a few allocas overflows the
default 8 MB stack.

It is the exact class `check_kinds_reachable`'s own history names ("an
out-of-bounds read in `ralloc` that took the process down on any file past
about 511 declarations") and `type_layout`'s ("a bare DFS over a DAG is
exponential"): a construct that scales with the program and was never measured
at scale. A stack overflow is an uncontrolled crash — the physical-safety
event the language exists to prevent — so it is not a stopgap-with-a-bigger-
stack candidate; the memory has to stop growing.

## The fix

**Every `alloca` is emitted into the entry block, once per call**, wherever in
the body the local is declared — the idiom every real compiler uses, and sound
for the same reason: the entry block dominates every other, so an alloca placed
there is valid at every use, and the value name does not move. A slot reused
across loop iterations is correct because each iteration writes it before
reading it, and a local whose address outlived its iteration is already refused
by the escape analysis (D-004), so nothing the language admits depends on a
fresh slot per iteration.

**In both codegens, by the same transform, so the fixpoint holds.** The seed
(`emit.py`) keeps a list of lines and inserts each alloca at a cursor just after
`entry:`, advancing it so they keep creation order. The real backend
(`ir_writer.npk`) streams, so it buffers a function's allocas and its body in
two sinks while the function is open and splices them — allocas first, then
body — into the module stream at the function's close (`irw_open_fn`,
`irw_close_fn`, `irw_alloca`; `sink_reset`/`sink_append` added to the Sink).
Both move each alloca line from its body position to the entry region in
creation order, and both produced byte-identical output before, so they produce
byte-identical output after — which the stage-1/stage-2 fixpoint confirms.

## The instrument

`check_allocas_hoisted` (harness) scans every emitted program's IR: an `alloca`
outside its function's entry block fails the run, so a later lowering that
writes one inline instead of through `irw_alloca`/`self.alloca` is caught here
rather than as a crash on a large input. It found nothing to fix in the
hoisted tree and catches a demoted alloca when one is planted.

## Done when

`npkc` compiles `src/` at the default stack; every alloca in the emitted IR is
in its function's entry block; the fixpoint holds byte-identically; `check_allocas_hoisted` runs on every
program; the full suite is green.
