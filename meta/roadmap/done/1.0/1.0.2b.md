# 1.0.2b — Generic function lowering

**Cycle 1.0.** The half 1.0.2 split out: a generic FUNCTION emits one body per
argument set. Gated on 1.0.2 (generic types).

## Why it was a separate subcycle

A generic type needs one substituted `%"npk.mod.Container<int32>" = type { … }`
per instantiation — a body walk. A generic function needs one whole FUNCTION per
argument set, and the two hard parts have no analogue on the type side:

1. **Nothing recorded which instantiations a program asks for.** A generic
   type's instantiations ARE the interned type table (an instance is a type, so
   D-108's interning dedups them and the emitter walks the table). A call's
   substituted signature is an anonymous `TY_FUNC` that says nothing about which
   function it came from, and for an INFERRED call — `extract(c)`, the common
   form — the arguments exist only in the checker's scratch, never in the AST.
2. **The call site has to name its specialization**, and a call node's slots are
   all spoken for (callee, argument window, generic count). Widening the AST to
   carry a backend index is the frontend rework the capability ladder exists to
   prevent.

## What it built

- **`FnInstTable`** (`types.npk`): the instantiations a program requests, one
  entry per (declaration, argument window, substituted type), deduped by
  comparing the ARGUMENTS — D-108's rule applied to functions. Recorded in
  `type_generic_call`, where the checker has already solved and bound-checked
  every argument, and where the window is committed into the AST's id pool so it
  outlives the call.
- **`emit_fn_instance`** (`ir_stmt.npk`): one specialized body, under the D-108
  spelling `identity<int32>` which `mangled_fn_sym` then qualifies and quotes.
  The generic declaration itself emits nothing — a template, like a generic
  struct.
- **The call site re-derives its instantiation** by matching its own argument
  types against the recorded instantiation's substituted parameter types. No new
  AST slot, no side table keyed by expression.

## The substitution's shape (the part that took three attempts)

`fn_signature` calls `bind_own_generics`, which rebinds the declaration's
parameters **unbound** on purpose — a definition is checked with `T` opaque
(D-107). So a generic scope pushed around `fn_signature` is discarded before any
annotation resolves. The working shape is both halves:

- **substitute what resolution returns** (the signature's success type, each
  parameter type) — the same move `type_generic_call` makes on the caller's side;
- **push the binding around the resolutions the BODY does** (parameter
  annotations, local `T:tmp` declarations), because those go through
  `resolve_type` directly and would otherwise report "there is no type named T".

Expressions need neither: the checker recorded every expression's type when it
walked the body, and the emitter reads recorded types. Only ANNOTATIONS resolve
at emit time, which is exactly what the binding serves.

## Tests

`tests/backend/programs/generics.npk` gains `identity<T>` called at `int32` and
`int64`: two definitions, two call sites, each reaching its own symbol, exit 45.
`tests/rejection/generics.npk` is RETIRED — it asserted the refusal this
subcycle removes, and the acceptance test is its inversion.

## Done when

Generic functions lower and run; each call reaches the specialization for its
arguments; the declaration emits nothing; the fixpoint holds.

## Outcome (recorded at close)

Landed as described. Harness 62 green (one fewer than 63: the retired rejection
test), fixpoint byte-identical over a substantially changed emitter — the
compiler compiles its own generic-function machinery.

Two mechanical defects surfaced only in the self-compile, not in the
frontend-only checker: `type_subst` and `type_display` were used in backend
modules that did not import `type_generic` / `type_names`. The frontend checker
had accepted the files individually; only npkc compiling ITSELF resolved every
name across the whole module graph. That is the selfhost stage earning its
place again.
