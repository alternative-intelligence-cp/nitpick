# 1.0.4 — Traits, impls, and generic families (D-161)

**Cycle 1.0.** Trait-method dispatch on concrete receivers, default methods, and
impls over generic families. Decided: `D-161` (and the default-method half of the
grammar audit).

## What it builds

- **D-163 hook:** `check_signature` compares the trait method's CONTRACT WINDOW,
  not only its parameter and return types — an impl of a `never fails` trait
  method may not silently drop the clause (D-163 rule 5, the direction of
  LOCK-002). The comparison is built here even though the licence lands at 1.1.

- **Trait-method dispatch on concrete receivers** — `x.trait_method()` where `x`'s
  type implements the trait, resolved through the impl table (the machinery exists
  for inherent methods; this extends it to trait impls) including **inherited
  defaults** (a trait method with a body, used by an impl that omits it).
- **Family impls** (D-161): the one contained `p_parse_impl` production change —
  after the generics window, a type; a following `:`-type means the first was the
  target (`impl:<T>:Box<T>:Sized2`), else the target is empty (blanket, unchanged).
  Per-instance impls (`impl:Box<int32>:Sized2`) already work and gain regression
  coverage. Overlap between a family and a per-instance impl for one (type, trait)
  is refused (§4.1, no specialization).
- **Derive on a generic subject** synthesizes the family form; until proven, it
  refuses generic subjects by name (never the broken `impl:Box:Eq` it emits today).

## Tests

A trait implemented on a concrete type, dispatched through a method call; a default
method inherited and overridden; `impl:<T>:Box<T>:Trait` checked and an instantiation
dispatching to it; an overlap refused; `#[derive(Eq)]` on `Box<T>` either generating
the family impl or refusing by name.

## Done when

Trait methods dispatch on concrete receivers with defaults; family impls parse,
resolve, check, and lower; overlap refuses; derive-on-generic behaves per D-161; the
fixpoint holds.

## Outcome (recorded at close)

**Trait dispatch, inherent methods, and inherited defaults all lower and run**
(`tests/backend/programs/traits.npk`, exit 21). Three pieces, each a real gap:

- **The `impl` block lowers** — it has no code of its own, so lowering it is
  emitting its members with `Self` bound to the target for the duration. That
  binding lives on the resolver, mirroring what `type_method_call` does on the
  checking side (`r.self_type = recv`), which is what keeps the two answers one
  answer. This also lights up 1.0.3's inherent methods, exactly as that
  subcycle's outcome predicted.
- **Inherited defaults are FOUND.** `find_method` asked only an impl's own
  members, so a default the impl omitted reported "no method". It now falls
  back to the trait — asked only when the impl is silent, the same
  concrete-outranks-general ordering the blanket search already used.
- **A `Self` receiver inside a default body resolves.** `Self` is the anonymous
  placeholder D-103 designed and carries no declaration, so `self.other()`
  inside a default had nothing to look `other` up on. The enclosing trait is
  carried beside it (`ExprTyper.self_trait`) rather than folded into it, so the
  placeholder keeps meaning exactly what D-103 says. What `Self` is guaranteed
  to have is what the trait declares — reaching an impl's method from there
  would reach past the guarantee into one implementor.
- **A default is emitted once per implementing impl**, with `Self` bound — it
  is a template over `Self`, the same shape a generic function is a template
  over its parameters (1.0.2b), and for the same reason.

Two symbol defects found by READING the emitted IR rather than by a failing
test: impl members and trait members were absent from the modmap, so both fell
through to the unqualified `@npk_<name>` fallback and lost D-156's
qualification silently. The fallback links; it just does not qualify.

**Family impls (D-161) are SPLIT OUT to 1.0.4b, and the reason is a
regression I caused and reverted.** The decision describes the production as
"parse a type after the generics; a following `:`-type means the first was the
target". Implemented literally, that BREAKS the blanket form — `impl:<T: P>:P`
has no type in the target position at all, so parsing one consumes the trait
and the following `:` is not there. The two forms are genuinely ambiguous at
that point and distinguishing them needs either a lookahead rule or a decision
about which spelling wins, which is a grammar question I will not answer inside
a lowering subcycle. Reverted, verified the blanket form parses again, and
carried the finding into 1.0.4b — where the D-161 amendment belongs.

**Derive-on-generic** rides with 1.0.4b: it synthesizes the family form, which
does not parse yet.
