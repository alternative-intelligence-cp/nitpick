# 1.0.6c — `T.Item`: a dotted suffix in type position (D-164)

**Cycle 1.0.** The projection D-160 assumed the parser already had. Decided as
**D-164** at 1.0.6b's close, once C-21 was fixed and the alternative it had to be
weighed against actually worked.

## What it builds

- **One branch in `p_suffixes`**, beside `->`, `?`, `[]` and `[N]`: a `.` after a
  type, followed by a name. The suffix loop is already the place where a base
  type accretes meaning, and this is one more accretion.
- **A new AST `TypeKind`** carrying (base type, name). Every walker over type
  nodes learns it — `resolve_type`, `type_mentions_self` (D-157's walk),
  `type_subst`, and the node-kind reachability check demands a case that
  exercises it. **A missed walker is a silent wrong answer, not an error**, which
  is the failure mode `ast.npk`'s own note about a literal's width suffix
  describes.
- **Resolution through the bound.** `T.Item` where `T` is a parameter: find the
  assoc among `T`'s bound traits, then substitute the impl's binding where `T` is
  known. 1.0.6 built both halves already — `assoc_of_trait` finds the member and
  `assoc_binding` resolves it — so this is a third caller rather than new
  machinery.
- **The ambiguity rule.** `T.Item` where two of `T`'s bounds declare `Item` is
  refused naming both, the same answer D-158 gives a method supplied by two
  bounds. No ordering tiebreak: after D-159's canonical ordering, "first" would
  be decided by how the traits are SPELT.

## The obligation this carries, which is not optional

**D-159's tie reopens the moment this lands.** That amendment says so in as many
words: with a dotted type spelling, two same-named traits from different modules
can both be named in one file — a glob import of both is still the loader's
ambiguity, but `dyn a.S & b.S` becomes expressible — so the canonical `dyn` bound
order must key on a **module-qualified** name rather than a bare one, or the two
spellings become two types with two layouts again.

The data exists: `build_modmap` walks the module graph to produce decl-index →
module-name. It is built in the BACKEND and interning happens in the frontend, so
the map (or the graph) has to reach `TypeResolver`. **That plumbing is part of
this subcycle**, and D-164 says so rather than leaving it to be discovered.

## Tests

`Iterator` with `assoc:Item`, an impl binding it, and a generic function over
`<T: Iterator>` that declares a variable of `T.Item` and returns it — the whole
point of the feature, and impossible today. Then: two bounds declaring one assoc,
refused naming both; a qualified type path (`a.Local`) now that one parses, which
the same production gives for free; and `dyn a.S & b.S` interning identically to
`dyn b.S & a.S` across two modules, which is the D-159 obligation made visible.

## Done when

`T.Item` parses, resolves through the bound and substitutes per impl; two bounds
declaring one assoc are refused naming both; the `dyn` bound order keys on a
module-qualified name and same-named traits from two modules no longer tie; every
type-node walker handles the new kind and the reachability check proves it; the
fixpoint holds.


## Outcome

**The grammar and the resolution landed; the substitution did not, and the
reason is architectural rather than incidental.**

What works:

- **`T.Item` parses** — one branch in `p_suffixes` beside `->`, `?` and `[]`,
  and a `TypeProjection` AST kind (base in `a`, name in the payload). There is
  no ambiguity with expression-position `.`: types and expressions are separate
  grammars with separate entry points.
- **It resolves through the bound.** `T`'s bounds are read from the PARAMETER'S
  DECLARATION rather than the bound table — the window travels with the
  declaration, so the answer does not depend on which scope a caller passed, and
  the resolver needed no new required pointer to answer a question the AST
  already holds.
- **Two bounds declaring one assoc is refused naming both** (`NITPICK-TYPE-020`),
  the answer D-158 gives a method supplied by two bounds.
- **A name no bound declares is refused by name** (`NITPICK-TYPE-001`) rather
  than falling through to the invalid type, which is the silent wrong answer a
  new type kind most easily becomes.
- **`func:element<T: Iterator> = T.Item(T:it) { pass (raw it.next()); };`
  typechecks** — a generic function declaring and returning the projected type.

Two fixes were needed to get there, both of the same shape as C-21:

**The call site had to bind the TRAIT, not just its parameters.** 1.0.6b bound a
generic trait's parameters at the call site; an assoc in the same signature needs
the trait itself, since `Item` is a member of it and in no scope. Same defect,
same place, the other half of what a trait's signature can mention.

**`TY_ASSOC` had to carry its BASE.** With only (trait, name), `T.Item` and
`U.Item` interned as one type, so a function generic over two iterators had one
element type and substitution had nothing to substitute. And the base is
whatever `Self` MEANS at the point of resolution, not the literal `Self` type —
hardcoding it made the declared `T.Item` and the `Item` in `next`'s signature two
different types, so a function returning one and calling the other did not
typecheck.

## What did not land, and the constraint behind it

**A concrete call through a projection.** `int32:v = raw first(c);` where
`first` returns `T.Item` and `c` is a `Counter` still refuses: nothing turns
`Counter.Item` into the `int32` the impl bound. It REFUSES rather than
miscompiles, which is the right failure mode, but the feature is not finished
until it does.

**`resolve_type` cannot consult the impl table, and that is deliberate.**
`ImplTable` is declared in `type_trait.npk`, which imports `resolve_type.npk` —
so a field on `TypeResolver` is a genuine import cycle, tried and reverted. It is
not an accident of layering either: the architecture's answer for anything
needing impls is a LATER PASS, which is exactly why instantiations are recorded
and `check_instantiations` runs after the table exists. `TypeResolver`'s own
comment says so — "so that bound satisfaction can be decided after the impl table
exists rather than while it is still being filled".

So assoc normalisation belongs in that tier, and **where exactly is a design call
worth making deliberately** rather than at the end of a long subcycle. The
candidate site is `type_access.npk`'s substitution of a generic call's signature,
which is in `ExprTyper` territory and has `e.impls` — but normalising there means
walking the substituted type structurally, which duplicates `type_subst`'s walk.
The options are to extend `type_subst` with an optional normaliser, to write a
second walk, or to normalise as its own pass over recorded instantiations. That
is **1.0.6d**, and it opens with that choice.

**D-159's module-qualified key also remains** — the obligation this decision
carries. A dotted type spelling now parses, so two same-named traits can be named
in one file and the canonical `dyn` bound order needs the qualified key. Nothing
exercises it yet, which is precisely why it must not be forgotten: it is 1.0.6d's
second item.
