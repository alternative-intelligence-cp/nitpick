# 1.0.5c — `dyn` lowering: vtables, thunks, construction, widening

**Cycle 1.0.** The backend half of D-158 and D-159. 1.0.5 built the frontend —
object safety, the layout, the canonical bound order, and dispatch — and
`ll_type` still answers `NITPICK-RUNG-001` for `TY_DYN`, so no `dyn` has ever
been emitted. This subcycle is what makes one run.

Split from 1.0.5 rather than left inside it because the frontend half is
complete and testable on its own: object safety refuses, dispatch resolves,
ambiguity refuses, and the layout is asserted — none of which needed a vtable to
exist. What follows needs all of it, and none of it needs re-doing.

**Gated on 1.0.5b.** A vtable is a table of a particular impl's methods, and
until 1.0.5b those methods do not have distinct symbols: two impls of one trait
on different types both emit `@"npk.<module>.<name>"` and `llc` refuses the
module. There is nothing to put in a table whose entries collide.

**`ll_type`'s `TY_DYN` arm stays a rung until this subcycle**, and the reason is
recorded in the code: lowering the SHAPE alone was tried at 1.0.5b's opening and
reverted within the hour. With a real `{ ptr, ptr }`, assignment stored a 4-byte
`Dog` into the 16-byte slot, loaded 16 bytes back with 12 uninitialised, and
called the CONCRETE method directly with the result — which returned the right
answer, because the struct's one field sits at offset 0. A silent miscompile
that passes its own test is worse than the refusal it replaced.

## What it builds

- **The vtable (D-158)**, one per (impl, trait). Entries in TRAIT DECLARATION
  ORDER — slot = declaration index, stable and source-derived, hash-free for the
  same reason D-156's symbols are. Each entry points at a **per-impl adapter
  thunk**: the caller always passes the data pointer plus the arguments, and the
  thunk — compiled against the concrete type, which it knows — loads the
  by-value receiver and calls the real method. That is what lets an impl keep
  its natural `Point:self` signature while the erased caller passes one pointer.
- **Construction**: a concrete value widened to `dyn A` builds `{ data, vtA }`.
  The data word's ownership follows the value's regime; nothing about `dyn`
  changes who drops it.
- **The call**: load the slot at the declaration index of the trait the method
  resolved through (`find_method` already returns the trait in `owner`), then
  call the thunk. The return is the trait signature's return, `Result`-wrapped
  like every call (D-013).
- **Widening (D-159)**: `dyn A & B → dyn A` is a VALUE REBUILD — copy the data
  word and the retained traits' vtable words into the smaller shape, positions
  statically known from the canonical order. No runtime tables and no
  prefix/subview scheme.
- **Retire the rung.** `ir_types.npk`'s `TY_DYN` arm stops returning
  `ll_rung("1.0")` and returns the `(N+1) x 8` aggregate.

## The D-159 loose end 1.0.5b closes

1.0.5 canonicalises the bound list by TRAIT NAME, which is source-derived and
ABI-stable — but **two same-named traits from different modules TIE**, and the
tie is currently broken by declaration index, which is deterministic within a
compilation and shifts if an unrelated declaration is added earlier. An ABI that
moves for an edit that touched nothing is not one this project can ship.

**Closed at 1.0.5b, by measurement.** Two same-named traits cannot both be
named in one file — a glob import of both is `NITPICK-RESOLVE-008` and the
qualified form does not parse — so the tie is unreachable and nothing here
depends on it. D-159 records what would reopen it.

## Tests

A program that constructs a `dyn Trait` from a concrete value, calls a method
through it, and exits with what the method returned — the first `dyn` this
compiler has ever run. Then: a two-bound `dyn` dispatching a method from each
bound; `dyn A & B` widened to `dyn A` and dispatched after widening; and a
`dyn` whose impl inherited the trait's DEFAULT method, since D-158 says the
vtable slot is filled with the default's thunk.

## Done when

A `dyn` constructs, dispatches and runs; a multi-bound `dyn` dispatches from
each bound; widening rebuilds and the widened value still dispatches; the
`TY_DYN` rung is gone from `ll_type`; the bound order keys on a module-qualified
name so two same-named traits cannot tie; the fixpoint holds.


## Outcome

**`dyn` constructs, dispatches, widens and runs.** `TY_DYN` is off the rung
list, and `tests/backend/programs/dyn_vtable.npk` exercises the single-bound
case, two implementors through one erased type, a multi-bound value dispatching
from each word, a widening followed by dispatch through the narrowed value, and
a slot filled by an inherited default that calls back into its impl.

The emitted shape, verified by reading it rather than inferred from an exit code:

```llvm
%s = alloca %Dog                       ; spilled — the erased half is a POINTER
store %Dog %v, ptr %s
%f = insertvalue { ptr, ptr } undef, ptr %s, 0
%g = insertvalue { ptr, ptr } %f, ptr @"npk.m.vt.Dog.Speaks", 1
%d = extractvalue { ptr, ptr } %g, 0
%t = extractvalue { ptr, ptr } %g, 1
%p = getelementptr ptr, ptr %t, i64 0  ; the method's DECLARATION index
%h = load ptr, ptr %p
call { i32, i32 } %h(ptr %d)           ; indirect, through the slot
```

Both positions are compile-time constants — the word from D-159's canonical
bound order, the slot from D-158's declaration index — so no runtime table is
consulted anywhere.

## What the shape needed that the plan did not say

**The vtable's NAME needed a pre-pass.** A `dyn` construction knows the concrete
type and its traits and nothing about the impl — and D-156 names the table in
the IMPL's module, which the construction site cannot reach. Emitting impls
before functions would not have fixed it either: impls and functions interleave
in module order, so a function that builds a `dyn` can be emitted before the
impl whose table it needs. `build_vtmap` walks every impl once and records
(self, trait) → symbol, the same answer `build_modmap` gives to the same shape
of problem.

**Spilling the value is what makes the data word exist.** A value has no address
until something gives it one. That the slot is in the current frame is safe
rather than lucky: `carries_pointer` already counts a `dyn` as carrying a
pointer, so the escape analysis refuses a `dyn` that outlives what it points at
exactly as it refuses a returned borrow — checked before relying on it.

**A non-object-safe trait gets no table, and that is not a refusal.** Its `dyn`
was already refused at every use (D-157), so no table is ever loaded; building
one anyway would mean thunking a method that returns `Self`, which has no erased
signature, and would turn a legal program — a non-object-safe trait nobody uses
as `dyn` — into a rung. `trait_is_object_safe`, split out at 1.0.5b, is what
makes that question askable without duplicating the rules.

**A family impl has no single table** (its target is a template, so each
instantiation would need its own), so a `dyn` over a trait implemented by a
generic family is a named rung rather than a silent omission. Nothing in the
suite reaches it; it is stated because the alternative is a wrong answer.

## The constraint this creates, stated so it is not discovered

**The seed rung-refuses `dyn`** (`bootstrap/generator/ntypes.py` assigns it to
1.0), so the two emitters never exchange one and `tests/backend/ir_types.npk`
needs no `// ll:` marker for it — the check exists for types that CROSS between
the seed and stage 1, and this one cannot.

The consequence is the part worth writing down: **`src/` itself cannot use `dyn`
until the seed is gone at 1.2.** The compiler is seed-built until the fixpoint
closes, so a `dyn` in the compiler's own source would be refused by the thing
building it. If a subcycle before 1.2 wants one, the seed learns `dyn` first.

## Done when

A `dyn` constructs, dispatches and runs; a multi-bound `dyn` dispatches from
each bound; widening rebuilds and the widened value still dispatches; the
`TY_DYN` rung is gone from `ll_type`; the bound order keys on a module-qualified
name so two same-named traits cannot tie; the fixpoint holds. **Met** — with the
bound-order clause closed at 1.0.5b by showing the tie unreachable rather than
by building the key.
