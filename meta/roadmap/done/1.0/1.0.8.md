# 1.0.8 — The diagnostic message is printed

**Cycle 1.0.** Found while writing 1.0.4c's overlap diagnostic. Every
diagnostic this compiler produces carries a hand-written message, and **nothing
prints it**. Scheduled here rather than noted, because it is a defect with a
known fix, and because it gets worse with every cycle that passes.

## What was measured

`Diagnostic` (`src/frontend/diagnostics.npk:23`) has a `message` field. Across
`src/`, `tools/` and `lib/` there are exactly **two** reads of it, both inside
`diagnostics.npk` itself: the duplicate-suppression comparison at line 108, and
`diag_render` at line 286. `diag_render` and its list form are called from
**one place in the whole tree** — `tests/frontend/diagnostics.npk:26`.

Both real drivers define their own printer instead:

| Printer | Prints | Missing |
|---|---|---|
| `src/main.npk:39` `emit_line` (npkc) | `CODE path:line:col` | the message |
| `tools/check.npk:22` `emit_line` | `CODE path:line:col` | the message |
| `diagnostics.npk:274` `diag_render` | `line:col: severity[CODE]: message` | the **file path** |

So there are three renderers, no two agree, the two that run drop the message,
and the one that keeps it drops the path — the very thing 0.8 added after the
first self-check run produced 119 findings with no way to say which file each
was in. A developer running `npkc` today sees:

```
NITPICK-TYPE-013 foo.npk:23:1
```

and nothing else. There are **79 diagnostic construction sites in `src/`**, each
with a message written to explain what the reader should do, and none of them
has ever reached a reader.

## Why this is a defect and not a cosmetic gap

**First, it is the project's own stated standard.** `emit_line`'s D-162 comment
says it outright: *"A diagnostic a reader cannot act on is worse than no
check."* That comment was written to justify rendering `<no span>` rather than
silently exiting 1 — and it applies with more force to the message, which is
the only part that says what to do about the refusal.

**Second, and worse: unprinted means unreviewed.** 1.0.4c wrote a coherence
message whose two halves were bound to declaration ORDER rather than to what
each impl was, so a per-instance impl written first would have been described to
the reader as the one that "covers every instance of the family" — backwards,
and confidently so. It was caught by reading the code, not by reading output,
because there is no output. **Every message in the tree is in that same
unreviewed state**, and the pile grows every cycle. That is the argument for
doing this inside 1.0 rather than filing it against 1.2 with `npkg`: the cost of
waiting is measured in unreviewed text.

## What it builds

- **One renderer, in `diagnostics.npk`, used by both drivers.** The format is
  the union of what the three have now — path, line, column, severity, code,
  and message — because each piece is there for a reason someone already found:
  the path from 0.8's 119-finding run, the `<no span>` fallback from D-162, the
  message from the 79 sites that wrote one. Both `emit_line` copies are deleted;
  a second renderer is what let the two formats drift apart in the first place.

  **The code stays first** — `CODE path:line:col: message` — rather than moving
  to the gcc shape (`path:line:col: error: message`). It is what 0.8 chose, what
  every expectation in the suite is written against, and what keeps the parser
  fix to one comparison; and it puts the STABLE identifier at the start of the
  line, where a reader scanning a wall of output finds it in the same column
  every time. `diag_render`'s current `line:col: severity[CODE]: message` is the
  odd one out and is the one that changes.
- **The message audit.** With the messages visible, read all 79. The 1.0.4c
  role-reversal bug is the existence proof that they need it; expect others of
  the same kind — a message that names the wrong one of two things, or describes
  a rule the code no longer implements.
- **The harness parser, in the SAME subcycle — this is the trap.**
  `harness.py`'s diagnostic reader splits each stderr line on whitespace and
  accepts it only `if len(parts) == 2`, i.e. exactly `CODE path:line:col`.
  Appending a message makes every line longer than two tokens, so the parser
  matches nothing, `got` comes back empty, and **every rejection test in the
  suite fails at once** with "expected [CODE], got []" — a failure that looks
  like the checker broke rather than like the printer changed. The fix is to
  key on position rather than count (`len(parts) >= 2`, span still the last two
  fields of the second token), which leaves every existing expectation valid,
  since expectations assert codes and spans and deliberately never the path or
  the message. Doing this in a separate subcycle is not an option: the two
  changes are only correct together.
- **The instrument: `check_one_renderer`.** A whole-tree check in the existing
  mould — no driver defines its own diagnostic printer, and no diagnostic is
  constructed with an empty message. Cheap, and it pins the thing that broke:
  the drift was possible only because a second renderer was allowed to exist.

## What is NOT in scope, stated so it is not silently assumed

**A source-line snippet with a caret is out.** The `SourceManager` has the text,
so it is buildable — but it changes nothing about what is refused, and it is
additive over the format this subcycle lands rather than a change to it. It goes
in with `npkg`'s output work at 1.2 if it goes in at all. Nothing later depends
on the decision, which is why it can sit; if that stops being true, it moves.

## Tests

The suite asserts on **codes and spans, never message text**, and that does not
change — `diagnostics.npk`'s comment gives the reason (codes are stable
identifiers, wording must stay free to improve).

The obvious addition does not fit and is worth saying so: the `diagnostic` KIND
compares *warnings* and requires the file to compile clean, so it cannot pin an
error's rendering. And the harness's reader discards everything but code, line
and column, so no existing kind can assert a rendered line. The format is
therefore covered **in `tests/frontend/diagnostics.npk`**, which already calls
`diaglist_render` directly and is the one place a rendered string is available
to assert on — extended to cover the path, the severity, the message, and the
spanless `<no span>` case D-162 repaired. That keeps wording free (the assertion
is on the SHAPE — that each part appears, in order) while making the renderer
itself a tested unit rather than, as now, a function with one caller and no
consumer.

## Done when

`npkc` and `tools/check.npk` print path, line, column, severity, code and
message through one shared renderer; the other two printers are gone; the
harness parser reads the longer line and **every existing rejection expectation
still passes unchanged** (that is the signal the format change was
compatible, not that it was absorbed); all 79 messages have been read against
what their code actually does, with any role-reversal or stale-rule defects
fixed; `check_one_renderer` runs on every harness invocation; the fixpoint
holds.

## Outcome

**The renderer, the parser, the instrument and the audit all landed — and the
audit found four code defects and two seed defects the messages had been
hiding.**

### The renderer

One formatter, `diag_line` in `diagnostics.npk`, returns the line as a
string and every driver writes it: `CODE path:line:col: message`, with
`note ` or `warning ` in front for those severities (an error is the unmarked
case), `<no span>` for a spanless diagnostic, `<unknown file>` for a file the
manager does not hold, and the overflow note — which no driver had ever
printed. There were FIVE renderers, not three: the two single-file tools had
their own `CODE line:col` as well. All four `emit_line`s are gone;
`check_one_renderer` refuses a new one and an empty message, and was made to
fail both ways before it was trusted. The harness reader keys on token
position, strips the span's trailing colon, and treats a `warning` prefix as
it treats `note`; every existing expectation passed unchanged on the first
full run, which is what says the format change was compatible.
`tests/frontend/diagnostics.npk` pins the shape line by line.

### The audit — 218 sites, not 79

The plan counted direct `diag_*` constructions; the `te_error`/`ty_error`/
`p_error` helpers quadruple that. Four parallel readers, one per file group,
reported 48 evidenced findings; each was verified against the code before
anything was changed. What they were, by class:

- **Role reversals and wrong names:** "`Color` is not a type" for an enum
  (`decl_kind_article` named nine kinds and answered "not a type" for the
  rest — a struct, an enum, a trait, a parameter, an associated type, all
  types); "is a type, not a value" for a macro or a module; "takes no `self`"
  for a `self` in the wrong position; "this declares `acquires <= 3`" about
  an implementation that inherited the bound; "D-004 rule B" for D-117's;
  "declared here … the local declaration wins" about two imports with no
  local declaration; the `MACRO-009` note saying "inside a macro body" at an
  invocation.
- **Stale rules:** "`tbb32` is not a number, so it has no arithmetic" in the
  branch below the one that accepts `tbb32 + tbb32` (a mixing refusal, said
  as one now); the lossy-cast lead-in "does not fit … can lose information"
  for four classes that lose nothing and assert something (a handle, a
  pointer, a tag read or forged) and enum reasons fabricated by falling
  through to the range sentences; "no operator yields a tag" for `Ord` on an
  enum (`=>! int32` has, since 0.8.0) and "nothing exposes a string's bytes"
  for `Hash` (`s.ptr[i]`, since 0.7.8) — both under `DERIVE_UNKNOWN` for names
  that are two of the seven, both under their own `DERIVE_NOT_GENERATED`
  now; "C has no universal failure convention" (D-002's rationale, retired by
  D-149); "a C variadic extern function".
- **Advice that could not be followed:** "write `42i32`" where the slot was a
  `tbb32` (the next check refused it — the slot-of-another-family case is its
  own sentence now); "the `f64` value … and cast" where the cast is lossy;
  "call the one you mean by its function form" where no form exists (D-102's
  promise is unimplemented — T-8); "name the trait whose associated type you
  mean" where no trait-qualified projection exists; "use a destructuring
  pattern" to match on a scalar type keyword; the `#wild_ptr` hint on the
  pointer-to-integer arm rather than the integer-to-pointer one.
- **Codes:** the impossible conversion shared `TYPE_LOSSY_CAST` with the
  lossy one under messages that said opposite things about `=>!` — it has
  `TYPE_NO_CAST` now; value-argument counts on builtins and arena operations
  carried the TYPE-argument arity code; "has no member" carried the mismatch
  code while `TYPE_NO_METHOD`'s own definition names it; `Net.Nope` and
  `Net.Nope(1)` said different things under different codes for one missing
  variant; a compiler defect carried the unknown-name code.
- **Unreachable:** D-057's hygiene explanation was behind `look != scope` in
  the branch where `look` is `scope`; the generic "cannot find it in this
  scope" was what a macro-body name printed, at the body.

### The code defects the messages exposed

- **SAFETY — any source `=>!` a kernel identifier.** `cast_class` tested the
  target alone, so `Point =>! fd`, a string, a pointer, a float were accepted
  as an opt-out. Only an integer may be (D-042, D-095); pinned in
  `casts.npk`.
- **SAFETY — `struct:A = { A?:a; }` escaped the cycle check.** The containment
  walk said "a pointer or an optional breaks the dependency: one word", and
  an `Optional` lays its value inline. Pinned in `struct_cycle_optional.npk`.
- **`$` outside a counted loop** was typed `int64` by the checker and refused
  by the EMITTER as "a defect in the compiler, not in this program" — the
  program's fault, reported as the compiler's. The checker refuses it now
  (`counter_outside_loop.npk`); the internal-defect text no longer claims
  more than it knows.
- **A spliced field lost its qualifier** — `wild int8->:buf;` in a macro body
  was refused for "carrying" what a field "could not", and the field has the
  same slot; the qualifier is carried (`splicing.npk` gains the case).
- **`'é'` was an unterminated literal**: the lexer took one byte of a
  SourceCharacter; it decodes UTF-8 now (`utf8_decode`, the inverse of the
  encoder), and `'ab'` is "holds more than one character", once, resynced.
- **The receiver was the one slot compared by equality**: `p.f()` with
  `f(Point?:x)` refused what `f(p)` accepted; it goes through `fits` and
  `emit_fit` like every other slot (paired in `check_slot_sites_agree`).
- **`type_mentions_self` had no `TypeProjection` arm** — D-164's obligation
  on every walker, so `Self.Item` off the receiver was invisible to object
  safety.
- **`type_display` printed `<type>`** for arrays, handles, arenas, ranges and
  projections, so "`<type>` and `<type>` are different types" was the whole
  of a refusal between two `Handle`s. Every one-operand kind renders.

### Two seed defects, found by writing one test

`tests/frontend/diagnostics.npk`'s byte scan crashed with a SIGBUS, and the
cause was the SEED: its binary-operator table was written tightest-first under
a recursion that makes the first row the loosest, so `i + k <= n` compiled as
`i + (k <= n)` — `||` was the tightest operator and `*` the loosest. Then the
UTF-8 decoder read a lead byte as negative: the seed widened `uint8 => int64`
with `sext` (it chose the extension by the TARGET's signedness) and typed a
string's bytes `int8` where the real checker has said `uint8` since 0.7.8.
`src/` survived both because every expression in it is parenthesised to one
operator and its sources are ASCII — and the byte-identical fixpoint is the
proof, since it compares the seed's reading of `src/` against the real
parser's. Every seed-compiled TEST written from now on would have had to
know. Both are fixed in the generator (D-085: a regeneration, not an
artifact change), and the fixpoint held.
