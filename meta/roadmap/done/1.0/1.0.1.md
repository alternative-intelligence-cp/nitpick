# 1.0.1 — Type identity by declaration, end to end

**Cycle 1.0, inserted after 1.0.0.** 1.0.0 set out to retire the interim
duplicate-name refusal and recorded that it could not — reading a two-module
emit error as the interned type table merging same-named types. A second
session investigated that note; it found the premise wrong in one place and
right in a different one, and this subcycle is the repair. Verified against the
code before adopting: the drafts were written from HEAD, and where the test
disagreed with the draft, the test won.

## What was true, and what was not

**1. The type table already interns by declaration (D-090).** `tt_struct` /
`tt_enum` intern on `(kind, decl, name)`; two `Local`s reach emission as two
entries with two bodies. The only collision was the pre-scheme spelling
`%Local`, which D-156's `%"npk.<module>.<Type>"` dissolves. "Intern by
qualified name" — 1.0.0's proposed follow-up — would have been a REGRESSION,
moving identity from the declaration to a string, weaker than D-090.

**2. The struct literal was typed by the expected type's BARE NAME.**
`struct_literal_type` compared `type_name(want) == name`, so a `b.Local{…}`
literal in an `a.Local` position was silently built as `a.Local` — meaning
changing with context (the blueprint rule's first facet), and D-129's
omitted-field check never running against the declaration the author wrote.
This was the real hole, and the "emit confusion" 1.0.0 saw: the front half
mis-typed the literal, the backend faithfully built the wrong aggregate, and
under module-qualified names the mismatch surfaced as an IR type error.

**3. A refusal with no span printed nothing and exited 1.** `emit_line`
relayed `srcmgr_path` on a `file = -1` span; the failure propagated through
`report` and was dropped. `check_duplicate_type_names` — the one refusal 1.0.0
chose to keep — pushed with `span_none()`, so it exited 1 in silence.

## What it built

- **D-162: the literal's type is the declaration its name resolves to in
  scope.** `struct_literal_type` resolves the name first; the expected type
  wins only when `type_decl_of(want) == sym.origin` — the declaration, which a
  generic instance carries in slot `a`, so `Container<int32>{…}` still takes
  its arguments from context. A same-named struct from another module falls
  through, and the mismatch is refused where the value is used (TYPE-007).
- **`check_duplicate_type_names` retired**, as 1.0.0 planned: with the literal
  hole closed, two same-named types are two declarations, two entries, two
  D-156 symbols — they link and run (`same_name_two_modules`, exit 13). The
  guard and its `header_kind` helper are gone.
- **A spanless diagnostic is rendered, not lost.** `emit_line` in `main.npk`
  and `tools/check.npk` renders `<no span>` for `file < 0` instead of relaying
  the failure. The remaining `span_none()` uses (module_graph, symbols) are
  best-effort — a real span when available, none otherwise — now visible.
- **`check_identity_by_decl`** (harness): every `type_name(...)` on a line with
  `==` / `!=` is listed; after D-162 there are none, so a new
  identity-by-name comparison is caught the way the first was not.

## An instrument considered and declined: `check_diags_spanned`

The draft proposed a second instrument forbidding `span_none()` near a
diagnostic. Declined with reason: the `emit_line` fix already makes any
spanless diagnostic VISIBLE (its correctness value), and the only remaining
`span_none()` diagnostic uses are legitimate best-effort fallbacks that carry
a real span in the common case — an instrument there is allowlist maintenance,
not a guard against a live hazard. The unconditional-span_none producer (the
retired guard) is gone.

## Tests, and a seed limitation they exposed

The tests live in `tests/backend/programs/` (npkc-only), not the conformance
or rejection suites — because those are compiled by the THROWAWAY SEED, whose
struct table is name-keyed (`self.structs = {}  # name -> fields`) and cannot
represent two same-named structs at all (same-named-type coexistence is a 1.0
feature beyond subset 1, like generics, which the seed also refuses). The
`backend` suite's glob is non-recursive, so `tests/backend/programs/` is swept
only by npkc, which has D-162.

- `tests/backend/programs/same_name_two_modules.npk` (+ `_a`, `_b`): two
  modules' `Local`s with different layouts, private so a wildcard import brings
  only the functions; the IR carries `%"npk.same_name_a.Local"` /
  `%"npk.same_name_b.Local"` and nothing spelled `%Local`; exit 13. It runs
  correctly (a_go builds a's one-field `Local`, not b's) — the positive proof
  that D-162 types the literal by the declaration in scope. **This also
  required the programs sweep to filter imported halves** (fixtures with no
  `main`), the rule the conformance sweep already had.
- The rejection behaviour (`b.Local` where `a.Local` is expected → TYPE-007; a
  partial → TYPE-027 against the right declaration) was VERIFIED against the
  real compiler (`tools/check.npk` emits exactly those two codes) but is not an
  automated suite case: it needs two same-named modules, which the seed cannot
  compile. Both codes are already covered by other tests (`no_implicit_widening`,
  `struct_literals`).

## Outcome (recorded at close)

Landed as D-162 plus the guard retirement and the spanless-diagnostic repair.
The 1.0.0 finding was corrected where it was tested: the type table was never
the problem, the struct-literal typer was, and same-named types now coexist
end to end. `check_identity_by_decl` runs on every harness invocation; the
fixpoint holds (the compiler's own `struct_literal_type` changed, so stage-1
bytes change and stage 2 reproduces them).
