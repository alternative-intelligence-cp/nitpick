### The BORROW-001 class is a COMPILER question, not a test question

Minimal reproducer, bisected down from `tests/frontend/resolve.npk`:

```nitpick
mod:probe;
struct:Box  = { wild int32->:p; int32:n; };
struct:Pair = { Box:b; int32:k; };
func:box_init = Box() never fails { pass Box{ p: (alloc(4i64)) =>! wild int32->, n: 1i32 }; };
func:touch = NIL(Box->:b, Pair->:o) never fails { pass NIL; };
func:make = Pair() never fails {
    Box:b = raw box_init();
    Pair:tmp = Pair{ b: raw box_init(), k: 0i32 };
    drop touch(@b, @tmp);                 // <- two borrows, passed together
    Pair:out = Pair{ b: b, k: 7i32 };     // <- BORROW-001 here
    pass out;
};
```

Discriminated by four probes:

- `@b` passed ALONE, then `b` returned by value in a struct — **accepted**.
- `@b` passed BESIDE a second borrow, then `b` returned the same way —
  **refused**, even when the second borrow is a local with no relationship to
  `b` whatsoever.
- Returning a struct that does not mention `b` — **accepted**, so the refusal
  is about `b` specifically.

So: once a local's address is passed alongside another borrow, the local
becomes borrowy, and a later **by-VALUE COPY** of it into a returned struct is
refused as returning a borrow. `Pair{ b: b, … }` copies the struct; the copy
carries the same `wild` HEAP pointers, which outlive the frame. Nothing frame-
rooted travels up.

That looks like an over-refusal, and D-208's own landing note records the
reason to suspect one before suspecting the tests: *"these analyses fail
closed, so over-refusal is the likelier defect"*. But it is a safety analysis,
the alternative reading is that four test helpers really do hand out frame
addresses, and **either answer is a decision about D-004 rule 2's precision**
rather than something to improvise while migrating tests. Hence the stop.

## Q1 — the BORROW-001 refusal is CORRECT. The connection it assumes is constructible in fully checked code.

The deciding fact is in `parse_type.npk:14`: **qualifiers are not part of the
type** — `stack`, `wild`, `wildx` ride the DECLARATION, so `wild int32->` and
`int32->` are one type id. A frame address therefore stores into a wild slot
with no cast, no `raw`, no `=>!`. This callee — the connection the reproducer's
refusal assumes `touch` might make — **checks clean today (exit 0)**:

```nitpick
mod:probe_launder;
struct:Box  = { wild int32->:p; int32:n; };
struct:Pair = { Box:b; int32:k; };
func:touch = NIL(Box->:bp, Pair->:op) never fails {
    int32->:t = @(op.k);   // param-rooted, so the 0.8.1 exemption leaves t unmarked
    bp.p = t;              // t "not borrowy" -> member store legal; wild int32-> IS int32->
    pass NIL;
};
```

That plants `@tmp.k` — a frame address — into `b.p`; `Pair:out = Pair{ b: b, … };
pass out;` copies it out of the frame; the caller holds a dangling pointer.
Under the analysis's modular worst-case-callee model the refusal is exactly
right, and the four helpers ARE handing callees that ability. So the answer to
"is it correct?" is yes — **but the same fact breaks the analysis in the unsound
direction twice**, both verified live:

**Hole 1 — the single-borrow exemption is false for self-connectable types.**
Rule B's one-borrow exemption says "with nothing else passed in, there is no
second borrow to store." The borrow itself is the second borrow. **Accepted
today (exit 0)**, and the returned copy's `.next` points into the dead frame:

```nitpick
mod:probe_self;
struct:Node = { Node->:next; int32:v; };
func:wire = NIL(Node->:p) never fails { p.next = p; pass NIL; };
func:make = Node() never fails {
    Node:n = Node{ next: NULL, v: 1i32 };
    drop wire(@n);
    pass n;               // copy carries &n; n dies with this frame
};
```

**Hole 2 — `dest_can_hold` matches exact types only, so derived interior
borrows walk past F-1.** The callee below stores `&pt.a` into a caller-owned
slot that outlives `user`'s frame; `dest_can_hold(Cell, Point)` answers no
because Cell holds an `int32->` slot, not a `Point->` one. **Accepted today
(exit 0)**:

```nitpick
mod:probe_derive;
struct:Cell  = { int32->:slot; };
struct:Point = { int32:a; int32:b; };
func:stash = NIL(Cell->:c, Point->:q) never fails {
    int32->:t = @(q.a);
    c.slot = t;
    pass NIL;
};
func:user = int32(Cell->:c) never fails {
    Point:pt = Point{ a: 1i32, b: 2i32 };
    drop stash(c, @pt);   // no refusal: exact-type match misses the interior borrow
    pass 3i32;
};
```

Both accepted programs put a frame address in memory that outlives the frame —
the exact class this language exists to refuse. So the migration question was
the small half. The analysis is currently strict where the compiler's own test
idiom lives and permissive where the danger lives.

## The repair — D-223, **RATIFIED by the user, 2026-08-29** (recorded in DECISIONS.md; D-004/D-117/D-146 carry the cross-references)

One regime rule plus one unified matcher. Three defects close, the four tests
pass **as written**, and the compiler's idioms survive — the last two claims
verified against the actual types below, the first by the new rejection cases.

**1. `NITPICK-BORROW-011` — a borrow may not be stored into a `wild`-qualified
place.** A wild slot holds manually-managed memory; a frame address is not
manual memory — `dalloc` on it frees a stack address, and the 0xAA poison and
quarantine instruments assume heap. The one door stays D-019's: `=>! wild T->`,
the explicit surrender of tracking, greppable. Classification reuses the walk's
existing borrowy machinery; a param-rooted `@` value is still a frame address
and refuses too; a pointer parameter stored whole is provenance-unknown and
fails closed (a site that legitimately needs it spells the `=>!`). Enforced at
the store sites rule 3 already owns — assignment, struct-literal field value —
where the slot's declaration and its `QUAL_WILD` bit (parser.npk:253) are
visible; the dest walk at escape.npk:1290-1311 already holds the member
DeclNode in hand.

**2. Rule B unified on one pairwise, derivation-aware, qualifier-aware
predicate.** `can_connect(dest_pointee, src)`: does `dest_pointee` transitively
contain a NON-wild pointer slot whose pointee is `src` itself or any type
reachable inside `src` (interior places — fields, elements; `any->` matches
everything; fuel-bounded, failing closed on generics and unknowns). Wild slots
are excluded because rule 1 closes them. This replaces three things at once:

- the count-based `borrowed >= 2` arm (the over-broad half — the reproducer's
  refusal came from here);
- `dest_can_hold`'s exact-type match (the under-sound half — hole 2);
- `escape_connect`'s blanket `carries_pointer` filter.

The pair arm marks local-rooted borrow argument A iff `can_connect(TA, TB)` for
some co-source B — **including B = A**, which closes hole 1: the one-borrow
exemption becomes "exempt iff not self-connectable", and the
`tt_intern(@t, k)`-then-`pass t` idiom keeps compiling because TypeTable's
pointer slots are all wild. The param-rooted-destination arm (F-1 / BORROW-002)
keeps its refusal, now derivation-aware.

**3. Why the four tests then pass unmodified.** Every engine table's pointer
slots are wild by convention — verified for Ast (ast.npk:142-181), SymbolTable
(symbols.npk:103), DiagList (diagnostics.npk:66, whose comment states the
convention: "Every other table in this compiler is wild storage behind a
pointer"), TokenList (token.npk:62), InternTable (intern.npk:17). None is a
destination under the new predicate, so `parser_init(@toks, @ast, @pd, it)` and
`collect_module(@tab, @ast, @diags, …)` mark nothing, `Run{ ast: ast, … }` is
clean, and `pass out` is accepted. Context structs (Parser, Escape, Resolver…)
keep plain slots and REMAIN destinations, so BORROW-002 keeps refusing the
capture-shaped sites — those three files get read per site, not annotated past.

**4. Landing order, inside 1.4.6.** The analysis fix + BORROW-011 + rejection
cases land as their own commit BEFORE the migration commit: the three probes
above become rejection cases (plus a pair-with-plain-slots case that still
refuses), and the Q1 reproducer becomes an ACCEPT case. The selfhost stage is
then the audit of src/: any site storing a borrow into a wild slot refuses by
name (expected: none; if one appears it is either a real hazard or spells its
`=>!`). Then the suite migration finishes on top with the four files untouched.

**5. The declined path, recorded.** Restructuring the four helpers around the

The decision is recorded as D-223 in DECISIONS.md; D-004, D-117 and D-146

## Q2 — TYPE-009 / TYPE-046: read all eight; the per-class decision rule

- **`TokenKind => int32`**: if the assertion is about the KIND, compare enum
  constants (or `pick`) — no cast at all. If the numeric value is genuinely the
  point (a stability pin on the discriminant), `=>!` is the honest spelling — a
  representation peek is precisely what `=>!` exists to state. Never chase the
  refused `=>`.
- **`int64` into `int32`**: prefer retyping the binding or expectation to
  `int64` (counts are int64-native); `=>!` only where the narrowing itself is
  what the case asserts.
- **TYPE-046 copies (`string`, `ModuleGraph`)**: three readings, pick per site —
  both copies used afterwards → the copy was load-bearing, make it an explicit
  clone; second use dead → `move`; callee only reads → borrow. A move-only
  refusal in a test is the compiler finding an accidental alias; identify which
  of the three it was before touching the spelling.
- The habit worry is answered by the discipline, not by avoiding the spellings:
  every site read, every spelling stating intent. An `=>!` that says "I mean
  the representation" in a test is the TOS system working as designed.

# D-223 implementation log (third session)

## Point 1 — `NITPICK-BORROW-011`, the wild-store rule

Landed as a **whitelist on the value's provenance**, not a blacklist on
borrows, which is what makes it fail closed: at a store into a `wild`-qualified
slot the value must be provably wild — an `=>! wild …->`/`=>! wildx …->` cast,
a read of another `QUAL_WILD` place, `NULL`, or a builtin whose signature hands
back wild storage. Everything else refuses, including a plain pointer parameter
and any call this walk cannot see through.

`builtin_returns_wild` reads the answer off **the generated signature table**
(`builtin_sig_ret` carries the qualifier in its text — `"wild int8->"`), not off
a name list of its own. A name list would have been the fourth copy of a fact
D-201 spent a subcycle reducing to one, and it would have gone stale the first
time a builtin was added.

Three store sites, as D-223 names them:

- the **declaration** (`wild T->:p = …`), whose qualifier is on the statement;
- the **assignment** (`b.p = …`), checked BEFORE the existing borrow-store
  rules, because the laundering shape is precisely one where the value is *not*
  a borrow the analysis has marked — `int32->:t = @(op.k);` is param-rooted, so
  0.8.1's exemption leaves `t` unmarked, and only the destination's qualifier
  can decide;
- the **struct-literal field value** (`Box{ p: … }`), whose field decl is
  readable at the literal.

Two spellings that are NOT builtins had to pass provenance through rather than
refuse: `move(p)` and `raw p` (`ExprRawUnwrapExpr`), which hand back their
operand unchanged. `$$i` and a parenthesised expression need no arm — the
parser produces no node for parentheses.

**The `src/` audit D-223 predicted found something, and the first reading of it
was mine being too quick.** `quickcheck` builds `tools/check.npk`, which pulls
in the FRONTEND only — so "the compiler compiles itself unchanged" was a claim
about a subset. Checking a test that imports the BACKEND surfaced two
`BORROW-011`s in `src/backend/ir/ir_types.npk`:

```nitpick
pub func:llctx_set_impls = NIL(LlCtx->:c, wild ImplTable->:t,
                               wild TypeResolver->:r) never fails {
    c.impls = t;
    c.tr = r;
```

Not a hazard — a gap in the rule. `place_is_wild` read the declaring STATEMENT
to find a `QUAL_WILD`, which finds locals and misses PARAMETERS, and wild
provenance arrives through a parameter as readily as through a local. Fixed by
reading `param_quals` for a `SYM_DECL` root.

The lesson is the one the harness exists to enforce: **`quickcheck` answers for
the frontend, and a rule that touches the whole tree is only audited by the full
run.** The claim to make after a quickcheck build is "the frontend compiles",
never "`src/` compiles".

Two facts worth recording for whoever extends this:

- **Bare builtins are `ExprCallExpr`**, not `ExprBuiltinExpr`. The latter is
  only the sigil form `#name<T>(…)`. A wild-provenance check that looked only at
  `ExprBuiltinExpr` would have refused every `wild int8->:p = alloc(…)` in the
  tree — which is how this arm got written correctly the first time, by asking
  the parser rather than assuming.
- **`Escape` has no `interns`**, but `x.tr.interns` does — the resolver it
  already carries for the F-1 destination walk.


## Points 2 and 3 — `can_connect`, and the five cases

`can_connect(dest_pointee, src)` replaces `dest_can_hold`, the `borrowed >= 2`
arm and `escape_connect`'s blanket `carries_pointer` filter, exactly as D-223
specifies. Two halves, and each closes one of the holes:

- **`type_reachable_in(t, src)`** — is `t` the source type or a type reachable
  at an interior place of it? This is what `dest_can_hold`'s exact match was
  missing. A callee handed `@pt` does not have to store `@pt`; it can store
  `@(q.a)`, whose type is `int32->`, into a slot that holds `int32->` perfectly
  well.
- **the `wild` exclusion on struct fields** — a wild slot is not a destination,
  because BORROW-011 refuses the store into one outright. This is the half that
  makes the engine tables stop being destinations.

The one-borrow exemption became "exempt iff not self-connectable": the
`escape_yields` early-out in `arg_can_hold_one` is gone, so an argument is
asked whether it can connect to ITSELF.

**All five cases behave as ratified, verified against the built checker:**

| case | verdict |
|---|---|
| `analysis/rejection/wild_store.npk` | three `BORROW-011`s — assignment, declaration, struct-literal field — plus the rule-2 refusal on returning the literal |
| `analysis/rejection/borrow_self_connect.npk` | `BORROW-001`; **accepted before D-223** |
| `analysis/rejection/borrow_derived_dest.npk` | `BORROW-002`; **accepted before D-223** |
| `analysis/rejection/borrow_pair_plain.npk` | `BORROW-001` — the counterweight |
| `accept/borrow_pair_wild.npk` | clean, including the compiler's own `wire(@ea, @eb)` … `pass Run{ a: ea, b: eb }` idiom |

The counterweight is the one worth keeping in view: it is the accept case with
`wild` deleted from one field, and it refuses. The repair is not a relaxation —
the qualifier decides, which is what D-223 set out to make true.

`wild_store.npk` draws a rule-2 diagnostic beside its three BORROW-011s,
because `literal_form` both builds the struct and returns it. That is correct
and worth stating: building it is one mistake, returning it is another, and
D-223's rule fires FIRST — at the store, where the mistake actually is.


## The four BORROW-001 files: two passed unmodified, two were real findings

D-223 predicted all four would compile as written. Two did — `resolve.npk` and
`expansion_output.npk`, exactly on the reasoning the decision gives (every
engine table's pointer slots are wild, so nothing in those calls is a
destination). The other two refused for reasons that had nothing to do with
rule B, and both were worth finding:

**`module_graph.npk` was a genuine dangling pointer.** Its helper held
`RootList:roots` as a LOCAL, put `@roots` into a `ModuleGraph` — whose `roots`
field is a PLAIN, non-wild pointer, so it is a destination under any reading —
and returned the graph. Every graph it handed back carried an address into a
frame that had already died. `src/driver/pipeline.npk` shows the shape that is
correct and has been all along: `RootList:roots` is a FIELD, and
`f.g = graph_init(@f.it, @f.diags, @f.roots, "")` is the self-wiring 0.8.1
permits — a pointer into X, held inside X, dying with X. The test now lets the
CALLER own the list, so the borrow is parameter-rooted and outlives by
construction. The Python seed compiled that bug for fifteen cycles.

**`resolve_types.npk` hit rule A, not rule B.** `diaglist_at` takes a borrow and
returns a `Diagnostic`, which carries a string; rule A marks the CALL's result
borrow-derived, so returning `.code` out of it refuses. Rule A has no
parameter-rooted exemption the way rules 2 and 3 do — a separate question from
D-223, and not one to answer while migrating tests. The site is fixed the way
this codebase already spells it: read the `Diagnostic` into a local, then
`string_concat(d.code, "")` to hand back storage the function owns, which is
what its `string` return type already claimed.

## The `src/` audit found one, and it was the rule's gap rather than a hazard

Recorded above: `wild`-qualified PARAMETERS were not recognised as wild places.
`llctx_set_impls(LlCtx->:c, wild ImplTable->:t, wild TypeResolver->:r)` storing
`t` into a wild field is wild-to-wild and entirely correct; `place_is_wild` was
reading the declaring STATEMENT, which finds locals and misses parameters.

## Q3 in practice: blocks, and what surfaced behind them

`ast_storage.npk` is the pattern for the six RESOLVE-001 files. Its second
`ExprId:lit` section became a `{ }` block with the section comment kept above it
(rider 3), and nothing in the section owns anything, so rider 2's scope-exit
question is moot — re-verified by exit code rather than by inspection.

Two Q2 sites surfaced behind it once the redeclaration stopped masking them,
and both are the `=>!` case the decision rule describes rather than the
avoid-it case:

- `expr_shape(k => ExprKind)` inside a loop enumerating every kind NUMBER. The
  checked cast is refused correctly — nothing proves `k` names a variant — and
  that is precisely what the loop exists to assert. `=>!` states "I mean the
  representation", which is the TOS system working as designed.
- `drop ast_add_expr(…)` discarding a value became `discard(raw …)`: two words,
  two claims, both checked.

And a third: the file's `failsafe` was `int32(Error:_~err) { exit 1i32; }` — no
`pick` at all, which D-179 refuses because `(*)` may stand beneath the names but
never in for them. The arms came from the compiler, not from a guess.


## The BORROW-002 trio was a BUFFER OVERFLOWING, not the analysis working

D-223 predicts that context structs keep plain slots, remain destinations, and
so keep refusing the capture-shaped sites — "read per site, not annotated past".
Reading them is what found this, and the reading came out the other way.

`type_access.npk`, `type_stmt.npk` and `type_generic.npk` all refused at the
SAME argument: `it`, in

```nitpick
ExprTyper:e = raw etyper_init(@ast, @types, @tab, it, @diags, scope,
                              @im, @bd, @inst, @fninsts, @ets);
```

`it` is an `InternTable->`, and `InternTable`'s only pointer slot is
`wild string->:items` — since BORROW-011 it can hold no borrow at all, so
`can_connect` answers no. It was never being asked.

`lb_tys`, the list of local-borrow pointee types the destination test compares
against, was a **fixed eight entries**: `local_borrows < 8` guarding the fill,
and a fail-closed `if (i >= 8) { pass true; }` on the read. That call passes
NINE local-rooted borrows. So every pointer argument became a destination by
OVERFLOW, and the answer had nothing to do with the types involved.

The buffer is now sized to the call — one receiver plus `count` arguments, a
number known at the site — and the fail-closed branch is gone with it. That is
not a relaxed safety posture. Fuel exhaustion on a recursive walk has to fail
closed, because the walk genuinely cannot know what it did not visit; this was
a fixed array for a list whose exact length was in hand. Failing closed on a
number you could have computed is a defect that happens to refuse.

**Why it stayed invisible for six cycles**: the seed ran no analyses, so the
only code exercising a nine-borrow call was the compiler's own test suite —
which the seed compiled. The switch is what made the analysis meet it.

And it is the strongest argument for D-223's "read per site" instruction:
reaching for an opt-out at those three sites would have papered over a live
defect and left it to refuse the next nine-argument call in silence.

## Rule A has no parameter-rooted exemption — recorded, not acted on

Six accessors of the shape

```nitpick
func:code0 = string(Ax->:x) never fails { pass ((raw diaglist_at(@x.diags, 0i64)).code); };
```

refuse under rule A: the call takes a borrow and returns a `Diagnostic`, which
carries a string, so the RESULT is borrow-derived — and rule A counts every
borrow argument, including parameter-rooted ones that rules 2 and 3 exempt by
0.8.1's reasoning. All six now read the `Diagnostic` into a local and return
`string_concat(d.code, "")`, which is this codebase's own explicit-copy idiom
and is honest about what leaves the function.

Whether rule A should gain the parameter-rooted exemption is the same shape of
question D-223 just answered for rule B, and it is OUTSIDE the ratified scope.
Written here rather than improvised: it is a decision, and it belongs to a
decision.


## Q2's TYPE-046 sites were all one shape, and `move` alone was the wrong answer

Five sites, all the same: a helper takes `string:name`, and hands it to
`intern_add`, whose second parameter is `move string:text` — the intern table
takes ownership of the bytes. Q2's three readings pick "second use dead →
`move`", and writing `move(name)` produced **`NITPICK-TYPE-047`: this parameter
was lent, not given (D-065: passing transfers nothing)**.

That refusal is the useful half. A lent parameter is not the callee's to give
away: the caller still owns it, and `move`ing it out would leave the caller's
binding pointing at bytes the intern table now owns. So the choice is not
"`move` or not" but "who owns this string" — and the honest answer for a helper
whose entire job is to hand the name to the interner is that the helper
CONSUMES it. The signatures say so now:

```nitpick
func:named = int32(Lx->:x, InternTable->:it, move string:name) never fails {
```

Every call site passes a literal, which is a temporary with no second name to
invalidate, so nothing else changed. The move analysis is what walked this from
the wrong fix to the right one in two steps — which is Q2's "identify which of
the three it was BEFORE touching the spelling", enforced rather than merely
advised.

## Rule A: three independent manifestations, none of them blocking

Recorded together because the pattern is now evidence rather than a hunch. Rule
A marks a CALL's result borrow-derived when any argument was a borrow
EXPRESSION and the result type can carry a pointer. It has neither of the two
precisions D-223 gave rule B: no parameter-rooted exemption (0.8.1's reasoning,
which rules 2 and 3 both apply), and the blanket `carries_pointer` rather than
a derivation-aware predicate.

1. **Six `code0` accessors** — `diaglist_at(@x.diags, 0i64)` returns a
   `Diagnostic` carrying a string. Fixed by reading into a local and returning
   `string_concat(d.code, "")`, this codebase's explicit-copy idiom.
2. **Two `exprtypes_for(@ast)` sites** — the wrapper only reads a count off the
   ast, so `exprtypes_init(raw ast_expr_count(@ast))` builds the same value
   without a borrow-derived result.
3. **One `irw_text(@w)` site** — and here rule A is right to be suspicious. It
   is a worst-case-callee model, and a function handed `@w` genuinely COULD
   return a view of it: `string_from_bytes` is that primitive, `irw_text` uses
   it internally, and D-186 exists because escaping views are a real hazard.
   The fix is the compiler's own idiom — the caller owns the writer, the helper
   takes `IrWriter->:w`, and the read has no `@`, which is precisely why `src/`
   threads writers as pointers and never trips this.

Every one had an honest test-side spelling, so nothing is blocked. Whether rule
A should gain D-223's two precisions is a decision, and it belongs to one.


## The switch's biggest find: `src/`'s OWN arithmetic was never overflow-checked

The last two failures were not refusals but **traps inside the compiler**, on
the two programs that use `extern` blocks. `gdb -ex "break npk_trap" -ex bt`
named the site in one step, after two wrong guesses of mine had cost far
longer — the 0.6 lesson ROADMAP records, applied: reach for the debugger before
building instrumentation.

```
#1  npk.bridge_stubs.bs_fnv_step ()
#2  npk.bridge_stubs.bs_fnv_str ()
#3  npk.bridge_stubs.bridge_in_module ()
```

`bs_fnv_step` was `pass ((h ^ v) * 1099511628211u64);` — FNV's multiply, which
IS the wraparound, on a plain `uint64`. Under D-210 that traps. It overflowed on
the first byte it ever hashed.

**Why it had never fired.** D-210 is a rule the REAL COMPILER enforces, and
`src/` was compiled by the PYTHON SEED, which emits no overflow checks. So
every deliberate-wrap site inside the compiler went unchecked for as long as
the seed was the builder. 1.4.2b's D-210 sweep read the sources and fixed
`intern.npk`'s FNV; it missed this second one, and nothing was enforcing the
rule on `src/` to catch the miss.

The switch put the snapshot in the seed's place, D-210's checks appeared in
`src/` for the first time, and the compiler trapped on its own input.

**The fix was already written down.** `intern.npk` carries a hand-decomposed
FNV keeping every partial product inside `uint64`, with a comment: "AT 1.4.7
this becomes the `uint128` spelling the prelude already uses." That
decomposition exists BECAUSE `src/` was bounded by what the seed could compile.
Since the switch it is bounded by the snapshot, which has `uint128` — so the
destination spelling is available now, and `bs_fnv_step` uses it: widen,
multiply where it cannot overflow, narrow with `=>!` to state the truncation.

**This is D-205's rule paying for itself on day one.** "`src/` may not use any
construct its current builder cannot compile" cuts both ways: it also means
`src/` is only held to the rules its builder ENFORCES. Swapping the builder for
a real compiler is what made the compiler's own source subject to the
compiler's own safety rules — and the first run found a live overflow.

**Owed, and named**: `intern.npk`'s decomposition can now become the one-line
`uint128` spelling too. It is correct as it stands (verified against the
wrapping form over boundary pairs and 200,000 random ones, per its comment), so
this is simplification rather than repair — 1.4.7 material, where its own
comment already schedules it.
