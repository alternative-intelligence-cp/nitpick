## The rule

A binding moved anywhere in a loop body is MOVED-FROM at the body's head
unless it is reassigned on EVERY path that reaches the back edge. The
`modmap_members` shape (one `move(x)` re-executed per iteration = N
moves of one value = N drops of one body) refuses with its own code.

### The plan's diagnosis did not survive contact

D-208 and this file both say the moved-from analysis is *straight-line*: that a
`move(x)` re-executed by a loop is not refused, and that the fix is to add
loop-header merge states. **It is refused, and has been since 0.5.3.**
`assign_loop_body` walks a body twice and `state_absorb_may` unions `moved` and
`freed` between the passes, which is exactly D-208's rule. Measured before
changing anything, at every loop form:

| shape | already |
|---|---|
| `move` in a `while` body, never reassigned | refused |
| reassigned before the back edge | accepted |
| declared inside the loop | accepted |
| reassigned on one `if` arm only | refused |
| nested loop, reassignment in the outer only | refused |
| `till` | refused |
| counted `for` | refused |

### What the hole actually was: parameters were not tracked AT ALL

`binding_slot` answered −1 for any symbol that was not a STATEMENT, every rule
here quietly does nothing on −1, and the state vector was sized by statement
count so there was no room for a parameter anyway. A `move` parameter moved
twice, a pointer parameter freed twice, and a read after either were all
**accepted, with no loop involved**.

The source stated the reasoning, and it is half right:

> "Parameters are assigned by the caller and are never `SYM_STMT`, so they are
> not in this table at all — which is the right answer rather than a convenient
> one: a parameter is assigned before the body starts, always."

True of DEFINITE ASSIGNMENT. The comment concluded it for all four vectors the
state carries, and `moved`/`freed`/`sealed` went with it.

This also explains the audit's own evidence better than the audit did:
`modmap_members` moved `canon`, a **`move` parameter**, once per member. It
type-checked because the parameter was invisible, not because the analysis was
straight-line. The loop was incidental.

### The work

1. The slot space is STATEMENTS THEN DECLARATIONS; a parameter's slot is
   `stmt_count + decl index`. Parameters are marked assigned at function entry —
   the half the old comment had right.
2. **One `symbol_slot` resolver.** Four sites resolved this inline as
   "not `SYM_STMT` → give up", and each independently excluded parameters from a
   rule that should always have covered them. One resolver now, so a fifth rule
   cannot make the mistake a fifth time.
3. The READ check reports moved/freed for any tracked binding and keeps
   "not assigned" for locals alone.

### Found in the compiler — 26 diagnostics, and one is a live double free

- **`emit_pick_chain` (`ir_stmt.npk`)**: `disc_ll`, a `move` parameter, handed
  to two `IrVal`s on consecutive lines. `iv` takes `move string:ll` and the
  `IrVal` OWNS it, so one string body had two owners and two drops. The same
  class as `modmap_members`, live since the pick chain was written. The range arm
  is the only one that builds two operands from the discriminant's type, which is
  why it survived. Cloned.
- **`fnem_iter_slot` (`ir_func.npk`)**: `move` out of a container ELEMENT, which
  does not empty the element (there is no drop flag on one) — the caller and the
  container held one body between them. A documented D-183 open ("no correct
  spelling yet"); the correct spelling available today is the one that
  allocates, and this is called once per `$` in a counted loop.
- **`iv_from_place` / `pv_from_iv` (`ir_expr.npk`)**: two fields of one root
  both moved, which the codebase already knows is refused ("two fields of one
  root cannot both move", `emit_raw`) and which was invisible here because the
  root is a parameter. Semantically sound — the bodies are distinct — so this is
  the documented over-refusal and takes its documented workaround.

### The judgment call: `invalidate_place` stops at a pointer

Tracking parameters made an existing over-approximation bite everywhere at once.
A free or move through a FIELD invalidated the ROOT binding, so
`out.buf = ralloc(out.buf, n)` with `out` a `Sink->` marked `out` freed — and
because an assignment through a field marks nothing, **nothing could clear it**.
Four places in the compiler stopped building, all of them correct code.

`invalidate_place` now stops when the path to the root crosses a POINTER, on the
grounds the drop machinery already runs on: a binding holding a pointer does not
own the pointee, and drops walk past one (D-183; `DiagList`'s own header says
so). Where the binding genuinely owns the aggregate the coarse rule is
unchanged, and `moves.npk` pins that.

What it gives up, stated plainly: `p.buf` freed and then read through the same
pointer is no longer refused. An alias could free the pointee anywhere and a
binding-granular walk would not have seen that either — so saying nothing
through a pointer is the honest answer, and 1.5's verifier is what reasons about
pointees. **User-approved** rather than assumed, since it narrows an existing
check.

The evidence that this belonged with the parameter change rather than after it:
most parameters that reach a field are pointers, so the coarse rule was
tolerable only while the bindings it was coarse about were invisible.
