## The four measurements, and why the last one is the diagnosis

| build | result |
|---|---|
| the patch's parent commit (`c79175a`, family 9 only) | FULL HARNESS GREEN, fixpoint byte-identical |
| family 10 alone (patch applied to `67ed06f`) | self-compiles cleanly, 15,291,741 bytes |
| both (the patch on HEAD) | traps as above |
| both, with `@npk_quarantine = internal global i64 1` in `runtime/npkrt.ll` (then `rm -rf .internal/quickemit` and rebuild) | **self-compiles cleanly** |

Quarantine poisons a freed block and never returns it to the bitmap, so a stale
pointer still passes `npk_small_check`'s watermark. The failure disappearing
under it means the pointer refers to a block that was **freed and reused** — a
use-after-free — not garbage and not an uninitialised table.

`npk_ralloc` frees the old block when it grows one, so **any second copy of a
list that has since grown is stale from that instant.** That is almost
certainly the shape; I could not find which copy.

## Ruled out by measurement, not argument — please don't re-derive these

- **Not a bad conversion.** The converted `inst_record` (`src/frontend/types.npk:1458`)
  is a faithful translation; both versions are quoted in 1.4.7.md.
- **Not mis-monomorphisation.** In the trapping build's IR
  (`.internal/quickemit/npkc.ll`), every `list_{init,reserve,push}` instantiation
  is distinct and each computes its own element size
  (`getelementptr %"npk.types.Instance"` vs `%"npk.type_trait.ImplEntry"`).
- **Not a dangling resolver.** `tr` and `f` are both live in the same frame at
  `src/driver/pipeline.npk:368`; `TypeResolver.instances` is a pointer field
  (`src/frontend/resolve_type.npk:116`); nothing copies `Front` by value
  (`$$m f` is a mutable borrow).
- **Not `ralloc` mis-dispatch.** It routes on the existing pointer via
  `npk_lg_find`, not on the requested size (`runtime/npkrt.ll`, `@npk_ralloc`).

## Why it is pre-existing rather than caused by the patch

Hazard shape, starting capacity (16) and doubling are identical before and
after, so growth timing is unchanged. What changed is LAYOUT: each converted
table went from `{ptr, i32, i32}` (16 bytes) to `{List}` = `{ptr, i64, i64}`
(24), which changes allocation sizes and therefore which block is reused when.
**Families 1-9 being green is not evidence the defect is absent from them** —
only that their layouts do not happen to trigger it. Assume the defect is in
`main` today.

## The hypothesis I would test first, and could not finish

An **interior pointer into a growable array, invalidated by growth**. Note what
the backtrace says: the ESCAPE ANALYSIS is calling `struct_field`, which
RESOLVES types, which INTERNS new ones and records instances — i.e. an analysis
pass mutates the type tables while walking. If any caller up that chain holds a
`Type->` or `Instance->` (or a `List` value copied out of one) across a call
that grows the same table, it is stale the moment `ralloc` moves the block.

Two things worth deciding on as well:
1. Is an analysis pass interning new types at all correct? `escape.can_connect`
   (`src/frontend/analysis/escape.npk:1552`) reaching `resolve_type` looks
   architecturally wrong to me independent of this bug.
2. `src/frontend/analysis/escape.npk:605` — `pass (x.holds[sy.origin => int64]);`
   indexes UNGUARDED, while its siblings at 144 and 179 both test
   `>= x.holds_count` first. `sy.origin` is a symbol's origin, not bounded by
   the statement count the array is sized to. Out-of-bounds READ, so not this
   corruption, but real, and in the same neighbourhood.

## What I want back

1. **The stale pointer**: which value is copied/held, where it is invalidated,

2. **The fix**, with a view on whether it should be a local repair or a rule
