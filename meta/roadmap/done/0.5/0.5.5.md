# 0.5.5 — `unknown` taint

**Cycle 0.5 — Static analyses.**

## Goal

`Result.value` after `fail()` is tainted, and reading it is refused.

## The rule, narrowed on purpose

`unknown` is **compiler-assigned and not user-writable** (`TYPE_REFERENCE` §27,
D-007). The prototype allowed `int32:val = unknown;` and used it as a general
degradation mechanism; that is struck. What survives is one thing: **the `value`
field of a `Result` that carries an error is tainted**, and the taint is cleared
by `ok()` or by checking `is_error`.

It is deliberately *not* the general degradation path. Division by zero on a plain
`int32` **traps**; on a `tbb` it yields sticky ERR and execution continues
(D-007). Three mechanisms live at Layer 2 and which one applies is determined by
**type, never by context** — so this analysis must not become a fourth.

## Work

1. Taint on `Result.value` where the `Result` came from `fail`.
2. Cleared by `ok()`, and by a check of `is_error` that dominates the read.
3. Reading a tainted value is refused, naming the check that would clear it.
4. `raw` and `?!` are the explicit ways through, and they clear it — the whole
   point of an escape hatch is that it is greppable, and both already are.

## Watch for

**`.is_error` is derived, not stored** (D-069) — `r.is_error` is `error != 0`, and
there is no field to read. So "checking `is_error`" means the comparison, and the
analysis has to recognise it in the forms a programmer writes it in rather than
one blessed spelling.

**A `pick` on the `Result` clears it too**, on the arm that matched success. That
is the idiomatic form and an analysis that only recognised an `if` would push
people toward the less idiomatic one.

## Done when

- Reading `.value` of a failed `Result` is refused.
- The same read after an `is_error` check is accepted.
- `ok()` clears it, and `unknown` remains unwritable by a programmer.

---

## What this found

**`ok()` does not clear the taint, because `ok` does not exist.** This plan's work
item 2 and its Done-when both name it; that was true when the plan was written and
stopped being true at **D-097**, which removed `ok` from the language — it asked
whether an ordinary value was `unknown`, and D-007 had already removed
user-writable `unknown`, so it was an operator whose subject was gone.

Checking `is_error` is the only route, and it was always the one that composed with
the `Result` discipline. Caught by reading `TYPE_REFERENCE` §27 before building
against the plan, which carries the correction inline.

**The plan's own warning was the design.** "The analysis has to recognise it in the
forms a programmer writes it in rather than one blessed spelling" — so the condition
**refines the two arms** rather than being counted as a mention. A syntactic
"was `is_error` tested" check would accept `if (r.is_error) { pass (r.value); }`,
which is the tainted branch with the test sitting right above it.

**`checked` settled the shape of the merge table.** Two of the five sets intersect
and three union, and the reason is now stateable rather than memorised: `must` and
`checked` **permit** something, so they must hold on every path; `may`, `moved` and
`freed` **forbid** something, so they fire on any path.

## What is deliberately narrow

**Only a binding-rooted read is checked.** `f().value` reads a temporary, and
nothing could have checked *that* temporary — the check would call `f` again and
get a different `Result`. The idiom is to bind it, and the binding is what this
tracks.

**Propagation needs no rule.** `TYPE_REFERENCE` §27 says the taint "propagates
through operations: `unknown + 1` → result is also `unknown`". Refusing the read at
its source makes that moot: a value that reached a variable was read from a checked
`Result`, so there is no tainted value in flight to propagate.

## Done when — all three met

- Reading `.value` of an unchecked `Result` is refused. ✓
- The same read after an `is_error` check is accepted, in every form a programmer
  writes it — early exit, both arms, the negation, and a `pick`. ✓
- `unknown` remains unwritable by a programmer. ✓ *(it is not a keyword, so the
  lexer has never admitted it — verified rather than assumed)*

Verified by making it fail, four times: `checked` unioning at a merge (5 findings,
not 6), an assignment no longer clearing it (5, not 6), the branch polarity ignored
(5, not 6), and no check recognised at all — which refuses **all six** clearing
forms in the acceptance suite, and is what shows the recognition is load-bearing
rather than decorative.
