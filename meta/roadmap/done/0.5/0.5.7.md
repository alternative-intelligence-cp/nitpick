# 0.5.7 — Diagnostics, suites, and closing

**Cycle 0.5 — Static analyses.**

## Goal

Every analysis has a code, a span, and a test. The frontend is complete through
Layer 1's structural half.

## Work

1. Codes centralised, as in 0.1.6, 0.2.1, 0.3.6 and 0.4.8.
2. `tests/analysis/rejection/` — whole programs that **type-check** and are
   refused by an analysis. Sited beside the other three for the reason the type
   suite gives: a file that stops at an earlier stage would satisfy a test written
   about a later one.
3. The negative-coverage checklist, worked through the way 0.4.8's was — every
   rule in D-004, D-007, D-008, D-056 and D-065 listed against the case that shows
   it refusing something.
4. Close the cycle — `done/0.5/`, ROADMAP, push.

## The check worth building here

0.2 and 0.3 got mechanical completeness checks; 0.4 could not have one and used
negative coverage instead. **This cycle needs both, plus a third thing neither
had.**

An analysis can visit every node and still be wrong about a *path*. So the measure
here is **path shape coverage**: for each analysis, a case that exercises it across
a branch, a loop that may run zero times, a `pick` arm, an early `pass`, and a
`defer`. That is a checklist in this file, worked through, because no script can
tell whether a merge was handled correctly — only whether it was reached.

## Watch for

**An analysis that is silent is indistinguishable from one that passed.** Every
subcycle's tests must include a case that the analysis *refuses*, and — as
throughout 0.4 — the refusal verified by making the check fail. A test that has
never failed is a test whose failure mode is unknown.

## Done when

- Every analysis code has a test.
- Every rule in the five decisions has a case showing it refuse something.
- Every analysis has a case per path shape.
- The cycle is archived and pushed.

## What this found

**The suite split was load-bearing, not tidy.** `tests/analysis/rejection/` now
sits beside the loader, type and backend suites. The analyses run only over a
program the type checker accepted, so a case written for `NITPICK-BORROW-001` that
failed to type would never reach the rule it guards — which 0.5.3 had already hit,
moving four cases into `types/rejection/places.npk` because a `TYPE-024` in the
same file stopped the program before the move rules ran.

**Acceptance stayed one suite for four stages.** Splitting it the way the
rejections are split would be four directories asserting the same thing: a program
the whole frontend accepts is accepted by every part of it. Silence has no stage.

**Five codes cannot have a test, and the reasons differ.** Three are rules whose
construct does not exist — thread spawn, `await`, closure capture — written and
walked and unreachable on purpose. Two are compiler-defect codes reachable only by
breaking the compiler.

**The bound-exhaustion codes turned out testable, and were worth the trouble**,
because failing closed IS the safety property rather than an implementation detail:

- `too_deep.npk` — a 400-term expression that trips four analyses' depth guards at
  once.
- `unsettled.npk` — a 72-link borrow chain written in reverse, so a round
  propagates exactly one link and the 64-round bound is exceeded. It proves the
  fixpoint REFUSES rather than reporting what it had.

**`too_deep.npk` surfaced a cascade, documented rather than suppressed.** The escape
checker's conservative "this may be a borrow" propagates into a second finding on
the binding below. Silencing it would mean a program with one over-deep expression
quietly got fewer checks than one without — and "we could not classify this, so we
will assume it is fine" is the one thing a borrow checker may never do.

## Path-shape coverage — the third measure

0.2 and 0.3 got mechanical completeness; 0.4 used negative coverage. This cycle
needed both plus a third: **an analysis can visit every node and still be wrong
about a path.**

`path_shapes.npk` is the cross-product — five analyses against a branch, a
zero-iteration loop, a `pick` arm, an early exit and a `defer`. Every cell fires.
Three are deliberately empty, each a judgement recorded in
`tests/analysis/rejection/README.md`:

- **moves × early exit** — an exit removes an arm from the merge and `moved`
  unions, so an exit can only ever *reduce* what is considered moved. There is no
  case where an early `pass` makes a use-after-move appear.
- **taint × `defer`** and **locks × `defer`** — a deferred body is walked with the
  state at its registration, so both see it as they see any other block. `escape`
  and `moves` have `defer` cases because for them the deferred body runs at a point
  that matters.

The file also carries one POSITIVE case, deliberately: an early `pass` before a
lower acquisition is correct code, and an analysis treating an exit as ordinary
flow would refuse it. It sits beside the shapes it is contrasted with rather than
in `tests/accept/`.
