# 0.3.0 — Reading a file

**Cycle 0.3 — Modules, symbols, visibility.**

## Goal

The frontend can name a file and read it. Two language-level questions get
settled first, because everything after them depends on the answers.

## Decision 1 — how a program receives its command-line arguments

**SETTLED as D-089, and not the way this plan proposed it.**

The proposal here was that `main` keep its zero-parameter signature and that
arguments come from an `args()` runtime function. That was written from the spec
set, which shows `func:main = int32()` everywhere — and the spec set had **lost**
the parameter form. The prototype has it, and the user remembered it:

```nitpick
pub func:main = int32(int32:argc, wild int8->:argv)     // nitpick/tests/regression/
```

The settled form is `func:main = int32(cstring[]:argv)` — one parameter, always,
with no `argc` because a slice carries its length. `_start` captures the stack
pointer before aligning it and hands the slice to `main`.

**The lesson is worth more than the decision.** A recommendation had already been
written on the strength of a document that had dropped the feature. Absence from
`meta/specs/` is not evidence of absence: the set was assembled from a separate
experiment and partly from a verbal retelling, and it has lost real things
silently. Check the prototype.

D-089 also restored the **declaration-site discard**, `Type:_~name`, which the
spec set had reduced to the body-level `discard(e)` form — dropping the one the
operator was invented for.

## Decision 2 — the file-reading primitive

**Settled: `read_file(path) → Result<string>`**, one call in the runtime floor,
rather than `open` / `read` / `close`.

**Its parameter is a `cstring`, not a `string`, and that is the whole of D-049.**
A `string` may contain `0u8` anywhere in its interior — it is length-carrying, so
an embedded NUL is just a byte. A `read_file` that took a `string` and
NUL-terminated it internally would silently truncate at the first one, and the
caller would have no indication: the path that was checked and the path that was
opened would be **different paths**. That is the poison-NUL vulnerability class,
and it is exactly what `cstring` exists to make impossible.

So the conversion is explicit and fallible — `to_cstring(string) → Result<cstring>`
— and the caller handles the failure like any other.

`SUBSET_1.md`'s governing principle decides it: *push complexity into the
compiler, away from the seed.* The seed is the least-audited artifact in the
chain. Three primitives with an fd protocol between them is more unaudited code
than one call that returns bytes, and the compiler gains nothing from the
finer grain — it reads whole source files and never seeks.

`IO_REFERENCE.md`'s `Stream` trait (D-075) is the real model and arrives with
`nlibc` in 0.8. This is the floor, not the design.

## Watch for

**`_start` is the one place where getting it wrong is silent.** The comment there
already records why the manual alignment exists: at `_start` the stack is not
laid out the way it is at a normal call, so a compiler-generated prologue can
leave `%rsp` misaligned and a later SSE spill faults. Capturing `argc`/`argv`
means reading through the pointer *before* the `andq`, and a mistake produces a
program that runs fine until someone passes an argument.

  a distinguishable code — not a trap, and not an empty string.
- `parse_check <path>` replaces `parse_check < path`, and the harness still
  passes.
