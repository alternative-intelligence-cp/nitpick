# 1.3.6 — `complex<T>`: the complex numbers (D-199)

`T` ∈ {`flt32`, `flt64`, `tfp32`, `tfp64`}; layout `{T, T}`; constructor
`complex(re, im)` type-directed like `simd(…)`; operators `+ - * /` with
float division by SMITH'S algorithm (the naive formula overflows at
|denominator| ≈ √max — a silent-wrong-answer class) and tfp elements on
the direct formulas under the ERR discipline (any component ERR → BOTH
components ERR). Methods `.re() .im() .conj() .abs2()` everywhere,
`.abs()` on float elements only. `ToString` "3+4i" via the element's
rendering.

## Design points, fixed at open (inside D-199's ratified frame)

1. **`TY_COMPLEX` (=45), a = the element type id**, interned by element;
   LL `{ float, float }` / `{ double, double }` / `{ i32, i32 }` /
   `{ i64, i64 }`. The four element types are the ratified list, refused
   otherwise at resolution.
2. **The constructor reuses `ExprVectorCtorExpr`** — the node already
   records WHICH keyword built it (the payload carries the token kind),
   so `complex(re, im)` is the same parse arm extended and two consumer
   branches, not a new AST kind. Exactly two arguments, each typed at
   the element.
3. **The arithmetic lives in the PRELUDE, in Nitpick, per element type**
   (the 1.3.5 architecture, and here it pays twice): the tfp bodies use
   the LANGUAGE'S OWN tfp operators, so Q scaling, saturation and
   stickiness arrive for free, with the "any → both" canonicalization an
   explicit `is_err` line a verifier reads; the float bodies write
   Smith's division as ordinary branches over IEEE-total ops — flt32
   computes IN flt32 (widening through double would double-round).
   Sixteen small functions (4 element types × add/sub/mul/div) plus
   `abs2`; the emitter unpacks `{T, T}`, calls the deterministic prelude
   symbol, repacks. `conj` is an inline negate of `im`; `.abs()` is
   `llvm.sqrt` over the `abs2` call, float-only (a fixed-point square
   root has no consumer — the shuffle refusal's own rule).
4. **No order, equality only.** The complex numbers have no total order
   — mathematics, not policy — so `< <= > >=` refuse by name
   (TYPE-053, the family's code); `==`/`!=` are per-component (IEEE
   semantics on floats — NaN components make `==` false and `!=` true;
   tfp components trap on ERR first, D-008 §5). The emitter's equality
   arm precedes D-169's non-scalar belt — the 1.3.5 lesson applied at
   the second member of the category.
5. **`is_err` follows the element family**: on tfp elements it is the
   component disjunction; on float elements it refuses (a float carries
   NaN, not ERR — TYPE-053). The ERR literal-by-context likewise: a
   `complex<tfp32>` slot takes `ERR` as the both-components triple…
   pair; a float-element slot refuses. No `pick` selectors (the frac
   posture, same reasoning).
6. **No casts at all** — D-199 ratifies construction, operators, and
   methods; every `complex` cast pair is CAST_IMPOSSIBLE with a message
   saying values are built with `complex(re, im)` and read with
   `.re()`/`.im()`. Element conversions happen at the components.
7. **No literals** (construction is the constructor) and no members —
   `.re()`/`.im()` are METHODS per D-199's list, not fields; the value
   model is not component-writable.
8. **`ToString`** is four PRELUDE instance impls
   (`impl:complex<flt64>:ToString` — concrete-instance impls are landed,
   tested machinery): sign-aware "3+4i" / "3-4i" via the element's own
   rendering; a tfp-element ERR pair renders "ERR".

## The work

1. Generator/types: `complex` moves from is-generic-only to
   `TY_COMPLEX` in GENERIC; `tt_complex`, element gate at resolve,
   predicates, display `complex<T>`.
2. Prelude: the four per-element cores + `abs2` + four ToString impls.
3. Checker: the ctor arm (arity 2, element-typed args), the operator
   arm (same-type, `%`/order refusals — TYPE-053), equality admission,
   `is_err`/ERR by element family, pick refusal, the cast refusals,
   method typing (`re/im/conj/abs2` everywhere; `abs` float-only).
4. Emitter: ctor (insertvalue pair), the arith arm (unpack → prelude
   call → repack; tfp taint handled INSIDE the prelude bodies — the
   emitter adds nothing), equality before the belt, `is_err`, ERR
   constant, methods (extract; fneg/0− for conj; sqrt intrinsic for
   abs), `ll_type`.
5. Tests: `complex_basic.npk` (both element families: construction,
   the four operators against hand answers — including a Smith case the
   naive formula would overflow — conj/abs2/abs, equality with NaN and
   with ERR-trap, stickiness on tfp elements, ToString), a cmp-trap
   program for tfp elements, rejection rows (ordering, float `is_err`,
   `.abs()` on tfp, bad element type, arity, casts, pick, mixing).
6. Docs: D-199 implementation record, TYPE_REFERENCE §21 sync,
   CLAUDE.md status.

## Close-out

Everything above landed as designed; the implementation record is on
D-199 in DECISIONS.md. Tests: `complex_basic.npk` (both element
families — the (3+4i)(2−1i) round trip, add/sub/conj/abs2/abs, a Smith
case whose naive denominator overflows to inf, NaN equality semantics,
exact tfp Q arithmetic, division by the zero complex → ERR, stickiness,
the any → both canonicalization, `ERR` by context, ToString on the
deterministic tfp rendering), `complex_cmp_err.npk` (the −4100 on
tainted equality), eleven refusal rows in `complex_rules.npk`. The
ordering refusal rides the shared not-ordered code with the mathematics
in the message ("compare `.abs2()` if magnitude is what is meant").

No new found-defect class this time — the 1.3.5 lessons were applied at
design (the equality arm was written ABOVE the belt from the start, the
reserved-word table was consulted before naming locals), and the only
build iterations were `cat5` arities, caught by npkc's own checker
before any full run.
