# 1.3.0 — Cycle open: the decision batch (G-4…G-10)

The survey's findings are in the README. This file is the batch itself: seven
proposals, each with a recommendation. Two carry questions that are the
user's to answer (marked **USER**): the ternary logic spelling (the ternary
family is the user's own design) and user-declared units (a grammar
addition, which is a language change and therefore theirs). Everything else
is recommendation-grade under settled decisions and the standing priority
order, ratified by the user before implementation proceeds past 1.3.1.

---

## G-4 (→ D-194) — `simd<T, N>`: the complete v1 surface

**Elements:** `int8..int64`, `uint8..uint64`, `flt32`, `flt64`, and `bool`.
NOT the twisted or ternary families — a per-lane sticky-ERR discipline
contradicts the purpose of mapping to hardware vector instructions (every
op would need per-lane ERR select chains, erasing the win); a "twisted
vector" is a library loop over scalars if it is ever needed. `bool` is
admitted BECAUSE comparisons produce `simd<bool, N>` and their results must
be bindable — a bool vector supports `== !=`, indexing, `.all()`/`.any()`,
and nothing else (no arithmetic, no elementwise logic in v1 — the
consumer-first rule; reopen with a consumer).

**Lanes:** `N` a comptime integer, 2..64, total size ≤ 64 bytes (the
AVX-512 ceiling). Powers of two recommended but not required — LLVM
legalizes odd widths by padding, and `vec3` (a real consumer) is 3 lanes.
Alignment = the next power of two ≥ size, capped at 64.

**Constructor:** `simd(a, b, …)` (the ExprVectorCtorExpr the parser has
carried since Phase A) is TYPE-DIRECTED from the annotation, the
`channel()`/`arena_make` precedent: `simd<flt64, 4>:v = simd(a, b, c, d);`.
Exactly N arguments, each fitting T — or exactly ONE argument, which
SPLATS to every lane. No annotation → refuse, same as `channel()`.

**Operations, all elementwise:** `+ - * /` (and `%` for integer elements);
`& | ^ << >>` for integer elements; comparisons `== != < <= > >=` yielding
`simd<bool, N>`. Integer vector division carries D-007: ANY zero lane traps
to `failsafe` (checked before the instruction — one `icmp`+`or`-reduce, not
per-lane branches). Float lanes are IEEE per D-037.

**Indexing:** `v[i]` reads a lane (bounds-checked, OutOfBounds trap);
`v[i] = x` writes one. `.len` is N as `int64`.

**Reductions, as methods:** `.sum()`, `.min()`, `.max()` on numeric
elements; `.all()`, `.any()` on `simd<bool, N>`. Lowered to the
`llvm.vector.reduce.*` intrinsics — instruction sequences, no libcalls, so
the zero-dependency scan stays green.

**Casts:** `simd<T, N> => simd<U, N>` elementwise under the scalar rules
(`=>` only where the scalar cast is lossless, `=>!` otherwise); N never
changes in a cast. No scalar↔vector casts — the splat constructor is the
one broadcast.

**Shuffles: OUT, by decision.** No shuffle/permute surface in the language.
Rationale: D-143's consumer-first rule — no Nikola consumer is in evidence,
the surface is large (masks, two-source forms), and a wrong shuffle API is
permanent. If a real consumer appears the question reopens as its own
decision with the consumer on the table. (This is a decision that it is not
going in, not a deferral.)

## G-5 (→ D-195) — `tfp*`: Q-format lowering and the ERR discipline

Per TYPE_REFERENCE §5 under D-036/D-037, with two implementation decisions:

**Lowering: native `iN`, not word-structs.** `tfp32`→`i32`, `tfp64`→`i64`,
`tfp128`→`i128`, `tfp256`→`i256` — deviating from §5's `{i64, …}` struct
tables for the wide pair. The wide integers are native since 0.9.3 and
byte-identical to the struct layout in memory; arithmetic on `iN` is direct
where struct marshalling would rebuild every operand. §5's tables update to
match.

**Arithmetic (D-144 branch-free, ERR = most-negative raw, sticky):**
- add/sub: the integer op, overflow saturating to ERR.
- mul: widen ×2, multiply, shift right by F, range-check back — overflow →
  ERR. (`tfp256` widens to `i512`; still native.)
- div: divisor zero → ERR (D-007's tbb rule, never the trap); else widen,
  shift left by F, divide, range-check.
- comparisons: ERR-aware per D-008 — `ERR == x` false, `ERR != x` true,
  orderings false on ERR.
- `is_err(x)` admits the tfp widths (the D-096 form, same as tbb).
- shifts/bitwise on the raw representation, per §5.
- negation is `0.0tfp64 - x` (no unary minus exists in the language).

**`.floor()` and `.trunc()` as METHODS on every width** — §5's
`tfp256_floor`/`tfp256_trunc` free functions become methods, one mechanism
instead of a name family.

**Literals** `3.14tfp64`: the decimal is converted at COMPILE TIME to the
nearest Q value by exact integer arithmetic (the D-193 machinery's inverse,
in the compiler, not the runtime); a literal that lands outside the width's
range refuses (TYPE-031's envelope discipline, not silent saturation).

**`ToString`: EXACT decimal, not shortest-round-trip.** A Q value is a
binary fraction with an exact finite decimal expansion (≤ F digits); the
canonical rendering is that exact expansion with trailing zeros trimmed and
a mandatory fraction digit ("2.5", "0.0625", "-3.0", "ERR"). Determinism is
the family's whole point; "shortest that round-trips" is a float concept
and does not apply.

## G-6 (→ D-196) — `dim256<Unit>`: units are exponent vectors

**The core:** a unit is an EXPONENT VECTOR over the seven SI base
dimensions (mass, length, time, current, temperature, amount, luminous
intensity). The named units are builtin names for vectors — `Meters` =
length¹, `Newtons` = mass¹·length¹·time⁻², `Joules` = mass¹·length²·time⁻²,
plus `Seconds`, `Kelvin`, `Kilograms`, and the spec examples'
`MetersPerSecond`. Multiplication/division ADD/SUBTRACT vectors — the
algebra is TOTAL, so TYPE_REFERENCE §5a's "if registered" hole dissolves:
`force * dist` IS the Joules vector whether or not anything named it; a
NAME is only needed where a human writes an annotation. Add/sub/compare
require equal vectors; mismatches refuse with both units displayed.
Everything is erased before lowering — `dim256` IS `tfp256` at the IR level
(D-036), and every G-5 rule applies to its arithmetic.

**Casts:** `dim256<U> => tfp256` drops the unit (always safe);
`tfp256 =>! dim256<U>` ASSERTS a unit onto a bare number (the acknowledged
form — §5a's "warning" for the reverse direction becomes a refusal without
`=>!`, because a silent unit-gain is how unit bugs are born).

**USER — user-declared units.** The builtin set covers the spec's examples,
but real physics wants `Radians`, `Hertz`, `Tesla`, `Pascals`… Two options:
- **(a) Builtin set only** — closed list, no grammar change; a missing name
  is written as arithmetic on named quantities and annotated `tfp256`.
- **(b) A `unit:` declaration** — `unit:Hertz = 1 / Seconds;` — one small
  grammar production; a unit name becomes a first-class annotation.
**Recommendation: (b).** It is exactly the semantic-intent lever the
language sells (the checker — and later the prover — consumes the author's
stated physics), the production is small, and the alternative pushes unit
names into comments. It is a grammar change, so it is the user's call — and
if (b) is chosen, it lands IN 1.3.3, not later (no deferring).

## G-7 (→ D-197) — the ternary/nonary bases

**Representation (the binary rung's, never the identity):** `trit`/`nit` =
`i8`, `tryte`/`nyte` = `i16`. `tryte` = 10 trits, `nyte` = 5 nits — the
same 59049 states (3^10 = 9^5), which is WHY both fit `i16`; §7's "2 nits"
was a spec defect, fixed at 1.3.0. ERR = a binary-spare state (−128 on
`i8`, −32768 on `i16`), sticky, D-144 discipline; on ternary hardware ERR
becomes that target's lowering choice (an eleventh trit, a flag word) — the
frontend never assumes the sentinel's binary value.

**Value operations:** `+ - *` at all four types; `/ %` at `tryte`/`nyte`
only (the prototype's shape — a three-state division is not an operation
anyone writes); comparisons at all four (balanced order); negation `0 - x`.
Overflow → ERR (a `tryte` past ±29524 has no eleventh trit).

**Digit access as methods:** `t.trit(i)` / `n.nit(i)` extract a digit
(bounds-checked), `.len` is 10/5/1. Conversions: `trit => tryte` widens
losslessly; `tryte =>! trit` narrows; decimal integers assign per the
literal rules (both spellings — decimal and balanced-sequence — per the
exotic spec, already lexed since D-147).

**USER — the Kleene logic spelling.** The prototype implements three-valued
logic on `trit`/`nit`: True=1, Unknown=0, False=−1; AND = min, OR = max,
NOT = value negation, all ERR-sticky. The family is the user's own design,
so the spelling is theirs:
- **(a) Operators `&` `|` on trit/nit** carry the Kleene meaning (D-036
  lets a non-integer type give an operator its own semantics; ternary
  hardware would implement exactly these as gates), with NOT as `0 - x`
  (it IS negation in balanced ternary) — no new spellings at all.
- **(b) Methods** `.and(o)` / `.or(o)` / `.not()` — explicit, no operator
  overloading question, three more names.
**Recommendation: (a)** — the blueprint's maximum-meaning-per-symbol rule,
and on a ternary target these are single instructions; but the author of
the family should say which reads as intended.

## G-8 (→ D-198) — `frac*`: invariant-normalized mixed numbers

Per TYPE_REFERENCE §20 and the prototype's invariants: `{whole: iN,
num: iN, denom: uN}`, value = whole + num/denom, and after EVERY operation
the five invariants hold (denom > 0; num ≥ 0 when whole ≠ 0; num < denom;
gcd(num, denom) = 1; sign on whole, or on num when whole = 0).
Normalization is automatic — an unnormalized rational overflows in a
handful of multiplies, so "call `frac_simplify` yourself" is a latent-ERR
generator, and the function list in §20 becomes OPERATORS `+ - * /` with
comparisons, per the blueprint's one-mechanism rule.

**ERR:** denom = 0, or any component at its width's most-negative — sticky,
D-144 style. Division by an exact zero → ERR (D-007's twisted rule).
Overflow during normalization (a product whose reduced form still exceeds
the width) → ERR: the family's promise is "exact or ERR", never "rounded".

**Casts:** `int => frac` lossless; `frac => flt64` and `frac =>! int`
per §20 (the flt conversion rounds, so it is `=>!` — correcting §20's
`=>`); width changes between frac widths widen with `=>`, narrow with
`=>!`. **`ToString`:** "whole num/denom" ("3 1/3", "-2 5/8", "0", "ERR") —
exact by construction.

## G-9 (→ D-199) — `complex<T>`

`T` ∈ {`flt32`, `flt64`, `tfp32`, `tfp64`} (§21's `fix32/fix64` were the
obsolete names). Layout `{T, T}`. Constructor `complex(re, im)`
type-directed like `simd()`. Operators `+ - * /`: float division uses
Smith's algorithm (the naive formula overflows at |denominator| ≈ √max —
a silent-wrong-answer class); tfp elements use the direct formulas under
the G-5 ERR discipline (any component ERR → both components ERR).
Methods: `.re()`, `.im()`, `.conj()`, `.abs2()` (magnitude squared —
total, no square root) on every element type; `.abs()` on float elements
only (`llvm.sqrt` lowers to the instruction; a fixed-point square root is
its own algorithm with no consumer in evidence — same consumer-first
refusal as shuffles, decided not deferred). `ToString`: "3+4i" / "3-4i"
via the element's own rendering.

## G-10 (→ D-200) — the library tier and its shapes

- **`lib/nvec.npk`**: `vec2`/`vec3`/`vec4` as structs over `simd<flt64, N>`
  with `.x/.y/.z/.w` accessors, dot/cross/length; `vec9` as a struct of
  nine `flt64` with the §25 `mRC` fields (it is a 3×3 matrix flat — matrix
  semantics, not a 9-lane vector; 3×3 multiply never maps to one vector op
  anyway).
- **`lib/ntensor.npk`**: `matrix<T>` `{ptr, rows: int64, cols: int64}` and
  `tensor<T>` with **rank capped at 9 and dims INLINE** —
  `{ptr, ndims: int64, dims: [9 x int64]}` — one allocation, no second
  indirection, and rank 9 is Nikola's manifold by construction (the
  prototype's `ttensor` carries `dims[9]` natively). `tmatrix`/`ttensor`
  are the same containers over `tryte` elements. All four OWN their heap
  cell — the 1.2 managed regime is real, so the drop frees it; owning
  elements inside follow the D-183 rules that already govern every
  container.
- Element bounds: `matrix<T>`/`tensor<T>` take the numeric scalars
  (int/uint/flt/tfp); indexing is bounds-checked; arithmetic surface in
  the library (methods), not the checker.
- **int64 dimensions, not the prototype's int32** — Nikola-scale tensors
  against a 2^31 ceiling is a foreseeable regret.
