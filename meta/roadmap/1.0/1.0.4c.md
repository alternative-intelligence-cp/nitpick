# 1.0.4c — Overlap refusal and derive-on-generic (D-161's remaining clauses)

**Cycle 1.0.** The two clauses of D-161 that 1.0.4b did not meet, scheduled
here rather than left dangling. Both have a WRONG behaviour today, not an
absent one, which is why they are their own subcycle rather than a footnote.

## 1. Overlap is refused at the impl, not at the call

Today a family impl and a per-instance impl for one (type, trait) both collect,
and the program is refused only when something CALLS the method —
`NITPICK-TYPE-020`, "ambiguous method". Measured:

```nitpick
impl:<T>:Box<T>:S     = { func:w = int64(Box<T>:self)     { pass 8i64; }; };
impl:Box<int32>:S     = { func:w = int64(Box<int32>:self) { pass 4i64; }; };
// refused at `b.w()`, not at the second impl
```

TRAITS_REFERENCE §4.1 is unambiguous: *"There is at most one implementation of
a given trait for a given type. Overlapping implementations are a compile
error."* At the impl, not at the use. The consequence of the current shape is
concrete: a library containing an overlap that nothing inside it calls compiles
clean and hands the error to its consumer, at a call site in code that did
nothing wrong.

**What it builds.** A pass over the collected impl table refusing a
per-instance impl that a family impl of the same trait already covers — the
shape `check_coherence` already has (D-111's two-blanket-impls-of-one-trait
check is the same question one step more general). The diagnostic names both
impls, as the blanket-conflict one does.

**The rule to state while doing it**: D-064 §7 has no specialization, so
"family plus per-instance" is not "the specific one wins" — it is an overlap,
and both spellings are refused together. That is the same answer §2.6 gives for
blanket-versus-concrete *lookup ordering* not being a licence to declare both.

## 2. `#[derive]` on a generic subject

Today `#[derive(Eq)]` on `struct:Box<T>` synthesizes `impl:Box:Eq` — the bare
declaration with no arguments — and the author is shown three
`NITPICK-TYPE-016` "generic arity" errors at `<derived-1>:2`, a synthesized
file they never wrote. That is the worst available outcome: a wrong impl AND a
diagnostic pointing nowhere the reader can act on.

D-161 settles what to do: **synthesize the family form**
(`impl:<T: Eq>:Box<T>:Eq` — the element bound mirroring the derived trait),
**or refuse the generic subject by name** until that lands. With family impls
now real (1.0.4b), the synthesis is the honest target; the by-name refusal is
the fallback if the bound synthesis turns out to need its own decision.

**What it builds.** Either the family synthesis, or `derive` refusing a generic
subject with a message naming the declaration (never `<derived-N>`), plus a
`tests/derive/rejection/` case pinning whichever lands.

## Tests

- `tests/types/rejection/`: a family impl and a per-instance impl of one trait,
  refused at the second impl with both named — and NOT requiring a call to
  trigger it.
- `tests/derive/rejection/generic_subject.npk` (refusal) or a program deriving
  `Eq` on `Box<T>` and comparing two instances (synthesis) — whichever D-161's
  first clause resolves to.
- An acceptance case that a family impl and a per-instance impl of *different*
  traits on one type still coexist: overlapping is per (type, trait).

## Done when

An overlap refuses at the impl with both named and no call required;
`#[derive]` on a generic subject either works or refuses by name, and no
diagnostic points at `<derived-N>` for it; the fixpoint holds.
