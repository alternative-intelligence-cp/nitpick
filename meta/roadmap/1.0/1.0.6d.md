# 1.0.6d — Normalising a projection, and D-159's qualified key

**Cycle 1.0.** The half of D-164 that 1.0.6c could not land, plus the obligation
that decision carries. Both are about the same thing: a name that needs
information from a layer above where it is currently asked.

## 1. Where assoc normalisation lives — the opening decision

`T.Item` resolves and substitutes its base, so `Counter.Item` exists as a type.
Nothing turns it into the `int32` that `impl:Counter:Iterator` bound, so a
concrete call through a projection refuses.

**It cannot be fixed in `resolve_type`.** `ImplTable` is declared in
`type_trait.npk`, which imports `resolve_type.npk`; a field on `TypeResolver` is
a real import cycle, tried at 1.0.6c and reverted. Nor should it be: the
architecture's answer for anything needing impls is a later pass, which is why
instantiations are recorded and `check_instantiations` runs after the table is
built — `TypeResolver`'s own comment states the rule.

Three candidate homes, and this subcycle opens by choosing one:

- **Extend `type_subst` with an optional normaliser.** One walk, but it puts an
  impl-shaped concern into the module that must not know about impls; the
  normaliser would have to arrive as a parameter from a caller that does.
- **A second structural walk in `ExprTyper` territory**, at
  `type_access.npk`'s substitution of a generic call's signature, where
  `e.impls` is in hand. Correct layer, but it duplicates `type_subst`'s
  traversal — and two walks over one type structure is the shape this codebase
  has been bitten by before.
- **Its own pass over recorded instantiations**, exactly as
  `check_instantiations` does for bound satisfaction. Most consistent with the
  existing architecture; the question is whether a normalisation that must
  produce a TYPE (rather than report) fits a pass that runs after the fact.

**Recommendation: the third**, on consistency grounds — but it is the one whose
mechanics need checking first, because the others produce a type where it is
needed and this one may not.

## 2. D-159's module-qualified key — the obligation D-164 carries

A dotted type spelling now parses, so `a.S` is expressible and two same-named
traits from different modules can be named in one file. D-159's amendment closed
its tie question by MEASURING that this was impossible; it is possible now, and
that amendment says in as many words what must happen: the canonical `dyn` bound
order keys on a module-qualified name, or `dyn a.S & b.S` and `dyn b.S & a.S`
become two types with two layouts again.

The data exists — `build_modmap` walks the module graph for decl-index →
module-name — but it is built in the BACKEND and interning happens in the
frontend, so the map or the graph has to reach `TypeResolver`. **Nothing
exercises this today**, which is exactly why it is scheduled rather than
trusted to be noticed.

## Tests

A concrete call through a projection, compiled and run: `first(c)` where `first`
returns `T.Item` and `Counter` binds it to `int32`. A projection nested inside
another type (`T.Item[]`), which is what decides whether the chosen home walks
structurally. And two modules each declaring a trait of one name, named
qualified in one `dyn`, interning identically in both orders.

## Done when

A concrete call through a projection compiles, links and runs; a nested
projection substitutes; the `dyn` bound order keys on a module-qualified name and
two same-named traits no longer tie; D-159's amendment and D-164 both record
which home was chosen and why; the fixpoint holds.


## Outcome

**Both items resolved, and the second by measurement rather than by building.**

### 1. Normalisation lives in `type_subst`

**The recommendation in this plan was wrong, and its own caveat is what caught
it.** A later pass over recorded instantiations cannot work: a generic call's
result type is compared against the declared type in the same expression check,
so a pass running afterwards arrives after the mismatch has been reported. The
caveat said "the question is whether a normalisation that must produce a TYPE
rather than report fits a pass that runs after the fact" — it does not.

`type_generic.npk` already imports `type_trait.npk` with no cycle back, so
`type_subst` can see the impl table and normalises inside the walk it already
does. **One walk, not two** — a second structural traversal is the shape this
compiler's own notes call out as having cost it defects repeatedly.

Three places needed it, found by following the failure rather than predicting it:

- `type_subst` itself, for a generic call's signature.
- **The backend's substitution too.** It first passed NULL on the reasoning that
  every assoc a valid program contains has been normalised by then. Wrong: the
  emitter RE-SUBSTITUTES a specialization's signature, so `T.Item` arrived at
  lowering and failed closed. `LlCtx` carries the table now.
- **`ll_type`, for a generic BODY's expression types.** Recorded with the
  parameter opaque (D-107), so `it.next()` reaches lowering carrying `T.Item` —
  exactly as `self.v` reached 1.0.4c carrying `T`. It is normalised inside
  `ll_type` rather than around it, because a projection can be nested and
  `ll_type` is the walk that recurses.

Verified end to end by reading the IR, not the exit code:
`@"npk.proj1.first<Counter>"` returns `{ i32, i32 }` — so `T.Item` became
`int32` — and calls `@"npk.proj1.Counter:Iterator.next"`.

### 2. D-159's key is NOT owed — the trigger was misidentified

This plan, D-164 and 1.0.6c's commit message all said a dotted type spelling
reopens D-159's tie. **It does not.** The production projects from a TYPE, and a
module is not a type: `dyn dyn_a.S` reports "there is no type named `dyn_a`".
Both of D-159's barriers still stand — the loader refuses two modules exporting
one name (`NITPICK-RESOLVE-008`, for non-glob imports as well as glob), and no
module-qualified type spelling exists.

D-164 also claimed the production "gives qualified type paths, which are
impossible today" as a side benefit. That was wrong and is corrected on the
decision. D-159's amendment is narrowed to what actually triggers it: a MODULE
becoming nameable in type position.

**That is real plumbing not built on a premise that was not true** — the second
time this cycle that testing a stated obligation before honouring it saved the
work, after 1.0.5b.
