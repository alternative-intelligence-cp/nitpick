# 1.0.6b — A generic trait's own parameter, under a bound

**Cycle 1.0.** Found at 1.0.6 while checking whether generic traits are a
working alternative to associated types. They are not, yet.

## What was measured

```nitpick
trait:Producer<T> = { func:make = T(Self:self); };                  // OK alone
struct:IntBox = { int32:v; };
impl:IntBox:Producer<int32> = { func:make = int32(IntBox:self) { … }; };  // OK

func:twice<P: Producer<int32>> = int32(P:p) { … };   // ← breaks the TRAIT
```

```
NITPICK-TYPE-001 gt3.npk:1:35     ← the `T` in the TRAIT's own signature
```

Adding a generic function whose BOUND names the generic trait makes the trait's
own parameter stop resolving, at its declaration, several lines away from the
thing that caused it. **Verified pre-existing** by building `HEAD` in a separate
worktree before any 1.0.6 change, so it is not associated-type work.

## Why it matters beyond itself

It is the reason **C-20 cannot be decided yet**. The question there is whether
external projection (`T.Item`) is necessary or merely convenient, and the answer
turns on whether the alternative — declaring the trait generic and naming the
argument directly — actually works. Right now it does not, so a comparison
between them would be a comparison against something imaginary.

## What to look at first

The trait's own parameter window is bound when its body is walked
(`type_stmt.npk`'s `DeclTraitDecl` branch sets `e.enclosing` from
`decl_generic_window`). A bound naming `Producer<int32>` resolves the trait
through `resolve_aggregate`, which instantiates it — and an instantiation walks
the trait's members. The suspicion is that the instantiation walk reaches the
method signatures with the FUNCTION's generic scope in place rather than the
trait's, so `T` is looked up among `P` and not found. **That is a suspicion, not
a diagnosis** — the first task is to establish which walk reports it, because
the span points at the declaration and the cause is at the use.

## Tests

The program above, as a real backend program: a generic trait, an impl binding
its argument, a generic function bounded by it, and a call that dispatches — the
whole path, since each part works alone today and only the combination fails.
Plus the frontend case pinning that the trait's own `T` resolves while a bound
mentions it.

## Done when

A generic trait can be named as a generic function's bound without breaking its
own parameter; the program above compiles, links and runs; C-21 is closed and
C-20 is decidable against a route that works; the fixpoint holds.
