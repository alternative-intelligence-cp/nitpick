# 1.0.6b — A generic trait's own parameter, under a bound

**Cycle 1.0.** Found at 1.0.6 while checking whether generic traits are a
working alternative to associated types. They are not, yet.

## What was measured

```nitpick
trait:Producer<T> = { func:make = T(Self:self); };                  // OK alone
struct:IntBox = { int32:v; };
impl:IntBox:Producer<int32> = { func:make = int32(IntBox:self) { … }; };  // OK

func:twice<P: Producer<int32>> = int32(P:p) { … };   // ← breaks the TRAIT
```

```
NITPICK-TYPE-001 gt3.npk:1:35     ← the `T` in the TRAIT's own signature
```

Adding a generic function whose BOUND names the generic trait makes the trait's
own parameter stop resolving, at its declaration, several lines away from the
thing that caused it. **Verified pre-existing** by building `HEAD` in a separate
worktree before any 1.0.6 change, so it is not associated-type work.

## Why it matters beyond itself

It is the reason **C-20 cannot be decided yet**. The question there is whether
external projection (`T.Item`) is necessary or merely convenient, and the answer
turns on whether the alternative — declaring the trait generic and naming the
argument directly — actually works. Right now it does not, so a comparison
between them would be a comparison against something imaginary.

## What to look at first

The trait's own parameter window is bound when its body is walked
(`type_stmt.npk`'s `DeclTraitDecl` branch sets `e.enclosing` from
`decl_generic_window`). A bound naming `Producer<int32>` resolves the trait
through `resolve_aggregate`, which instantiates it — and an instantiation walks
the trait's members. The suspicion is that the instantiation walk reaches the
method signatures with the FUNCTION's generic scope in place rather than the
trait's, so `T` is looked up among `P` and not found. **That is a suspicion, not
a diagnosis** — the first task is to establish which walk reports it, because
the span points at the declaration and the cause is at the use.

## Tests

The program above, as a real backend program: a generic trait, an impl binding
its argument, a generic function bounded by it, and a call that dispatches — the
whole path, since each part works alone today and only the combination fails.
Plus the frontend case pinning that the trait's own `T` resolves while a bound
mentions it.

## Done when

A generic trait can be named as a generic function's bound without breaking its
own parameter; the program above compiles, links and runs; C-21 is closed and
C-20 is decidable against a route that works; the fixpoint holds.


## Outcome

**Three defects, not one**, and the two I did not expect were mine.

**C-21 as reported.** A generic trait named as a bound broke the trait's own
parameter. The call site resolved the trait's method signature with the CALLER's
generics in scope, so `T` in `func:make = T(Self:self)` was looked up among the
caller's `P`, missed, and reported at the TRAIT's declaration — lines away from
the call that caused it. `check_signature` has bound this correctly on the impl
side since D-111; `trait_binding` became `pub` and the call side now uses the
same function. One question, one answer, one implementation.

**A regression from 1.0.5c.** The vtable emitter reads the TRAIT's method
signature to shape a thunk, and never bound the trait's parameters — so a
generic trait with an impl was refused by `npkc` for a program the frontend had
already accepted. Introduced by the subcycle that added that read; no test had a
generic trait with an impl, so the suite was green over a program that could not
compile.

**A regression from 1.0.5b, and the worst of the three.** When symbols began
carrying their impl, a definition became `IntBox:Producer.make` while every call
through a BOUND kept emitting `@npk.<module>.make`. `llc` refuses it outright —
*use of undefined value*. It applies to non-generic traits too, so it was never
about associated types or generics at all: **every call through a generic
parameter's bound was broken for two subcycles.**

Fixing it needed both ends, and neither could do it alone. At check time the
receiver is the PARAMETER, so there is no impl to name; at emit time the
parameter has been substituted, so there is. The trait travels on the call
(`callee_trait`, beside `callee_sym`) and the emitter combines it with the
substituted receiver.

## What this says about the suite, honestly

All three were invisible for one reason: **no test ever called a method through
a generic parameter's bound.** Bound, call, and impl each had coverage; the
COMBINATION had none.

**No instrument would have caught it, and it is worth saying so rather than
inventing one.** `llc` does reject the undefined reference — the moment a test
exists. `check_zero_dependency` scans objects, and llc fails before producing
one. `check_kinds_lowered_or_refused` asks whether every KIND lowers, which is a
different question from whether every combination is reachable. The gap was
coverage, and the fix is a test.

**The transferable lesson is about symbol schemes.** When the symbol for a
definition changes, every site that NAMES that symbol is a caller and must move
with it. At 1.0.5b I checked the emitter and the call path I was editing; the
bound path names symbols too and I did not think of it as a caller. A scheme
change is a change to an interface with more implementors than it looks like.

`tests/backend/programs/trait_bounds.npk` pins all three. Each alone yields a
program that does not compile, so the exit code is only reached if all three
hold — which is what makes it a regression test rather than three assertions.

**And a fifth missing import surfaced only in the self-compile** (`trait_binding`
in `emit_program.npk`), the same recurring defect: the frontend-only checker
resolves such names transitively and `npkc` compiling itself does not.
