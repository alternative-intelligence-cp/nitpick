# 1.0.6c — `T.Item`: a dotted suffix in type position (D-164)

**Cycle 1.0.** The projection D-160 assumed the parser already had. Decided as
**D-164** at 1.0.6b's close, once C-21 was fixed and the alternative it had to be
weighed against actually worked.

## What it builds

- **One branch in `p_suffixes`**, beside `->`, `?`, `[]` and `[N]`: a `.` after a
  type, followed by a name. The suffix loop is already the place where a base
  type accretes meaning, and this is one more accretion.
- **A new AST `TypeKind`** carrying (base type, name). Every walker over type
  nodes learns it — `resolve_type`, `type_mentions_self` (D-157's walk),
  `type_subst`, and the node-kind reachability check demands a case that
  exercises it. **A missed walker is a silent wrong answer, not an error**, which
  is the failure mode `ast.npk`'s own note about a literal's width suffix
  describes.
- **Resolution through the bound.** `T.Item` where `T` is a parameter: find the
  assoc among `T`'s bound traits, then substitute the impl's binding where `T` is
  known. 1.0.6 built both halves already — `assoc_of_trait` finds the member and
  `assoc_binding` resolves it — so this is a third caller rather than new
  machinery.
- **The ambiguity rule.** `T.Item` where two of `T`'s bounds declare `Item` is
  refused naming both, the same answer D-158 gives a method supplied by two
  bounds. No ordering tiebreak: after D-159's canonical ordering, "first" would
  be decided by how the traits are SPELT.

## The obligation this carries, which is not optional

**D-159's tie reopens the moment this lands.** That amendment says so in as many
words: with a dotted type spelling, two same-named traits from different modules
can both be named in one file — a glob import of both is still the loader's
ambiguity, but `dyn a.S & b.S` becomes expressible — so the canonical `dyn` bound
order must key on a **module-qualified** name rather than a bare one, or the two
spellings become two types with two layouts again.

The data exists: `build_modmap` walks the module graph to produce decl-index →
module-name. It is built in the BACKEND and interning happens in the frontend, so
the map (or the graph) has to reach `TypeResolver`. **That plumbing is part of
this subcycle**, and D-164 says so rather than leaving it to be discovered.

## Tests

`Iterator` with `assoc:Item`, an impl binding it, and a generic function over
`<T: Iterator>` that declares a variable of `T.Item` and returns it — the whole
point of the feature, and impossible today. Then: two bounds declaring one assoc,
refused naming both; a qualified type path (`a.Local`) now that one parses, which
the same production gives for free; and `dyn a.S & b.S` interning identically to
`dyn b.S & a.S` across two modules, which is the D-159 obligation made visible.

## Done when

`T.Item` parses, resolves through the bound and substitutes per impl; two bounds
declaring one assoc are refused naming both; the `dyn` bound order keys on a
module-qualified name and same-named traits from two modules no longer tie; every
type-node walker handles the new kind and the reachability check proves it; the
fixpoint holds.
