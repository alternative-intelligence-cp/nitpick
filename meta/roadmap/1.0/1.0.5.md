# 1.0.5 — `dyn`: object safety, dispatch, ABI (D-157/D-158/D-159)

**Cycle 1.0.** The three `dyn` decisions land together because they are one
boundary. Decided: `D-157` (object safety), `D-158` (dispatch + vtables), `D-159`
(multi-bound ABI).

## What it builds

- **D-163 hook:** `find_method`'s `TY_DYN` path returns the TRAIT's declaration,
  never a concrete impl's — so 1.1's licence reads the trait's `never fails`
  contract for a `dyn` call (the vtable hides which impl runs, D-163 rule 5).

- **Object safety, extended (D-157):** `check_object_safe` walks the full type tree
  of every parameter and the return, refusing `Self` anywhere but the receiver, and
  rule 3 (no generic methods) unified. This is a **safety fix** — the current check
  reads only the return node.
- **Vtables (D-158):** per (impl, trait), entries in trait-declaration order, each a
  per-impl adapter thunk (caller passes data ptr + args; thunk loads the by-value
  receiver and calls the real method). `find_method` gains its `TY_DYN` path: own
  methods of the named traits only, ambiguity across bounds refused.
- **Multi-bound ABI (D-159):** `dyn` over N traits interns as `{data, vt_1…vt_N}`,
  bounds canonically ordered so slots are static; widening (`dyn A & B → dyn A`) is a
  value rebuild. Fixes `types.npk`'s flat 16-byte interning.

## Tests

A `dyn Trait` constructed from a concrete value and a method called through it; a
supertrait method NOT reachable through the subtrait's `dyn` (refused); an ambiguous
method across two bounds refused; `dyn A & B` widened to `dyn A` and dispatched; a
trait with `Self` in a non-receiver position refused object-unsafe; `dyn` of an
assoc-mentioning trait refused.

## Done when

Object safety refuses every non-receiver `Self`; `dyn` construction and dispatch run;
multi-bound layout and widening work; the vtable is declaration-indexed and
thunk-backed; the fixpoint holds.

**Met for the frontend half; the lowering moved to 1.0.5b** — see below.

## What landed

**D-157 — object safety walks the whole type tree. Met.** Rule 2 read the
RETURN's top node and nothing else, so `bool(Self:self, Self:other)` passed
object safety outright and behind a vtable the erased second argument would have
been read at the wrong layout. `type_mentions_self` now walks generic arguments,
pointees, elements, function parameters and returns, over every parameter and
the return. The receiver may *be* `Self`; it may not *contain* one. No
size-based carve-out: `Handle<Self>` is refused by name even though its size
does survive erasure, because one uniform rule beats an exception a reviewer has
to remember.

**Rules 1 and 2 do not both fire for one mistake** — found by the harness, not
by reasoning. `int32(int32:k, Self:self)` is `self` in the wrong POSITION, and
the extended rule 2 reported it a second time as "mentions `Self` in parameter
`self`, and only the receiver may" — of a parameter that is named `self`. With
no receiver at all the phrase has no referent, so the parameter scan is skipped
once rule 1 has reported. The return is still scanned, and rule 1 refuses the
trait either way, so what is dropped is a line of noise rather than a refusal.
`tests/frontend/type_access.npk` case 183 asserts the COUNT, which is what
caught it; the reason is now written beside it.

**Fuel exhaustion fails CLOSED.** The walk sets `found` as well as `exhausted`,
so a tree it could not finish refuses the trait — and reports `TYPE_INTERNAL`
alongside, because that is a compiler defect rather than a fault in the program.
A safety check that answers "nothing found" for the one input it could not read
is the failure mode this shape exists to prevent.

**D-159 — the layout and the canonical order. Frontend met.** `tt_dyn` was a
flat 16 bytes whatever the bound count: right for `dyn A` and wrong for every
wider one, so `dyn A & B & C`'s last two vtable pointers had nowhere to live. It
is `(N+1) x 8` now. And the bound window is sorted by trait NAME before
interning (`dyn_sort_bounds`), so `dyn A & B` and `dyn B & A` are ONE interned
type with one layout — they were two, with two different answers to which word
holds which vtable. The key is the name rather than the interned id (assigned in
encounter order) or the declaration index (which shifts when an unrelated
declaration is added earlier — an ABI that moves for an edit that touched
nothing). This needed `name_lt`, the tree's first string ordering, written in
`intern.npk` beside `string_eq` and named for its domain because it compares
`.ptr` bytes as int8 — lexicographic only while the bytes are ASCII, which every
identifier is.

**D-158 — dispatch. Frontend met.** `find_method` had no `TY_DYN` path at all,
so every method call on a `dyn` fell through to the impl-table walk, which looks
up by the receiver's type and finds nothing: the construct was unusable end to
end. `find_in_dyn` searches the named traits' OWN member lists in bound order.
A supertrait's methods are NOT reachable through a `dyn` of the subtrait — the
decided no, verified rather than assumed. Two bounds supplying one name is
`TYPE_AMBIGUOUS_METHOD` with no ordering tie-break, because after the canonical
order "first" would be decided by how the traits are spelt.

**The D-163 hook is in place**: the `TY_DYN` path returns the TRAIT's
declaration, never an impl's, which is what 1.1's licence reads for a `dyn`
call.

## Measured

- `tests/types/rejection/object_safety.npk` — ten refusals: the three original
  rules, `dyn` of a non-trait, and the six D-157 cases that PASSED before
  (later parameter, `Self?`, `Self[]`, `Self->`, `Boxed<Self>`, and a nested
  receiver). `Drawable` — receiver-only `Self`, ordinary parameter and return —
  reports nothing, so the rule is not merely refusing everything.
- `tests/types/rejection/dyn_dispatch.npk` — ambiguity across two bounds
  refused, a name no bound declares refused, and the supertrait method refused
  through the subtrait's `dyn`; three positive dispatches clean.
- `tests/frontend/resolve_types.npk` — `dyn A` is 16 bytes, `dyn A & B` is 24,
  three bounds are 32, and `dyn Printable & Drawable` interns to the SAME type
  as `dyn Drawable & Printable`.
- Full harness green: `types` 22 → 23, `grammar` 285 → 286, and stage 1 rebuilt
  itself byte-identically.

## What moved to 1.0.5b, and why

Everything that needs a vtable to EXIST: emission of the per-(impl, trait)
tables and their adapter thunks, `dyn` construction, call-through-slot, and
widening as a value rebuild — plus retiring `ll_type`'s `TY_DYN` rung, which
still answers `NITPICK-RUNG-001`.

The split is along a real seam rather than a convenient one. The frontend half
is complete and independently testable — object safety refuses, dispatch
resolves, ambiguity refuses, the layout is asserted — and none of it needs
redoing when the backend lands. 1.0.5b also closes D-159's one remaining hole:
two same-named traits from different modules TIE under the name sort and fall
back to declaration index, and the stable key is the module-qualified name,
which needs the backend's decl-to-module map reachable from the resolver.
