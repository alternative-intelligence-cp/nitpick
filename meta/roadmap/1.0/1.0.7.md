# 1.0.7 — `Optional<T>` lowers, and the first generic collection

**Cycle 1.0, closing the language half.** With generics lowering (1.0.2/1.0.2b),
traits and assoc types real (1.0.4–1.0.6d) and every slot built through one
helper (1.0.6e), the parameterized library surface becomes buildable —
`Optional<T>` first, the refusal grammar #13 named 1.0 for. No new decision;
one correction to this plan's own earlier wording, below.

## 1. `Optional<T>` is compiler-known, not a library struct — the correction

The map for this subcycle (written at 0.8-close) said "`Optional<T>` as a
library type where D-099 left a compiler-known one". Read literally that is
wrong, and it is corrected here rather than built:

- **D-099 strikes every readable member.** `.has_value` and `.value` are IR
  field names, not source members; `??` and `?.` are the accessors that cannot
  be wrong. A library `struct<T>:Optional` would have fields, and hiding them
  would be a struct whose fields are not members — a context-dependent special
  case of exactly the kind the blueprint rule forbids.
- **TYPE_REFERENCE §11.1 fixes the layout** — `{ i8 has_value, T value }`, tag
  first — and `tt_optional` already interns it with that layout. The
  representation is decided; only the lowering is missing.
- **`Result<T>` is the precedent.** It is the other "builtin that takes generic
  arguments" (`resolve_type.npk`), it is compiler-known, and it lowers to its
  fixed shape. Two parameterized wrappers with two mechanisms is the cost the
  blueprint rule exists to avoid.

So `Optional<T>` lowers as `Result<T>` does: `ll_type` answers `{ i8, <T> }`,
the emitter builds and reads it by position, and nothing in `lib/` declares it.
"Library" in this subcycle's title means the second half — a collection written
in Nitpick over the generics that now lower.

## 2. What it builds — the `Optional` half

- **`ll_type(TY_OPTIONAL)`** → `{ i8, <T> }`. The interned layout
  (`tt_optional`: a 1-byte field, then `T` at its alignment) is pinned against
  the LLVM shape — but NOT in `tests/frontend/type_layout.npk`, which the seed
  compiles, and the seed refuses `Optional` (`ntypes.py` names it 1.0). The pin
  lives in the real-backend program instead: the address difference between
  two elements of an `int32?[2]` (LLVM's stride) against `#size_of<int32?>()`
  (the frontend's table), for a scalar and for a struct element. A frontend
  size that disagreed would under-allocate every `wild T?->` buffer.
- **`NIL` where an `Optional` is expected** is typed AS the `Optional` (D-099,
  `type_sentinel`), so the emitter meets a sentinel literal whose recorded type
  is `TY_OPTIONAL` and answers **`zeroinitializer`** — tag 0 and a ZEROED value
  half, never `undef`. The spec's IR comment writes `i32 undef` for the empty
  value; a defined byte is strictly safer under a verifier and costs nothing,
  and it is the same choice the `fail` desugar makes for a `Result`'s value
  half (§11.2: "zero-initialized if error").
- **The wrap** — a bare `T` meeting an `Optional<T>` slot — is `emit_fit`'s
  second case (1.0.6e built the function for `dyn`): `insertvalue` the tag `1`
  and the value over `zeroinitializer`. One function, every slot, the same list
  `fits` licenses and `check_slot_sites_agree` pairs.
- **`== NIL` and `!= NIL`** lower as a TAG TEST: extract field 0, compare with
  0. Both operand orders (D-099 fixed `NIL == opt` at the checker; the emitter
  honours both). **Two `Optional`s that are neither `NIL`** fall to the
  general aggregate-equality path — which today emits `icmp` on an aggregate
  and is refused by `llc` ("icmp requires integer operands"; measured on a
  struct at this subcycle's opening). That path becomes a NAMED refusal here
  (`==` on a non-scalar, naming 1.0) so it fails by name rather than at `llc`;
  what aggregate equality MEANS — fieldwise, `Eq`-dispatched, or refused at the
  checker — is a decision owned by 1.0.9, because it is the same question for
  structs, arrays, `Result`, `string` and `dyn`.
- **`a ?? d`** — the value, or `d`, LAZILY: `d` evaluates only on the empty
  path, the shape `?` on a `Result` already lowers (0.9.7) with the tag in
  place of the error word. `d` meets the inner type through `emit_fit`, since
  the checker typed it with `fits(inner, d)`.
- **`a?.f`** — tag test; empty yields `zeroinitializer` of the RESULT type,
  present extracts the value, reads `f`, and wraps it — unless `f` is itself an
  `Optional`, in which case the checker already flattened the type and the
  field is returned as it is (TYPE_REFERENCE §11.1: `?.` flattens rather than
  manufacturing `Optional<Optional<T>>`).
- **`pass NIL;` in a function returning `T?`** is the empty one
  (`type_stmt.npk` already types it so) and lowers through the same sentinel
  path; `pass v;` wraps through `emit_fit` at the `pass` slot.
- **Retires** three rung strings: `TY_OPTIONAL` in `ll_type`, `?.`, and `??`.

## 3. What it builds — the collection half

A generic growable list **written as a test program, not adopted in `src/`**
(C-13: the seed is the builder until 1.2, and the seed has no generics). It is
the shape `TokenList` has by hand — `wild T->:items`, `count`, `cap`, grown by
doubling through `alloc`/`ralloc` and `#size_of<T>()` — and it proves, in one
file, the things the concrete collections will need when they convert:

- a generic struct holding `wild T->` and `#size_of<T>()` **inside a generic
  body**, substituted per specialization;
- its methods through a GENERIC TRAIT over the family
  (`trait:Stack<E>` … `impl:<T>:List<T>:Stack<T>`) with `push`, `at`, `len`,
  instantiated at two element types in one program — **not an inherent family
  impl, because none can be spelled**: D-161's amended segment rule reads
  `impl:<T>:List<T>` as a blanket impl of a trait named `List<T>` (measured at
  this subcycle's opening: `NITPICK-TYPE-012`, "not a trait"). The decision
  text said the inherent family "falls out" of the original resolution; the
  amendment's rule is the candidate it listed as "no inherent families",
  adopted without saying so. Raised at 1.0.9 as **D-171** (the user's call —
  it is a spelling): recommend the blanket form take an explicit target
  (`impl:<T: P>:T:Loggable`, "for `T`, implement `Loggable`"), so ONE rule
  reads every impl — `impl:<generics>:Target(:Trait)?` — and the inherent
  family arrives with no new token and no shape-dependent disambiguation;
- a second trait impl over the family (`impl:<T>:List<T>:Sized`) reached
  through a bound;
- a generic struct built as a VALUE inside a generic body (`List{ … }` in
  `list_make<T>`), which reaches lowering recorded as `List<T>` (D-107) and
  must be named, laid out and headed as `List<int32>` — measured at this
  subcycle's opening as `llc` refusing `%"List<T>"` where `%"List<int32>"` was
  declared. `subst_emitted_param` answers for a bare `T`; the instantiation
  case walks through `type_subst`, which re-interns and records the instance,
  so a late instance (one no annotation ever named) gets its header after the
  bodies — legal, since textual IR resolves named types in any order;
- an `Optional`-returning accessor (`func:find = T?(List<T>->:self, …)`), which
  is where the two halves of this subcycle meet and the reason they share one.

**What it does NOT build: a `for` over it.** `for` is range-form by decision
(D-023), the backend lowers ranges, slices and arrays, and "a `for` over this
iterable" is a rung string 1.0.9 owns together with the checker hole found
beside it (a `for` binding's type is never compared with the element type, and a
struct is accepted as an iterable — measured at this subcycle's opening).

## Outcome

**Both halves landed; the collection half found four defects under it, three
of them interning or monomorphization holes that no program had reached.**

### The `Optional` half — as planned

`{ i8, T }` from `ll_type`; `NIL` as `zeroinitializer`; the wrap as
`emit_fit`'s second case (and `check_slot_sites_agree` forced the `??` pairing
to be written, as designed); `== NIL`/`!= NIL` a tag test in either order;
`??` lazy through a slot, the `?` shape; `?.` with the flattening rule;
`pass NIL;`/`pass v;`; an `Optional` argument, field, array element,
`Optional<Point>`, `bool?`. The layout pin lives in the program (the seed
refuses `Optional`, so `type_layout.npk` cannot ask): two elements of zeroed
bytes, a store through element 1, and the first non-zero byte must sit exactly
`#size_of` in — for `int32?` and `Point?`. Non-scalar `==` is a named refusal
(`tests/rejection/nonscalar_compare.npk`), D-169's to define.

`emit_member` split into the base emission and `emit_member_from`, so `?.`
hands in the value it unwrapped and reads the field through the one path `.`
uses.

### The collection half — what it found

1. **An instantiation's identity was its mangled NAME (D-108 §1), and the
   name cannot tell two same-named parameters apart.** `first<T>` and
   `second<T>` both spelled `List<T>`, so the second's instance WAS the
   first's, with the first's `T` in its argument window; `l.items[0]` in the
   second reported "expected `T`, found `T`". Every earlier program had one
   generic function per generic struct, or different parameter names.
   `tt_instance` now compares the window's CONTENTS (D-108 amended). The same
   defect one table away, exposed by the fix: a `dyn`'s identity was its bound
   window's START, so two spellings of `dyn Speaks` were two types — masked
   while `Pair<dyn Speaks>` deduped by name (`Pair<<type>>`, since
   `type_display` could not render a `dyn`), and `llc` refused the
   redefinition the moment it deduped by contents. `tt_dyn` compares contents
   and interns the spelling as the type's name; `%"npk.m.Pair<dyn Speaks>"` is
   reversible now.

2. **A generic struct built as a VALUE inside a generic body lowered as the
   template.** `List{ … }` in `list_make<T>` is recorded as `List<T>`
   (D-107); `ll_type` substituted a bare `T` and not a `T` inside an
   instance's window. `subst_emitted_type` walks through `type_subst`, which
   re-interns and RECORDS the instance, and `emit_late_headers` emits the
   headers of instances the bodies created, after the bodies — textual IR
   resolves a named type wherever its definition appears. Template-shaped
   instances (`type_mentions_param`) get no header.

3. **No transitive monomorphization.** `pair_of<T>` calling
   `list_make::<T>(…)` records `list_make<T>` with `T` opaque; the instance
   loop emitted that template (refusing `#size_of<T>` with nothing bound) and
   never created `list_make<int64>`. Now a template-shaped instance is skipped
   by the loop, and `fninst_concrete` substitutes its arguments under the
   specialization being emitted and records the concrete request; the loop
   re-reads the table's count, so it is the worklist. The same for a family
   impl's method reached through a bound or through a receiver that mentions
   the parameter (`note_family_instance`, bound positionally as `bind_blanket`
   binds) — which required family instances to be emitted FROM the worklist
   rather than from the impl block, where only the instances recorded before
   the block were reachable (`emit_family_instance`, at the impl's recorded
   scope, since an impl has no symbol for `symtab_home_scope` to find).

4. **A family impl satisfied a method call and no BOUND.** `type_implements`
   had three sources — concrete impl, parameter bounds, blanket impl — and
   `find_method` a fourth, the family rule (1.0.4b). `total<S: Sized>(li)`
   was refused for a type whose `size()` the same table resolved. The fourth
   source is added, by the same declaration-identity rule.

### What the collection could not be, and why

Its mutators are free generic functions over `List<T>->`: an inherent impl
over a family cannot be spelled (D-161's segment rule reads it as a blanket
impl; **D-171** raised), and a trait method cannot take `Self->` (the
one-level substitution refuses it), so no method of a generic struct can
mutate it today. That is `TokenList`'s own shape, made generic, and the test
says so rather than pretending otherwise. D-166's recommended `Iterator.next
= Item?(Self->:self)` depends on the same `Self->` question; noted for 1.0.9.

### Instruments and tooling

`check_slot_sites_agree` did its job on the first edit that touched its
table. The diagnostic MESSAGE was needed three times today and is printed
nowhere (1.0.8); the interning defect was found by printing it for one build.
`tests/backend/programs/generic_list.npk` is the regression for all four
findings above; `optional.npk` for the first half.

**Reserved words that cost a build:** `any` (a type keyword) as a local name;
`on` (a keyword) as a local name in the test.

**The first full run failed three ways, all fixed before the commit:** two
backend unit tests asserted that `Optional` is a rung (one used it as the
stand-in for "a type no rung lowers" — the stand-in is a variadic function type
now, 1.1's); and the self-compile found two helpers the seed had resolved
transitively (`ll_ok`, `SUBST_FUEL_LL` needed `pub`) — 1.0.6b's recurring
finding, the fifth and sixth time.

Harness: 61 green (60 → 61 with `nonscalar_compare`), programs 67 → 69,
rungs 8 → 9, grammar 294 → 297, fixpoint byte-identical.
