# 1.0.3 — UFCS method calls

**Cycle 1.0.** `x.method()` lowering for concrete receivers — the syntax the
frontend has typed since 0.4.6 (UFCS was never removed) but no rung lowered. No new
decision; the type checker already resolves the call.

## What it builds

- **D-163 hook:** the resolved callee of `x.method()` must be as reachable as
  `f(x)`'s — `callee_decl` answers for both — because 1.1's `raw`/`drop` licence
  reads a call's resolved callee for its `never fails` contract, method calls
  included.

- **Method-call lowering** — `x.magnitude()` emits the call to the resolved free
  function or inherent method with `x` as the first argument, the receiver
  auto-addressed or copied per its parameter form (the same one-level dereference
  D-098 gives plain access).
- The concrete collections (`TokenList`, …) **become expressible** as method-bearing
  types — but are NOT yet rewritten in `src/` (C-13: the builder switches at 1.2).

## Tests

A struct with an inherent method called through `x.m()`; a free function called both
as `f(x)` and `x.f()` (UFCS equivalence, D-006); a method returning a value used in
an expression; auto-addressing of a by-pointer receiver.

## Done when

`x.method()` lowers and runs for inherent methods and UFCS free functions; the
equivalence with `f(x)` holds at runtime; the fixpoint holds.

## Outcome (recorded at close)

`x.method()` lowers for UFCS free functions: `doubled(p)` and `p.doubled()`
emit the SAME call, which is D-006's equivalence made real at the IR level
rather than asserted in a spec. `p.scaled(3i32)` passes the receiver plus its
arguments. `tests/backend/programs/ufcs.npk` runs (exit 49);
`tests/rejection/ufcs.npk` is RETIRED — it asserted the refusal this subcycle
removes, and the acceptance test is its inversion.

**The callee is READ, not re-derived — and that IS the D-163 hook.** Resolving
`m` means asking the impl table, then the bound table, then the scope; the
emitter holds none of them, and a second copy of that lookup would be a second
answer waiting to drift from the checker's. So `ExprTypes` gained a `callee`
column — the same key and lifetime as the recorded type — set where
`type_method_call` settles on a declaration. The hook the D-163 merge asked
for ("`callee_decl` answers for `x.m()` as for `f(x)`") is therefore not a
future promise: the slot exists, and 1.1's licence reads it.

**Inherent `impl` methods are NOT in this subcycle**, and the boundary is
worth stating: an `impl` block is still rung-refused at emit (1.0.4's work), so
`p.sum()` on an inherent method refuses at the `impl`, not at the call. The
call machinery is complete — `emit_method_call` reads whatever declaration the
checker resolved, whether it came from an impl or the scope — so 1.0.4 lands
the impl block and inherent methods work with no further call-side change.

**Receiver adjustment as the language actually defines it.** The plan said
"auto-addressed or copied per its parameter form", and the emitter does adjust
— but the CHECKER refuses `p.bump()` where `bump` takes `Point->` (TYPE-007,
no implicit address-of, D-092's no-implicit-conversion rule reaching pointers).
So the pointer path in the emitter is reachable only for a receiver that is
already a pointer, and the address-taking branch stands ready for the day a
decision permits it rather than inventing one here.

One defect surfaced only in the self-compile again: `type_access.npk` used
`exprtypes_set_callee` without importing `expr_types.npk`. The frontend-only
checker resolved it transitively; npkc compiling itself did not.
