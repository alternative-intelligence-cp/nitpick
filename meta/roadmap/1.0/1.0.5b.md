# 1.0.5b — `dyn` lowering: vtables, thunks, construction, widening

**Cycle 1.0.** The backend half of D-158 and D-159. 1.0.5 built the frontend —
object safety, the layout, the canonical bound order, and dispatch — and
`ll_type` still answers `NITPICK-RUNG-001` for `TY_DYN`, so no `dyn` has ever
been emitted. This subcycle is what makes one run.

Split from 1.0.5 rather than left inside it because the frontend half is
complete and testable on its own: object safety refuses, dispatch resolves,
ambiguity refuses, and the layout is asserted — none of which needed a vtable to
exist. What follows needs all of it, and none of it needs re-doing.

## What it builds

- **The vtable (D-158)**, one per (impl, trait). Entries in TRAIT DECLARATION
  ORDER — slot = declaration index, stable and source-derived, hash-free for the
  same reason D-156's symbols are. Each entry points at a **per-impl adapter
  thunk**: the caller always passes the data pointer plus the arguments, and the
  thunk — compiled against the concrete type, which it knows — loads the
  by-value receiver and calls the real method. That is what lets an impl keep
  its natural `Point:self` signature while the erased caller passes one pointer.
- **Construction**: a concrete value widened to `dyn A` builds `{ data, vtA }`.
  The data word's ownership follows the value's regime; nothing about `dyn`
  changes who drops it.
- **The call**: load the slot at the declaration index of the trait the method
  resolved through (`find_method` already returns the trait in `owner`), then
  call the thunk. The return is the trait signature's return, `Result`-wrapped
  like every call (D-013).
- **Widening (D-159)**: `dyn A & B → dyn A` is a VALUE REBUILD — copy the data
  word and the retained traits' vtable words into the smaller shape, positions
  statically known from the canonical order. No runtime tables and no
  prefix/subview scheme.
- **Retire the rung.** `ir_types.npk`'s `TY_DYN` arm stops returning
  `ll_rung("1.0")` and returns the `(N+1) x 8` aggregate.

## The D-159 loose end this also closes

1.0.5 canonicalises the bound list by TRAIT NAME, which is source-derived and
ABI-stable — but **two same-named traits from different modules TIE**, and the
tie is currently broken by declaration index, which is deterministic within a
compilation and shifts if an unrelated declaration is added earlier. An ABI that
moves for an edit that touched nothing is not one this project can ship.

The stable key is the MODULE-QUALIFIED name. The data exists — `build_modmap` in
`emit_program.npk` walks the module graph to build decl-index → module-name —
but it is built in the BACKEND and interning happens in the frontend, so this
needs the map (or the graph) reachable from `TypeResolver`. Doing it here rather
than at 1.0.5 keeps one plumbing change in one place, alongside the emission
work that already holds the modmap.

## Tests

A program that constructs a `dyn Trait` from a concrete value, calls a method
through it, and exits with what the method returned — the first `dyn` this
compiler has ever run. Then: a two-bound `dyn` dispatching a method from each
bound; `dyn A & B` widened to `dyn A` and dispatched after widening; and a
`dyn` whose impl inherited the trait's DEFAULT method, since D-158 says the
vtable slot is filled with the default's thunk.

## Done when

A `dyn` constructs, dispatches and runs; a multi-bound `dyn` dispatches from
each bound; widening rebuilds and the widened value still dispatches; the
`TY_DYN` rung is gone from `ll_type`; the bound order keys on a module-qualified
name so two same-named traits cannot tie; the fixpoint holds.
