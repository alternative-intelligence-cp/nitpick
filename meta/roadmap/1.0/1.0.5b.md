# 1.0.5b — A method's symbol names its impl (D-156 amended)

**Cycle 1.0.** Found at 1.0.5c's opening, by reading emitted IR for a two-impl
program rather than by any test. **The compiler emits invalid LLVM for an
entirely ordinary program**, and it has since impl methods were first emitted.

## What was measured

D-156's symbol scheme is `@"npk.<module>.<name>"`. It says nothing about
methods, and the implementation took the only reading available: a method's
symbol is its module and its own name. So a method's symbol does not mention
the impl it belongs to, and two impls collide:

```nitpick
trait:Speaks = { func:say = int32(Self:self); };
struct:Dog = { int32:v; };
struct:Cat = { int32:v; };
impl:Dog:Speaks = { func:say = int32(Dog:self) { pass 1i32; }; };
impl:Cat:Speaks = { func:say = int32(Cat:self) { pass 2i32; }; };
```

```
define { i32, i32 } @"npk.m.say"(%"npk.m.Dog" %a0) { …
define { i32, i32 } @"npk.m.say"(%"npk.m.Cat" %a0) { …

llc: error: invalid redefinition of function 'npk.m.say'
```

**Two shapes, and the second is worse.**

- **Two impls of one trait on different types.** Each writes its own `say`; both
  are `npk.m.say`. One declaration per symbol, two symbols wanted.
- **Two impls INHERITING one trait default.** 1.0.4 emits a default once per
  implementing impl, correctly — the default's `Self` is a different type in
  each. But all those emissions share ONE declaration index, so no map keyed by
  declaration can give them distinct names. One declaration, N symbols wanted.

The second is why this is a subcycle rather than a line in `build_modmap`: the
modmap is decl-indexed, and the fix has to be computed per EMISSION.

## Why it was never caught

Nothing that reaches the backend has ever had two impls of one trait. Three
files do (`types/rejection/coherence.npk`, `types/rejection/traits.npk`,
`types/rejection/impl_overlap.npk`) and all three are REJECTION tests that stop
at the checker; a fourth (`accept/lock_levels.npk`) is an acceptance test, which
is checked and never emitted. The 61 real-backend programs each implement a
trait at most once.

**The instrument that would have caught it does not exist.** `check_zero_dependency`
scans for UNDEFINED symbols; nothing scans for DUPLICATE definitions, and `llc`
only sees a program the harness actually compiles.

## The amendment

A method's symbol is qualified by the **impl it belongs to**, which is exactly
the pair D-158 says a vtable is per: **(target type, trait)**.

```
@"npk.<module>.<Target>:<Trait>.<name>"    a trait impl's method
@"npk.<module>.<Target>.<name>"            an inherent impl's method
@"npk.<module>.<name>"                     a free function, unchanged
```

Still hash-free, still path-free, still source-derived — D-156's three
properties are the reason the scheme exists and none of them is given up. An
inherent method and a trait method of one name on one type get different
symbols, which they must: `find_method` lets both exist and refuses only the
ambiguous CALL.

**The qualifier is a function of (method declaration, receiver type)**, and both
ends already have that pair: `emit_impl_block` binds `Self` before emitting, and
a call site knows its receiver's type and gets the trait from `find_method`'s
`owner`. What is missing is that the two do not compute it through one function
today, so this subcycle adds one and routes both through it.

## What it builds

- **One symbol function**, taking the method declaration and the resolved
  receiver type, used by BOTH emission and every call site. Two derivations of
  one symbol is how a caller comes to name a definition that does not exist.
- **The trait-default case**, which needs the emission's `Self` rather than the
  declaration's owner — the same information, taken from where the emission
  stands rather than from where the declaration was written.
- **The D-159 loose end**, folded in because it is the same sentence: the
  canonical `dyn` bound order keys on a trait's bare NAME, so two same-named
  traits from different modules tie and fall back to declaration index, which
  shifts under an unrelated edit. The module-qualified name fixes it, and this
  subcycle is where module qualification is already being handled.
- **The instrument: `check_no_duplicate_symbols`.** Every `define`/`@global` in
  each emitted module, counted. This defect produced invalid IR for four years
  of the project's own test programs without one of them noticing, because no
  program happened to hit it and nothing was looking. `llc` is not the check —
  it only ever sees what the harness compiles.

## Tests

The two programs above, as real backend programs: two impls of one trait on
different types, each dispatched and each returning its own answer; and two
impls inheriting one trait default, both calling it. Both produce invalid IR
today, which is the point. Plus an inherent method and a trait method sharing a
name on one type, each called through the spelling that disambiguates it.

## Done when

Two impls of one trait emit distinct symbols and both run; two impls inheriting
one default emit distinct symbols and both run; an inherent and a trait method
of one name coexist; `check_no_duplicate_symbols` runs on every harness
invocation; the `dyn` bound order keys on a module-qualified name; D-156 carries
the amendment; the fixpoint holds.
