# 0.3.2 — Path resolution

**Cycle 0.3 — Modules, symbols, visibility.**

## Goal

`use "…"` becomes a file on disk, by exactly one rule.

## The rule (`BUILD_REFERENCE.md` §3)

A `use` path resolves in exactly one way, **decided by its first character**:

| Form | Resolves against |
|---|---|
| `use "./util.npk"`, `use "../x/y.npk"` | the **importing file's** directory |
| `use "nfs/path.npk"` | the **dependency roots** |
| `use std.math.*` | the standard library |

A dependency named `nfs` declared at `../nfs` roots at **`../nfs/src/`**, so
`use "nfs/path.npk"` is `../nfs/src/path.npk`.

## Ambiguity is an error

**If two dependencies both supply `x/y.npk`, the build fails and names both.**
Not first-match, and not manifest order.

The reason is worth keeping in front of you while implementing it: resolution
order must never be something a reader has to know the manifest's declaration
order to predict. A first-match rule means adding a dependency can silently
change which file an existing `use` resolves to, in a module nobody edited.

## Work

1. Path classification by first character, with no fallback between classes — a
   `./` path that does not exist is an error, not a retry against the roots.
2. Dependency roots from `nitpick.toml`, each rooting at `<dep>/src/`.
3. Collect **every** candidate before deciding, so ambiguity is detectable at
   all. A resolver that returns on first hit cannot report the second.
4. Logical paths (`std.math.*`) against the standard library root.
5. Path normalisation: `./a/../b.npk` and `b.npk` are the same file and must
   produce the same file id, or a module loads twice and every symbol in it
   duplicates.

## Watch for

**No network, ever** (D-078). Resolution is a filesystem operation against roots
the manifest already names.

## Done when

- Each of the three forms resolves, and the wrong root is never consulted.
- Two roots supplying one path fails and names both.
- `./a/../b.npk` and `b.npk` are one file id.
