# 0.3.3 — The module graph

**Cycle 0.3 — Modules, symbols, visibility.**

## Goal

From a root file, the whole program — loaded once each, in any order, with the
same result.

## Work

1. Load the root, parse it, collect its symbols, queue its `use` targets.
2. Repeat until the queue empties. A file already loaded is not reloaded; its
   file id is returned.
3. **Cycles are legal** (D-086) and need no special handling *provided* phase 1
   completes for every module before phase 2 begins for any. That ordering is
   the entire mechanism.
4. Unresolvable cycles — a struct whose size depends on itself other than
   through a pointer, a `const` whose initialiser depends on itself — are
   reported **naming the members in the order they refer to each other.**
5. `mod:name;` loads `name.npk` or `name/mod.npk` relative to the declaring file
   (`MODULE_REFERENCE.md` §1.1), and finding both is an ambiguity error by the
   same rule as 0.3.2.

## The property to design for, not test for

**Resolution must not depend on which module the loader entered first.**

This is a reproducibility requirement (D-078) before it is a convenience. A build
that depends on entry order differs between the stage-1 and stage-2 compilers,
and the bootstrap fixpoint check (D-085) fails for a reason unconnected to
correctness — which would be a genuinely awful thing to debug.

Two habits keep it true, and both are cheap if adopted now and expensive to
retrofit:

- **Anything iterated must be iterated in a deterministic order.** Insertion
  order is deterministic; a hash order is not. Where a set is needed, sort it by
  something stable — file id, then span.
- **Nothing may be decided by "whichever came first" unless first is defined by
  the source.** Ambiguity-is-an-error (0.3.2) is the same rule wearing different
  clothes.

## Done when

- A graph with a cycle loads and every symbol resolves.
- The same graph entered from a different root produces the same symbol table.
- An unresolvable cycle names its members in reference order.
