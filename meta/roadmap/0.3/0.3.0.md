# 0.3.0 — Reading a file

**Cycle 0.3 — Modules, symbols, visibility.**

## Goal

The frontend can name a file and read it. Two language-level questions get
settled first, because everything after them depends on the answers.

## Decision 1 — how a program receives its command-line arguments

**The spec set does not say.** `main` is `func:main = int32()` in every document
that shows it, with no parameter form and no alternative mechanism. A compiler
driver cannot start without one.

**Proposed: `main` keeps its signature; arguments come from a runtime function.**

```nitpick
func:main = int32() {
    string[]:argv = raw args();
    ...
};
```

- `main` is **already** the special case — a bare `int32` rather than
  `Result<int32>`, `exit` instead of `pass`, mandatory `failsafe` alongside it
  (D-013, D-014). Adding an optional-parameter form gives it two shapes, and a
  reader then has to know which one a given program used. D-088 removed exactly
  that cost from `mod` and `extern` this week.
- Arguments are **process state**, like the environment, the working directory
  and the process id. None of those are parameters to `main` either, and there is
  no reason this one should be.
- It sidesteps the C ownership question entirely. There is no `argv` array whose
  lifetime the callee must reason about; `args()` returns an owned `string[]`.

Needs a `DECISIONS.md` entry and a line in `IO_REFERENCE.md`, which currently
says nothing about the process's own inputs.

## Decision 2 — the file-reading primitive

**Proposed: `read_file(path) → Result<string>`**, one call in the runtime floor,
rather than `open` / `read` / `close`.

`SUBSET_1.md`'s governing principle decides it: *push complexity into the
compiler, away from the seed.* The seed is the least-audited artifact in the
chain. Three primitives with an fd protocol between them is more unaudited code
than one call that returns bytes, and the compiler gains nothing from the
finer grain — it reads whole source files and never seeks.

`IO_REFERENCE.md`'s `Stream` trait (D-075) is the real model and arrives with
`nlibc` in 0.8. This is the floor, not the design.

## Work

1. Settle both decisions; record them.
2. `npk_args` and `npk_read_file` in `bootstrap/runtime/npkrt.ll`, plus their
   entries in the seed's builtin tables.
3. `_start` must capture the stack pointer **before** aligning it — the original
   `%rsp` is where `argc` and `argv` live, and the current prologue destroys it.
4. `src/frontend/source.npk` grows `srcmgr_load(path)`: read, intern the path,
   register, return the file id. Reading the same path twice returns the same id.
5. `tools/parse_check.npk` takes a path argument instead of stdin.

## Watch for

**`_start` is the one place where getting it wrong is silent.** The comment there
already records why the manual alignment exists: at `_start` the stack is not
laid out the way it is at a normal call, so a compiler-generated prologue can
leave `%rsp` misaligned and a later SSE spill faults. Capturing `argc`/`argv`
means reading through the pointer *before* the `andq`, and a mistake produces a
program that runs fine until someone passes an argument.

## Done when

- `func:main = int32()` is unchanged, and `args()` returns the command line.
- `read_file` reads a file whole, and a missing file is an errored `Result` with
  a distinguishable code — not a trap, and not an empty string.
- `parse_check <path>` replaces `parse_check < path`, and the harness still
  passes.
