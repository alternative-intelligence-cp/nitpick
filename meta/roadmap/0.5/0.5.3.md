# 0.5.3 — `move`, moved-from bindings, and manual memory

**Cycle 0.5 — Static analyses.**

## Goal

A moved-from binding is invalid until reinitialised (D-065).

## The rule

`move(place)` is a **keyword operator on a place**, not a qualifier and not a
function — it returns no `Result` and could not be one. D-065's own example is the
test:

```nitpick
wild int8->:buffer = malloc(100i64);
wild int8->:moved  = move(buffer);

free(buffer);   // use after move
```

**Explicit only, no implicit moves.** Nothing moves because it was assigned or
passed; a move happens where `move` is written, which is what makes the analysis a
question about one operator rather than about every expression.

## Work

1. Moved-from state per binding, merged at branches the way assignment is —
   moved on one arm and not the other is **moved**, which is the opposite
   direction from definite assignment and is the easiest thing here to get
   backwards.
2. Reinitialisation clears it: a binding assigned after a move is valid again.
3. `nodrop` — the qualifier parses and nothing reads it. It suppresses the drop
   of a `wild` binding, which is the one case where *not* dropping is correct
   rather than a leak.
4. **The qualifiers get their meaning**: `wild` and `wildx` mark unchecked manual
   memory, and this is where "which allocations are live" starts being tracked at
   all.

## What belongs to Phase B and is said here so it is not looked for

The **K-semantics `exit` rule** — no live `wild`/`wildx` at `exit`, or it traps
back into `failsafe` — needs a runtime allocation registry
(`SAFETY_ARCHITECTURE.md`: "memory allocations must be tracked globally"). That is
Phase B's, and the static half here is only the part visible in one function.

Saying so is the point: a leak check that looked complete and covered one function
would be a promise nothing keeps.

## Watch for

**The merge runs the opposite way from definite assignment.** Assigned-on-some-path
is *not assigned*; moved-on-some-path *is* moved. Both are the conservative answer
and they point in different directions, which is exactly the kind of asymmetry a
shared merge helper gets wrong once and silently.

## Done when

- Using a binding after `move` is refused, and D-065's own example is the test.
- Reassigning after a move makes it usable again.
- Moved on one branch and not the other is refused after the merge.
