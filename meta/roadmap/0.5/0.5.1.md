# 0.5.1 — Second-class borrows and escape

**Cycle 0.5 — Static analyses.**

## Goal

A borrow passes **down** the call stack and never travels **up** (D-004).

## The rule, and why it is not a preference

D-004's five rules, in the decision's own order:

1. `@local` yields a **borrow**, not a first-class pointer.
2. A borrow may not appear in the value of `pass`, `fail`, or `return`.
3. A borrow may not be stored into any aggregate that is not provably
   shorter-lived than the borrow.
4. A borrow may not cross an **`extern` call**, a **thread spawn**, or an
   **`await` point**.
5. A **closure may not capture a borrow**.

Passing a borrow downward as an argument is always safe and needs no annotation,
because the callee's frame is strictly inner. **That is the entire lifetime
system** — no lifetime variables, no variance, no subtyping.

The reason this shape was chosen is the reason to implement it exactly: full
lifetime inference is the single largest source of complexity in a borrow checker
and the hardest part to verify, and a smaller checker is a more verifiable one
(D-003's rationale). Every generalisation that creeps in here is paid for at
Astrée.

## Work

1. Rules 2–5, each with its own diagnostic naming which one broke.
2. `stack`'s existing escape rule generalised to all borrows — the qualifier
   parses today and nothing reads it, and D-004 says outright that this rule is
   the precedent being generalised.
3. Rule 4's three crossings. **`extern` is the one that matters most and is the
   easiest to forget**: the callee may retain the borrow and the compiler cannot
   see that, which is the same argument the zero-dependency rule rests on.
4. Rule 5 is checkable and empty today — closures are removed (D-018) — so it is
   written as a refusal that cannot currently fire, with a comment saying so
   rather than being silently omitted.

## Watch for

**Rule 3 is deliberately strict to start**, and D-004 says so: if real compiler
code needs borrow-into-inner-aggregate, relax it *then, with evidence*. Relaxing
it now because a test is awkward to write is the failure mode that decision
anticipated.

**`await` does not exist yet and the rule still must.** `async` lowering is cycle
1.1, so rule 4's suspension clause cannot fire — write it, test that it parses and
is reached, and say in the code that it is unreachable at this rung. A rule added
after the analysis is verified is a re-verification nobody can afford.

## Done when

- Returning a borrow is refused, naming the rule.
- Storing one into a longer-lived aggregate is refused.
- Passing one downward is accepted, with no annotation anywhere.
- A borrow crossing an `extern` call is refused.

## What this found

Four of the six things this subcycle changed were **repairs**, and every one of
them dated to a cycle that had already "finished" the construct. The roadmap
predicted this shape after 0.4 and it recurred exactly:

| Found | Dated to | Symptom |
|---|---|---|
| The type checker never descended into a nested `mod` | 0.4 | `pass "not an int32";` accepted inside a `mod` block |
| The resolver put every nested module's members in the **first** one's scope | 0.3 | a call between siblings failed; reordering the declarations fixed it |
| `collect_impls` / `collect_bounds` skipped nested modules | 0.4 | an `impl` one level down was absent from the impl table entirely |
| An `extern` function had no type at all | 0.4 | **every** foreign call refused as "`open` is a type, not a value" |

Recorded as **D-114** (extern functions are typed, and it is a `Result<T>`) and
**D-115** (one function answers where a nested module's members live, and every
walk calls it).

The escape analysis itself was the smaller half of the work. That is worth saying
plainly, because it is the third cycle running where the new code was easier than
what it uncovered.

## Two things this subcycle could not settle at first

Both were **language-surface decisions** and both were frontend-blocking under the
capability ladder. **The first is now settled** — as D-117, and the opposite way to
the recommendation that was made first.

### A parameter cannot be declared second-class — SETTLED, D-117

D-004 says passing a borrow downward is always safe "because the callee's frame is
strictly inner". That is true of the callee's own locals and **not** of what the
callee returns:

```nitpick
func:launder = int32->(int32->:q) { pass q; };      // accepted today
func:caller  = int32->() {
    int32:x = 5i32;
    pass (raw launder(@x));                          // accepted today
};
```

`caller` returns a pointer into its own dead frame, and rule 2 never sees a borrow
because a call's result is not one. **The escape rules are defeated by one function
call.**

Closing it needs a way to say "this parameter receives a borrow", so that rule 2
refuses `pass q;` inside `launder`. `AST_REFERENCE.md` lists `borrow_imm` /
`borrow_mut` as `VarDeclStmt` qualifiers and D-004 cites them as existing
machinery — but **neither is a keyword**, `p_parse_param` accepts no qualifier at
all, and the spec does not put them on parameters even in prose.

**The recommendation was to give parameters the two qualifiers, and it was wrong.**
Checking it against this compiler is what showed why. Every context struct here is
built from pointer parameters and handed back —

```nitpick
func:ctx_init = Ctx(int32->:a, int32->:b) { pass Ctx{ a: a, b: b }; };
```

— and `resolver_init`, `etyper_init`, `tyres_init`, `graph_init` and `escape_init`
are all that shape. Once a parameter is a borrow binding, that `pass` is a rule 2
violation and **the compiler stops compiling itself**, while being perfectly safe:
those pointers are the *caller's*, and the struct goes straight back to that
caller.

What the diagnosis missed is why D-004 is right. **A pointer parameter never
points into the callee's own frame** — so a callee cannot make an escape out of
one, and `pass q;` above is `launder` handing the caller's pointer back to the
caller. The escape is one level up, and so is the fix:

- **Rule A** — a call's result is a borrow if an argument was one and the result
  type can carry a pointer. `launder` closed; `sum_through(@x, @y)` returns an
  `int32` and stays ordinary code.
- **Rule B** — two or more borrow arguments may have been connected to each other
  by the callee, so each one whose pointee can hold a pointer is marked. One borrow
  argument is exempt, because there is no second borrow to store into it — and
  `tt_intern(@t, …)` is the compiler's other universal idiom.

No new syntax, no annotation anywhere, and the compiler still compiles. Recorded as
**D-117**; verified by breaking all three parts, each of which loses exactly the
finding it is responsible for.

`borrow_imm` / `borrow_mut` may still be wanted for the OTHER half of D-004 — the
aliasing rules that make `$$i` many-readers and `$$m` exclusive. That is a
different question and is not settled here.

### A C variadic tail has no type

`func:printf = int32(int8->:fmt, ..*) fails on result < 0i32;` is refused
(`NITPICK-TYPE-023`). A Nitpick variadic writes `..*T[]:rest` and every trailing
argument is checked against `T`; a C `..*` names nothing, and the obvious filler
`any[]` is a bare `any`, which the type system refuses on purpose.

This must be settled before Phase B — `nlibc` and every syscall wrapper are
`extern` declarations. See D-114.

## What rule 2's `fail` arm turned out to be

**Structurally unreachable, and checked anyway.** D-004 names `fail` beside `pass`
and `return`, but a `fail` carries an error *code* — `Result`'s error field is a
`tbb32` (D-005) — so a pointer cannot reach that position at all: `fail @x;` is
refused by the type checker before any analysis sees it.

Written and walked regardless, for the reason rules 4 and 5 are: "cannot happen"
and "nobody checked" are the two answers this cycle exists to keep apart.

## The analysis's own bug, found by writing the plan's own sentence down

The cycle README says an analysis that is **right on straight-line code and wrong
after a merge** is the shape this cycle has to keep catching. The first version of
this one was that shape:

```nitpick
while (i < n) {
    if (i > 0i32) { pass p; }   // checked here, on a binding not yet marked
    p = @x;                     // marked here
}
```

Which bindings hold a borrow is **dataflow**, and marking them in source order
answers it wrongly wherever a binding is assigned after it is used. On the second
iteration `p` holds `@x` and is returned, and the walk had already gone past.

Fixed by splitting the pass in two: **marking runs to a fixpoint, then reporting
runs once.** Marks only ever go unset-to-set, so the rounds converge; the round
bound is there because an unbounded loop in a checker is not a checker, and
exceeding it refuses the program rather than under-reporting.

Verified by putting it back: with marking and reporting in one pass, the loop case
goes silent — **nine findings where there are ten**.

Two smaller holes closed at the same time, both fail-open before:

- **A binding the analysis does not track.** Of the three kinds of binding, only a
  local is tracked; a `pick` pattern binding and a `for` loop binding are not,
  because each takes its value from a destructuring. `escape_binding` answered
  `false` for both, which is an escape hatch reached by writing `pick`. A borrow
  reaching either is now refused (`NITPICK-BORROW-009`).
- **Fuel exhaustion answered `false`.** A classifier that says "not a borrow" when
  it stopped looking lets an escape through. It now answers `true` and the pass
  reports `NITPICK-BORROW-007` in its own words — a borrow checker that fails open
  is worse than none, because the property was claimed.

## The suite that was missing

`tests/types/accept/` is new, and it exists because **a rejection suite cannot
tell a correct analysis from one that refuses everything**. An escape checker
answering "yes, a borrow" to every expression passes all nine cases in
`rejection/borrows.npk`.

That gap mattered little in 0.4 and matters a great deal here: these analyses are
deliberately conservative — they fail closed on fuel exhaustion, on an
unclassified node, on anything undecidable — and over-refusal is the failure mode
they are most likely to have. Removing the deref pointer-type test refuses
`pass (<-p);` in four places, and only the acceptance suite catches it.
